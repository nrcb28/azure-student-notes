## AZ-900 · 操作系统与运行环境的控制

实验用应用必须安装自己的 Linux 内核驱动。哪种托管方式最符合这个要求？

- **A.** 在 Microsoft 365 中运行应用。
- **B.** 使用采用兼容 Linux 镜像的 Azure 虚拟机。
- **C.** 部署到 App Service 的托管运行时。
- **D.** 把驱动放进普通的 Azure Function。

<details>
<summary>思路：</summary>

**B. 使用采用兼容 Linux 镜像的 Azure 虚拟机。**

关键是能管理来宾操作系统。兼容的 Azure VM 允许团队管理系统环境和驱动，同时也把操作系统的维护责任留给团队。托管应用平台虽然方便，但如果不开放所需的内核控制能力，就无法满足这个要求。

- **A.** Microsoft 365 是可以直接使用的软件，并不是安装任意内核驱动的运行环境。
- **C.** App Service 的托管运行时不提供这里需要的来宾内核管理能力。
- **D.** 普通的 Function 不提供这里需要的内核驱动控制能力。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/compute-decision-tree) · [建议复习章节：](03-compute.md)

</details>

## AZ-900 · 水平扩展与状态

笔记 API 在负载均衡器后面增加了多个实例。任何实例都可能被替换，但用户会话必须保留。目前会话只放在各实例的内存中。应该改什么？

- **A.** 增加每个实例的 CPU。
- **B.** 继续把会话放在内存中，只开启会话粘滞路由。
- **C.** 把会话状态移到合适的共享外部存储中。
- **D.** 给每个实例分配一个公网 IP 地址。

<details>
<summary>思路：</summary>

**C. 把会话状态移到合适的共享外部存储中。**

水平扩展会把请求分散到多个实例，因此重要的会话状态不能只依赖某个实例的内存。合适的外部存储能让替换后的实例重新读取状态。粘滞路由无法在原实例消失后保住它的内存。应用还需要处理访问外部状态服务时的连接和故障问题。

- **A.** 增加 CPU 无法在实例被替换后保留它的内存。
- **B.** 被固定选中的实例一旦消失，即使有粘滞路由，会话仍然会丢失。
- **D.** 公网地址不提供共享或持久的会话状态。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/architecture/guide/design-principles/scale-out) · [建议复习章节：](01-fundamentals.md)

</details>

## AZ-104 · 存储数据权限

用户拥有某个存储帐户的 Contributor 角色。使用该用户 Entra 身份发出的 Blob 请求已到达服务，但因缺少数据权限而被拒绝。用户只需要读取一个容器中的 Blob。符合最小权限原则的做法是什么？

- **A.** 在该容器的作用域内分配 Storage Blob Data Reader 角色。
- **B.** 在整个订阅上分配 Owner 角色。
- **C.** 开放所有入站网络端口。
- **D.** 把存储帐户密钥发给用户。

<details>
<summary>思路：</summary>

**A. 在该容器的作用域内分配 Storage Blob Data Reader 角色。**

资源管理权限与 Blob 数据权限是两回事。Storage Blob Data Reader 提供所需的读取能力，容器作用域又把授权限制在实际需求内。题目已经说明问题在数据权限，因此授予广泛的管理权或修改无关的网络配置，都不是适度的解决办法。

- **B.** 订阅级 Owner 远超“读取一个容器”的需求。
- **C.** 开放端口不会补上缺少的数据操作授权。
- **D.** 帐户密钥提供的访问范围比这里的需求大得多。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access) · [建议复习章节：](06-identity.md)

</details>

## AZ-104 · RBAC 权限继承

用户既有直接分配给某台 VM 的 Reader 角色，也属于一个在订阅作用域拥有 Reader 的组。你只删除了 VM 上的直接角色分配，但用户仍能读取这台 VM。原因是什么？

- **A.** Azure 自动给所有用户分配所有 VM 的 Reader。
- **B.** 资源组标签恢复了已删除的角色分配。
- **C.** 删除角色之前总是必须先删除 VM。
- **D.** 组的角色分配仍然通过继承授予访问权限。

<details>
<summary>思路：</summary>

**D. 组的角色分配仍然通过继承授予访问权限。**

删除一个角色分配，不会消除从其他分配中获得的权限。组在订阅作用域拥有 Reader，所以成员仍可继承对 VM 的读取权限。在把问题归咎于服务故障或继续加权限之前，先检查直接分配、组成员身份和上级作用域。

- **A.** 不存在给所有用户统一授予 Reader 的规则。
- **B.** 标签用于分类资源，不会重新创建角色分配。
- **C.** 删除角色分配不要求删除它所保护的资源。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview) · [建议复习章节：](06-identity.md)

</details>

## AZ-305 · 恢复目标与 RPO

当前设计每 24 小时才保留一个成功且可恢复的数据库恢复点。业务现在要求灾难后最多只能丢失最近 1 小时的数据。哪个改动能直接弥补这个差距？

- **A.** 增加 API 服务器的 CPU。
- **B.** 设计间隔不超过 1 小时的可恢复数据保护点，并验证恢复过程。
- **C.** 添加一个费用预警预算。
- **D.** 把资源组重命名为 production。

<details>
<summary>思路：</summary>

**B. 设计间隔不超过 1 小时的可恢复数据保护点，并验证恢复过程。**

RPO 用时间表示可以接受丢失多少最近的数据。每天一次的恢复点无法独自满足 1 小时的目标。数据保护设计必须足够频繁地产生可恢复状态，并验证这些状态确实能恢复。提高应用算力或修改费用标签，都不会改变现有恢复数据的新旧程度。

- **A.** API 的 CPU 不会提高恢复数据的保护频率。
- **C.** 预算针对支出发出预警，不会减少数据丢失。
- **D.** 资源组名称不会改变恢复点的生成频率。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/well-architected/reliability/disaster-recovery) · [建议复习章节：](10-architecture.md)

</details>

## AZ-305 · 专用连接的 DNS

存储服务已禁用公共访问，也已建立专用终结点。但客户端仍把服务主机名解析为公网 IP，其他专用网络路径则可用。首先应该排查什么？

- **A.** 给客户端分配订阅级 Owner。
- **B.** 永久硬编码公网 IP。
- **C.** 客户端使用的专用 DNS 区域、链接和转发配置。
- **D.** 无限增加应用的重试次数。

<details>
<summary>思路：</summary>

**C. 客户端使用的专用 DNS 区域、链接和转发配置。**

客户端解析出的目的地址，与预期的专用连接不一致。应检查该服务推荐的专用 DNS 配置，以及客户端如何访问这套 DNS，包括区域链接和转发。连接时仍应使用服务主机名。修好 DNS 本身不会授予数据权限，但无关的管理权和无限重试也修不好这个解析问题。

- **A.** Owner 不会改变客户端的名称解析。
- **B.** 公共访问被禁用后，公网地址不是预期的连接目的地。
- **D.** 重复请求无法修复每次都返回同样错误结果的 DNS 配置。

</details>

## AZ-400 · 提升已测试构件

流水线先测试一个容器镜像，然后使用可能变化的依赖从源码重新构建生产镜像。怎样确保生产环境拿到的就是通过测试的镜像？

- **A.** 只重新测试源码注释。
- **B.** 使用 latest 标签，但不记录它指向哪个镜像。
- **C.** 因为源码提交没变，所以跳过测试。
- **D.** 提升同一个已测试镜像，并用不可变摘要标识它。

<details>
<summary>思路：</summary>

**D. 提升同一个已测试镜像，并用不可变摘要标识它。**

即使源码提交相同，工具、依赖或基础镜像变化后，构建结果也可能不同。直接提升已测试的镜像，可以避免重新构建带来的差异。不可变摘要标识的是实际构件，而标签以后可能指向别处。环境配置仍需要单独验证，并以受控方式管理。

- **A.** 源码注释无法标识已经构建出的镜像。
- **B.** 可变标签以后可能指向另一个镜像。
- **C.** 提交没有变化，不能证明重新构建的产物也完全一样。

## AZ-400 · 金丝雀发布的判断信号

一次金丝雀发布的 CPU 和内存正常，但下载文档时会返回错误的文件。是否继续部署，应该依据什么？

- **A.** 反映功能正确性的信号，以及事先定义的停止或回滚条件。
- **B.** 只看 CPU，因为基础设施健康就说明结果正确。
- **C.** 检查返回文件之前，先换更大的 VM。
- **D.** 删除旧日志，让仪表板看起来更清爽。

<details>
<summary>思路：</summary>

**A. 反映功能正确性的信号，以及事先定义的停止或回滚条件。**

发布版本可能运行得很轻松，却给用户返回错误的业务结果。继续推广时，需要能反映用户操作是否正确的信号，而不只是基础设施利用率。预先定义停止或回滚条件，才能把这些证据用于决策。还要检查数据兼容性：回退应用代码，并不会自动撤销这次发布造成的有害数据修改。

- **B.** CPU 和内存正常不能证明用户拿到的文档正确。
- **C.** 增加算力本身不能修复应用的错误输出。
- **D.** 删除证据只会让调查更困难，并不能纠正结果。

## DP-900 · 事务工作负载

大学的选课服务需要预留最后一个实验课名额，同时创建学生的选课记录，且这两个动作必须作为一个保持一致性的操作完成。哪种工作负载描述最符合这个要求？

- **A.** 按学期汇总选课情况的分析工作负载。
- **B.** 每晚核对各个独立名额更新的批处理工作负载。
- **C.** 将相关更改一并提交的事务工作负载。
- **D.** 分别发布名额和选课事件，但不协调其提交的流式工作负载。

<details>
<summary>思路：</summary>

**C. 将相关更改一并提交的事务工作负载。**

这个要求针对一个范围明确的小型操作，其中的相关更改必须一起成功或一起失败。这就是事务行为：在选课记录和名额记录不一致时，不能让另一个请求预留同一个最后名额。历史报表属于分析工作，数据访问方式也不同。事件和后续核对可以支持更完整的架构，但仅靠独立更新无法满足这里的一致性要求。

- **A.** 按学期汇总用于回答历史情况的问题，无法协调这次实时请求所需的名额预留和选课记录更改。
- **B.** 每晚核对会留下一段名额数与选课记录可能不一致的时间，不符合立即保持一致性的要求。
- **D.** 发布事件可以通知其他系统，但分别提交的事件本身不能让两项源数据更改成为原子操作。

## DP-900 · ETL 与 ELT 的顺序

研究团队提取昨天的下载记录，在处理服务中移除无效标识符，然后将清洗后的记录加载到报表数据仓库。哪种描述符合这个执行顺序？

- **A.** ETL，因为转换发生在加载到报表目标之前。
- **B.** ELT，因为只要最终目标是数据仓库，就一定在仓库内进行转换。
- **C.** 流式处理，因为下载记录最初来自应用事件。
- **D.** 只有编排，因为协调各个步骤就不再需要转换。

<details>
<summary>思路：</summary>

**A. ETL，因为转换发生在加载到报表目标之前。**

ETL 指先提取，再转换，最后加载到预定目标。这里是在报表数据仓库收到清洗后的记录之前处理无效标识符。ELT 则会先加载数据，再利用目标系统的处理能力进行转换。昨天的记录是范围有限的一批输入。编排器可以协调这些活动，但在同一条管道中，编排和转换承担不同的职责。

- **B.** ELT 的关键是先加载，再在目标系统内转换；仅仅选择数据仓库作为目标，并不能决定这个顺序。
- **C.** 数据最初来自事件，并不代表后续处理就是流式处理。这个作业处理的是范围明确的一天记录，而不是持续到达的记录。
- **D.** 编排负责协调依赖关系和恢复，而移除无效标识符会改变数据，仍然属于单独的转换职责。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/etl) · [建议复习章节：](../certifications/zh/DP-900.md)

</details>

## SC-900 · MFA 因素类别

一名学生正在比较登录方案。假设验证器设备已经注册，且必须在设备上批准登录，以下哪个例子同时使用了知识因素和持有因素？

- **A.** 先输入密码，再输入记住的安全问题答案。
- **B.** 先输入大学账户密码，再输入记住的另一个服务密码。
- **C.** 先输入密码，再在同一个网站输入记住的 PIN，不使用与设备绑定的验证器。
- **D.** 先输入密码，再通过该学生已注册的验证器设备批准登录。

<details>
<summary>思路：</summary>

**D. 先输入密码，再通过该学生已注册的验证器设备批准登录。**

密码代表学生知道的信息，而对已注册验证器设备的控制提供持有因素。因此，同时要求这两项就结合了不同类别的因素。两个记住的秘密即使内容不同，也仍然属于知识因素。这种分类并不意味着所有 MFA 方法都同样能抵御网络钓鱼；大学的访问策略还需要考虑方法选择、注册、恢复和实际强制执行。

- **A.** 密码和记住的答案都是知识因素；多一次知识验证并没有增加所需的持有因素。
- **B.** 使用不同密码可以区分凭据，但两者都是记住的秘密，仍属于同一类因素。
- **C.** 题目排除了与设备绑定的验证器：将 PIN 作为另一个网站秘密输入，提供的是知识，而不是持有设备的证明。

## SC-900 · Purview 数据处理

大学需要在受支持的文档共享活动中检测学生标识符，并在匹配已配置规则时警告或限制外部共享。Purview 的哪项功能最直接满足这个要求？

- **A.** 仅用于记录共享活动已经发生的审核功能。
- **B.** 配置了恰当范围并经过测试的策略的数据丢失防护（DLP）。
- **C.** 配置为将文档保留七年的保留功能。
- **D.** 仅命名为 Confidential、未配置保护或 DLP 的敏感度标签。

<details>
<summary>思路：</summary>

**B. 配置了恰当范围并经过测试的策略的数据丢失防护（DLP）。**

DLP 根据已配置的策略评估敏感信息和相关活动，并能对受支持的操作发出警告或施加限制。设计时仍需明确位置、检测条件、接收者、例外和预期响应。审核提供活动证据，保留管理内容生命周期，标签则传达分类信息或应用已配置的保护。单有标签名称，无法实现本题所描述的外部共享限制。

- **A.** 审核通过记录活动来支持调查，但记录一次共享本身并不会提供所需的策略警告或限制。
- **C.** 将文档保存指定时间是在管理其生命周期，并不能决定这次外部共享是否应当继续。
- **D.** 仅有标签名称不会配置共享限制；必须通过保护设置或合适的 DLP 策略实现预期行为。

## AZ-700 · 最长前缀路由

实验用 VM 有两条处于活动状态的有效路由：用户定义的 0.0.0.0/0 路由指向网络设备，系统 10.20.0.0/16 路由经过 VNet 对等互连。没有更具体的路由。发往 10.20.7.5 的流量会选择哪个下一跃点？

- **A.** VNet 对等互连，因为匹配的 /16 前缀更具体。
- **B.** 网络设备，因为用户定义路由始终优先于所有系统路由。
- **C.** 两个下一跃点，因为 Azure 会将数据包复制到所有匹配的路由。
- **D.** 没有下一跃点，因为匹配前缀重叠会使路由表无效。

<details>
<summary>思路：</summary>

**A. VNet 对等互连，因为匹配的 /16 前缀更具体。**

Azure 首先从匹配的路由中选择前缀最长的那一条。目标地址属于 10.20.0.0/16，这比 0.0.0.0/0 更具体，所以这个数据包使用处于活动状态的对等互连路由。当适用路由的前缀长度相同时，路由来源的优先级才有意义；它不会让用户定义的默认路由在所有情况下都优先。选出下一跃点，也不代表防火墙已经放行或应用访问已经获准。

- **B.** 这里路由来源的优先级不会覆盖最长前缀选择；用户定义的默认路由没有活动的对等互连路由具体。

## SC-200 · 响应操作的幂等性

Sentinel 剧本创建了一个大学事件工单，但成功响应丢失了。重试可能为同一项已批准操作再创建一个工单。哪种工作流控制最能解决这个问题？

- **A.** 延长超时时间，并认为只要没有收到响应就一定没有工单。
- **B.** 每次重试都生成新的操作标识符，让所有请求看起来相互独立。
- **C.** 持久保存事件与操作的键以及工单状态，在重试该操作时核对或复用已有结果。
- **D.** 只对传入的警报记录去重，允许创建工单的步骤不检查状态就重复执行。

<details>
<summary>思路：</summary>

**C. 持久保存事件与操作的键以及工单状态，在重试该操作时核对或复用已有结果。**

幂等性意味着，重复执行同一个逻辑操作时保持预期结果，而不会额外产生副作用。持久保存的事件与操作键、已记录的状态，以及外部工单引用，可以让重试找到或核对已经完成的工作。在检查前，丢失响应意味着结果未知。工作流还需要次数有限的重试、明确的责任人，以及适合创建工单的权限；仅对警报去重不能控制操作执行。

- **A.** 延长超时可以减少部分失败，但响应丢失后，外部工单是否已经创建仍然不确定。
- **B.** 新标识符会让重试看起来像一项新工作，使工作流无法识别这其实是已经尝试过的同一个逻辑操作。
- **D.** 警报去重控制的是输入记录；如果操作执行没有自己的状态检查，重试下游步骤仍然可能重复创建工单。

- **D.** 更换主机却保留相同的文件夹访问拒绝，会使已确认的存储权限问题继续出现在新的会话路径中。

- **B.** 只要观察到一次删除，就永久忽略 E 的所有后续更改。

## SC-100 · 恢复目标验证

一次恢复演练设定 RTO 为两小时，RPO 为 15 分钟。中断于 11:00 UTC 开始。获授权的文档读取在 12:30 恢复，但数据只恢复到 10:40。假设这些就是约定的测量边界，哪项评估正确？

- **A.** 两个目标都达到，因为服务在两小时内恢复。
- **B.** 达到 RPO，但未达到 RTO。
- **C.** 两个目标都未达到，因为任何数据损失都违反 RTO。
- **D.** 达到 RTO，但恢复点比中断早 20 分钟，因此未达到 RPO。

<details>
<summary>思路：</summary>

**D. 达到 RTO，但恢复点比中断早 20 分钟，因此未达到 RPO。**

RTO 衡量可接受的中断时长：获授权的读取在 90 分钟后恢复，处于两小时目标以内。RPO 衡量可接受的近期数据损失：11:00 发生中断，数据仅恢复到 10:40，留下 20 分钟的缺口，超过 15 分钟目标。这是两项独立检查，满足其中一项并不等于满足另一项。演练应记录两个测量结果，以及使既定业务操作能够恢复的依赖条件。

- **B.** 实际中断 90 分钟，未超过两小时，而 20 分钟的数据缺口超过 15 分钟；这个选项把结果反过来了。
- **C.** RTO 关注中断持续时间，而不是是否存在任何数据损失；虽然 RPO 未达标，测得的 90 分钟恢复仍满足 RTO。
