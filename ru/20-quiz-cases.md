## AZ-900 · Контроль над вычислительной средой

Для лабораторного приложения нужно установить собственный драйвер ядра Linux. Какой вариант размещения лучше всего подходит под это требование?

- **A.** Запустить приложение в Microsoft 365.
- **B.** Использовать виртуальную машину Azure с совместимым образом Linux.
- **C.** Развернуть приложение в управляемой среде App Service.
- **D.** Поместить драйвер в обычную Azure Function.

<details>
<summary>Почему подходит этот ответ</summary>

**B. Использовать виртуальную машину Azure с совместимым образом Linux.**

Ключевое требование — управление гостевой операционной системой. Совместимая виртуальная машина Azure позволяет команде настраивать эту среду и её драйверы. При этом обслуживание ОС тоже остаётся задачей команды. Управляемая платформа приложений здесь не подходит, если она не даёт нужного доступа к ядру.

- **A.** Microsoft 365 предоставляет готовое ПО, а не среду для произвольных драйверов ядра.
- **C.** Управляемая среда App Service не предоставляет необходимое администрирование гостевого ядра.
- **D.** Обычная Function не даёт требуемого контроля над драйверами ядра.

## AZ-900 · Горизонтальное масштабирование и сеансы

В API для учебных заметок добавляют экземпляры за балансировщиком нагрузки. Любой экземпляр могут заменить, но пользовательские сеансы должны сохраниться. Сейчас сеансы находятся только в памяти каждого экземпляра. Что нужно изменить?

- **A.** Увеличить мощность CPU каждого экземпляра.
- **B.** Оставить сеансы в памяти и включить только привязку запросов к одному экземпляру.
- **C.** Перенести состояние сеансов в подходящее общее внешнее хранилище.
- **D.** Назначить каждому экземпляру общедоступный IP-адрес.

<details>
<summary>Почему подходит этот ответ</summary>

**C. Перенести состояние сеансов в подходящее общее внешнее хранилище.**

Горизонтальное масштабирование распределяет запросы между экземплярами, поэтому важное состояние сеанса не должно зависеть только от памяти одного из них. Подходящее внешнее хранилище позволит новому экземпляру получить это состояние. Одна лишь привязка запросов не сохранит память исчезнувшего экземпляра. Приложению также нужно обрабатывать доступ к внешнему сервису состояния и его сбои.

- **A.** Дополнительная мощность CPU не сохраняет память после замены экземпляра.
- **B.** При исчезновении выбранного экземпляра сеанс потеряется даже с привязкой запросов.
- **D.** Общедоступные IP-адреса не обеспечивают общее или долговременное хранение состояния сеансов.

[Источник](https://learn.microsoft.com/en-us/azure/architecture/guide/design-principles/scale-out) · [Что перечитать](01-fundamentals.md)

## AZ-104 · Доступ к данным хранилища

У пользователя есть роль Contributor для учётной записи хранения. Запрос к Blob с его идентичностью Entra доходит до сервиса, но отклоняется из-за отсутствия разрешения на данные. Пользователю нужно только читать BLOB-объекты в одном контейнере. Как применить принцип наименьших привилегий?

- **A.** Назначить Storage Blob Data Reader в области действия этого контейнера.
- **B.** Назначить Owner для всей подписки.
- **C.** Открыть все входящие сетевые порты.
- **D.** Передать пользователю ключ учётной записи хранения.

<details>
<summary>Почему подходит этот ответ</summary>

**A. Назначить Storage Blob Data Reader в области действия этого контейнера.**

Разрешения на управление и разрешения на данные Blob разделены. Storage Blob Data Reader даёт необходимое право чтения, а область действия контейнера ограничивает доступ указанной задачей. В условии уже установлено, что не хватает разрешения на данные. Широкие административные права или несвязанные изменения сети здесь несоразмерны задаче.

- **B.** Роль Owner на уровне подписки намного шире требуемого чтения одного контейнера.
- **C.** Открытие портов не выдаёт недостающее разрешение на данные.
- **D.** Ключ учётной записи предоставляет гораздо более широкий доступ, чем требуется.

## AZ-104 · Наследование разрешений RBAC

У пользователя есть Reader, назначенный напрямую для виртуальной машины, а также через группу с ролью Reader на уровне подписки. Ты удаляешь только прямое назначение для ВМ. Пользователь всё ещё может читать сведения о ВМ. Почему?

- **A.** Azure автоматически выдаёт всем пользователям Reader для всех ВМ.
- **B.** Тег группы ресурсов восстанавливает удалённое назначение.
- **C.** Удаление роли всегда требует удаления ВМ.
- **D.** Назначение группе по-прежнему предоставляет унаследованный доступ.

<details>
<summary>Почему подходит этот ответ</summary>

**D. Назначение группе по-прежнему предоставляет унаследованный доступ.**

Удаление одного назначения не отменяет разрешения из других назначений. У группы есть Reader на уровне подписки, поэтому её участники могут наследовать этот доступ к ВМ. Проверь прямые назначения, членство в группах и родительские области действия, прежде чем считать оставшийся доступ ошибкой сервиса или выдавать дополнительные права.

- **A.** Общего назначения Reader всем пользователям не существует.
- **B.** Теги классифицируют ресурсы и не создают заново назначения ролей.
- **C.** Роль можно удалить без удаления защищённого ресурса.

## AZ-305 · Цели восстановления

В текущем проекте пригодная для восстановления точка базы данных успешно создаётся только раз в 24 часа. Теперь после аварии бизнес допускает потерю данных не более чем за последний час. Какое изменение непосредственно устраняет это несоответствие?

- **A.** Увеличить мощность CPU сервера API.
- **B.** Обеспечить пригодные для восстановления защищённые состояния с интервалом не более часа и проверить восстановление.
- **C.** Добавить бюджет с оповещением о расходах.
- **D.** Переименовать группу ресурсов в production.

<details>
<summary>Почему подходит этот ответ</summary>

**B. Обеспечить пригодные для восстановления защищённые состояния с интервалом не более часа и проверить восстановление.**

RPO описывает допустимый объём потери свежих данных, выраженный во времени. Одни лишь ежедневные точки восстановления не обеспечивают цель в один час. Схема защиты должна создавать пригодные для восстановления состояния достаточно часто, а восстановление нужно проверить. Быстрые серверы приложения или обозначения затрат не меняют возраст доступных для восстановления данных.

- **A.** Мощность CPU API не увеличивает частоту создания защищённых состояний данных.
- **C.** Бюджет предупреждает о расходах, а не о потере данных.
- **D.** Название группы ресурсов не меняет частоту точек восстановления.

## AZ-305 · Частный DNS

Общедоступный доступ к сервису хранения отключён, а частная конечная точка уже создана. Клиент всё ещё разрешает имя сервиса в общедоступный IP-адрес. Сам частный сетевой маршрут доступен. Что стоит проверить первым?

- **A.** Назначить клиенту Owner на уровне подписки.
- **B.** Навсегда прописать общедоступный IP-адрес вручную.
- **C.** Частные зоны DNS, их связи и пересылку запросов, которыми пользуется этот клиент.
- **D.** Неограниченно увеличивать число повторных запросов приложения.

<details>
<summary>Почему подходит этот ответ</summary>

**C. Частные зоны DNS, их связи и пересылку запросов, которыми пользуется этот клиент.**

Клиент получает неверный адрес назначения для предполагаемого частного подключения. Исправление DNS само по себе не выдаёт разрешения на данные, но посторонние привилегии и бесконечные повторы не устраняют это несоответствие.

- **A.** Роль Owner не меняет разрешение имён на клиенте.
- **B.** После отключения общедоступного доступа публичный адрес — неверное назначение.
- **D.** Повторение запроса не исправляет устойчиво неверную конфигурацию DNS.

## AZ-400 · Продвижение протестированных артефактов

Конвейер тестирует один образ контейнера, а затем заново собирает его из исходного кода для production с зависимостями, которые могут измениться. Как убедиться, что в production попадёт именно протестированный образ?

- **A.** Повторно проверить только комментарии в исходном коде.
- **B.** Использовать тег latest, не фиксируя, на какой образ он указывает.
- **C.** Пропустить тесты, поскольку коммит исходного кода не изменился.
- **D.** Продвинуть тот же протестированный образ, идентифицируя его неизменяемым digest.

<details>
<summary>Почему подходит этот ответ</summary>

**D. Продвинуть тот же протестированный образ, идентифицируя его неизменяемым digest.**

Один и тот же коммит может дать разные результаты сборки при изменении инструментов, зависимостей или базовых образов. Продвижение уже протестированного образа исключает такое отличие из-за повторной сборки. Неизменяемый digest идентифицирует сам артефакт, тогда как тег может указывать на другой образ. Конфигурацию среды всё равно нужно отдельно проверять и контролировать.

- **A.** Комментарии исходного кода не идентифицируют собранный артефакт.
- **B.** Изменяемый тег позже может указывать на другой образ.
- **C.** Неизменившийся коммит не доказывает идентичность повторно собранного результата.

## AZ-400 · Сигналы для canary-развёртывания

В canary-релизе загрузка CPU и памяти обычная, но при скачивании документов пользователи получают неверные файлы. На чём должно основываться решение о дальнейшем развёртывании?

- **A.** На сигналах функциональной корректности и заранее заданном критерии остановки или отката.
- **B.** Только на CPU: здоровая инфраструктура доказывает правильность результатов.
- **C.** На переходе к более мощной ВМ до проверки возвращаемых файлов.
- **D.** На удалении старых журналов, чтобы панель мониторинга выглядела аккуратнее.

<details>
<summary>Почему подходит этот ответ</summary>

**A. На сигналах функциональной корректности и заранее заданном критерии остановки или отката.**

Релиз может потреблять мало ресурсов и при этом выдавать неверный результат для пользователя. Для продвижения нужны сигналы, отражающие пользовательскую операцию, а не только загрузку инфраструктуры. Заранее заданное правило остановки или отката помогает действовать на основании этих данных. Проверь и совместимость данных: откат кода сам по себе не отменяет вредные изменения данных, сделанные релизом.

- **B.** CPU и память не доказывают, что пользователи получают нужные документы.
- **C.** Дополнительная вычислительная мощность сама по себе не исправляет неверный вывод приложения.
- **D.** Удаление свидетельств затрудняет расследование и не исправляет результат.

## DP-900 · Транзакционные нагрузки

Университетский сервис записи должен зарезервировать последнее свободное место в лабораторной группе и создать запись студента как одну согласованную операцию. Какое описание нагрузки лучше всего соответствует этому требованию?

- **A.** Аналитическая нагрузка, которая подсчитывает записи по семестрам.
- **B.** Пакетная нагрузка, которая каждую ночь согласует независимые изменения числа мест.
- **C.** Транзакционная нагрузка, которая фиксирует связанные изменения вместе.
- **D.** Потоковая нагрузка, которая публикует отдельные события о месте и записи, не согласуя их фиксацию.

<details>
<summary>Почему подходит этот ответ</summary>

**C. Транзакционная нагрузка, которая фиксирует связанные изменения вместе.**

Требование относится к небольшой конкретной операции, связанные изменения которой должны либо вместе завершиться успешно, либо вместе не выполниться. Это транзакционное поведение: другой запрос не должен зарезервировать то же последнее место, пока сведения о записи и вместимости расходятся. Историческая отчётность относится к аналитической работе с иными способами доступа к данным. События и последующая сверка могут быть полезны в более широкой архитектуре, но сами по себе независимые обновления не выполняют указанное требование согласованности.

- **A.** Агрегация по семестрам отвечает на вопросы о прошлом; она не согласует резервирование места и изменение записи, необходимые для этого текущего запроса.
- **B.** Ночная сверка оставляет промежуток, в котором число мест и записи могут расходиться, что противоречит требованию немедленной согласованности.
- **D.** Публикация событий может уведомлять другие системы, но события с независимой фиксацией сами по себе не делают два исходных изменения атомарными.

## DP-900 · Порядок ETL и ELT

Исследовательская группа извлекает вчерашние записи о скачиваниях, удаляет недопустимые идентификаторы в сервисе обработки, а затем загружает очищенные записи в хранилище для отчётности. Какое описание соответствует этому порядку?

- **A.** ETL, поскольку преобразование выполняется до загрузки в целевое хранилище для отчётности.
- **B.** ELT, поскольку любой процесс с загрузкой в хранилище выполняет преобразование внутри этого хранилища.
- **C.** Потоковая обработка, поскольку записи о скачиваниях изначально получены из событий приложения.
- **D.** Только оркестрация, поскольку согласование шагов устраняет необходимость преобразования.

<details>
<summary>Почему подходит этот ответ</summary>

**A. ETL, поскольку преобразование выполняется до загрузки в целевое хранилище для отчётности.**

ETL означает извлечение, преобразование и последующую загрузку в заданную целевую систему. Здесь недопустимые идентификаторы обрабатываются до того, как хранилище отчётности получает очищенные записи. При ELT данные сначала загрузили бы, а затем преобразовали средствами целевой системы. Ограниченный набор вчерашних записей представляет собой пакетные входные данные. Оркестратор может координировать эти действия, но оркестрация и преобразование описывают разные обязанности в одном конвейере.

- **B.** При ELT загрузка предшествует преобразованию в целевой системе; сам выбор хранилища в качестве назначения не определяет этот порядок.
- **C.** Происхождение из событий не делает последующую обработку потоковой: это задание обрабатывает ограниченный суточный набор, а не непрерывно поступающие записи.
- **D.** Оркестрация координирует зависимости и восстановление, тогда как удаление недопустимых идентификаторов меняет данные и остаётся отдельной задачей преобразования.

## SC-900 · Категории факторов MFA

Студент сравнивает варианты входа. Какой пример сочетает фактор знания с фактором владения, если устройство аутентификации зарегистрировано, а подтверждение обязательно?

- **A.** Пароль, после которого вводится запомненный ответ на контрольный вопрос.
- **B.** Университетский пароль, после которого вводится другой запомненный пароль сервиса.
- **C.** Пароль, после которого на том же сайте вводится запомненный ПИН-код, без аутентификатора, привязанного к устройству.
- **D.** Пароль, после которого вход подтверждается через зарегистрированное устройство аутентификации студента.

<details>
<summary>Почему подходит этот ответ</summary>

**D. Пароль, после которого вход подтверждается через зарегистрированное устройство аутентификации студента.**

Пароль представляет собой то, что студент знает, а контроль зарегистрированного устройства аутентификации обеспечивает фактор владения. Обязательное использование обоих сочетает разные категории факторов. Два запомненных секрета остаются факторами знания, даже если их строки различаются. - **C.** Использовать поддерживаемый туннель IPsec поверх ExpressRoute, проверив маршрутизацию, поддержку шлюзов и требуемую пропускную способность.

- **D.** TLS между приложением и базой данных защищает другой участок и не обеспечивает явно требуемую защиту от VPN-устройства кампуса до шлюза Azure.

- **C.** Сохранить сведения об удалении и версии 98 и отклонить обновление 94 как более старое, допуская при этом корректное более новое изменение.
- **D.** Удалить контрольную точку и повторно обработать изменения строго в порядке поступления без сравнения версий.

<details>
<summary>Почему подходит этот ответ</summary>

**C. Сохранить сведения об удалении и версии 98 и отклонить обновление 94 как более старое, допуская при этом корректное более новое изменение.**

Порядок бизнес-изменений определяется последовательностью источника, поэтому обновление 94 не должно восстанавливать запись, удалённую изменением 98. Сохранение удаления и его версии позволяет идемпотентному слиянию отклонять устаревшие изменения, принимая допустимую более позднюю версию. Время поступления здесь не определяет порядок. Вместе нужны стабильные ключи, детерминированное сравнение версий и надёжное сохранение прогресса; повторный запуск входных данных без этих правил не исправляет проблему порядка.

- **A.** Порядок поступления может отличаться от порядка изменений источника; применение более старого обновления ошибочно восстановит запись, удалённую более новым изменением.
- **B.** Постоянный запрет также отклонит допустимую последующую повторную запись студента; слияние должно сравнивать версии, а не запрещать все будущие изменения для ключа.
- **D.** Повторная обработка в том же порядке поступления без проверки версий может снова восстановить удалённую запись; само удаление контрольной точки не обеспечивает соблюдение порядка изменений источника.

## DP-700 · Пути доступа в Fabric

Университетский отчёт правильно применяет ограничения на уровне строк и имеет метку конфиденциальности. Тот же аналитик может напрямую читать исходные файлы с данными отдельных студентов через разрешённый путь OneLake. Политика допускает только итоги по учебным модулям. Что инженеру следует изменить и проверить?

- **A.** Переименовать метку в «Строго конфиденциально» и считать, что её название применяет ограничения строк отчёта при прямом чтении файлов.
- **B.** Ограничить нижележащий путь доступа минимально необходимыми разрешениями и от имени аналитика проверить разрешённые итоги и запрещённые подробные данные.
- **C.** Скрыть подробную таблицу в отчёте, не меняя прямых разрешений аналитика на файлы.
- **D.** Выдать более широкую роль рабочей области, чтобы существующие ограничения строк отчёта автоматически управляли всеми путями доступа.

<details>
<summary>Почему подходит этот ответ</summary>

**B. Ограничить нижележащий путь доступа минимально необходимыми разрешениями и от имени аналитика проверить разрешённые итоги и запрещённые подробные данные.**

Ограничение, применяемое отчётом или механизмом запросов, не распространяется автоматически на отдельный путь прямого доступа к файлам. Инженер должен согласовать с политикой разрешения рабочей области, элемента, механизма запросов и файлов и проверить каждый предусмотренный путь с идентичностью аналитика. Метка конфиденциальности задаёт контекст управления данными или настроенную защиту, но одно её название не обеспечивает одинаковую авторизацию повсюду. Более широкие разрешения могут открыть дополнительные пути вместо устранения этого пробела.

- **A.** Изменение названия классификации не настраивает отдельную границу файлового доступа и не применяет автоматически ограничения строк механизма отчёта через OneLake.
- **C.** Скрытие содержимого отчёта меняет только его представление; у аналитика остаётся указанный прямой путь к исходным файлам с данными отдельных студентов.
- **D.** Более широкая роль рабочей области расширяет доступ и не превращает ограничения строк отчёта в универсальное правило для каждого механизма запросов и файлового пути.

## SC-100 · Ответственность за остаточный риск

Архитектор документирует, что у предлагаемой университетской платформы заметок остаётся существенный риск простоя после всех практически осуществимых мер контроля. Команда безопасности рекомендует продолжить, но порядок управления требует принятия бизнес-риска. Кто должен разрешить принятие этого остаточного риска?

- **A.** Аналитик SOC, который может закрыть связанный тикет безопасности.
- **B.** Ответственный владелец бизнес-риска с необходимыми полномочиями, зафиксировав риск и условия пересмотра решения.
- **C.** Поставщик продукта, поскольку его оценка соответствия заменяет бизнес-решение университета.
- **D.** Облачный администратор только потому, что он может развернуть ресурсы.

<details>
<summary>Почему подходит этот ответ</summary>

**B. Ответственный владелец бизнес-риска с необходимыми полномочиями, зафиксировав риск и условия пересмотра решения.**

Остаточный риск остаётся риском для деятельности организации и после выбора технических мер. Уполномоченный и подотчётный владелец риска должен решить, допустим ли он, используя сведения архитектора о влиянии, предположениях о вероятности, альтернативах и оставшихся пробелах. Решение должно определять область действия, условия пересмотра и ответственность. Рекомендации безопасности, права на развёртывание ресурсов и оценки поставщиков помогают принять решение, но не дают автоматически требуемых университетом полномочий на принятие риска.

- **A.** Закрытие операционного тикета — разрешение в рабочем процессе; оно не устанавливает полномочий принимать существенный бизнес-риск за университет.
- **C.** Оценка поставщика может помочь выбрать меры контроля, но не заменяет ответственное решение университета о собственном оставшемся операционном риске.
- **D.** Возможность развернуть ресурсы означает технические полномочия; сценарий отдельно требует уполномоченного бизнес-владельца для принятия остаточного риска простоя.

## SC-100 · Проверка целей восстановления

Учение по восстановлению задаёт RTO в два часа и RPO в 15 минут. Простой начинается в 11:00 UTC. Авторизованное чтение документов возобновляется в 12:30, а данные восстановлены только по состоянию на 10:40. Считайте эти границы измерений согласованными. Какая оценка верна?

- **A.** Обе цели выполнены, поскольку сервис возобновил работу в течение двух часов.
- **B.** RPO выполнен, а RTO нарушен.
- **C.** Обе цели нарушены, поскольку любая потеря данных нарушает RTO.
- **D.** RTO выполнен, но RPO нарушен, поскольку точка восстановления находится за 20 минут до простоя.

<details>
<summary>Почему подходит этот ответ</summary>

**D. RTO выполнен, но RPO нарушен, поскольку точка восстановления находится за 20 минут до простоя.**

RTO измеряет допустимую длительность перерыва: авторизованное чтение возобновляется через 90 минут, в пределах двухчасовой цели. RPO измеряет допустимую потерю последних данных: восстановление на 10:40 при простое с 11:00 оставляет разрыв в 20 минут, превышающий цель в 15 минут. Это независимые проверки, и выполнение одной не обеспечивает другую. В учении следует зафиксировать оба измерения и зависимости, которые позволили возобновить определённую бизнес-операцию.

- **A.** Восстановление сервиса в установленный срок выполняет только RTO; отдельный 20-минутный разрыв точки восстановления всё ещё превышает указанный RPO.
- **B.** Перерыв длится 90 минут, то есть менее двух часов, а 20-минутный разрыв данных превышает 15 минут; этот вариант меняет результаты местами.
- **C.** RTO относится к длительности перерыва, а не к наличию любой потери данных; измеренное восстановление за 90 минут выполняет эту цель, несмотря на нарушение RPO.

## AZ-120 · Fencing SAP и единственный пишущий узел

Во время обсуждения учебного инцидента кластера SAP HANA теряется связь с основным узлом, а вторичный не может выполнить его fencing — принудительную изоляцию. Команда не может подтвердить, что основной узел перестал принимать записи. Как лучше всего сохранить целостность данных до переключения?

- **A.** Отключить fencing и сделать вторичный узел основным, чтобы панель кластера сразу показала работающие ресурсы.
- **B.** Сделать вторичный узел основным, поскольку последний успешный статус репликации доказывает, что старый основной уже не может писать.
- **C.** Следовать поддерживаемой процедуре инцидента, восстановить или проверить fencing и подтвердить изоляцию прежнего пишущего узла до разрешения записей после переключения.
- **D.** Перенести виртуальный адрес сервиса на вторичный узел, оставив прежнему основному с неопределённым состоянием возможность записи.

<details>
<summary>Почему подходит этот ответ</summary>

**C. Следовать поддерживаемой процедуре инцидента, восстановить или проверить fencing и подтвердить изоляцию прежнего пишущего узла до разрешения записей после переключения.**

Потеря связи не доказывает остановку основного узла. Fencing изолирует узел, который не может безопасно продолжать работу, обеспечивая требование единственного пишущего узла и снижая риск split brain. Команда должна проверить поддерживаемую конфигурацию fencing и кворума, сохранить сведения о состоянии и установить, что старый пишущий узел изолирован, прежде чем разрешить записи после переключения. Исправность репликации и перенос адреса не обеспечивают такой изоляции, а отключение fencing убирает критически важный механизм защиты.

- **A.** Отключение fencing убирает механизм изоляции пишущего узла с неопределённым состоянием, поэтому кажущаяся доступность может обернуться конфликтующими основными узлами.
- **B.** Предыдущий результат репликации описывает перенос данных в тот момент; он не доказывает, что недоступный основной узел сейчас перестал принимать записи.
- **D.** Перенос виртуального адреса меняет путь клиентов, но сам по себе не мешает старому основному узлу писать через другие сеансы или пути.

## AZ-120 · Записи SAP после переключения

- **A.** Остановить записи, определить, какое состояние данных считать достоверным, сохранить транзакции целевой системы и согласовать поддерживаемый план сверки или обратной миграции до повторного открытия пишущей системы.
- **B.** Направить DNS обратно на неизменённую исходную систему и предположить, что новые заказы целевой системы уже есть там.
- **C.** Перезаписать целевую систему из старой исходной, затем возобновить закупки, не выявляя транзакций, созданных после переключения.
- **D.** Открыть для записи обе системы, пока бизнес-пользователи позднее решают, какие заказы сохранить.

<details>
<summary>Почему подходит этот ответ</summary>

**A. Остановить записи, определить, какое состояние данных считать достоверным, сохранить транзакции целевой системы и согласовать поддерживаемый план сверки или обратной миграции до повторного открытия пишущей системы.**

- **D.** Разрешение записей в обеих средах создаёт расходящиеся истории транзакций, усложняет сверку и нарушает необходимый контроль единственной системы записи, служащей источником достоверных данных.
