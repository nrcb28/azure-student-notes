## AZ-900 · Контроль над вычислительной средой

Для лабораторного приложения нужно установить собственный драйвер ядра Linux. Какой вариант размещения лучше всего подходит под это требование?

- **A.** Запустить приложение в Microsoft 365.
- **B.** Использовать виртуальную машину Azure с совместимым образом Linux.
- **C.** Развернуть приложение в управляемой среде App Service.
- **D.** Поместить драйвер в обычную Azure Function.

<details>
<summary>Почему подходит этот ответ</summary>

**B. Использовать виртуальную машину Azure с совместимым образом Linux.**

Ключевое требование — управление гостевой операционной системой. Совместимая виртуальная машина Azure позволяет команде настраивать эту среду и её драйверы. При этом обслуживание ОС тоже остаётся задачей команды. Управляемая платформа приложений здесь не подходит, если она не даёт нужного доступа к ядру.

- **A.** Microsoft 365 предоставляет готовое ПО, а не среду для произвольных драйверов ядра.
- **C.** Управляемая среда App Service не предоставляет необходимое администрирование гостевого ядра.
- **D.** Обычная Function не даёт требуемого контроля над драйверами ядра.

## AZ-900 · Горизонтальное масштабирование и сеансы

В API для учебных заметок добавляют экземпляры за балансировщиком нагрузки. Любой экземпляр могут заменить, но пользовательские сеансы должны сохраниться. Сейчас сеансы находятся только в памяти каждого экземпляра. Что нужно изменить?

- **A.** Увеличить мощность CPU каждого экземпляра.
- **B.** Оставить сеансы в памяти и включить только привязку запросов к одному экземпляру.
- **C.** Перенести состояние сеансов в подходящее общее внешнее хранилище.
- **D.** Назначить каждому экземпляру общедоступный IP-адрес.

<details>
<summary>Почему подходит этот ответ</summary>

**C. Перенести состояние сеансов в подходящее общее внешнее хранилище.**

Горизонтальное масштабирование распределяет запросы между экземплярами, поэтому важное состояние сеанса не должно зависеть только от памяти одного из них. Подходящее внешнее хранилище позволит новому экземпляру получить это состояние. Одна лишь привязка запросов не сохранит память исчезнувшего экземпляра. Приложению также нужно обрабатывать доступ к внешнему сервису состояния и его сбои.

- **A.** Дополнительная мощность CPU не сохраняет память после замены экземпляра.
- **B.** При исчезновении выбранного экземпляра сеанс потеряется даже с привязкой запросов.
- **D.** Общедоступные IP-адреса не обеспечивают общее или долговременное хранение состояния сеансов.

[Источник](https://learn.microsoft.com/en-us/azure/architecture/guide/design-principles/scale-out) · [Что перечитать](01-fundamentals.md)

</details>

## AZ-104 · Доступ к данным хранилища

У пользователя есть роль Contributor для учётной записи хранения. Запрос к Blob с его идентичностью Entra доходит до сервиса, но отклоняется из-за отсутствия разрешения на данные. Пользователю нужно только читать BLOB-объекты в одном контейнере. Как применить принцип наименьших привилегий?

- **A.** Назначить Storage Blob Data Reader в области действия этого контейнера.
- **B.** Назначить Owner для всей подписки.
- **C.** Открыть все входящие сетевые порты.
- **D.** Передать пользователю ключ учётной записи хранения.

<details>
<summary>Почему подходит этот ответ</summary>

**A. Назначить Storage Blob Data Reader в области действия этого контейнера.**

Разрешения на управление и разрешения на данные Blob разделены. Storage Blob Data Reader даёт необходимое право чтения, а область действия контейнера ограничивает доступ указанной задачей. В условии уже установлено, что не хватает разрешения на данные. Широкие административные права или несвязанные изменения сети здесь несоразмерны задаче.

- **B.** Роль Owner на уровне подписки намного шире требуемого чтения одного контейнера.
- **C.** Открытие портов не выдаёт недостающее разрешение на данные.
- **D.** Ключ учётной записи предоставляет гораздо более широкий доступ, чем требуется.

[Источник](https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access) · [Что перечитать](06-identity.md)

</details>

## AZ-104 · Наследование разрешений RBAC

У пользователя есть Reader, назначенный напрямую для виртуальной машины, а также через группу с ролью Reader на уровне подписки. Ты удаляешь только прямое назначение для ВМ. Пользователь всё ещё может читать сведения о ВМ. Почему?

- **A.** Azure автоматически выдаёт всем пользователям Reader для всех ВМ.
- **B.** Тег группы ресурсов восстанавливает удалённое назначение.
- **C.** Удаление роли всегда требует удаления ВМ.
- **D.** Назначение группе по-прежнему предоставляет унаследованный доступ.

<details>
<summary>Почему подходит этот ответ</summary>

**D. Назначение группе по-прежнему предоставляет унаследованный доступ.**

Удаление одного назначения не отменяет разрешения из других назначений. У группы есть Reader на уровне подписки, поэтому её участники могут наследовать этот доступ к ВМ. Проверь прямые назначения, членство в группах и родительские области действия, прежде чем считать оставшийся доступ ошибкой сервиса или выдавать дополнительные права.

- **A.** Общего назначения Reader всем пользователям не существует.
- **B.** Теги классифицируют ресурсы и не создают заново назначения ролей.
- **C.** Роль можно удалить без удаления защищённого ресурса.

[Источник](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview) · [Что перечитать](06-identity.md)

</details>

## AZ-305 · Цели восстановления

В текущем проекте пригодная для восстановления точка базы данных успешно создаётся только раз в 24 часа. Теперь после аварии бизнес допускает потерю данных не более чем за последний час. Какое изменение непосредственно устраняет это несоответствие?

- **A.** Увеличить мощность CPU сервера API.
- **B.** Обеспечить пригодные для восстановления защищённые состояния с интервалом не более часа и проверить восстановление.
- **C.** Добавить бюджет с оповещением о расходах.
- **D.** Переименовать группу ресурсов в production.

<details>
<summary>Почему подходит этот ответ</summary>

**B. Обеспечить пригодные для восстановления защищённые состояния с интервалом не более часа и проверить восстановление.**

RPO описывает допустимый объём потери свежих данных, выраженный во времени. Одни лишь ежедневные точки восстановления не обеспечивают цель в один час. Схема защиты должна создавать пригодные для восстановления состояния достаточно часто, а восстановление нужно проверить. Быстрые серверы приложения или обозначения затрат не меняют возраст доступных для восстановления данных.

- **A.** Мощность CPU API не увеличивает частоту создания защищённых состояний данных.
- **C.** Бюджет предупреждает о расходах, а не о потере данных.
- **D.** Название группы ресурсов не меняет частоту точек восстановления.

[Источник](https://learn.microsoft.com/en-us/azure/well-architected/reliability/disaster-recovery) · [Что перечитать](10-architecture.md)

</details>

## AZ-305 · Частный DNS

Общедоступный доступ к сервису хранения отключён, а частная конечная точка уже создана. Клиент всё ещё разрешает имя сервиса в общедоступный IP-адрес. Сам частный сетевой маршрут доступен. Что стоит проверить первым?

- **A.** Назначить клиенту Owner на уровне подписки.
- **B.** Навсегда прописать общедоступный IP-адрес вручную.
- **C.** Частные зоны DNS, их связи и пересылку запросов, которыми пользуется этот клиент.
- **D.** Неограниченно увеличивать число повторных запросов приложения.

<details>
<summary>Почему подходит этот ответ</summary>

**C. Частные зоны DNS, их связи и пересылку запросов, которыми пользуется этот клиент.**

Клиент получает неверный адрес назначения для предполагаемого частного подключения. Проверь рекомендуемую для сервиса конфигурацию частного DNS и то, как клиент ею пользуется, включая связи и пересылку. Продолжай использовать имя сервиса. Исправление DNS само по себе не выдаёт разрешения на данные, но посторонние привилегии и бесконечные повторы не устраняют это несоответствие.

- **A.** Роль Owner не меняет разрешение имён на клиенте.
- **B.** После отключения общедоступного доступа публичный адрес — неверное назначение.
- **D.** Повторение запроса не исправляет устойчиво неверную конфигурацию DNS.

## AZ-400 · Продвижение протестированных артефактов

Конвейер тестирует один образ контейнера, а затем заново собирает его из исходного кода для production с зависимостями, которые могут измениться. Как убедиться, что в production попадёт именно протестированный образ?

- **A.** Повторно проверить только комментарии в исходном коде.
- **B.** Использовать тег latest, не фиксируя, на какой образ он указывает.
- **C.** Пропустить тесты, поскольку коммит исходного кода не изменился.
- **D.** Продвинуть тот же протестированный образ, идентифицируя его неизменяемым digest.

<details>
<summary>Почему подходит этот ответ</summary>

**D. Продвинуть тот же протестированный образ, идентифицируя его неизменяемым digest.**

Один и тот же коммит может дать разные результаты сборки при изменении инструментов, зависимостей или базовых образов. Продвижение уже протестированного образа исключает такое отличие из-за повторной сборки. Неизменяемый digest идентифицирует сам артефакт, тогда как тег может указывать на другой образ. Конфигурацию среды всё равно нужно отдельно проверять и контролировать.

- **A.** Комментарии исходного кода не идентифицируют собранный артефакт.
- **B.** Изменяемый тег позже может указывать на другой образ.
- **C.** Неизменившийся коммит не доказывает идентичность повторно собранного результата.

## AZ-400 · Сигналы для canary-развёртывания

В canary-релизе загрузка CPU и памяти обычная, но при скачивании документов пользователи получают неверные файлы. На чём должно основываться решение о дальнейшем развёртывании?

- **A.** На сигналах функциональной корректности и заранее заданном критерии остановки или отката.
- **B.** Только на CPU: здоровая инфраструктура доказывает правильность результатов.
- **C.** На переходе к более мощной ВМ до проверки возвращаемых файлов.
- **D.** На удалении старых журналов, чтобы панель мониторинга выглядела аккуратнее.

<details>
<summary>Почему подходит этот ответ</summary>

**A. На сигналах функциональной корректности и заранее заданном критерии остановки или отката.**

Релиз может потреблять мало ресурсов и при этом выдавать неверный результат для пользователя. Для продвижения нужны сигналы, отражающие пользовательскую операцию, а не только загрузку инфраструктуры. Заранее заданное правило остановки или отката помогает действовать на основании этих данных. Проверь и совместимость данных: откат кода сам по себе не отменяет вредные изменения данных, сделанные релизом.

- **B.** CPU и память не доказывают, что пользователи получают нужные документы.
- **C.** Дополнительная вычислительная мощность сама по себе не исправляет неверный вывод приложения.
- **D.** Удаление свидетельств затрудняет расследование и не исправляет результат.

[Источник](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/safe-deployments) · [Что перечитать](12-devops.md)

</details>
