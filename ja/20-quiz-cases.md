## AZ-900 · OS と実行環境の管理

実習用アプリで独自の Linux カーネルドライバーをインストールする必要がある。この要件に最も合う実行環境はどれ？

- **A.** Microsoft 365 上でアプリを実行する。
- **B.** 互換性のある Linux イメージを使った Azure 仮想マシンを利用する。
- **C.** App Service のマネージドランタイムにデプロイする。
- **D.** 標準的な Azure Function の中にドライバーを入れる。

<details>
<summary>考え方：</summary>

**B. 互換性のある Linux イメージを使った Azure 仮想マシンを利用する。**

決め手はゲスト OS を管理できること。互換性のある Azure VM なら、その環境とドライバーを自分たちで管理できる。その分、OS の保守もチームの仕事になる。マネージドなアプリ基盤は便利でも、必要なカーネル操作が許可されなければ、この要件には合わない。

- **A.** Microsoft 365 は利用するための完成したソフトウェアであり、任意のカーネルドライバーを動かす環境ではない。
- **C.** App Service のマネージドランタイムでは、必要なゲストカーネルの管理ができない。
- **D.** 標準的な Function では、必要なカーネルドライバーの管理権限が得られない。

</details>

## AZ-900 · 水平スケーリングと状態

ノート共有 API がロードバランサーの背後でインスタンスを増やす。どのインスタンスも交換される可能性があるが、利用者のセッションは維持したい。現在、セッションは各インスタンスのメモリにしかない。何を変えるべき？

- **A.** 各インスタンスの CPU を増やす。
- **B.** セッションをメモリに置いたまま、スティッキーなルーティングだけを有効にする。
- **C.** セッション状態を適切な共有の外部ストアへ移す。
- **D.** 各インスタンスにパブリック IP アドレスを割り当てる。

<details>
<summary>考え方：</summary>

**C. セッション状態を適切な共有の外部ストアへ移す。**

水平スケーリングでは複数のインスタンスが要求を処理する。大切なセッション状態を、どれか一つのメモリだけに依存させてはいけない。適切な外部ストアなら、交換後のインスタンスも状態を取得できる。スティッキーなルーティングだけでは、選ばれたインスタンスが失われたときのメモリを守れない。外部の状態管理サービスへの接続や障害への対処も必要になる。

- **A.** CPU を増やしても、交換されたインスタンスのメモリは維持できない。
- **B.** 固定先のインスタンスが失われれば、スティッキーなルーティングでもセッションは失われる。
- **D.** パブリック IP はセッション状態の共有や永続化を実現しない。

## AZ-104 · ストレージのデータ権限

ある利用者はストレージアカウントの Contributor ロールを持っている。その利用者の Entra ID で送った Blob 要求はサービスに届くが、データ権限が足りず拒否される。必要なのは、一つのコンテナー内の Blob の読み取りだけ。最小権限に合う対応はどれ？

- **A.** そのコンテナーをスコープとして Storage Blob Data Reader を割り当てる。
- **B.** サブスクリプション全体に Owner を割り当てる。
- **C.** 受信ネットワークポートをすべて開く。
- **D.** ストレージアカウントキーを利用者に渡す。

<details>
<summary>考え方：</summary>

**A. そのコンテナーをスコープとして Storage Blob Data Reader を割り当てる。**

リソースの管理権限と Blob データの権限は別。Storage Blob Data Reader は必要な読み取りを許可し、コンテナーのスコープは対象を要件の範囲に限定する。この問題ではデータ権限の不足が分かっているので、広い管理権限を与えたり、無関係なネットワーク設定を変えたりするのは適切ではない。

- **B.** サブスクリプションの Owner は、一つのコンテナーを読むという要件を大きく超える。
- **C.** ポートを開いても、足りないデータ操作の認可は追加されない。
- **D.** アカウントキーは、今回必要な範囲よりずっと広いアクセスを与える。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access) · [復習する章：](06-identity.md)

</details>

## AZ-104 · RBAC の継承

ある利用者には VM へ直接 Reader が割り当てられており、さらにサブスクリプションのスコープで Reader を持つグループにも所属している。VM への直接の割り当てだけを削除したが、その利用者はまだ VM を読み取れる。なぜ？

- **A.** Azure はすべての利用者に、全 VM の Reader を自動で与えるから。
- **B.** リソースグループのタグが、削除した割り当てを復元するから。
- **C.** ロールを削除するには、必ず VM も削除しなければならないから。
- **D.** グループ経由の割り当てによる、継承されたアクセスが残っているから。

<details>
<summary>考え方：</summary>

**D. グループ経由の割り当てによる、継承されたアクセスが残っているから。**

一つの割り当てを消しても、別の割り当てから得た権限までは消えない。グループはサブスクリプションの Reader を持つので、メンバーはそのアクセスを VM にも継承できる。サービスの不具合と判断したり、権限を追加したりする前に、直接の割り当て、グループ所属、上位スコープを確認しよう。

- **A.** すべての利用者に Reader を与える共通の仕組みはない。
- **B.** タグはリソースを分類するもので、ロールの割り当てを作り直すものではない。
- **C.** ロールの割り当てを削除するために、対象リソースを削除する必要はない。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/role-based-access-control/scope-overview) · [復習する章：](06-identity.md)

</details>

## AZ-305 · 復旧目標と RPO

現在の設計では、正常に復旧できるデータベースの復旧ポイントを 24 時間に一度だけ保持している。災害後に失ってよい直近のデータを、最大 1 時間分にしたい。この差を直接埋める変更はどれ？

- **A.** API サーバーの CPU を増やす。
- **B.** 復旧可能なデータ保護ポイントの間隔が 1 時間を超えないよう設計し、復旧を検証する。
- **C.** 費用アラート用の予算を追加する。
- **D.** リソースグループの名前を production に変える。

<details>
<summary>考え方：</summary>

**B. 復旧可能なデータ保護ポイントの間隔が 1 時間を超えないよう設計し、復旧を検証する。**

RPO は、失われてもよい直近のデータ量を時間で表す目標。1 日に一度の復旧ポイントだけでは、1 時間という目標には足りない。十分な頻度で復旧可能な状態を作る設計にして、実際に復旧できるか検証する必要がある。アプリの CPU や費用のラベルを変えても、使える復旧データの古さは変わらない。

- **A.** API の CPU を増やしても、復旧用データの保護頻度は上がらない。
- **C.** 予算は支出を通知するもので、データ損失を抑えるものではない。
- **D.** リソースグループの名前は、復旧ポイントの頻度を変えない。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/well-architected/reliability/disaster-recovery) · [復習する章：](10-architecture.md)

</details>

## AZ-305 · プライベート接続の DNS

ストレージサービスのパブリックアクセスは無効で、プライベートエンドポイントも存在する。しかしクライアントは、サービスのホスト名をまだパブリック IP に解決している。プライベート側のネットワーク経路は利用できる。まず何を調べる？

- **A.** クライアントにサブスクリプションの Owner を与える。
- **B.** パブリック IP を恒久的にハードコードする。
- **C.** そのクライアントが使うプライベート DNS ゾーン、リンク、転送設定を調べる。
- **D.** アプリの再試行回数を際限なく増やす。

<details>
<summary>考え方：</summary>

**C. そのクライアントが使うプライベート DNS ゾーン、リンク、転送設定を調べる。**

クライアントの名前解決が、意図したプライベート接続とは違う宛先を返している。そのサービスで推奨されるプライベート DNS 構成と、クライアントからそこへ到達する仕組みを、リンクや転送も含めて確認する。接続には引き続きサービスのホスト名を使う。DNS の修正だけでデータ権限は付与されないが、無関係な管理権限や無限の再試行もこの不一致を直せない。

- **A.** Owner を与えても、クライアントの名前解決は変わらない。
- **B.** パブリックアクセスを無効にした後は、パブリックアドレスは意図した接続先ではない。
- **D.** 要求を繰り返しても、毎回同じ誤った結果を返す DNS 設定は直らない。

## AZ-400 · テスト済み成果物の昇格

パイプラインがコンテナーイメージをテストした後、変更され得る依存関係を使ってソースから本番用に再ビルドする。テストを通過したイメージを確実に本番へ届けるには？

- **A.** ソースのコメントだけを再テストする。
- **B.** どのイメージを指すか記録せず、latest タグを使う。
- **C.** ソースのコミットが同じなのでテストを省く。
- **D.** 不変のダイジェストで特定した、テスト済みの同じイメージを本番へ昇格させる。

<details>
<summary>考え方：</summary>

**D. 不変のダイジェストで特定した、テスト済みの同じイメージを本番へ昇格させる。**

ソースのコミットが同じでも、ツール、依存関係、ベースイメージが変われば成果物は変わり得る。テスト済みイメージをそのまま昇格させれば、再ビルドによる差を避けられる。不変のダイジェストは、付け替え可能なタグとは違い、実際の成果物を特定する。ただし、環境設定は別途検証し、管理された方法で扱う必要がある。

- **A.** ソースのコメントは、ビルドされた成果物を特定しない。
- **B.** 変更可能なタグは、後で別のイメージを指すことがある。
- **C.** コミットが同じだけでは、再ビルドした成果物も同じとはいえない。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/container-registry/container-registry-concepts) · [復習する章：](12-devops.md)

## AZ-400 · カナリアリリースの判断材料

カナリアリリースの CPU とメモリは正常だが、文書のダウンロードで別のファイルが返ってくる。デプロイを進めるかどうかは、何を基準に決めるべき？

- **A.** 機能が正しく動くことを示す指標と、事前に定めた停止またはロールバックの基準。
- **B.** インフラが正常なら結果も正しいので、CPU だけ。
- **C.** 返されたファイルを調べる前に、より大きな VM を使う。
- **D.** ダッシュボードをすっきりさせるため、古いログを削除する。

<details>
<summary>考え方：</summary>

**A. 機能が正しく動くことを示す指標と、事前に定めた停止またはロールバックの基準。**

余裕を持って動いているリリースでも、利用者に誤った結果を返すことはある。展開を進めるには、インフラの使用率だけでなく、利用者の操作の正しさを示す指標が必要。停止やロールバックの基準を決めておけば、その証拠を判断につなげられる。データの互換性も確認する。アプリのコードを戻しても、そのリリースが加えた有害なデータ変更まで自動で元に戻るわけではない。

- **B.** CPU とメモリが正常でも、利用者に正しい文書が届くとは限らない。
- **C.** 計算リソースを増やすだけでは、アプリの誤った出力は直らない。
- **D.** 証拠を消すと調査が難しくなり、結果の誤りも直らない。

## DP-900 · トランザクションワークロード

大学の履修登録サービスで、残り一つの実習枠の確保と学生の履修登録を、整合性のある一つの操作として実行する必要がある。この要件に最も合うワークロードの説明はどれ？

- **A.** 学期別に履修登録を集計する分析ワークロード。
- **B.** 実習枠への独立した更新を毎晩照合するバッチワークロード。
- **C.** 関連する変更をまとめてコミットするトランザクションワークロード。
- **D.** 実習枠と履修登録のイベントを、コミットを調整せず別々に発行するストリーミングワークロード。

<details>
<summary>考え方：</summary>

**C. 関連する変更をまとめてコミットするトランザクションワークロード。**

この要件で必要なのは、関連する変更がまとめて成功するか、まとめて失敗する、小さく限定された操作。これがトランザクションの振る舞いに当たる。履修登録と定員の記録が食い違う間に、別の要求が同じ最後の枠を確保してはいけない。過去の集計は、アクセスの仕方が異なる分析の仕事。イベントや後からの照合は全体の構成に役立つことがあるが、独立した更新だけでは、この整合性の要件を満たさない。

- **A.** 学期別の集計は過去の状況を調べる処理であり、この要求で必要な実習枠の確保と履修登録の変更を連動させない。
- **B.** 夜間の照合では、実習枠の数と履修登録が食い違う時間が生じ、即時に整合性を保つ要件に反する。
- **D.** イベントの発行で他のシステムへ通知はできるが、別々にコミットしたイベントだけでは、元の二つの変更を不可分にはできない。

## DP-900 · ETL と ELT の順序

研究チームが前日のダウンロード記録を抽出し、処理サービスで無効な識別子を除去してから、整えた記録をレポート用ウェアハウスに読み込む。この順序を表す説明はどれ？

- **A.** レポートの格納先へ読み込む前に変換するため、ETL。
- **B.** ウェアハウスを最終的な格納先にする処理は、必ずその内部で変換するため、ELT。
- **C.** 元のダウンロード記録がアプリのイベントから来ているため、ストリーミング。
- **D.** 手順を調整すれば変換が不要になるため、オーケストレーションのみ。

<details>
<summary>考え方：</summary>

**A. レポートの格納先へ読み込む前に変換するため、ETL。**

ETL は、抽出、変換、目的の格納先への読み込みという順序を指す。ここではレポート用ウェアハウスへ整えた記録を渡す前に、無効な識別子を処理している。ELT なら、先にデータを読み込み、その格納先の処理能力を使って変換する。前日分という範囲の決まった記録はバッチ入力。オーケストレーターでこれらの処理を調整できるが、調整と変換は同じパイプライン内の別の役割。

- **B.** ELT かどうかは、格納先に読み込んでからそこで変換する順序で決まる。行き先がウェアハウスというだけでは、この順序は決まらない。
- **C.** 元がイベントでも、後続処理がストリーミングになるとは限らない。このジョブは次々に届く記録ではなく、一日分の範囲が決まった記録を処理する。
- **D.** オーケストレーションは依存関係や復旧を調整する。一方、無効な識別子の除去はデータを変えるため、変換という別の役割のまま。

[Microsoft Learn：](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/etl) · [復習する章：](../certifications/ja/DP-900.md)

## SC-900 · MFA の要素の種類

ある学生がサインイン方式を比較している。認証デバイスは登録済みで、そのデバイスによる承認が必須だとする。知識要素と所持要素を組み合わせている例はどれ？

- **A.** パスワードの後に、記憶している秘密の質問の答えを入力する。
- **B.** 大学のパスワードの後に、記憶している別のサービスのパスワードを入力する。
- **C.** パスワードの後に、デバイスに結び付いた認証器を使わず、同じ Web サイトへ記憶している PIN を入力する。
- **D.** パスワードの後に、学生の登録済み認証デバイスで承認する。

<details>
<summary>考え方：</summary>

**D. パスワードの後に、学生の登録済み認証デバイスで承認する。**

パスワードは学生が知っていることを示し、登録済み認証デバイスを使えることは所持要素を示す。両方を必須にすれば、異なる種類の要素を組み合わせられる。覚えている秘密を二つ使っても、文字列が違うだけで、どちらも知識要素。この分類は、すべての MFA 方式が同じようにフィッシングに強いという意味ではない。大学のアクセスポリシーでは、方式の選定、登録、復旧、実際の強制適用も検討する必要がある。

- **A.** パスワードも記憶した答えも知識要素。知識をもう一度確認しても、必要な所持要素は加わらない。
- **B.** 異なるパスワードを使えば資格情報を分けられるが、どちらも覚えている秘密であり、同じ種類の要素に属する。
- **C.** この例ではデバイスに結び付いた認証器を使わない。Web サイトへ別の秘密として入力する PIN は、デバイスの所持の証明ではなく知識要素になる。

## SC-900 · Purview のデータ管理

大学が、対応する文書共有操作に含まれる学生の識別情報を検出し、設定したルールに一致したら外部共有を警告または制限したい。この要件に最も直接対応する Purview の機能はどれ？

- **A.** 共有が行われた記録だけを残す監査。
- **B.** 適切な対象範囲を設定し、テストしたポリシーによるデータ損失防止（DLP）。
- **C.** 文書を 7 年間保持するよう設定した保持機能。
- **D.** 保護も DLP も設定せず、Confidential という名前だけを付けた秘密度ラベル。

<details>

## SC-100 · 復旧目標の検証

復旧演習で RTO を 2 時間、RPO を 15 分に設定した。停止は 11:00 UTC に始まった。認可された文書の読み取りは 12:30 に再開したが、復元できたデータは 10:40 まで。これらが合意済みの測定範囲だとすると、正しい評価はどれ？

- **A.** 2 時間以内にサービスを再開したので、両方の目標を達成した。
- **B.** RPO は達成したが、RTO は未達。
- **C.** データを少しでも失うと RTO に違反するため、両方とも未達。
- **D.** RTO は達成したが、復旧ポイントが停止の 20 分前なので、RPO は未達。

<details>
<summary>考え方：</summary>

**D. RTO は達成したが、復旧ポイントが停止の 20 分前なので、RPO は未達。**

RTO は許容できる中断時間を測る。認可された読み取りは 90 分後に再開し、2 時間の目標内に収まっている。RPO は許容できる直近のデータ損失を測る。11:00 の停止に対して 10:40 までの復元では 20 分の差があり、15 分の目標を超える。二つは独立して確認するもので、一方を満たしても他方を満たしたことにはならない。演習では両方の測定値と、定義された業務操作を再開できた依存関係を記録するべき。

- **A.** 目標時間内のサービス復旧が満たすのは RTO。別に測る復旧ポイントの 20 分の差は、指定された RPO を依然として超えている。
- **B.** 中断は 90 分で 2 時間以内だが、データの差は 20 分で 15 分を超えている。この選択肢では結果が逆になっている。
- **C.** RTO が扱うのは中断の長さであり、データ損失の有無ではない。RPO は未達でも、測定された 90 分の復旧は RTO の目標を満たす。

## AZ-120 · SAP のフェンシングと単一の書き込み主体

SAP HANA クラスターの机上演習で、プライマリとの通信が失われ、セカンダリからフェンシングできなくなった。チームは、プライマリが書き込みの受け付けを停止したか確認できない。引き継ぎの前にデータ整合性を最もよく守る対応はどれ？

- **A.** フェンシングを無効にしてセカンダリを昇格し、クラスターのダッシュボードにすぐリソースの稼働を表示する。
- **B.** 最後に成功したレプリケーションの状態が旧プライマリの書き込み停止を証明すると考え、セカンダリを昇格する。
- **C.** サポートされるインシデント手順に従ってフェンシングを復旧または検証し、旧書き込みノードの隔離を確認してから、引き継ぎ先の書き込みを許可する。
- **D.** 書き込み可能か不明なプライマリの状態を変えずに、仮想サービスアドレスをセカンダリへ移す。

<details>
<summary>考え方：</summary>

**C. サポートされるインシデント手順に従ってフェンシングを復旧または検証し、旧書き込みノードの隔離を確認してから、引き継ぎ先の書き込みを許可する。**

通信が途絶えても、プライマリの停止が証明されたわけではない。フェンシングは、安全に継続できないノードを隔離し、書き込み主体を一つに保つ要件を守って、スプリットブレインのリスクを減らす。チームはサポートされるフェンシングとクォーラムの構成を調査し、状態の根拠を保全し、旧書き込みノードが隔離されたと確認してから引き継ぎ先での書き込みを許可する必要がある。レプリケーションの正常性やアドレスの移動ではこの隔離を実現できず、フェンシングの無効化は重要な安全策を取り除いてしまう。

- **A.** フェンシングを無効にすると、状態不明の書き込みノードを隔離する仕組みが失われる。見かけの可用性と引き換えに、競合するプライマリが生じかねない。
- **B.** 過去のレプリケーション結果が示すのは、その時点でのデータ転送。到達不能なプライマリが今も書き込みを受け付けていないとは証明できない。
- **D.** 仮想アドレスの移動はクライアントの経路を変えるが、それだけでは旧プライマリが別のセッションや経路で書き込むことを防げない。

## AZ-120 · SAP 切り替え後の書き込み

大学の SAP 移行で、移行先を購買処理に開放し、ユーザーが新しい発注を作成した。変更していない移行元は隔離したまま。その後の検証で問題が起き、ロールバックを検討することになった。新しい業務トランザクションを最もよく守る計画はどれ？

- **A.** 書き込みを停止し、正とするデータ状態を決め、移行先のトランザクションを保全して、サポートされる照合または逆移行の計画に合意してから、書き込みを再開する。
- **B.** DNS を変更して元の移行元へ戻し、移行先の新しい発注もそこに存在すると考える。
- **C.** 切り替え後のトランザクションを特定せず、古い移行元で移行先を上書きして購買処理を再開する。
- **D.** 業務ユーザーが後で残す発注を決める間、移行元と移行先の両方で書き込みを再開する。

<details>
<summary>考え方：</summary>

**A. 書き込みを停止し、正とするデータ状態を決め、移行先のトランザクションを保全して、サポートされる照合または逆移行の計画に合意してから、書き込みを再開する。**

移行先で新しい書き込みを受け付けた後のロールバックは、インフラの変更に加えてデータの扱いを決める作業になる。変更していない移行元に戻ると新しい発注を取り残しかねず、両方で書き込みを再開するとトランザクションが分岐する。手順書では書き込みを停止し、根拠と新しい業務データを保全し、正とする状態を選び、責任を持つ業務所有者とともにサポートされる照合や逆方向の移行を使うべき。購買処理を再開する前に検証し、書き込み主体を一つに保つ必要がある。

- **B.** DNS はクライアントの接続先を変えるが、切り替え後の発注を変更していない移行元へコピーするものではない。戻すだけでは、新しいトランザクションを取り残す可能性がある。
- **C.** 古い移行元で上書きすると、移行先の正当な発注を失う可能性がある。まず切り替え後の業務上の変更を特定し、保全する計画が必要。
- **D.** 両方の環境で書き込みを受け付けると、トランザクションの履歴が分岐する。照合が難しくなり、正とする書き込み主体を制御する要件にも反する。

## AZ-802 · AD サービスの検出

教室のネットワーク変更後、Windows のドメインクライアントは公開 Web サイトを名前解決できるが、ドメインコントローラーを検出できない。公開 DNS リゾルバーを使っており、想定した AD DNS サーバーには到達でき、SRV レコードも正常。時刻も正しい。示された証拠に最も合う対応はどれ？

- **A.** リゾルバーの経路を調べる前に、全学生のパスワードをリセットする。
- **B.** 承認済みの AD 対応 DNS 経路を戻し、SRV による検出、コントローラーへの到達、影響を受けたログオンを検証する。
- **C.** 公開リゾルバーだけを使う経路を残したまま、認証の時刻関連の確認を無効にする。
- **D.** コントローラーの検出を変えずに、学生を Domain Admins に追加する。

<details>
<summary>考え方：</summary>

**B. 承認済みの AD 対応 DNS 経路を戻し、SRV による検出、コントローラーへの到達、影響を受けたログオンを検証する。**

公開 Web サイトの名前解決だけでは、非公開の AD サービスを検出できる証明にはならない。ここで判明した不一致はリゾルバーの経路であり、AD レコードが正常で時刻が正しいという条件は、このケースの調査範囲を絞る。承認された変更で意図した DNS 構成を戻し、サービスの検出、到達、ログオンを別々に検証する。まだ認証に失敗するなら、実際のすべてのログオン障害が同じ原因だと考えず、その正確な証拠を調べる。

- **A.** パスワードを変えても、欠けた AD サービスの検出経路は得られない。一斉リセットは、観察された DNS の不一致に対応する前に無関係な変更を加えてしまう。
- **C.** このシナリオでは時刻が正しいと明示されている。認証の確認を弱めても、設定済みの公開リゾルバーで非公開のドメインサービスを検出できるようにはならない。
- **D.** ディレクトリ権限を広げてもコントローラーの検出は直らず、判明したクライアントの DNS 設定の問題に対応しないまま、過剰な権限を与えてしまう。

## AZ-802 · Hyper-V の復旧の境界

Hyper-V 実習では、標準へのフォールバックを許さないゲスト対応の運用チェックポイントと、VM ストレージを失っても残る保護済み復旧コピーが必要。Production 設定が、同じストレージ上の標準チェックポイントへフォールバックした。指定された二つの境界を満たす計画はどれ？

- **A.** Production を指定したことがゲストの整合性処理の成功を証明すると考え、標準チェックポイントを受け入れる。
- **B.** Hyper-V レプリカだけを有効にし、必要な独立した過去の復旧ポイントがすべて得られると考える。
- **C.** AVHDX ファイルを手動で削除し、同じストレージのチェックポイントを保護済み復旧コピーとして残す。
- **D.** ProductionOnly を検討してゲストの整合性の前提条件を修復し、それとは別に、復元の手順を検証した保護済みバックアップを維持する。

<details>
<summary>考え方：</summary>

**D. ProductionOnly を検討してゲストの整合性の前提条件を修復し、それとは別に、復元の手順を検証した保護済みバックアップを維持する。**

Production モードはフォールバックを許可できるため、実際の標準チェックポイントは、要求された整合性の動作と食い違う。ゲストの前提条件を調べる間、ProductionOnly ならそのフォールバックを拒否できる。有効な運用チェックポイントでも、独立して保持されたバックアップとは違い、VM と一緒にストレージチェーンを失い得る。別の保護済みコピーと、サポートされる復元の検証が二つ目の要件に対応する。チェックポイントのモードを変えるだけでは、その境界は得られない。

- **A.** 指定した設定より、結果としてのチェックポイントの種類のほうが強い証拠。標準へのフォールバックでは、運用の整合性処理が正常完了したとは示せない。
- **B.** レプリカは複製した VM の復旧に対応するが、望ましくない変更も伝播し得る。それだけでは、必要な独立した過去のバックアップとテスト済みの復元は確立しない。
- **C.** AVHDX の手動削除は VM のディスクチェーンを壊す可能性があり、同じ故障したストレージ上のコピーでは、指定された独立した復旧の境界を満たせない。
