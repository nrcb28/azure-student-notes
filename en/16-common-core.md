# Common study core

[←](README.md) · [Advanced labs](17-advanced-labs.md)

The same concepts, cases, and evidence in eight languages. Study these twelve units, develop the twenty certification units, and verify lab results. Earlier notes remain supplementary; their historical length varies.

<a id="core-cloud"></a>

## 1. Responsibility and scaling

For an API, allocate operating system, dependencies, data, and access between provider and team. Adding instances does not fix local state. Submit a responsibility matrix and a two-instance request test.

<a id="core-resources"></a>

## 2. Scopes and lifecycle

Separate tenant, management, subscription, and resource-group boundaries. Decide what is deleted together and which network is shared. Submit an ownership diagram and inspect dependencies before moving or deleting.

<a id="core-compute"></a>

## 3. Execution and health

Compare VMs, PaaS, functions, and containers by control, duration, and operations. A started app may listen on the wrong port. Submit choice, alternative, and port, startup, and dependency checks.

<a id="core-data"></a>

## 4. Data and restoration

Separate objects, files, and transactions; JSON does not mandate an engine. Replicas, versions, and backups cover different risks. Map documents and metadata and check consistency after recovery.

<a id="core-network"></a>

## 5. Routing and resolution

Follow DNS, IP, route, filters, listener, and authentication separately. Peering is not automatically transitive. Submit a hop table and explain why university clients can still fail to reach a private endpoint.

<a id="core-identity"></a>

## 6. Identity and permissions

Separate authentication, authorisation, directory roles, and Azure roles. Inspect inheritance and groups before granting more. Specify student, API, and worker actions with minimal scope and access verification.

<a id="core-governance"></a>

## 7. Rules and exemptions

Separate audit, deny, and remediation. Describe remediation identity and permissions, existing resources, and reviewed exemptions. Submit a pilot policy, expected impact, and criteria for moving from audit to deny.

<a id="core-monitor"></a>

## 8. Signals and evidence

Choose functional success, latency, and work age. Check collection and destination before querying. Submit an alert with window, volume, threshold, owner, and action; explain how averages can hide problems.

<a id="core-cost"></a>

## 9. Cost units and assumptions

Compare low, expected, and high usage with hours, operations, transfer, and retention. Include idle capacity and residual costs. Submit assumptions and sensitivity rather than a fixed rate or a budget claimed as an automatic cap.

<a id="core-recovery"></a>

## 10. Complete recovery

Define RTO/RPO per data set and service. Include identity, DNS, permissions, and configuration, not only backups. Submit restore order, isolated test, functional validation, and return plan; distinguish replicas, backups, and integration recovery.

<a id="core-messaging"></a>

## 11. Messages and duplicates

Choose queues, events, or streaming by requirement. Explain lost acknowledgements, repetition, ordering, and failed messages. Submit stable identifiers, idempotent operations, and replay strategy without assuming exactly-once delivery.

<a id="core-delivery"></a>

## 12. Delivery and trust

Promote a tested, identified artifact. Separate trusted code, permissions, and PR data. Submit meaningful tests, authorisation, promotion signals, and rollback; demonstrate why code rollback does not always reverse data changes.
