## Approach and reference

This guide aims to help you explain a choice in your own words. Recognising a service logo is only a start; you still need to understand the problem it solves. AZ-900 focuses on concepts and distinctions rather than advanced configuration.

## 1. Consumption and responsibility

Buying servers usually means upfront investment, capacity planning, and maintenance. Cloud consumption lets us request capacity without buying that equipment, but adds service dependencies, configuration work, and recurring costs.

**CapEx** refers to capital expenditure and **OpEx** to operating expenditure. Moving to Azure does not automatically transform every cost: agreements, licences, and staffing still matter.

Suppose our notes app receives five times more traffic during exams. Horizontal scaling can add instances. For this to help, the database must cope and sessions should not depend on one instance's memory.

**Predictability** has two sides. For performance, we measure and size resources. For costs, we estimate usage and review bills. A variable bill is not necessarily unpredictable, but it needs observation.

With IaaS, we maintain the guest operating system. PaaS delegates more platform work. With SaaS, we use an application but still manage access, data handling, and available settings. Responsibility changes distribution; it does not disappear.

### Worked scenario

The lecturer requires specific Linux kernel modules. A VM fits better than a web platform that does not expose that level of control. If the task is a standard API, App Service can save work. Operating system control is the deciding requirement, not which option sounds newer.

## 2. Understanding the Azure map

A subscription provides administration and billing boundaries. A resource group organises resources with related lifecycles. Management groups help apply rules across subscriptions.

A region determines the location of a regional resource. A zone provides physical separation within a region. Distributing components across zones can improve fault tolerance when the service supports it.

An availability set distributes VMs across fault and update domains; it is not equivalent to multiple regions. Azure Virtual Desktop provides virtual desktop and application capabilities rather than simply renaming a VM.

Sovereign clouds address particular needs and can have different endpoints, services, and availability. Do not assume an Azure global tutorial works unchanged everywhere.

**Useful question:** which failure does this design address? Another instance can help with a process failure. Multiple zones address another failure scope. Multiple regions add regional recovery options and complexity.

## 3. Choosing compute

| Scenario clue | Option to investigate | Reason |
|---|---|---|
| Operating system control | VM | Allows administration of that environment |
| Compatible web application or API | App Service | Reduces server administration |
| Event-triggered code | Functions | Fits trigger-based execution |
| Application packaged as an image | Container platform | Runs a consistent package |
| Managed remote desktops | Azure Virtual Desktop | Addresses desktop and application delivery |

Containers package dependencies and support consistency, but do not guarantee security or scaling. Serverless abstracts servers while retaining plans, quotas, and billing.

Do not confuse **scale up**, changing one instance's capacity, with **scale out**, adding instances. Autoscaling is also different from high availability: one large instance remains one instance.

## 4. Networking: follow the connection

A VNet defines a virtual network. Subnets divide address space. An NSG filters traffic. DNS resolves names: having a route does not help if a name points to the wrong destination.

A VPN uses an encrypted tunnel. ExpressRoute provides private connectivity through a provider; encryption is a separate requirement. Peering connects VNets subject to constraints.

A public endpoint uses public addressing under the service's controls. That does not imply anonymous access. A private endpoint provides private-address connectivity to a supported service.

**Example:** a storage account can retain a public endpoint and require authentication. A public URL does not prove that anyone can read its contents.

## 5. Storage, transfer, and migration

Blob Storage suits objects such as PDFs. Azure Files provides shares. Managed Disks support VMs. Choose according to access patterns rather than file size alone.

Access tiers change the balance between storing and retrieving. A frequently opened document rarely fits Archive. Geographical redundancy is not a way to recover every earlier version: replication and backup address different risks.

For moving data, distinguish:

- **AzCopy:** scriptable command-line transfers.
- **Storage Explorer:** graphical interaction with storage resources.
- **Azure File Sync:** file synchronisation and caching in supported Windows Server scenarios.
- **Azure Migrate:** discovery, assessment, and migration depending on workload.
- **Data Box:** device-based transfer in supported scenarios where networking is unsuitable.

Migration is more than copying. Validate permissions, integrity, dependencies, and the cutover to the new system.

## 6. Identity and defence in depth

Entra ID manages identities. Entra Domain Services provides managed domain services for supported scenarios. They are not interchangeable names.

SSO reduces repeated sign-ins. MFA adds factors. Passwordless avoids passwords with supported methods. None removes the need for authorisation.

**Zero Trust** involves explicit verification, least privilege, and assuming breaches can occur. Defence in depth combines identity, network, application, data, and operational layers.

In our app, a signed-in student should not modify another student's notes merely by changing an identifier in a URL. Application authorisation must check that request.

Defender for Cloud helps assess posture and protect workloads, depending on plans and settings. It does not replace the people who assess and address findings.

## 7. Governance, tools, and observation

| Requirement | Tool or concept |
|---|---|
| Restrict deployment regions | Azure Policy |
| Grant a team read access | Azure RBAC |
| Reduce accidental deletion | Management locks |
| Classify resources by project | Tags |
| Data governance and protection | Microsoft Purview capabilities |
| Manage supported resources outside Azure | Azure Arc |
| Improvement recommendations | Azure Advisor |
| Incidents affecting used services | Service Health |

Portal, CLI, and PowerShell offer different management interfaces. Cloud Shell provides a managed shell experience; local installation is not always needed, but features and persistence depend on configuration.

ARM is the management layer. ARM templates and Bicep describe infrastructure. Code improves review and repeatability; it does not guarantee sound design.

Monitor combines metrics, logs, and alerts. Application Insights adds application observation. Log Analytics queries available logs. Not every log arrives automatically: collection needs configuring.

## 8. Costs and numerical assumptions

An app has 100 GB of documents, few reads, and traffic spikes. Its bill is not simply 100 GB times a rate: operations, retrieval, transfer, compute, and monitoring can contribute.

A budget alerts rather than universally stopping spending. A calculator estimates rather than guaranteeing a bill. Tags help analyse costs but do not independently organise permissions.

To compare options, record assumptions: running hours, traffic, region, redundancy, and retention. Recalculate when they change. A long-term consumption commitment rarely makes sense for an afternoon lab.

## 9. Practice without deploying

Design the notes app on paper:

1. Choose API hosting and justify the control level.
2. Separate documents from metadata.
3. Identify who must authenticate.
4. Propose a governance rule and an access role.
5. Explain which failure the design tolerates.
6. List five cost components.
7. Choose a signal to verify application health.

**Expected output:** a decision table and a drawing where every component has a reason. A list of product names is missing the important part.

Then try the [general lab](../../en/13-laboratorios.md), reviewing costs and cleanup.

## 10. Original questions with explanations

**A company retains its own servers and integrates Azure services. Which model is this?** Hybrid. Integration between environments is the deciding clue, not the vendor.

**Does MFA grant database read access?** No. It strengthens authentication; authorisation is configured separately.

**What prevents deployments outside approved regions?** A policy with the appropriate effect and scope. A tag records information but does not enforce a restriction on its own.

**What would you investigate for low CPU and high web latency?** Dependencies, networking, blocking, and queries. CPU is only one signal.

**Do two regions eliminate backups?** No. Logical mistakes can affect replicated data.

**What remains after a successful deployment operation?** Validating application behaviour and dependencies.

## 11. How I would review

First explain comparisons without notes. Then change one scenario requirement: operating system control, private access, tolerable data loss, or budget. Finally, review the official objectives and mark anything you cannot explain.

I would not use memorised question scores as my only readiness measure. Explaining why an alternative fails a requirement matters more than recognising an answer.

**Exit criterion:** explain ten different decisions, correct your mistakes, and complete a lab while understanding what you created.
