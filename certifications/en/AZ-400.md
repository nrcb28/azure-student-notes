## 1. Work flow and communication

Every app change should be traceable from a need to a deployed version. Issues, pull requests, pipeline runs, and releases need a comprehensible relationship.

A useful board shows pending, active, blocked, and completed work. Limiting work in progress can reduce unfinished tasks and expose bottlenecks.

Distinguish:

- **Lead time:** time from a defined starting point to delivery.
- **Cycle time:** time from active work to completion.
- **Deployment frequency:** how often releases happen.
- **Change failure rate:** the proportion causing incidents or intervention.
- **Recovery time:** time taken to restore service.

Define start and end precisely before comparing metrics. Measuring people by commits or lines of code encourages unhelpful behaviour.

Notifications should reach someone who can act. A channel receiving every repository event will eventually be ignored. Release notes explain changes and risks; a list of hashes may not help users.

Webhooks integrate systems but need suitable validation, retries, and duplicate handling. Do not assume a notification arrives exactly once.

## 2. Git and branching strategy

**Trunk-based development** favours frequent small integrations. **Feature branches** isolate work temporarily. **Release branches** can support several maintained versions. Choose according to delivery needs rather than a popular diagram.

For a small app, I would use short branches, PRs, and protected main. Feature flags can divide larger changes without weeks of divergence.

### Operations to understand

- Merge combines histories.
- Rebase reapplies commits and changes identifiers.
- Revert creates a change undoing another.
- Reset moves references and may alter the index and files depending on mode.
- Cherry-pick applies a selected change elsewhere.
- Reflog can help locate previous local references while retained.

On shared branches, revert often preserves history better than rewriting published commits. A local technique should not become a universal rule.

Git LFS stores large files using pointers and separate storage. Adding it now does not remove historical binaries automatically.

If a credential is published, revoke or rotate it first. Removing it from the latest commit does not remove history or copies. History cleanup may need coordination and tools, but never replaces revocation.

## 3. Build once and promote the artifact

A run should produce an identifiable package or image. Promote that artifact from testing to production with environment configuration rather than recompiling different code.

An image tag can move. For reproducible deployments, record a digest or immutable identifier and its relationship to the commit.

### Versions and packages

SemVer expresses major, minor, and patch according to the project's contract. CalVer uses dates. Neither helps if different outputs share the same version identifier.

Feeds such as Azure Artifacts and GitHub Packages distribute dependencies under supported formats and permissions. Consider internal packages, external upstreams, retention, and promotion.

Lockfiles reduce unexpected dependency changes. They do not independently prove safety or full reproducibility.

**Case:** the pipeline worked yesterday and fails today without code changes. Investigate base images, unpinned dependencies, agent tools, and external services.

## 4. Tests and quality gates

Unit tests check small units. Integration tests check real component collaboration. End-to-end tests cover complete flows. Load tests examine behaviour under demand.

Do not put all confidence in slow end-to-end tests or isolated unit tests alone. Choose a combination according to the failures worth detecting.

Coverage measures executed code, not automatically assertion quality. A 100% score with weak assertions provides little confidence.

A useful gate has criteria, ownership, and an exception process. Controls that can be bypassed without a record are weak. Constant noisy blocks encourage workarounds.

Flaky tests need investigation. Repeating until green hides issues and distorts metrics. Temporary quarantine can have an owner and review date; permanent neglect is different.

## 5. Agents, runners, and execution

Hosted runners reduce maintenance. Self-hosted runners can reach specialised networks and tools but require patching, isolation, capacity planning, and cleanup.

Do not run untrusted fork code on a persistent runner with production access. A PR can alter scripts as well as application code.

In YAML, distinguish stages, jobs, and steps. Dependencies establish order; conditions influence execution. Parallel independent tasks can reduce duration but increase consumption and shared-resource conflicts.

Reusable templates reduce repetition. Version them and control who can change them because one template change may affect many repositories.

Caches accelerate restoration; artifacts carry outputs. They are not interchangeable. Incomplete cache keys can reuse incompatible data.

## 6. Deployment strategies

| Strategy | Idea | Risk to watch |
|---|---|---|
| Rolling | Replace instances progressively | Mixed-version compatibility |
| Blue-green | Prepare another environment and switch traffic | Cost and shared data |
| Canary | Expose a traffic subset | Weak signals or biased samples |
| Rings | Expand through successive groups | Differences between groups |
| Feature flags | Enable behaviour without redeployment | Flag debt and combinations |
| A/B | Compare variants for an experiment | Confusing experimentation with safe delivery |

A canary is ineffective if we watch only CPU while the feature returns incorrect results. Define signals, thresholds, duration, ownership, and rollback.

Slots do not create an isolated copy of every dependency. Review settings, connections, and swap behaviour.

### Database changes

Use expand-and-contract where suitable: add a compatible structure, deploy code that can coexist, migrate data, and remove the old structure later.

If the old code cannot understand the new schema, rollback may not restore service. Test version sequences and avoid premature destructive migrations.

## 7. IaC and configuration

Infrastructure needs a review flow: change, validation, plan, approval where appropriate, application, and verification.

Terraform retains state. Protect it, coordinate access, and use locking where the backend supports it. State can contain sensitive information.

Bicep describes Azure resources through ARM. What-if helps inspect proposed changes but does not guarantee availability, permissions, or absence of every side effect.

Application configuration differs from infrastructure and secrets. Separate environment values without duplicating the entire pipeline.

Resource approvals and checks in Azure Pipelines are not simply YAML conditions editable by the pipeline author: resource administrators manage them through the relevant capabilities. [Official reference](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals?view=azure-devops).

## 8. Delivery chain security

Consider source, dependencies, identity, runner, artifact, and destination:

- Review changes and protect branches.
- Analyse code with appropriate tools.
- Check dependency vulnerabilities.
- Detect secrets.
- Scan images and bases.
- Record provenance and composition where appropriate.
- Limit automation permissions.
- Control approval and deployment authority.

An SBOM lists components; it does not certify safety. Scanner findings still need context and treatment.

OIDC exchanges short-lived tokens through federated trust. Restrict that trust to the appropriate repository, branch, or environment, and assign minimal Azure permissions. [GitHub model](https://docs.github.com/en/actions/concepts/security/openid-connect).

Client, tenant, and subscription identifiers are not credentials. Storing them as variables does not grant access without valid identity and trust.

Do not expose production credentials to every PR event. Review author-controlled values, scripts, and events combining privilege with untrusted content.

## 9. Instrumentation and feedback

Deployment begins observation. Relate versions to errors, latency, and user behaviour.

OpenTelemetry provides instrumentation and signal transmission models and tools. Select runtime-compatible integrations rather than copying old SDK examples without checking support.

For our app, measure:

- Successful download proportion.
- Upload and read latency.
- Time to complete analysis.
- Age of pending messages.
- Errors by deployed version.
- Cost and capacity during peaks.

Distributed tracing requires context propagation. Separate logs in each service are insufficient by themselves.

Useful postmortems explain impact, timeline, contributing factors, and owned actions. Blame discourages information sharing. Be more careful is not a verifiable action.

## 10. Lab without production access

Use a test branch in a learning project:

1. Create an issue describing a small improvement.
2. Implement it with a test that can fail meaningfully.
3. Open a PR and run local checks.
4. Define an artifact version and commit relationship.
5. Design a test publication stage on paper.
6. Identify its identity and scope.
7. Define promotion and rollback conditions.
8. Explain post-release version verification.

This repository includes a [locally executable documentation check](../../tools/check_docs.py). It does not deploy Azure and demonstrates deterministic validation before publication.

## 11. Reasoned questions

**Does rebuilding for production preserve exactly what was tested?** Not necessarily. Tools or dependencies may change. Promoting an artifact reduces that difference.

**Does OIDC remove the need for Azure permissions?** No. It avoids a long-lived credential, but authorisation remains necessary.

**Does high coverage prove quality?** Not alone. Examine what assertions verify.

**Are A/B and canary equivalent?** No. Both may split traffic, but they have different objectives.

**Can a YAML edit remove every approval?** No, when checks are controlled on resources through the appropriate system.

**Does deleting a secret from a file make it safe?** No. Revocation and exposure investigation come first.

**Readiness:** follow a change from need to production, show what was tested, and explain how to detect and recover from failure.
