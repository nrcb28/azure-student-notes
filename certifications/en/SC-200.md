# SC-200 · Microsoft Security Operations Analyst

[Certifications](README.md) · [Ten cases](SC-200-cases.md) · [Workbook](SC-200-workbook.md)

SC-200 asks us to turn security signals into defensible decisions. For the university notes app, I would want to explain which account, device, message, or cloud resource is involved, what the evidence supports, and who may authorise a response.

## 1. Separate the products' jobs

Defender XDR coordinates detection, investigation, and response across supported Microsoft security products. A suspicious Microsoft 365 message, endpoint event, and identity signal may become parts of one incident. Coverage depends on licensing, provisioning, and onboarding; a portal does not imply every campus device is monitored. [Defender XDR overview](https://learn.microsoft.com/en-us/defender-xdr/microsoft-365-defender).

Sentinel adds SIEM analysis across connected Microsoft and other sources, plus response orchestration. The shared Defender portal does not make these capabilities interchangeable. Sketch the campus estate first: Microsoft 365 mail, Azure workloads, on-premises directory and servers, and third-party network appliances. Assign each needed signal a source and an investigation owner.

## 2. Establish data coverage before writing detections

For each source, record connector prerequisites, authentication, collection scope, destination table, event time, expected delay, and retention. Windows Security Events via AMA uses collection rules; Syslog and CEF have their own collection paths. A connected status is weaker evidence than the required event actually arriving with usable fields. [Sentinel connectors](https://learn.microsoft.com/en-us/azure/sentinel/connect-data-sources).

Inspect table schemas instead of guessing column names: Defender hunting commonly uses `Timestamp`, while Sentinel tables often use `TimeGenerated`. Record types and stable identifiers. Plan least-privilege RBAC for readers, incident responders, detection authors, and automation identities. Logs can contain personal data, tokens, and document paths: minimise collection, restrict exports, and agree retention and storage location with the data owner.

## 3. Distinguish alerts, incidents, and entities

An alert reports a detection; an incident groups related evidence for investigation. An entity is something involved, such as an account, device, IP address, or file. Several alerts about one student account do not automatically prove several independent compromises, and a shared campus IP does not establish a shared attacker.

Triage combines severity with asset importance, confidence, exposure, and current activity. Assign an owner, preserve original identifiers, and write the initial question. For the notes app, “did this account access unpublished solutions?” is more useful than “investigate everything”. Keep classification, supporting observations, missing evidence, and proposed next steps separate in the case record.

## 4. Build a timeline and bound the response

Order email, sign-in, endpoint, application, and cloud activity in UTC. Keep event time distinct from ingestion time; delays can explain apparent reversals. Pivot using verified account and device identifiers, then expand the time window and related resources deliberately. State both the confirmed scope and the unobserved areas.

Containment may interrupt lectures or research. In our tabletop, propose an account restriction or device isolation only with the incident authority, affected service owner, impact estimate, and recovery conditions documented. An alert is not permission to act. Track proposed, approved, attempted, and confirmed actions separately. Closing the incident requires a supported explanation and follow-up work, not merely an empty queue.

## 5. Reason about KQL on a fixed dataset

This synthetic example is for offline reading, not a tenant query or an observed Azure result. Times are UTC. [KQL hunting concepts](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-query-language).

```kusto
let Events = datatable(Timestamp:datetime, EventId:string, Account:string, Result:string)
[
 datetime(2026-10-30T09:00:00Z), "e1", "student-a", "Denied",
 datetime(2026-10-30T09:00:00Z), "e1", "student-a", "Denied",
 datetime(2026-10-30T09:02:00Z), "e2", "student-a", "Denied",
 datetime(2026-10-30T09:03:00Z), "e3", "student-b", "Allowed"
];
Events
| where Timestamp >= datetime(2026-10-30T09:00:00Z)
    and Timestamp < datetime(2026-10-30T09:03:00Z)
| where Result == "Denied"
| distinct EventId, Account
| summarize DeniedEvents=count() by Account
```

Expected result: `student-a`, `2`. The half-open window excludes the boundary event. `where` filters, `project` selects columns, and `summarize` changes the aggregation level. `distinct` removes identical projected pairs; it does not establish that arbitrary similar events are duplicates. Here `EventId` is explicitly assumed stable. Choose `join` kind and keys explicitly: many-to-many matches can multiply rows, and default `innerunique` deduplicates the left side by join key. Review schemas, nulls, case sensitivity, and cardinality before interpreting counts.

## 6. Hunt with a falsifiable hypothesis

Try: “an account receiving a suspicious message subsequently accessed private course material from an unfamiliar device”. Define the relevant population, UTC interval, source coverage, expected behaviour, and competing explanation, such as an authorised device replacement.

Hunting can find activity that has not triggered an alert. An empty result means the query found no matching available rows under its conditions; it cannot prove no compromise occurred. Missing onboarding, retention, permissions, parser errors, and narrow filters can all limit visibility. Save the hypothesis, query version, relevant rows or bookmarks, limitations, and next question. Threat intelligence suggests leads; matching an indicator still needs context and freshness checks.

## 7. Tune detections with evidence

A scheduled Sentinel analytics rule and an XDR custom detection need the correct source data, supported query shape, schedule, lookback, identifiers, and entity mapping. Overlapping windows can repeat matches; grouping and suppression choices affect what analysts see.

In the notes app, a legitimate bulk course import could resemble unusual file access. Review labelled synthetic benign and concerning examples. A false positive alerts on benign activity; a false negative misses activity we intended to detect. Broadly excluding every lecturer might reduce noise while hiding the concerning case. Record the rule version, proposed exception scope, expected outcomes, and remaining gaps before any authorised production change. An ATT&CK mapping describes intended coverage, not proof that detection works.

## 8. Normalise carefully across sources

ASIM supplies common schemas and parsers so compatible Sentinel content can work across diverse sources. Query-time parsers provide a normalised view; ingest-time transformations can write supported normalised tables. [ASIM overview](https://learn.microsoft.com/en-us/azure/sentinel/normalization).

For campus firewall and cloud authentication events, check the chosen schema and each parser's supported source. Confirm how outcomes, accounts, IP addresses, and timestamps map using synthetic records. A common field name does not guarantee identical meaning or complete coverage. Keep original source identifiers available for investigation. Record missing and unmapped values explicitly rather than treating an empty field as a successful authentication or an absence of activity.

## 9. Design automation as a controlled workflow

Sentinel automation rules can trigger playbooks built with Logic Apps. Distinguish permission to manage an incident, run a playbook, allow Sentinel to invoke it, and authorise its downstream operations. A responder role alone does not supply all of these permissions. [Playbook roles and workflow](https://learn.microsoft.com/en-us/azure/sentinel/automation/automate-responses-with-playbooks).

Design a tabletop workflow that enriches a case, requests approval for disruptive containment, and records the decision. Give its identity only the required scope. Use incident/action identifiers and state checks for idempotency: retrying the same request should not create duplicate tickets or repeat an unnecessary restriction. Specify timeouts, partial failures, an accountable owner, and recovery evidence. This exercise sends nothing and executes no response.

## 10. Verify cloud and AI-assisted conclusions

Defender for Cloud workload alerts can add evidence about an Azure server or storage resource. Preserve the resource ID, subscription, workload, relevant time, and applicable plan assumptions. A posture recommendation and an active-threat alert answer different questions. Correlate workload evidence with identity and application activity without assuming that temporal proximity proves causation.

Copilot can help summarise incidents or draft KQL, but its output may be incomplete or incorrect. Verify every consequential claim against source records, identifiers, UTC bounds, and query semantics. [Copilot capabilities and limitations](https://learn.microsoft.com/en-us/defender-xdr/application-card-copilot-defender). Record corrections and analyst judgement. All exercises use fictional evidence; no deployment, live investigation, full coverage, or passing guarantee is claimed.
