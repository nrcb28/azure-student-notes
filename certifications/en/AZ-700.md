## 1. Plan addresses before creating networks

Start with an inventory of campus, Azure, partner, and future network ranges. Overlapping private ranges make peering and hybrid routing difficult; using an RFC 1918 address does not make it globally unique inside our organisation.

For example, reserve 10.70.0.0/16 for the project, then 10.70.1.0/24 for web and 10.70.2.0/24 for data. A /24 contains 256 IPv4 addresses; Azure reserves five in an ordinary subnet, leaving 251 assignable addresses. Service-specific requirements still apply. A delegated subnet, gateway, or firewall can require a particular name, size, exclusivity, or delegation. Check those conditions before allocating the remaining space.

Write a reason for each boundary: lifecycle, routing, trust, service requirements, or growth. An extra subnet alone does not create a security boundary with useful enforcement.

## 2. Connect networks deliberately

VNet peering connects compatible, nonoverlapping networks without merging their ownership or security controls. If A peers with B and B peers with C, A does not automatically gain connectivity to C. Draw every required path.

A hub can host shared connectivity and inspection, but a hub-and-spoke diagram is not a transit configuration. Inspect peer settings, forwarded traffic, route tables, and the appliance or gateway that carries the traffic. Gateway transit supports sharing a gateway under compatible settings; it is not a general promise of automatic spoke-to-spoke forwarding. [Peering reference](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview).

## 3. Read effective routes in both directions

A route selects a next hop; it does not grant application access. Identify the source subnet, destination address, matching prefixes, route origin, and actual effective next hop. A broad 0.0.0.0/0 user-defined route should not be assumed to override every more-specific route.

When introducing a network virtual appliance, check its forwarding configuration, supported topology, capacity, and return path. A request might cross one stateful firewall while the reply returns another way. That asymmetry can break a connection even when each subnet appears reachable separately. Record the route in each direction before adding more exceptions. [Azure routing](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-udr-overview).

## 4. Treat DNS as part of the connection

Ask the actual client which address the service hostname resolves to. A private endpoint is unhelpful if that client still selects an unreachable public destination.

Document private zones, VNet links, DNS server settings, and forwarding between campus and Azure. Azure DNS Private Resolver can participate in supported hybrid resolution designs; inbound and outbound behaviour should be drawn separately. Keep the service hostname so certificate validation and service routing remain correct. Do not hide a DNS mistake with a permanent public-IP entry. DNS success also does not prove that the service accepts the caller's identity. [Private endpoint DNS](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns).

## 5. Compare hybrid paths and failure domains

A site-to-site VPN commonly supplies an IPsec tunnel across the internet. ExpressRoute provides private connectivity through supported connectivity arrangements. Private connectivity does **not** mean traffic is encrypted automatically.

Choose encryption according to the required protection boundary. MACsec applies to supported ExpressRoute Direct physical links; an IPsec design can protect an end-to-end connection. Check throughput and operational consequences rather than treating either as a free label.

For resilience, list the circuits, locations, providers, gateways, customer devices, and routes that could fail together. A backup VPN needs working advertisements, return routes, sufficient capacity, and tested application recovery. Two connections in a diagram can still share one failure domain. [ExpressRoute encryption](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-about-encryption).

## 6. Pick application delivery by protocol and scope

| Need | Candidate to investigate |
|---|---|
| Distribute TCP/UDP flows | Azure Load Balancer |
| Regional HTTP routing, TLS handling, or WAF | Application Gateway |
| Global HTTP application delivery and acceleration | Azure Front Door |
| DNS-based endpoint selection | Traffic Manager |

These are starting points, not an exclusive feature matrix. Application Gateway also has supported TCP/TLS capabilities; verify the current feature and configuration rather than declaring it exclusively HTTP. Traffic Manager answers DNS; it does not proxy each user request. DNS caches affect changes in destination.

For any candidate, specify frontend, backend, protocol, probe, certificate handling, and failure behaviour. A healthy probe can coexist with incorrect document downloads. [Delivery comparison](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/load-balancing-overview).

## 7. Distinguish two forms of service access

A private endpoint gives a supported service a private network interface address in the VNet. A service endpoint identifies and secures supported subnet-to-service access using the service's endpoint model; it does not put that service's public endpoint at a private address in the subnet.

For storage, check endpoint approval, service subresource, DNS, network restrictions, and data authorisation separately. Adding a private endpoint does not automatically disable all public access. A private path also does not grant permission to read a container. State both the intended network path and the allowed identity.

## 8. Match controls to the problem

NSGs filter applicable network traffic with priorities and stateful behaviour. Inspect subnet and interface rules together; changing a rule need not terminate every established connection immediately. Azure Firewall can centralise supported network/application filtering and translation. A WAF evaluates supported web traffic; it is not a replacement for a general routing design. DDoS protection addresses availability threats and does not authorise users.

Use precise hypotheses: “new TCP 443 traffic is denied by this rule” is more useful than “security is broken.” Avoid broad allow rules as a diagnostic habit.

## 9. Gather evidence in a useful order

Check hostname resolution, selected destination, effective next hop, applicable filters, listening process, TLS, and application permission. Use Network Watcher capabilities appropriate to the resource: next-hop analysis, IP flow verification, effective rules, connection troubleshooting, or packet capture. Their prerequisites and scope differ.

One permitted packet prediction is not proof of a successful authenticated request. Preserve the source, destination, protocol, port, timestamp, observation, and next hypothesis. Network Watcher is not a universal substitute for PaaS or application telemetry. [Diagnostic tools](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview).

## 10. Practise a packet walk without deploying

Draw campus, a hub, a web spoke, and private storage. Build a table for normal operation, DNS failure, and primary-link failure. For each, record forward and return paths, enforcement points, expected observation, and one confirming test. Reject one plausible but unsuitable fix.

Then inspect the existing [network lab](network-lab.md). Its VNet and NSG configuration does not contain the gateways or running workloads from your design. Keep design predictions separate from observed results. These new exercises have not been deployed in Azure; real deployments require a suitable test subscription, permissions, service checks, and cleanup.
