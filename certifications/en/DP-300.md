# DP-300 · Administering Microsoft Azure SQL Solutions

[Certification routes](README.md) · [Ten cases](DP-300-cases.md) · [Workbook](DP-300-workbook.md) · [Español](../es/DP-300.md)

A database that accepts connections is only the beginning. For DP-300, I would study how to keep data usable, secure, recoverable, and reasonably fast when something changes. The running example is our university notes app: students upload documents, while a SQL database stores ownership, modules, and download permissions.

## 1. Choose a platform by requirements

Azure SQL Database suits database-focused applications with managed infrastructure. Managed Instance supports more instance-level SQL Server behaviour, but compatibility still needs checking. SQL Server on an Azure VM offers operating-system control and greater compatibility, alongside more administration. They are not interchangeable names for the same deployment.

For the notes app, list required features, dependencies, maintenance responsibilities, and recovery targets before picking a size. An OS-level agent could change the decision; familiarity with one product is not a requirement. Compare current Azure Arc and SQL database in Microsoft Fabric capabilities when relevant, rather than treating either as an automatic replacement for every Azure SQL workload.

[Platform comparison](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview?view=azuresql).

## 2. Plan a migration as a sequence

Inventory database size, versions, logins, jobs, cross-database dependencies, and application assumptions. Assess compatibility before copying data. Separate schema conversion, initial transfer, ongoing changes, and cutover; a successful transfer does not establish that the application works.

An offline migration includes a planned write outage. An online approach can reduce that outage where supported, but still needs a controlled final transition. Define the source of truth, how writes stop, how remaining changes are verified, and who can authorise reopening access. Compare row counts and important business totals, then test permissions, scheduled tasks, and application behaviour. A rollback plan must address writes made after cutover, not just reconnect to an old copy.

## 3. Follow the complete access path

Diagnose connection failures in order: client name resolution, network path, service configuration, authentication, and database authorisation. A private endpoint does not create a database user. An Azure management role does not automatically grant permission to read a SQL table.

Use a suitable Entra identity where supported and provision the necessary database principal and permissions. For the app, grant the operations its function needs rather than using a shared administrator. Keep deployment, application, and incident-response identities distinct. Confirm the actual identity and target database before changing access. For network configuration, check the chosen SQL offering: SQL Database firewall rules cannot simply be transplanted to Managed Instance.

[Layered security](https://learn.microsoft.com/en-us/azure/azure-sql/database/security-overview?view=azuresql).

## 4. Protect data at the right layer

Transport encryption protects the connection. TDE addresses encryption of database files at rest. Always Encrypted has a different boundary and involves compatible client drivers and key handling. A requirement to protect selected values from database administrators needs that boundary examined; enabling TDE alone does not establish it.

Dynamic data masking changes how results are presented for users without the relevant unmasking permission. It does not replace authorisation or make broad query access harmless. Decide who can query rows, who can administer keys, and what appears in logs and exports. Auditing helps record activity, but its destination, retention, access, and review process need ownership too.

## 5. Establish a useful baseline

“Slow” needs a measured meaning: a download-permission lookup that normally takes 30 milliseconds now takes 800. Record query identity, time window, duration, CPU, reads, and application concurrency. Compare the same operation and similar load; a quiet midnight test is a weak comparison for afternoon traffic.

Query Store retains query, plan, and execution information useful for examining regressions. Confirm its configuration and available history before expecting yesterday's evidence. Platform metrics identify resource pressure; waits, blocking chains, and plans help explain why work is delayed. Missing evidence should be recorded as a limitation, not converted into a confident cause.

[Query Store](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store?view=sql-server-ver17).

## 6. Tune one hypothesis at a time

A new plan, stale statistics, unsuitable indexing, a changed parameter pattern, or a long transaction could explain a slowdown. Check the evidence and choose a reversible experiment. An extra index can speed a lookup while increasing write work and storage. A scan is not automatically an error; consider rows needed and the available access paths.

Test a representative workload before and after a change, including concurrent writes. Plan forcing may help a demonstrated regression, but requires monitoring and a way to remove it. Scaling resources is reasonable when capacity is the identified constraint. Routine shrinking, rebuilding everything, or killing sessions without understanding their work can add disruption and hide the original cause.

## 7. Automate for the platform you actually run

SQL Server and Managed Instance support SQL Agent; Azure SQL Database does not provide that service. Elastic Jobs is an option for supported T-SQL tasks across SQL Database targets. An orchestration service may be appropriate when the workflow crosses databases, storage, and external systems.

For every job, specify its identity, target set, schedule, timeout, retry policy, and failure notification. A task that inserts a monthly result should avoid creating duplicates if a response is lost and it runs again. Record completion per intended unit of work, and distinguish a job that ran from a business result that was verified. Test with synthetic data and an isolated target first.

[Automation options](https://learn.microsoft.com/en-us/azure/azure-sql/database/job-automation-overview?view=azuresql).

## 8. Separate backup, availability, and disaster recovery

Backups support recovery to retained states. Point-in-time restore and long-term retention serve different time horizons; choose retention from the requirement before an incident. For SQL Database, restore creates a database rather than overwriting an existing one. A recovery plan therefore includes validation and reconnecting the application appropriately.

Replication and availability mechanisms address failure scenarios, but can also carry a legitimate destructive change. An additional replica does not replace the need to recover an earlier state. Define RPO as acceptable recent data loss and RTO as acceptable restoration time. Test both with realistic dependencies. Region, tier, configuration, and replication mode affect the available design; do not invent a universal recovery duration.

[Backup restoration](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups?view=azuresql) · [Business continuity](https://learn.microsoft.com/en-us/azure/azure-sql/database/business-continuity-high-availability-disaster-recover-hadr-overview?view=azuresql).

## 9. Recover the application, then plan the return

A database failover is not the finish line. Check supported endpoints, DNS resolution, authentication, reconnect behaviour, and consistency across dependent stores. A failover-group listener can preserve the application's endpoint, but clients still need to reconnect successfully. Include monitoring and scheduled work on the new primary.

Before returning, establish which database is authoritative and how changes will be synchronised. Record decision owners and stop conditions. A guessed failback can lose valid writes even after the initial recovery succeeded.

## 10. Offline operational exercise

Without creating cloud resources, prepare a runbook for the notes app. Choose a platform, draw access boundaries, and write a baseline table. Invent a plan-regression incident and a separate accidental-deletion incident; name the evidence that distinguishes them. Describe restoration to an isolated database and a functional check using synthetic records.

Label every entry **EXPECTED**, **OBSERVED**, or **NOT EXECUTED**. A diagram or local SQL exercise cannot prove an Azure restore duration. Submit the assumptions, verification criteria, permission needs, rollback steps, and retained-data cleanup decision.
