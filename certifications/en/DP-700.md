A data engineer turns those operational records into trustworthy analytics: which modules lack resources, when demand peaks, and whether yesterday's figures can be reproduced. The useful question is what makes each result correct and explainable.

## 1. Draw the Fabric boundaries

Microsoft Fabric is a SaaS analytics platform, not another name for Azure Synapse Analytics. Shared concepts do not establish identical runtimes, permissions, or deployment behaviour. OneLake provides a common logical data lake; workloads supply different ways to process and consume data.

A workspace groups items such as lakehouses, notebooks, warehouses, and pipelines. Capacity supplies shared compute resources; it is not the folder containing your files. Distinguish tenant settings, workspace configuration, item definitions, stored data, and running jobs. For our app, draw the enrolment source, raw landing data, curated tables, and report consumers. Label ownership and freshness requirements at each boundary before selecting tools. [Fabric overview](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview).

## 2. Choose storage and table semantics

A lakehouse suits file-oriented ingestion and Spark engineering alongside SQL consumption. A warehouse suits a relational analytics workflow centred on T-SQL. Compare supported operations and team requirements; neither name alone guarantees performance. A lakehouse SQL analytics endpoint is a query surface, not an interchangeable warehouse write engine.

Delta tables combine columnar data files with a transaction log. A directory of arbitrary Parquet files lacks that table's transactional semantics. Keep raw source records when replay and audit requirements justify them, then produce validated tables and a clear analytical grain. Define whether one row represents a download, an enrolment, or a daily module total. Mixing grains silently corrupts aggregation. [Lakehouse and Delta tables](https://learn.microsoft.com/en-us/fabric/data-engineering/lakehouse-and-delta-tables).

## 3. Treat shortcuts as dependencies

A OneLake shortcut references a target location instead of establishing an independent backup. Source deletion, changed permissions, or a moved target can affect readers. Deleting the shortcut itself does not delete its target. A shared path therefore needs an owner, an access agreement, and a continuity plan.

For a library-owned module catalogue, a shortcut can avoid maintaining another copy. Verify internal versus external shortcut authentication, the connection identity where applicable, target permissions, and the consuming engine's access path. Do not assume every reader's identity passes through identically. Record schema-change expectations and test a permitted reader and a denied reader. Availability of the pointer does not establish authorisation to its contents. [OneLake shortcuts](https://learn.microsoft.com/en-us/fabric/onelake/onelake-shortcuts).

## 4. Match orchestration and transformation

A pipeline coordinates copies, dependencies, parameters, schedules, retries, and failure paths. A notebook expresses programmable transformations and can participate in orchestration. Choose PySpark for distributed file processing and transformations, SQL for relational operations, and KQL for suitable event-oriented analysis. Dataflow Gen2 is another option when its preparation model fits the task.

Our nightly workflow copies enrolments, validates keys, transforms records, then publishes module totals only after checks succeed. Parameterise the processing window and destination. Separate control-plane completion from data acceptance: a green copy activity can still deliver the wrong day. Explain why batch, mirroring, or a stream meets the freshness requirement, and check source support rather than assuming continuous replication works for every database.

## 5. Make incremental loads replayable

A high-water mark identifies processed source changes. Capture a bounded upper value, load the intended interval, validate and commit output, then advance durable progress. Advancing it before successful publication risks omissions. A timestamp alone can miss tied values, late changes, or deletions; use stable ordering, overlap with deduplication, or suitable change data capture.

CDC can represent inserts, updates, and deletes when supported and configured. A plain modified-date query cannot discover a physically deleted row without another signal. Deduplicate each batch using a stable business key and deterministic version ordering before an idempotent merge. Preserve delete/version information when necessary so a delayed older update cannot resurrect a removed enrolment. Rerunning a completed batch should preserve the same business state.

## 6. Design streams around time and recovery

Batch processing handles bounded input; streaming handles continuing arrivals, often through microbatches. Event time is when a download happened. Processing time is when the engine handled it. A delayed mobile upload can belong to yesterday's event-time window even when processed today.

Choose eventstreams, Spark Structured Streaming, or KQL-based processing from transformation, state, latency, and operational requirements. Define window boundaries, allowable lateness, and correction rules. Streaming watermarks bound state and late-event handling; they serve a different purpose from a batch extraction high-water mark. Checkpoints retain progress and state for recovery. They do not alone prove end-to-end duplicate prevention: source replay, sink behaviour, and idempotent writes also matter. [Spark streaming into a lakehouse](https://learn.microsoft.com/en-us/fabric/data-engineering/lakehouse-streaming-data).

## 7. Make data quality observable

Specify required columns, types, null rules, allowed values, and key uniqueness. Adding an optional field differs from changing a numeric field into free text. Schema evolution needs an explicit compatibility decision and downstream checks; automatically accepting everything can turn a source error into a published contract.

Retain invalid records in a controlled quarantine with reason codes and source identifiers. Avoid logging real student details unnecessarily. Measure accepted, rejected, duplicate, deleted, and published records, and reconcile them with a defined accounting rule. Missing module references may need delayed dimension handling rather than silent deletion. Synthetic tests should include duplicate keys, malformed dates, unknown modules, and replayed changes. A successful task is not evidence that these rules passed.

## 8. Check every access route

Workspace roles, item permissions, SQL permissions, semantic-model rules, and OneLake file or table access operate at different boundaries. A rule enforced through one engine does not establish protection through another route. Prefer the minimum access needed for each engineer, analyst, and execution identity.

For university analytics, test permitted module totals and denied student-level detail using the intended reader identity. Review direct file access as well as report queries. Row-, column-, object-, and file-level restrictions must match the selected engine and current feature support. Sensitivity labels and endorsement communicate governance context; applying a label alone does not automatically implement every required authorisation rule. Include exports and logs in the review. [Fabric permission model](https://learn.microsoft.com/en-us/fabric/security/permission-model).

## 9. Deploy definitions with environment awareness

Git integration supports versioning supported item definitions. Deployment pipelines move supported content between stages. Neither implies that every source record, secret, permission, connection, or runtime state is copied with the definition. Check support for the item type and dependencies before planning promotion.

Separate development, test, and production configuration: workspace and item references, connection bindings, execution identities, parameters, schedules, and environment dependencies. Keep credentials outside source control. For our app, inspect that the test pipeline reads synthetic enrolments and cannot publish into production. Compare versions, run acceptance checks, then enable scheduled work deliberately. Plan how to revert definitions and repair any data already written; reverting code does not reverse all data changes. [Deployment pipelines](https://learn.microsoft.com/en-us/fabric/cicd/deployment-pipelines/intro-to-deployment-pipelines).

## 10. Diagnose from a baseline and practise offline

Record run identifiers, source windows, row counts, rejected records, duration, freshness, and capacity utilisation. Inspect the failing activity and underlying error before rerunning. A permission failure needs a different response from malformed input or an unavailable source. Repeated retries can multiply partial writes.

For slow jobs, compare similar workloads: Spark stage skew and shuffle, tiny files, partition pruning, query plans, pipeline concurrency, and competing capacity demand. Partitioning by student identifier can create excessive small partitions. Test one justified change against correctness and latency thresholds; scaling is useful when measured capacity pressure explains the problem.

Use the [offline workbook](DP-700-workbook.md) to reason through a synthetic change log and the [ten cases](DP-700-cases.md) to defend decisions. Label predictions EXPECTED and unperformed Fabric checks NOT EXECUTED. Local reasoning cannot establish Fabric throughput or production recovery behaviour.
