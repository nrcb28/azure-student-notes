# AZ-305 · Designing Microsoft Azure Infrastructure Solutions

## Design means defending decisions

Architecture rarely has one best option for everything. An option meets particular requirements at an acceptable cost and complexity. The skill is explaining that relationship without hiding limitations.

## 1. Turn vague statements into requirements

Our university app serves documents across faculties. Before choosing services, ask:

- How many concurrent users and what growth?
- Which data is public or private?
- In which jurisdictions may it be stored?
- How long can the application be unavailable?
- How much recent data may be lost?
- What budget and operational skills exist?
- Which integrations and licences are already in place?

Separate functional requirements, such as uploading a PDF, from quality attributes, such as latency and recovery.

**Example:** always available is not verifiable. A monthly availability objective defined over particular operations can be measured. Selecting one resource with a similar SLA is insufficient because the complete path has dependencies.

Multiplying availability figures can illustrate serial dependencies under simplified assumptions. It is not an exact calculation when failures correlate or redundancy and partial degradation exist.

## 2. Identity and governance at scale

Organise boundaries around administration, risk, billing, and policies. A subscription for every tiny component can complicate management; one subscription for everything may prevent required isolation.

Management groups apply common governance. Subscriptions bound administration and quotas. Resource groups organise lifecycles. Tags classify resources but are not security boundaries.

For users, consider federation and sign-in experience. For workloads, prefer managed identities where suitable. For administrators, minimise permanent privilege and assess temporary elevation and auditing where capabilities and licensing allow.

An on-premises application requiring domain protocols cannot be migrated by blindly replacing its domain with Entra ID. Investigate Kerberos, LDAP, domain join, and other real dependencies.

**Example decision:** allow the API to access only its documents. Developers deploying to test should not automatically become production administrators.

Key Vault alone is insufficient if every developer can read secrets or required rotation never occurs. Design access, retrieval, and behaviour during outages.

## 3. Observability belongs in the design

For several teams, decide where logs go, who can query them, retention, and costs. Centralisation supports correlation; separation can address access or residency. Do not mandate one workspace without examining requirements.

The business signal matters: uploaded documents becoming readable. VM health is useful but does not prove a student can download notes.

Define an SLI, such as successful reads, and an SLO with a justified window and exclusions. An error budget represents the failure allowance under that objective and helps prioritise reliability work.

Logs should support investigation without unnecessarily storing document content, tokens, or personal data. Retention needs operational and legal justification.

## 4. Choosing storage and databases

Start with data shape, queries, consistency, size, latency, recovery, and cost.

| Dominant requirement | Option to assess | Remaining question |
|---|---|---|
| Relationships and transactions | Managed relational database | Which compatibility and capacity? |
| Advanced compatibility with an existing SQL instance | SQL Managed Instance or another compatible route | Which exact features are required? |
| Full engine and operating system control | Database on a VM | Can we operate and recover it? |
| Binary documents | Blob Storage | Which access, retention, and redundancy? |
| Shared files | Azure Files or a compatible option | Which protocol and identity? |

Do not choose Cosmos DB only because the application uses JSON. Query patterns and distributed requirements matter; a serialisation format does not determine a database.

Read scaling does not imply write scaling. Read replicas help certain workloads but require examining consistency and support. Caches introduce invalidation, expiry, and stale-data risks.

Assess capacity-sharing options such as elastic pools where appropriate. For variable workloads, investigate compatible serverless options without assuming universal zero idle cost.

### Integration and analytics

ETL or ELT moves and transforms data for analytical purposes. Unlimited historical queries should not harm transactional users.

Separate operational and analytical data when their patterns justify it. Choose integration tools, lakes, and warehouses according to volume, frequency, transformations, governance, and team skills.

## 5. Continuity: recover the entire service

Our example requires a two-hour RTO and fifteen-minute RPO. These are exercise requirements, not capabilities automatically assigned to a product.

Document:

1. Which data has each objective.
2. How recovery points are created.
3. What replicates synchronously or asynchronously.
4. How long destination capacity takes to provision.
5. How identity, networking, and configuration recover.
6. How clients and DNS switch.
7. How integrity is validated.
8. How the service returns to its primary environment.

**Active-active** can distribute traffic but complicates data and coordination. **Active-passive** reduces some complexity but may need longer recovery. An empty destination does not recover instantly.

Dependencies include image registries, secrets, DNS, automation, and external providers. A replicated application unable to obtain credentials may remain unavailable.

Isolate recovery exercises so they cannot send real emails, charge customers, or overwrite production. Measure observed recovery time against the objective.

**Design criteria:** [Well-Architected Framework](https://learn.microsoft.com/en-us/azure/well-architected/).

## 6. Compute and application architecture

Choose VMs for specific operating system needs, PaaS to reduce operations where suitable, containers for compatible packaged workloads, and batch processing for scheduled compute jobs.

Microservices are optional. A modular monolith can simplify transactions and deployments for a small team. Split components when independent scaling, availability, or change cycles justify it.

For document analysis, queues allow a quick upload response. The interface must still expose processing states and failures: asynchronous work does not disappear.

API Management can support API publication, policies, and controls depending on tier and configuration. It does not replace all internal authorisation. App Configuration can centralise configuration and feature flags; it is not an indiscriminate secret store.

## 7. Networking and traffic entry

Distinguish global from regional traffic, web from non-web, inbound from outbound, and public from private. This avoids choosing a product simply because its name includes balancing.

- Front Door: global entry for supported web scenarios.
- Application Gateway: regional web routing and WAF options.
- Load Balancer: layer 4 TCP/UDP connections.
- Traffic Manager: DNS selection, with caching implications.

Hub-spoke can centralise connectivity and shared services. Correct routing is not automatic. Design name resolution, inspection, return paths, and unwanted asymmetry.

For on-premises connectivity, compare VPN and ExpressRoute against bandwidth, latency, resilience, costs, and requirements. A private circuit does not replace encryption design.

Private endpoints need clients that resolve and reach private addresses. With on-premises networks, hybrid name resolution is part of the solution.

## 8. Migration without losing dependencies

Before moving an application:

1. Inventory servers, databases, files, and dependencies.
2. Measure actual utilisation.
3. Identify compatibility and licensing.
4. Choose a strategy per workload.
5. Prepare identity and networking.
6. Migrate a pilot.
7. Validate data and behaviour.
8. Prepare cutover and rollback.
9. Retire the source only with sufficient evidence.

Rehosting moves with limited change; replatforming adapts to a platform; refactoring changes more application structure. Retiring or retaining a workload can also be valid.

Azure Migrate assists supported scenarios but does not replace conversations with people who know hidden scheduled jobs and integrations. Moving the VM without its shared directory can leave the application incomplete.

For data, choose initial transfer and an approach for changes during migration. Volume and cutover window matter as much as the product.

## 9. Complete case with alternatives

**Situation:** five faculties, private documents, PDF uploads and downloads, seasonal traffic, and three operators.

**Initial proposal:** PaaS API, managed relational metadata database, Blob documents, workload identity, and an analysis queue. Private connectivity between components where requirements and costs justify it.

**Reasoning:** reduces operating system work, separates binaries from queries, and allows document processing to scale differently from web traffic.

**Initially reject:** AKS without demonstrated need, multiple regions without defined RTO/RPO, and a large analytics platform for basic reports.

**Still validate:** regional support, required plans, student authentication, per-document permissions, backups, recovery, observability, costs, and load.

**New constraint:** data must remain within one jurisdiction. Reassess resources, replicas, backups, logs, and dependencies. Changing one region setting is insufficient.

## 10. Design exercises and answers

**Does zero RPO mean zero RTO?** No. Data loss and recovery time are different objectives.

**Is active-active across two regions always better?** No. It may violate residency, add conflicts, or exceed operational capacity.

**The API uses JSON but needs relational transactions. Should we choose NoSQL?** Not based on that clue. Transaction and query requirements matter more than exchange format.

**What would you record for a difficult choice?** An ADR containing context, requirements, alternatives, decision, consequences, and review conditions.

### Practical submission

Write two ADRs: compute and recovery. Include one reasonable rejected alternative, a validation measure, and an assumption whose change would require reviewing the decision.

**Readiness:** defend the proposal and explain which requirement would make another option preferable. Memorising one reference architecture does not solve every case.
