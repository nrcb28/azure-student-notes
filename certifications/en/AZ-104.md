## Moving beyond fundamentals

Knowing a service's purpose is not enough here. We need to interpret configuration, apply permissions, deploy, and troubleshoot. I would study by predicting a result, trying it in a test environment, checking it, and explaining differences.

## 1. Directory identities and resource access differ

Entra ID contains users, groups, and other identities. Directory roles administer the directory. Azure RBAC authorises resource actions. A user administrator is not automatically a subscription Owner.

For a team, I would prefer a group over repeated individual assignments. Consider group type, membership, and who can change members. If the group is privileged, the ability to change membership matters too.

Guests collaborate through external identities. Inviting someone should not grant broad access: assign the specific resource and permission, and review directory policies.

SSPR supports password resets under compatible methods, licences, and configuration. Enabling it for some users does not mean everyone is covered or has registered suitable methods.

### Interpreting assignments

An identity has Reader at subscription scope and Contributor on one group. Within that group it receives permissions from both; elsewhere it does not gain Contributor.

Removing a direct assignment from a resource may leave inherited access. Check the effective identity, groups, scope, role, applicable conditions, and propagation.

NotActions exclusions in a role definition are not global denials. Another assignment can grant the action. Deny assignments operate differently.

**Technical reference:** [Azure RBAC model](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview).

## 2. Governance and subscriptions

Management groups support rules shared across subscriptions. Resource groups organise lifecycles. Names alone are insufficient separation when production and testing need different permissions or policies.

To introduce Policy into an existing environment:

1. Choose a limited scope.
2. Review parameters and exclusions.
3. Audit the impact.
4. Configure identity and permissions where required.
5. Run remediation where appropriate.
6. Check new deployments and existing resources.

ReadOnly and CanNotDelete locks act on management operations and can affect apparently read-only operations implemented with POST. They do not generally protect every data operation.

Moving resources requires checking support, dependencies, and source/destination restrictions. Moving regions can require a different procedure from changing groups. It is not a universal cut-and-paste operation.

**Example:** before deleting an old group, list resources and inspect locks, dependencies, and recovery. The word old does not prove it is unused.

## 3. Storage: authorisation, networking, and protection

When a blob operation fails, ask: can I reach the service, who am I, and may I perform this action? Permission changes do not fix DNS, and opening the network does not supply a missing data role.

### Access methods

- Entra ID data roles associate permissions with identities.
- Account keys provide broad access and should not be distributed to every application.
- SAS tokens delegate restricted, time-limited permissions.
- Stored access policies apply to supported SAS types, not every token.
- A user delegation SAS for Blob uses Entra-based delegation.

A SAS is a credential. Keep it out of issues, screenshots, and logs. Revocation depends on how it was issued; not every token is revoked in the same way.

### Data protection

Versioning retains versions where supported and configured. Soft delete supports recovery within the retention period. Azure Files snapshots provide recovery points according to configuration.

Lifecycle rules automate transitions and deletion under conditions. Check older versions, retention requirements, and immutability before applying them.

Object replication has account, versioning, policy, and blob requirements. It is not a generic solution for every protocol or data type.

For Azure Files, distinguish share access from directory/file permissions when using identity-based authorisation. Review protocol, connectivity, and identity environment support.

**Practice:** complete the [storage lab](../../en/13-laboratorios.md) and explain why a management Contributor might create an account but still fail to list blobs.

## 4. VMs: inventory, changes, and availability

A VM needs more than an image: size, disks, interface, subnet, and access configuration. Not every VM needs a public IP.

For a startup incident:

1. Check state and diagnostics.
2. Inspect recent changes and disk space.
3. Separate operating system failures from networking.
4. Use supported recovery tools.
5. Avoid deleting disks without understanding their role and recovery options.

A VM's temporary disk is not persistent storage. A separate data disk is not a backup merely because it differs from the system disk.

Resizing can require restarting or deallocation, and available sizes depend on constraints and capacity. Check compatibility before promising an uninterrupted change.

Zones and availability sets address placement differently. VM Scale Sets coordinate instances but still need suitable images, scaling, updates, and health checks.

Disk encryption and encryption at host operate at different layers. Check size and configuration compatibility rather than assuming one setting covers every location where data exists.

## 5. PaaS, containers, and declarative deployment

An App Service Plan provides capacity for hosted applications. Scaling the plan or its instance count differs from changing application code.

Custom domains require validation and DNS. HTTPS requires an appropriate certificate and binding. Correct name resolution does not establish correct TLS configuration.

Slots support preparing another version when the plan allows them. Check slot-specific settings and shared dependencies: a test application should not accidentally write to production data.

**App Service networking:** VNet integration supports outbound connections into or through a network. It does not automatically make inbound web access private. Review private endpoints and compatible controls for inbound access. [Integration reference](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration).

For containers, a registry stores images and a runtime starts them. Pull failures can involve credentials, networking, names, or missing tags.

For Bicep or ARM, inspect parameters, resources, dependencies, and outputs before execution. Exported resources do not always produce clean reusable templates.

## 6. Networking: effective rules and routes

Consider VNet 10.30.0.0/16, web subnet 10.30.1.0/24, and data subnet 10.30.2.0/24. A rule permits HTTPS from one source to web. It does not also grant database or application permissions.

NSGs evaluate priorities: lower numbers come first. With subnet and interface NSGs, traffic must pass applicable filters. NSGs are stateful; changing a rule does not necessarily terminate every existing connection.

Application security groups reference logical interface groups in rules. Service tags represent Azure-maintained address sets, not users or application identities.

Routes are selected according to Azure's prefix and source rules. Inspect effective routes before adding speculative routes.

**Technical reference:** [NSGs](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-groups-overview).

### DNS and load balancing

Private zones need suitable links and resolution for their consumers. Creating a private endpoint without reviewing DNS may leave clients using the public endpoint.

For a load balancer, inspect frontend, backend, rule, and health probe. A backend must satisfy the probe and serve real traffic. Allowing probes while blocking the application port is insufficient.

Bastion supports administrative access without directly exposing every VM's SSH or RDP port to the Internet. Its deployment has requirements and costs.

## 7. Monitoring with a purpose

Define healthy behaviour first: successful request proportion, latency, and document processing capacity. Then select metrics, logs, and alerts.

Diagnostic settings send supported categories to configured destinations. They do not automatically collect every signal from every resource.

An alert has scope, signal, condition, and actions. Action groups define recipients and actions. Alert processing rules modify notification processing under rules; they do not fix the incident itself.

Network Watcher and Connection Monitor help investigate connectivity. Check resolution, routing, effective rules, and the listening process before blaming the firewall.

**Exercise:** a backend is unhealthy. Document the probe port, expected response, allowing rules, and whether the process is listening.

## 8. Backup and recovery

Recovery Services vaults and Backup vaults support different workloads and capabilities. Choose according to the protected resource rather than name preference.

A policy specifies schedule and retention. Meaningful evidence includes successful recovery points and a restoration that meets the objective.

Site Recovery replicates supported workloads. Test failover validates recovery separately from a real production switch; prepare isolation and test cleanup.

Before failover, inspect RPO, replication health, destination networking, DNS, and dependencies. Afterward verify service and plan return operations.

## 9. Suggested operational lab

In a test subscription:

1. Reuse the general lab and retain its variables.
2. Inspect access assignments in the portal without broadly changing them.
3. Check tags, storage configuration, and authentication.
4. Review available metrics and describe an alert.
5. Draw a two-subnet VNet without deploying additional networking.
6. Predict rules allowing API-to-data traffic.
7. Explain file restoration and its required configuration.
8. Follow the general lab cleanup.

This exercise has not been deployed in Azure from these notes. Record expected and observed results separately.

## 10. Cases to reason through

**Can create accounts but cannot download blobs.** Check data roles and authentication method before granting Owner.

**Access works by IP but not name.** Inspect DNS, certificate, and expected host; do not immediately blame NSGs.

**The new slot uses the real database.** Check slot-specific connections and settings before swapping.

**A new rule does not cut an existing session.** Consider stateful behaviour, actual source, and effective rules.

**Backup succeeded but the service is not recovered.** A successful copy job and full application recovery are different evidence.

**Readiness:** describe the steps, predict outcomes, and explain how to verify them without defaulting to broad permissions.
