# AZ-140 · Configuring and Operating Microsoft Azure Virtual Desktop

[Certifications](README.md) · [10 cases](AZ-140-cases.md) · [Workbook](AZ-140-workbook.md) · [Español](../es/AZ-140.md)

I would study Azure Virtual Desktop (AVD) as a university computer lab whose machines can be replaced while students keep their working environment. Our example delivers the notes app and a programming toolkit to a morning class. The important question is whether a student can sign in, recover their profile, and work comfortably.

## 1. Draw the service and customer responsibilities

Microsoft operates the AVD broker, gateway, and other service components. We remain responsible for session-host VMs, their images, applications, network, identity integration, profile storage, and operational policies. A working control plane cannot repair an exhausted profile share.

A host pool groups session hosts with common configuration. An application group defines published desktops or RemoteApps and their user assignments; a workspace brings registered application groups into the user's feed. A session host is the VM running the session. Draw those relationships before diagnosing an empty feed. These notes use Azure Resource Manager resources; legacy AVD classic and traditional self-managed Remote Desktop Services are different management models.

## 2. Choose pooled or personal capacity deliberately

A pooled host pool shares session hosts among users; supported Windows Enterprise multi-session images allow concurrent sessions. A personal pool assigns individual desktops to users, using automatic or direct assignment according to requirements. Personal assignment and a user's application-group entitlement solve different problems.

For our interchangeable student lab, begin by evaluating pooled desktops. A researcher needing a dedicated machine might justify personal assignment. Measure representative CPU, memory, disk, graphics, and application behaviour before choosing VM size or maximum sessions. Neither “multi-session” nor a VM's core count proves a safe student density. Record the chosen operating system and licensing eligibility; Windows client and Windows Server requirements differ. [Prerequisites](https://learn.microsoft.com/en-us/azure/virtual-desktop/prerequisites).

## 3. Separate identity, entitlement, and session sign-in

Microsoft Entra ID authenticates access to AVD. Supported host configurations include Entra join, AD DS domain join, and Microsoft Entra Domain Services join. AD DS is the traditional domain service; Entra Domain Services provides managed domain capabilities; Entra ID is not a domain controller. Choose according to application, policy, profile-storage, and authentication dependencies.

Trace feed authentication, application-group assignment, host sign-in rights, and file access separately. Azure management Contributor does not automatically grant a student a desktop. Plan supported single sign-on and Conditional Access with the exact client, join type, authentication method, and required service applications. A second password prompt is evidence to investigate, not proof that Conditional Access failed. Keep privileged administration separate from student access.

## 4. Explain the actual network path

Base reverse connect establishes outbound HTTPS/TCP connectivity from client and host to AVD services; it does not require exposing public TCP 3389 on session hosts. Check current required endpoints, DNS, proxy behaviour, and routes.

RDP Shortpath adds UDP transport when supported. The managed listener option needs direct private reachability and a configured listener, normally UDP 3390. Managed or public ICE/STUN options discover a usable path; TURN can relay supported public-network sessions. Their prerequisites differ, so a private listener rule is not a universal Shortpath configuration. TCP reverse connect remains the fallback when UDP cannot establish. Check client/platform support and cloud availability. Compare actual transport, round-trip delay, packet loss, and host-to-profile latency. [Shortpath requirements](https://learn.microsoft.com/en-us/azure/virtual-desktop/configure-rdp-shortpath); [network foundations](../../en/05-networking.md).

## 5. Keep persistent profiles outside replaceable hosts

FSLogix profile containers preserve the user's profile on supported storage instead of depending on a particular pooled VM's local disk. Separate the notes app's authoritative data from desktop preferences and caches. Profile persistence is not automatically application-data backup.

For SMB storage, validate both share-level access and NTFS permissions. Select a supported identity/Kerberos arrangement for the host join and storage service; check DNS, tickets, time, and encryption compatibility. A successful Azure portal login proves none of those conditions. Size storage for sign-in bursts, capacity, and latency. Default single-container connections are not permission for arbitrary concurrent writers. Plan disconnection, locks, backup, restoration, and recovery objectives before a profile incident. Multiple path entries alone do not establish resiliency. [FSLogix configuration examples](https://learn.microsoft.com/en-us/fslogix/concepts-configuration-examples).

## 6. Choose an application delivery method and validate it

Installing supported applications in the base image is straightforward but ties updates to the image lifecycle. A managed installation process can update suitable applications separately. Current App Attach can deliver supported packages from accessible storage; publishing a RemoteApp controls presentation and entitlement, while packaging controls delivery. They are related decisions.

For our notes editor, document dependencies, licensing, package compatibility, storage access, and assignment to the host pool and user. Test first launch, updates, and a second user on a multi-session host. Do not assume every installer can become a working package or use old MSIX app attach instructions as the current management model. Keep a tested fallback version. [Current App Attach overview](https://learn.microsoft.com/en-us/azure/virtual-desktop/app-attach-overview).

## 7. Treat images as versioned releases

Build a documented golden image with supported OS, agents, applications, security settings, and update state. Keep build inputs and image versions so the lab can be reconstructed. Azure Compute Gallery can distribute versions; review [compute basics](../../en/03-compute.md) before planning the VM lifecycle.

Introduce a new version to a small validation group. Test authentication, profile attachment, notes editing, printing or redirection where required, and session performance. Drain old hosts to prevent new sessions while handling existing sessions according to the maintenance policy; drain mode does not instantly log everyone out. Replace hosts gradually. Preserve the earlier image and a capacity-aware rollback path. Patching every live host simultaneously makes a shared classroom dependency fragile.

## 8. Match scaling to the class timetable

A scaling plan governs supported autoscale behaviour using schedules and capacity settings. Distinguish power management of existing hosts from dynamic host creation/deletion, whose host-pool prerequisites and availability must be checked. Start VM on Connect starts eligible stopped hosts when users connect; it is not a complete timetable or spare-capacity strategy.

For 48 simultaneous students and a measured limit of 12 sessions per host, four available hosts meet demand without failure headroom. Five provide one-host headroom under those assumptions. Model boot time, unhealthy hosts, drain state, and storage limits. Specify service permissions, exclusion handling, and active-session policies before ramp-down. A saving forecast should include disks, storage, networking, monitoring, and licences as well as VM runtime. [Scaling-plan requirements](https://learn.microsoft.com/en-us/azure/virtual-desktop/autoscale-create-assign-scaling-plan).

## 9. Follow one failed connection through evidence

Record UTC time, pseudonymous user identifier, client version, resource, session host, and connection correlation ID. Correlate connection, checkpoint, error, agent-health, and relevant network records with host performance and FSLogix logs. Enable appropriate diagnostic settings and host collection before expecting historical evidence. AVD Insights helps investigate experience; its data collection still needs configuration.

Distinguish missing feed, failed host sign-in, slow profile attachment, and a sluggish application after sign-in. An absent AVD connection record can mean the attempt never reached the service. Compare a successful student session at the same time and avoid collecting note contents or credentials. [Diagnostic categories and correlation](https://learn.microsoft.com/en-us/azure/virtual-desktop/diagnostics-log-analytics).

## 10. Rehearse recovery without deploying

Run an offline tabletop for a morning login burst, one unavailable host, and an inaccessible profile share. Write predictions, the evidence needed to confirm each hypothesis, a responsible operator, rollback conditions, and a clear recovery criterion. Restoring VMs alone does not restore identity, DNS, application packages, profile access, or the notes API.

Agree recovery-time and recovery-point objectives for profiles and application data separately. Include alternate-region dependencies, profile consistency, available VM capacity, and return-to-primary steps. Document who owns each continuing cost and who responds to an alert. Complete the [ten cases](AZ-140-cases.md) and [five workbook units](AZ-140-workbook.md). These exercises change no tenant and make no claim of Azure deployment or tested failover.
