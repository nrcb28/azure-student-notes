I would approach this specialty as an infrastructure student joining a university's enterprise SAP team. Our fictional university uses SAP for purchasing and finance, with interfaces to a research portal. We design the Azure platform and recovery process; we do not configure SAP business processes.

## 1. Inventory the landscape before drawing VMs

Record each SAP system identifier (SID), environment, version, OS, database, interfaces, dependencies, and owner. Distinguish application servers, ABAP SAP Central Services (ASCS), Enqueue Replication Server (ERS), Java Central Services (SCS), and HANA. ASCS coordinates messaging and enqueue services; ERS supports enqueue replication. Another application server does not automatically protect either central services or the database.

Map campus identity, DNS, time synchronization, transport directories, batch jobs, printers, and research-portal connections. Assign Azure infrastructure, OS, SAP Basis, database, security, and business-validation responsibilities. An infrastructure diagram without these boundaries cannot tell us who approves a migration or verifies purchasing. Review [supported configurations](https://learn.microsoft.com/en-us/azure/sap/workloads/planning-supported-configurations).

## 2. Size a supported combination

CPU count alone cannot select an SAP VM. Verify certification and support for the exact workload, VM family, OS release, database version, storage, and deployment topology. SAP HANA hardware certification has workload-specific conditions; a VM suitable for an application tier is not automatically a certified HANA target.

Use SAP sizing outputs, SAP Application Performance Standard (SAPS) requirements where relevant, measured peaks, HANA memory needs, growth, and failure headroom. Evaluate VM-level storage throughput and network limits alongside disk capabilities. Check regional capacity, quotas, and support arrangements. Document licensing requirements with the responsible team; these notes supply no SAP licence or entitlement. The deliverable is justified capacity assumptions, never a universally sufficient fixed SKU.

## 3. Build the landing zone and direct network paths

Separate production and nonproduction access with a suitable subscription and resource-group hierarchy, least-privilege roles, policy, and privileged administration. Trace user, management, integration, replication, and backup flows. Keep application and database tiers in supported networking arrangements; do not insert a network appliance into a SAP kernel application-to-database path simply to reuse a generic diagram.

Specify DNS forwarding, name ownership, firewall rules, routes, and dependency reachability. ExpressRoute supplies private connectivity, not automatic end-to-end encryption; select encryption controls explicitly where required. Validate Accelerated Networking support and configuration. A successful ping cannot prove a purchasing transaction's latency or authentication path. See [deployment planning](https://learn.microsoft.com/en-us/azure/sap/workloads/planning-guide).

## 4. Balance placement, latency, and failure isolation

Availability zones separate infrastructure failure domains; availability sets address different placement concerns. Neither creates application failover by itself. Measure latency for the actual region, zones, VM types, and workload, including synchronous replication. A topology must meet both response-time and recovery requirements.

Proximity placement groups (PPGs) constrain colocation to improve latency when justified. A single PPG does not stretch its colocation guarantee across zones or replace zone isolation. Extra constraints can complicate capacity allocation and resizing. Start from supported placement guidance, add a PPG only for an evidenced need, and document degraded operation. For the university, explain how losing one zone affects remaining application capacity and database takeover.

## 5. Treat HANA storage as a latency design

Plan `/hana/data`, `/hana/log`, and `/hana/shared` separately using a supported filesystem and storage layout. Data loading and savepoints need throughput; transaction-log writes need low latency; shared files also affect startup and cluster health. Capacity in terabytes alone proves none of these characteristics.

Check the selected storage type's VM compatibility, limits, striping or data-volume partitioning guidance, and replica consistency requirements. Host caching and Write Accelerator settings depend on the exact disk, VM, and volume role; never copy one cache policy to every volume. Keep backup placement and temporary storage responsibilities explicit. Record both disk and aggregate VM limits against representative demand. Use [HANA storage configurations](https://learn.microsoft.com/en-us/azure/sap/workloads/hana-vm-operations-storage).

## 6. Explain how failover stays safe

HANA System Replication copies database changes; a supported cluster automates decisions and resource movement. Protect ASCS/SCS through its own supported HA design, including ERS and shared-file requirements where applicable. Configure virtual names, load-balancer probes, resource agents, and startup dependencies consistently.

Quorum helps determine which partition may act. Fencing isolates a node that cannot safely continue, reducing split-brain risk. Select the supported Azure fence-agent or SBD arrangement for the distribution and architecture. Never disable fencing to make an unhealthy cluster appear available. Rehearse lost communication, failed probes, and takeover ordering on paper, identifying the single permitted writer. See the [SLES HANA HA guide](https://learn.microsoft.com/en-us/azure/sap/workloads/sap-hana-high-availability).

## 7. Separate recovery copies from replication

Replication can quickly propagate an accidental deletion. Backups, retained logs, and a supported restore process provide recovery to an earlier acceptable point. Define recovery point objective (RPO) as tolerable data loss and recovery time objective (RTO) as tolerable interruption; establish them with business owners.

Choose workload-aware database backups and logs, retention, protection boundaries, and restoration dependencies. A VM or storage snapshot is not automatically an application-consistent SAP/HANA backup. Specify supported coordination and consistency before using snapshots. A backup job's success is weaker evidence than a restore followed by database and business validation. Include identity, encryption-key access, required files, and backup availability during a regional failure.

## 8. Make migration cutover reversible in practice

Assess compatibility and dependencies before selecting a homogeneous copy, database migration, upgrade, or HANA transition. Match the supported tool and SAP procedure to the source and target; moving VM disks does not validate every SAP migration. Estimate transfer duration, change rate, downtime, and final synchronization, then rehearse with representative data.

Write gates for write freeze, final transfer, source isolation, DNS/interface changes, technical checks, business acceptance, and reopening writes. Name decision owners and rollback deadlines. After new target writes, switching DNS back can lose or fork transactions: rollback needs reconciliation or supported reverse data movement. Record this as a data decision, including who authorizes it, rather than calling the old VM a complete rollback plan.

## 9. Operate with reviewed automation and ownership

Review Bicep/ARM or SAP Deployment Automation Framework changes for supported images, placement, storage, identity, dependencies, and destructive differences. Keep credentials outside source control; use approved secret references and access controls. Stage OS, kernel, agent, and database updates with compatibility checks, backup evidence, cluster-aware sequencing, and rollback criteria.

Correlate Azure VM, disk, network, and availability evidence with SAP and database health. [Azure Monitor for SAP solutions](https://learn.microsoft.com/en-us/azure/sap/monitor/about-azure-monitor-sap-solutions) needs configured providers and collection; an empty workbook does not prove health. For RISE, the contract and responsibility matrix govern SAP-managed resources. Document customer network, identity, interface, and escalation boundaries using [RISE integration guidance](https://learn.microsoft.com/en-us/azure/sap/workloads/rise-integration).

## 10. Rehearse an entire service recovery

Our offline tabletop removes the primary region during a university purchasing run. Recover application services, central services, database, identity, DNS, routes, integration endpoints, secrets, and usable capacity in the required order. Decide how replication lag affects acceptance and prevent the old primary from resuming writes independently.

Test the plan against a successful purchase and research-portal exchange, with named validators and predicted timing. Include return-to-primary synchronization, controlled switchover, and closure evidence. Review performance and continuing cost categories before resizing or making capacity commitments; measure failure headroom again after changes. Complete the [cases](AZ-120-cases.md) and [workbook](AZ-120-workbook.md). These are architecture and runbook exercises, with no Azure deployment, SAP execution, or measured failover claimed.
