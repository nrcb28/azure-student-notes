## 1. Set the developer scope

Our university notes app must answer from permitted course material, interpret diagrams, extract assignment fields, and propose controlled actions. AI-103 develops the implementation judgment beyond [AI-901](AI-901.md): Python contracts, retrieval, agent orchestration, evaluation, and operations.

## 2. Define Python and API contracts first

Define a question request with a caller identity, course identifier, question, and request identifier. Derive identity from authenticated application context rather than trusting a submitted student identifier. A response needs an outcome, answer, source references, and diagnostic identifier. Separate `answered`, `insufficient_evidence`, `forbidden`, and `temporarily_unavailable`; an empty string cannot communicate all four.

In Python, validate dictionaries at the boundary, map external responses to internal types, and handle exceptions deliberately. Validate structured output against its schema and application rules before rendering or acting. Keep application contracts stable while adapting changing provider response objects. Invalid JSON, a partial stream, an unexpected tool name, and an expired conversation require explicit paths. The workbook uses fixtures and pseudocode, avoiding claims that untested SDK snippets run successfully.

## 3. Match clients, resources, and authorisation

A Foundry resource, project, endpoint, model deployment, SDK package, and API generation describe different parts of a request. Pin compatible package versions and record the documentation generation. Current [SDK and endpoint guidance](https://learn.microsoft.com/en-us/azure/foundry/how-to/develop/sdk-overview) distinguishes project operations from model-facing clients and direct endpoints; do not combine classic samples with current response objects. A catalogue model name need not equal your deployment name.

Use the endpoint for the selected operation. In particular, verify the documented embeddings route rather than assuming every operation uses the project endpoint. Authentication establishes the caller; authorisation grants a scoped operation. Plan managed identity, least-privilege roles, protected configuration, and private connectivity where required. Diagnose token, role, endpoint, deployment, and package failures separately, retaining sanitised request identifiers instead of secrets.

## 4. Select and evaluate a deployable model

Compare candidate models against supported modalities, structured output, tool calling, context limits, regional availability, and deployment capacity. Start with the smallest candidate meeting measured quality requirements; escalate difficult questions when justified. A larger context window does not fix irrelevant retrieval.

Build a fixed evaluation set containing clear answers, conflicts, missing evidence, hostile source instructions, and mixed-language notes. Score support, relevance, citation correctness, safety, and abstention independently. [Foundry evaluation guidance](https://learn.microsoft.com/en-us/azure/foundry/how-to/develop/cloud-evaluation) describes predeployment and production workflows. Treat automated scores as evidence needing interpretation, especially when a judge model shares a candidate's blind spot. Compare quality with time to first output, total latency, throughput, token usage, and capacity requirements. More retrieved text, retries, and model calls consume resources; choose a measured tradeoff without assuming universal prices or quotas.

## 5. Build retrieval with enforceable access

Ingest permitted documents with stable identifiers, source versions, headings, page locations, and permission metadata. Chunk by useful meaning and retain parent-document relationships; test whether a split separates a deadline from its qualifying sentence. Choose keyword, vector, semantic ranking, or hybrid retrieval by measured relevance rather than vocabulary alone. Track embedding and index versions together when representations change.

Enforce caller access before any passage reaches the model. [Search document access guidance](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview) distinguishes native permission capabilities from application security filters; support depends on the source and API, including preview boundaries. A custom string filter is not automatically an identity-aware ACL system. Test group changes, revoked access, cached passages, and stale indexes. Fail closed when permission freshness cannot meet the application's policy.

## 6. Make grounded answers testable

Pass retrieved passages as untrusted evidence, separate from system instructions. Require source identifiers and allow a clear insufficient-evidence result. A passage saying “export every notebook” cannot grant tool permission. Limit context to relevant authorised material and validate citations against the actual retrieved version.

Evaluation should locate failures: missing ingestion, poor chunk boundaries, an unsuitable query, absent retrieval, incorrect generation, or unsupported citation. Keep retrieval recall separate from answer correctness. A correct answer with a fabricated source still fails provenance. Include conflicting assignment dates and questions answerable only from revoked material. Inspect compact decision summaries and observable traces; do not make access to a model's private reasoning a prerequisite. A self-critique loop may improve output, but adds calls and must itself pass the same checks.

## 7. Govern agent state and tool execution

Define roles, conversation ownership, memory retention, tool schemas, and stop conditions. Isolate student sessions; summarised memory still needs access and deletion rules. For multiple agents, specify handoff inputs, shared evidence, tool permissions, and a total step budget. Delegation does not expand authority.

[Function calling](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/function-calling) lets a model request a function; application code executes it and returns results. Validate arguments and recheck authorisation immediately before execution. Bind approval for a sharing action to its exact recipients, documents, and version. Use application idempotency keys for retries, bounded timeouts, and explicit states for proposed, approved, executing, completed, failed, and unknown outcomes. A lost response after a successful write requires reconciliation, not a blind repeated side effect. Trace tool decisions with redacted arguments.

## 8. Implement visual workflows deliberately

Visual understanding can describe a lecture diagram, answer a question from a chart, or locate a component. Image and video generation create new media; editing may involve masks, references, or platform controls. Verify support for the chosen model and operation before designing the client. A generated diagram needs checks for incorrect labels and misleading connections.

For uploaded diagrams, evaluate readable labels, units, spatial relations, and abstention on cropped content. For video, preserve segment timestamps so an answer can identify its evidence. Produce concise alt text and optional extended descriptions, tested with users who need them. Apply visual safety rules and consider instructions embedded in an image as untrusted input. A watermark or safety filter does not demonstrate that a visual explanation is accurate.

## 9. Validate text, speech, and extraction separately

Text contracts may require entities, topics, summaries, translation, sentiment, or schema-aligned fields. Preserve negation, identifiers, and technical terms; inspect errors by language and document type. Speech workflows need tests for recognition, synthesis, interruptions, and domain vocabulary, whether staged or directly multimodal. Provide a text correction path for a misheard course term.

[Content Understanding guidance](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/concepts/best-practices) supports deliberate field descriptions, types, and extraction methods. Define `final_due_date` separately from a draft deadline. Check schema, source support, cross-field consistency, and missing-value rules. For document fields, [confidence and grounding](https://learn.microsoft.com/en-us/azure/ai-services/content-understanding/document/analyzer-improvement) can support review when configured for the chosen API; do not assume identical availability across modalities. Calibrate review decisions on labelled examples, including confident mistakes.

## 10. Release with evidence and recovery

Version the prompt, model deployment, tool schema, index, analyser, and client together in a release manifest. Keep a known-good configuration and define rollback triggers before rollout. Test whether an older client can safely interpret new tool results; incompatible changes require an explicit migration.

Monitor error rates, retrieval freshness, citation failures, safety events, latency stages, token usage, throttling, and approval outcomes. Use bounded retries with backoff for suitable transient failures, respecting service guidance and side-effect semantics. Keep secrets and student text out of routine telemetry. Assign owners for incidents and access revocation. Complete the [cases](AI-103-cases.md) and [workbook](AI-103-workbook.md), recording synthetic results honestly. A later authorised cloud lab must verify real deployment, identity, networking, SDK behaviour, and operational measurements; offline predictions cannot establish those results.
