# DP-300 · 管理 Microsoft Azure SQL 解决方案

## 1. 按要求选择平台

Azure SQL Database 适合以数据库为中心、采用托管基础设施的应用。Managed Instance 支持更多 SQL Server 实例级行为，但仍须核对兼容性。Azure VM 上的 SQL Server 提供操作系统控制和更广兼容性，同时也需要更多管理。三者不是同一部署的不同名字。

对笔记应用，选规格之前先列出所需功能、依赖、维护责任和恢复目标。操作系统级代理可能改变决策；熟悉某产品本身不算需求。相关时比较当前 Azure Arc 和 Microsoft Fabric 中 SQL 数据库的能力，不要把任何一项当作所有 Azure SQL 负载的自动替代品。

[平台比较](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview?view=azuresql)。

## 2. 把迁移规划成一系列步骤

清点数据库大小、版本、登录名、作业、跨数据库依赖和应用假设。复制前先评估兼容性。区分架构转换、首次传输、持续变更和切换；数据传输成功，不证明应用正常。

离线迁移包含计划内停止写入。受支持时，在线方案可以缩短停止时间，但仍需受控的最终切换。要定义权威数据源、如何停止写入、如何核验剩余变更，以及谁有权恢复访问。比较行数与重要业务总数，再验证权限、计划任务和应用行为。回滚方案必须处理切换后新增的写入，不能只重新连接旧副本。

## 3. 检查完整访问路径

按客户端名称解析、网络路径、服务配置、身份验证和数据库授权的顺序诊断。专用终结点不会创建数据库用户，Azure 管理角色也不会自动授予 SQL 表读取权限。

在支持的位置使用合适的 Entra 身份，并配置必要的数据库主体和权限。应用只应获得其功能所需操作，不要共用管理员。将部署、应用和事件响应身份分开。修改权限前确认实际身份和目标数据库。网络配置要对应所选 SQL 产品：不能把 SQL Database 防火墙规则原样搬到 Managed Instance。

[分层安全](https://learn.microsoft.com/en-us/azure/azure-sql/database/security-overview?view=azuresql)。

## 4. 在正确层面保护数据

传输加密保护连接。TDE 处理数据库文件的静态加密。Always Encrypted 的边界不同，涉及兼容客户端驱动和密钥管理。如果要求数据库管理员不能看到某些明文值，就要考察该边界；单独启用 TDE 不能证明已经满足。

动态数据掩码改变没有相应取消掩码权限的用户看到的结果，不替代授权，也不能让宽泛查询权限变得无害。明确谁可查询行、谁可管理密钥，以及日志和导出会出现什么。审核能记录活动，但其目标位置、保留期、访问与复核流程也需要负责人。

## 5. 建立有用的基线

“慢”要有可测量的含义：原本 30 毫秒的下载权限查询，现在变成 800 毫秒。记录查询标识、时间窗、耗时、CPU、读取量和应用并发。比较相同操作与相近负载；安静的午夜测试，不适合作为下午高峰的比较基准。

Query Store 保存查询、计划和执行信息，便于调查性能回退。期望看到昨天证据前，先确认其配置和现存历史。平台指标显示资源压力；等待、阻塞链和执行计划帮助解释为何延迟。缺失证据要记为限制，不能变成自信的原因判断。

[Query Store](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store?view=sql-server-ver17)。

## 6. 一次验证一个调优假设

新计划、过期统计信息、不合适的索引、参数模式变化或长事务，都可能使查询变慢。查看证据，选择可逆实验。额外索引可能加快查找，同时增加写入和存储成本。扫描不自动意味着错误，要看需要多少行以及有哪些访问路径。

在修改前后测试有代表性的负载，包括并发写入。对已经证实的回退，计划强制可能有用，但需要监控和撤销方式。容量确为瓶颈时，扩容也合理。惯例性收缩、重建全部对象，或者不了解工作就终止会话，可能增加中断并掩盖原始原因。

## 7. 按实际平台选择自动化

SQL Server 与 Managed Instance 支持 SQL Agent，Azure SQL Database 不提供该服务。Elastic Jobs 可用于支持的 SQL Database 目标上的 T-SQL 任务。流程横跨数据库、存储和外部系统时，可能更适合编排服务。

每项作业都要规定身份、目标集合、时间表、超时、重试策略和失败通知。写入月度结果的任务，应避免在成功响应丢失、再次执行时产生重复。按预定工作单元记录完成状态，区分作业运行过与业务结果已验证。先用合成数据和隔离目标测试。

[自动化选项](https://learn.microsoft.com/en-us/azure/azure-sql/database/job-automation-overview?view=azuresql)。

## 8. 区分备份、可用性与灾难恢复

备份支持恢复到保留状态。时间点还原与长期保留服务不同时间跨度；事故前就应按要求选定保留策略。SQL Database 还原会创建数据库，而不是覆盖已有数据库，因此恢复计划还包括验证和让应用正确重新连接。

复制与可用性机制处理故障场景，却也可能传播合法提交的破坏性修改。多一个副本不能替代恢复历史状态的能力。RPO 表示可接受的近期数据损失，RTO 表示可接受的恢复时间，要结合真实依赖验证两者。区域、层级、配置和复制模式影响可用设计，不应编造普遍适用的恢复耗时。

[备份还原](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups?view=azuresql) · [业务连续性](https://learn.microsoft.com/en-us/azure/azure-sql/database/business-continuity-high-availability-disaster-recover-hadr-overview?view=azuresql)。

## 9. 恢复应用，再规划返回

数据库故障转移不是终点。核对受支持终结点、DNS 解析、身份验证、重连行为，以及依赖存储之间的一致性。故障转移组侦听器可保留应用终结点，但客户端仍须成功重连。还要把新主库上的监控和计划任务纳入恢复。

返回前，确定哪个数据库具有权威性，以及如何同步变化。记录决策负责人和停止条件。即使首次恢复成功，凭猜测执行故障回复仍可能丢失有效写入。

## 10. 离线运维练习

不创建云资源，为笔记应用准备操作手册。选择平台、画访问边界、写基线表。分别虚构计划回退和误删除事件，说明哪些证据能区分它们。描述还原到隔离数据库，并用合成记录执行功能检查的方案。

每项都标为 **EXPECTED（预期）**、**OBSERVED（观察）** 或 **NOT EXECUTED（未执行）**。图示或本地 SQL 练习不能证明 Azure 还原耗时。提交假设、验证标准、权限需求、回滚步骤和保留数据清理决定。继续完成[五个练习单元](DP-300-workbook.md)与[十个原创案例](DP-300-cases.md)。这里不声称执行过 Azure 操作。
