# SC-200 · Microsoft 安全运营分析师

[认证](README.md) · [十个案例](SC-200-cases.md) · [练习册](SC-200-workbook.md)

SC-200 要求我们把安全信号转化为经得起检验的决策。对于大学笔记应用，我希望能够解释涉及哪个账户、设备、消息或云资源，证据支持什么结论，以及谁有权授权响应。

## 1. 区分各产品的职责

Defender XDR 协调受支持 Microsoft 安全产品之间的检测、调查和响应。一封可疑 Microsoft 365 消息、一个终结点事件和一个身份信号，可能成为同一事件的不同部分。覆盖范围取决于许可、预配和接入；有门户并不意味着校园每台设备都已被监测。[Defender XDR 概述](https://learn.microsoft.com/en-us/defender-xdr/microsoft-365-defender)。

Sentinel 对已连接的 Microsoft 及其他来源增加 SIEM 分析和响应编排。共用 Defender 门户并不意味着这些能力可以互换。先画出校园环境：Microsoft 365 邮件、Azure 工作负载、本地目录和服务器，以及第三方网络设备。为每种所需信号指定来源和调查负责人。

## 2. 编写检测前先建立数据覆盖

为每个来源记录连接器前提条件、身份验证、收集范围、目标表、事件时间、预期延迟和保留期。通过 AMA 收集 Windows 安全事件会使用收集规则；Syslog 和 CEF 各有自己的收集路径。已连接状态的证明力弱于所需事件确实到达且字段可用。[Sentinel 连接器](https://learn.microsoft.com/en-us/azure/sentinel/connect-data-sources)。

检查表架构，不要猜测列名：Defender 搜寻通常使用 `Timestamp`，而 Sentinel 表通常使用 `TimeGenerated`。记录类型和稳定标识符。为读取者、事件响应人员、检测编写者及自动化身份规划最小权限 RBAC。日志可能包含个人数据、令牌和文档路径：尽量减少收集、限制导出，并与数据所有者约定保留期和存储位置。

## 3. 区分警报、事件和实体

警报报告一项检测；事件把相关证据归组以便调查。实体是涉及的对象，例如账户、设备、IP 地址或文件。针对一个学生账户的多个警报，并不自动证明发生了多起独立入侵；共享校园 IP 也不能确定攻击者相同。

分诊需要结合严重性、资产重要性、置信度、暴露程度和当前活动。指定负责人、保留原始标识符，并写下最初的问题。对笔记应用而言，“这个账户是否访问了尚未发布的答案？”比“调查一切”更有用。在案件记录中，分别保存分类、支持性观察、缺失证据和拟议后续步骤。

## 4. 建立时间线并限定响应

按 UTC 对邮件、登录、终结点、应用和云活动排序。区分事件时间和摄取时间；延迟可以解释表面上的先后倒置。使用已核实的账户和设备标识符展开关联，再有意识地扩大时间窗口和相关资源范围。说明已确认的范围和未观察到的区域。

遏制可能中断授课或研究。在我们的桌面推演中，只有在记录事件授权、受影响服务负责人、影响估计和恢复条件后，才提出账户限制或设备隔离。警报并不是执行操作的许可。分别跟踪拟议、已批准、已尝试和已确认的操作。关闭事件需要有依据的解释和后续工作，而不只是一个空队列。

## 5. 在固定数据集上推理 KQL

这个合成示例供离线阅读使用，并非租户查询，也不是已观察到的 Azure 结果。时间均为 UTC。[KQL 搜寻概念](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-query-language)。

```kusto
let Events = datatable(Timestamp:datetime, EventId:string, Account:string, Result:string)
[
 datetime(2026-10-30T09:00:00Z), "e1", "student-a", "Denied",
 datetime(2026-10-30T09:00:00Z), "e1", "student-a", "Denied",
 datetime(2026-10-30T09:02:00Z), "e2", "student-a", "Denied",
 datetime(2026-10-30T09:03:00Z), "e3", "student-b", "Allowed"
];
Events
| where Timestamp >= datetime(2026-10-30T09:00:00Z)
    and Timestamp < datetime(2026-10-30T09:03:00Z)
| where Result == "Denied"
| distinct EventId, Account
| summarize DeniedEvents=count() by Account
```

预期结果：`student-a`，`2`。半开时间窗口排除了边界事件。`where` 筛选行，`project` 选择列，`summarize` 改变聚合层级。`distinct` 删除投影后完全相同的组合；它不能证明任意相似事件就是重复事件。这里明确假定 `EventId` 稳定。显式选择 `join` 的类型和键：多对多匹配会增加行数，而默认的 `innerunique` 会按联接键对左侧去重。解释计数前，检查架构、空值、大小写敏感性和基数。

## 6. 用可证伪的假设进行搜寻

可以尝试：“收到可疑消息的账户随后从陌生设备访问了私人课程资料。”定义相关群体、UTC 区间、来源覆盖、预期行为，以及其他解释，例如已授权的设备更换。

搜寻能够发现尚未触发警报的活动。空结果意味着查询在给定条件下没有找到匹配的可用行；它不能证明没有发生入侵。未接入、保留期、权限、解析器错误和过窄的筛选条件，都可能限制可见性。保存假设、查询版本、相关行或书签、局限和下一个问题。威胁情报提供线索；匹配某个指标仍需要上下文和时效性检查。

## 7. 用证据调整检测

计划的 Sentinel 分析规则和 XDR 自定义检测需要正确的来源数据、受支持的查询形式、计划、回溯窗口、标识符及实体映射。窗口重叠可能重复匹配；分组和抑制选择会影响分析人员看到的内容。

在笔记应用中，合法的批量课程导入可能看起来像异常文件访问。审核已标注的正常和可疑合成示例。误报是对正常活动发出警报；漏报是未检测到原本希望发现的活动。把所有讲师一概排除，可能减少噪声，却隐藏可疑案例。在任何已授权的生产更改之前，记录规则版本、拟议例外范围、预期结果和剩余缺口。ATT&CK 映射描述预期覆盖，并不能证明检测有效。

## 8. 谨慎地跨来源规范化

ASIM 提供通用架构和解析器，使兼容的 Sentinel 内容能够跨不同来源使用。查询时解析器提供规范化视图；摄取时转换可以写入受支持的规范化表。[ASIM 概述](https://learn.microsoft.com/en-us/azure/sentinel/normalization)。

对于校园防火墙和云身份验证事件，检查所选架构及每个解析器支持的来源。用合成记录确认结果、账户、IP 地址和时间戳如何映射。字段名相同不保证含义相同或覆盖完整。保留原始来源标识符供调查使用。明确记录缺失及未映射的值，不要把空字段当作身份验证成功或没有活动。

## 9. 将自动化设计为受控工作流

Sentinel 自动化规则可以触发基于 Logic Apps 构建的操作手册。区分管理事件、运行操作手册、允许 Sentinel 调用操作手册，以及授权下游操作的权限。响应人员角色本身并不提供所有这些权限。[操作手册角色和工作流](https://learn.microsoft.com/en-us/azure/sentinel/automation/automate-responses-with-playbooks)。

设计一个桌面推演工作流，用于丰富案件信息、对有干扰性的遏制请求审批，并记录决策。只给工作流身份所需范围。使用事件和操作标识符及状态检查来实现幂等性：重试相同请求不应创建重复工单，或再次执行不必要的限制。明确超时、部分失败、负责人员和恢复证据。本练习不发送任何内容，也不执行响应。

## 10. 核实云端及 AI 辅助结论

Defender for Cloud 工作负载警报可以为 Azure 服务器或存储资源补充证据。保留资源 ID、订阅、工作负载、相关时间和适用计划的假设。安全态势建议与活动威胁警报回答不同问题。关联工作负载证据、身份和应用活动时，不要假定时间接近就证明因果关系。

Copilot 可以帮助汇总事件或起草 KQL，但其输出可能不完整或错误。对照来源记录、标识符、UTC 边界和查询语义，核实每项有影响的论断。[Copilot 能力和局限](https://learn.microsoft.com/en-us/defender-xdr/application-card-copilot-defender)。记录更正和分析人员判断。继续完成[案例](SC-200-cases.md)、[练习册](SC-200-workbook.md)和[可观测性笔记](../../zh/08-observability.md)。所有练习都使用虚构证据；不声称完成部署、实时调查、完整覆盖，也不保证通过考试。
