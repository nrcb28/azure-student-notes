# AZ-700 · 十个案例与推理答案

[指南](AZ-700.md) · [练习册](AZ-700-workbook.md) · [目录](README.md)

以下是原创学习场景，不是官方题或泄露题。展开答案前，先说清要求、排除替代方案并确定证据。没有声称已执行 Azure 操作。

## 1. 校园和新 Azure VNet 都使用 10.70.0.0/16，普通对等互连或 VPN 能让地址不再含糊吗？

<details>
<summary>推理过程</summary>

地址重叠是设计问题，不是少一条放行规则。建立标准对等互连或混合连接前，先清点实际网络，选择不重叠的地址空间。有些场景支持地址转换方案，但会带来限制，必须明确设计。仅凭一个相同私有范围的目标地址，数据包无法表达究竟要去哪里。证据应包含范围清单、修订地址规划和各目标的预期路线。

</details>

## 2. A 与 B、B 与 C 分别对等互连，A 仍到不了 C，应给源 VM 分配 Owner 吗？

<details>
<summary>推理过程</summary>

不应。VNet 对等互连不会自动传递，Azure 管理角色也无法补出缺失网络路径。要决定使用直接连接还是受支持的中转设计，双向核对路由、转发和安全。如果涉及共享网关，检查其具体传输设置，不能假设它转发所有辐射网络流量。有用证据是完整数据包路径和有效下一跳，而不是更广的管理角色。

</details>

## 3. 新默认路由指向防火墙，但去更具体前缀的流量仍走别处，所有用户定义路由都坏了吗？

<details>
<summary>推理过程</summary>

未必。查看全部适用路由与实际目标，不应假设宽泛默认路由会覆盖每一条更具体的路由。按 Azure 路由选择规则比较前缀、来源和有效下一跳，并确认预期路由表已关联源子网。证据要展示竞争前缀和观察到的下一跳。修改安全规则，不能证明最终选中了哪条路线。

</details>

## 4. 请求经过有状态设备，响应却走另一条路，为什么看似允许的连接仍会失败？

<details>
<summary>推理过程</summary>

有状态设备可能需要看到连接的双向流量。不对称路由使回包错过记录原始流的设备，或到达没有匹配状态的另一台设备。应核对去程与回程路由、设备转发和地址转换。验证这个假设前，不要随意增加入站放行。有效交付物是同时包含两条路径的图，以及相关终结点或受支持诊断工具的观察。

</details>

## 5. 存储已关闭公共访问，API 有可用专用终结点却仍解析出公共地址，应先检查什么？

<details>
<summary>推理过程</summary>

先调查 API 客户端真正使用的 DNS 路径：服务器设置、专用区域、VNet 链接和混合转发。继续使用服务主机名，让它为预期专用连接返回适当地址。分配 Storage Blob Data Reader 无法纠正公共 DNS 答案。解析与路由正常后，再单独验证数据授权。分别记录主机名、解析地址、解析器、终结点子资源和后续带身份验证的操作。

</details>

## 6. 要求校园到 Azure 的数据加密，仅购买 ExpressRoute 就满足了吗？

<details>
<summary>推理过程</summary>

没有。ExpressRoute 的专用连接与加密是不同性质，流量默认不加密。明确保护对象和起止边界。MACsec 是 ExpressRoute Direct 链路上的支持选项，不是每条提供商线路都自动可用。合适的 IPsec 设计可以处理端到端要求。比较兼容性、性能并记录密钥运维。专用路径图本身不足以证明加密。

</details>

## 7. 团队要按 DNS 选择区域，却以为所有请求都经过 Traffic Manager，应纠正哪里？

<details>
<summary>推理过程</summary>

Traffic Manager 提供基于 DNS 的终结点选择，不作为请求代理。客户端直接连接选定目标，缓存可能延缓 DNS 变化对它的影响。如果需要全球 HTTP 代理交付，应按要求评估 Azure Front Door；如果需要区域 HTTP 路由，应评估 Application Gateway。把 DNS 交换与应用连接分别画出，并解释健康信息怎样影响选择。

</details>

## 8. 子网启用了服务终结点，为什么不能证明存储账户已在其中拥有专用终结点地址？

<details>
<summary>推理过程</summary>

服务终结点与专用终结点是不同设计。启用服务终结点，不会为存储账户在该子网中创建专用网络接口。应核对实际服务终结点配置、服务网络规则和身份验证方式。如果要求明确需要专用目标地址，就评估受支持的专用终结点及其 DNS 与访问配置。记录解析目标和资源配置，不要因为都叫“终结点”就把两者等同。

</details>

## 9. 新拒绝规则阻止新连接，但已有会话继续运行，NSG 一定忽略了规则吗？

<details>
<summary>推理过程</summary>

不是。NSG 有状态，规则变化不一定立即打断已有流。先区分真正的新连接和复用会话，再检查子网与接口两层有效规则。核对源、目标、端口、协议和优先级，不只看规则名。观察记录要说明测试是否创建新流。扩大角色或删除 VM 都不能解释这种行为。

</details>

## 10. 图上有 ExpressRoute 和备用 VPN，声称应用连接有韧性之前还缺什么证据？

<details>
<summary>推理过程</summary>

识别共享故障域，验证完整备用路径。核对客户设备、提供商、对等位置、网关、路由通告、回程路由、隧道容量、DNS 依赖和应用重连。图上多一条线，不证明故障时流量会正确选择它。提出隔离且获授权的测试，记录预期与观察、恢复和回归正常标准。笔记只提供设计练习，不声称已执行该故障转移。

</details>
