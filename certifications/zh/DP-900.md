## 1. 先问数据需要回答什么问题

在我们的大学笔记应用里，下载文件、办理选课和查看每月活动报告属于不同的工作负载。我会先写清操作，再选产品：哪些记录必须一起改变？结果允许多旧？谁可以读取？保存 PDF 不一定要用数据库，有 JSON 也不代表不能用数据库。

## 2. 数据表示与工作负载要分开判断

结构化数据有明确的排列方式，例如带有列类型的选课表。半结构化数据也有组织，但不要求所有记录拥有相同字段；JSON 文档可以带可选的元数据。就搜索内容而言，扫描的练习页属于非结构化数据，即使文件名遵守统一规则也是如此。

CSV 适合小规模表格交换，但要约定编码、分隔符和缺失值的处理。JSON 能表达嵌套结构。Parquet 按列组织，常适合分析扫描。文件格式本身不提供权限、业务规则或数据质量保证。

事务工作通常是许多范围较小的操作，例如预留名额并一致地更新剩余容量。分析工作则汇总历史，例如比较各课程、各学期的选课人数。一个数据库可以参与两种工作，但重型报告可能抢占线上应用资源。先确定可接受的数据新鲜度，不要没有理由就要求“实时”。

## 3. 关系设计把关联明确写出来

假设有 Students、Courses 和 Enrolments。主键标识一行；数据库实施相应约束时，外键表达关联。Enrolments 连接学生和课程，不必把课程名称复制到每个学生记录。规范化可以减少某些重复和更新异常，但不意味着任何报告都应该采用拆分到极致的结构。

表保存行；视图展示保存的查询，不一定是另一份独立存储的数据。索引提供访问路径，也增加存储和写入成本。存储过程把数据库端操作组织起来。事务在数据库的并发和隔离行为下帮助相关修改保持一致，却无法修复从未写进系统的业务规则。

理解 SELECT、INSERT、UPDATE、DELETE、CREATE 和 GRANT 的用途。执行 UPDATE 或 DELETE 前，先预测影响的行，并用样本数据检查条件。语句成功，也可能改错记录。

## 4. 选择 Azure SQL 的运维模式

Azure SQL Database 是托管数据库服务。Azure SQL Managed Instance 为许多既有 SQL Server 应用提供面向实例的兼容能力。在 Azure VM 上运行 SQL Server 可以访问操作系统，但也把更多管理责任留给团队。查询语法相近，不代表部署、兼容性和维护责任相同。

新笔记应用应该比较所需功能、连接方式、恢复要求、运维投入和负载形态。迁移时先清点依赖：实例级功能和外部组件可能改变目标选择。“托管”不免除访问、架构、应用查询和恢复要求方面的责任。Azure 也有 PostgreSQL 和 MySQL 的托管产品；沿用应用原有引擎，可能比套用 SQL Server 术语更重要。应核对具体产品和支持版本，不能把所有引擎当作可互换的服务。

[来源：Azure SQL 选择](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview)。

## 5. 对象、共享文件和实体各有用途

Blob Storage 保存 PDF、图片等对象。Azure Files 为适用的文件访问需求提供托管文件共享。Table Storage 使用非关系实体模型，并不是关系 SQL 表服务。托管磁盘又属于另一种存储抽象。

笔记应用的一种合理设计是把文件内容放在 Blob，把归属元数据放在数据库。需要说明上传中途失败时两部分如何保持一致。将文件和元数据分开存储，不会自动获得跨服务事务协调。创建存储账户的权限，也不同于读取其中 Blob 的权限。下载令牌属于凭据，不要写进共享笔记。

[来源：存储服务](https://learn.microsoft.com/en-us/azure/storage/common/storage-introduction)。

## 6. 理解文档数据库适合什么场景

Azure Cosmos DB 通过所支持的 API 和数据模型服务于非关系应用场景。文档式记录可能适合字段灵活的课程元数据，不必把每个可选属性都变成关系表中的一列，但这不能证明所有负载都应该放进去。

先看应用的读取、更新、关联、一致性要求和运行限制。拥有类似 SQL 的查询语言，不自动等于关系行为，也不表示可以任意进行关系连接。在基础阶段，应能比较文档、键值实体、对象与关系行。详细应用实现和性能调优不在本单元范围内。

[来源：Cosmos DB 概述](https://learn.microsoft.com/en-us/azure/cosmos-db/overview)。

## 7. 沿着管道追踪数据

批处理处理有界的数据集合，例如昨天的下载记录。流处理处理不断到来的事件，追求有限延迟，但仍要应对重复、迟到和失败。仪表板每秒刷新，不证明所有源事件都已到达。

ETL 在加载到预定目标前转换数据。ELT 先加载，再使用目标端的处理能力进行转换。这两个缩写都不保证数据干净。应定义记录标识、类型、拒绝记录处理和核对规则。统计源事件、接受事件和拒绝事件，解释差异，而不是隐藏差异。编排协调步骤、依赖和失败恢复，它与转换本身不同。

[来源：ETL 和 ELT](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/etl)。

## 8. 从存储走向有用的分析

数据湖可以保存多种数据，留待后续处理；数据仓库把分析数据组织起来，支持一致的查询和报告；湖仓结合两种思路。只有明确所有者、格式、质量和发现方式，一堆文件才会变成可用的数据资源。在星型模型中，事实表记录可度量事件，维度表提供描述背景；添加总计前先确定粒度。

Azure Synapse Analytics 提供分析和集成能力。Microsoft Fabric 在 SaaS 平台中整合多种数据与分析负载。Power BI 支持语义模型、报告和仪表板。它们承担相关但不能互换的角色。画图前先定义“完成的下载”这类度量、时区和刷新边界，否则两张看似正确的报告可能在数不同的东西。

[来源：Fabric 概述](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview)。

## 9. 设计练习与证据

不创建云资源，为 PDF、选课和月度下载报告画一个设计。准备六条合成记录，包含一个重复事件和一个缺少课程标识的记录。为各数据集选择存储，说明可接受的报告延迟，并写清重复和无效记录的处理。写一条示例 SQL 查询，或者在纸上解释预期结果。把设计预测与实际执行观察分开记录。

DBA 关注数据库运行，数据工程师关注数据的移动和整理，分析师通过模型和报告回答问题。职责可以重叠，但每项质量检查都要有负责人。对照[通用数据章节](../../zh/04-storage.md)检查设计，再尝试[十个案例](DP-900-cases.md)，先不要展开答案。
