# AZ-140 · 配置和运营 Microsoft Azure Virtual Desktop

[认证](README.md) · [10 个案例](AZ-140-cases.md) · [练习册](AZ-140-workbook.md) · [西班牙语](../es/AZ-140.md)

我会把 Azure Virtual Desktop（AVD）视为一间大学机房：机器可以更换，而学生仍然保留工作环境。我们的示例向上午的课程提供笔记应用和编程工具包。关键问题是学生能否登录、恢复自己的配置文件并舒适地工作。

## 1. 画出服务方和客户的职责

Microsoft 运营 AVD 连接代理、网关和其他服务组件。我们仍负责会话主机虚拟机、其映像、应用、网络、身份集成、配置文件存储和运营策略。正常工作的控制平面无法修复已耗尽的配置文件共享。

主机池把配置相同的会话主机归组。应用组定义发布的桌面或 RemoteApp 及其用户分配；工作区把已注册的应用组呈现在用户的订阅源中。会话主机是运行会话的虚拟机。诊断订阅源为空之前，先画出这些关系。这些笔记使用 Azure Resource Manager 资源；旧版 AVD 经典模式和传统自主管理的远程桌面服务采用不同的管理模型。

## 2. 有意识地选择池化或个人容量

池化主机池在用户之间共享会话主机；受支持的 Windows Enterprise 多会话映像允许并发会话。个人池根据需求通过自动或直接分配，将独立桌面分配给用户。个人分配与用户的应用组访问授权解决不同问题。

对于可互换使用的学生机房，先评估池化桌面。需要专用机器的研究人员可能有理由使用个人分配。选择虚拟机大小或最大会话数前，先测量具有代表性的 CPU、内存、磁盘、图形和应用行为。“多会话”或虚拟机核心数都不能证明某个学生密度安全。记录所选操作系统和许可证资格；Windows 客户端与 Windows Server 的要求不同。[前提条件](https://learn.microsoft.com/en-us/azure/virtual-desktop/prerequisites)。

## 3. 区分身份、访问授权和会话登录

Microsoft Entra ID 验证对 AVD 的访问身份。受支持的主机配置包括 Entra 加入、AD DS 域加入，以及 Microsoft Entra Domain Services 加入。AD DS 是传统域服务；Entra Domain Services 提供托管域功能；Entra ID 不是域控制器。应根据应用、策略、配置文件存储和身份验证依赖关系选择。

分别追踪订阅源身份验证、应用组分配、主机登录权限和文件访问。Azure 管理角色 Contributor 不会自动授予学生桌面。根据确切客户端、加入类型、身份验证方法和所需服务应用，规划受支持的单一登录和条件访问。第二次密码提示是需要调查的证据，并不能证明条件访问失败。将特权管理与学生访问分开。

## 4. 解释真实网络路径

基本反向连接从客户端和主机向 AVD 服务建立出站 HTTPS/TCP 连接；不需要在会话主机上向公网开放 TCP 3389。检查当前所需终结点、DNS、代理行为和路由。

在支持的情况下，RDP Shortpath 增加 UDP 传输。托管网络侦听器选项需要直接的专用网络可达性及配置好的侦听器，通常使用 UDP 3390。托管或公共网络的 ICE/STUN 选项发现可用路径；TURN 可以中继受支持的公共网络会话。其前提条件不同，因此专用侦听器规则不是通用的 Shortpath 配置。当 UDP 无法建立时，TCP 反向连接仍是后备路径。检查客户端与平台支持和云可用性。比较实际传输、往返延迟、丢包率和主机到配置文件存储的延迟。[Shortpath 要求](https://learn.microsoft.com/en-us/azure/virtual-desktop/configure-rdp-shortpath)；[网络基础](../../zh/05-networking.md)。

## 5. 将持久配置文件放在可替换主机之外

FSLogix 配置文件容器把用户配置文件保存在受支持存储中，而不是依赖某台池化虚拟机的本地磁盘。将笔记应用的权威数据与桌面偏好及缓存分开。配置文件持久化不自动等于应用数据备份。

对于 SMB 存储，同时验证共享级访问和 NTFS 权限。为主机加入方式和存储服务选择受支持的身份与 Kerberos 组合；检查 DNS、票证、时间和加密兼容性。成功登录 Azure 门户不能证明这些条件中的任何一项。根据登录高峰、容量和延迟为存储定容。默认的单容器连接方式不允许任意并发写入者。在配置文件事件发生前，规划断开连接、锁、备份、还原和恢复目标。仅列出多个路径并不能建立复原能力。[FSLogix 配置示例](https://learn.microsoft.com/en-us/fslogix/concepts-configuration-examples)。

## 6. 选择并验证应用交付方式

在基础映像中安装受支持应用很直接，但会把更新与映像生命周期绑定。受管理的安装流程可以单独更新适合的应用。当前的 App Attach 可以从可访问存储交付受支持的包；发布 RemoteApp 控制呈现和访问授权，而打包控制交付。这些是相关决策。

对于笔记编辑器，记录依赖关系、许可、包兼容性、存储访问，以及对主机池和用户的分配。测试首次启动、更新，以及多会话主机上的第二个用户。不要假定每个安装程序都能转成可用包，也不要把旧 MSIX app attach 指南当作当前管理模型。保留经过测试的后备版本。[当前 App Attach 概述](https://learn.microsoft.com/en-us/azure/virtual-desktop/app-attach-overview)。

## 7. 将映像视为版本化发布

构建有文档记录的黄金映像，包含受支持的操作系统、代理、应用、安全设置和更新状态。保留构建输入和映像版本，以便重建机房。Azure Compute Gallery 可以分发版本；规划虚拟机生命周期前，先复习[计算基础](../../zh/03-compute.md)。

先向小型验证组引入新版本。测试身份验证、配置文件附加、笔记编辑、所需的打印或重定向，以及会话性能。让旧主机进入排空模式以阻止新会话，同时根据维护策略处理现有会话；排空模式不会立刻注销所有人。逐步替换主机。保留旧映像和考虑容量的回滚路径。同时为所有运行中的主机打补丁，会使课堂共同依赖的系统变得脆弱。

## 8. 让缩放适应课表

缩放计划利用日程和容量设置来控制受支持的自动缩放行为。区分现有主机电源管理与动态创建或删除主机，后者的主机池前提条件及可用性必须核实。Start VM on Connect 会在用户连接时启动符合条件的已停止主机；它不是完整的课表或备用容量策略。

对于 48 名同时使用的学生，若测得每台主机限制为 12 个会话，四台可用主机能够满足需求，但没有故障余量。在这些假设下，五台可以提供一台主机的故障余量。建模启动时间、不健康主机、排空状态和存储限制。缩减容量前明确服务权限、排除处理和活动会话策略。节省预测除了虚拟机运行时间，还应包含磁盘、存储、网络、监测和许可。[缩放计划要求](https://learn.microsoft.com/en-us/azure/virtual-desktop/autoscale-create-assign-scaling-plan)。

## 9. 沿证据追踪一次失败连接

记录 UTC 时间、用户假名标识符、客户端版本、资源、会话主机和连接关联 ID。把连接、检查点、错误、代理运行状况及相关网络记录，与主机性能和 FSLogix 日志关联。应先启用适当诊断设置和主机收集，再期待历史证据。AVD Insights 有助于调查用户体验；其数据收集仍需要配置。

区分订阅源缺失、主机登录失败、配置文件附加缓慢，以及登录后应用迟缓。缺少 AVD 连接记录，可能意味着尝试从未到达服务。与同一时间成功的学生会话比较，避免收集笔记内容或凭据。[诊断类别和关联](https://learn.microsoft.com/en-us/azure/virtual-desktop/diagnostics-log-analytics)。

## 10. 不部署资源也能演练恢复

针对早晨登录高峰、一台不可用主机和无法访问的配置文件共享，开展离线桌面推演。写下预测、确认每项假设所需的证据、负责操作人员、回滚条件和明确恢复标准。仅恢复虚拟机不能恢复身份、DNS、应用包、配置文件访问或笔记 API。

分别约定配置文件和应用数据的恢复时间目标及恢复点目标。包括备用区域依赖关系、配置文件一致性、可用虚拟机容量和返回主区域的步骤。记录谁负责每项持续成本，以及谁响应警报。完成[十个案例](AZ-140-cases.md)和[五个练习单元](AZ-140-workbook.md)。这些练习不更改租户，也不声称已进行 Azure 部署或测试过故障转移。
