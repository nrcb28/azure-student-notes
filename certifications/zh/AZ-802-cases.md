# AZ-802 · 10 个案例与推理答案

[指南](AZ-802.md) · [五单元练习册](AZ-802-workbook.md) · [目录](README.md)

这些是原创大学实验场景，不是官方试题。打开答案前，先提出假设、另一种解释和所需证据。这里提到的命令是供获授权 Windows 实验使用的拟议检查，并不宣称已执行或完成生产恢复。每个问题都包含完整场景，让训练器和 Anki 导出保留其上下文。

## 1. 教室网络更改后，域客户端能解析公用网站，却找不到域控制器。其解析器是公用 DNS 服务；配置中的 AD DNS 服务器可达，且已知 SRV 记录健康。客户端时间正确。第一项修复应该是重置所有学生的密码吗？

<details>
<summary>答案</summary>

不应该。所给证据首先指向客户端的名称解析路径。公用 DNS 成功并不能证明可以发现私有 AD 服务记录。记录客户端解析器、相关 SRV 查询及结果，再将这条路径与获批的实验 DNS 配置比较。适当修正应恢复预期的、能解析 AD 的解析器路径，并在扩大更改前验证发现、控制器可达性以及受影响的登录。

服务器健康、时间正确这些假设缩小了本次调查范围，并不意味着现实中每次登录失败都是 DNS 问题。如果发现成功而身份验证仍失败，应继续检查准确错误、账户状态、协议和安全通道证据。保留带时间戳和实际选中控制器的前后记录。重置全部密码会更改无关状态，无法解决已识别的解析器不匹配，还可能掩盖有用证据。若获批更改破坏其他必要解析，回退应恢复已记录的客户端配置，而不是留下尚未理解其行为的公用与私有解析器组合。

</details>

## 2. 研究组成员身份更改在 LAB-DC1 可见，但远端楼宇的控制器尚不可见。那里的客户端使用第二台控制器，复制报告 DNS 相关失败，新共享也无法访问。把用户加入另一个特权组是适当修复吗？

<details>
<summary>答案</summary>

不是。观察到的目录版本差异和复制失败，提供了在扩大权限前应先调查的具体解释。记录更改时间、接受更改的控制器、客户端选中的控制器和复制错误。检查复制伙伴的 DNS 记录、配置的解析器、连接和身份验证前提条件。核实远端子网是否映射到预期站点，但不要假定更改站点计划就能修复 DNS 失败。

执行受支持修复后，确认该成员身份更改已经到达相关控制器。随后获取合适的新用户登录或会话令牌，并以该用户身份测试预期共享；目录收敛和授权上下文刷新是两项独立检查。如果访问仍失败，还应检查共享和文件系统权限。保持组权限有限，同时记录允许与拒绝测试。加入无关特权组，可能在复制仍损坏、学生访问范围被扩大的同时掩盖症状。交付物应是更改收敛和访问时间线；在实验真正给出观察之前，预测应明确标为预测。

</details>

## 3. 一个隔离的分校教室计划使用 RODC。有人建议允许在那里缓存大学特权管理员的密码，以便 WAN 中断时登录。房间的物理保护弱于主数据中心。设计审查应该要求什么？

<details>
<summary>答案</summary>

否定“只要是 RODC，缓存任何凭据都安全”的假设。审查其密码复制策略、有效的允许与拒绝成员关系、委派管理和设备丢失流程。特权账户应排除在该分支凭据缓存之外。如果某账户在有效策略中同时被允许和拒绝，拒绝优先。确定确实需要断网访问的少量普通账户，并检查最终有效策略，不要仅凭组名判断。

计划应区分缓存用户身份验证与需要可写控制器的操作，后者包括新的或更改后的目录状态。定义 WAN 中断期间哪些服务仍可用，以及操作人员如何在不削弱域边界的情况下获得批准的管理路径。证据包括分支威胁假设、选定账户、有效缓存决策、控制器连接和设备丢失响应。不要把密码或缓存内容作为证据公开。恢复计划必须考虑受影响的缓存凭据和被攻破的服务器，不能只替换硬件，就假定所有目录机密始终受保护。

</details>

## 4. 一台已连接 Azure Arc 的服务器，仍无法完成从服务器 B 到文件服务器 C 的远程作业。有人提出广泛委派凭据，并在域控制器上使用默认 JEA 虚拟账户，但任务只需要一项有限的服务操作。Arc 连接能证明这种设计合理吗？

<details>
<summary>答案</summary>

不能。Arc 连接创建 Azure 管理关系，并不会让服务器加入 AD、创建林信任，或自动把交互操作人员的凭据委派给 C。画出第一和第二跃点、每一跳的协议、有效身份及所需的具体操作。诊断失败发生在哪个授权或身份验证边界。第一个会话成功，并不能证明第二项资源会接受预期身份。

选择方法前，审查受支持的第二跃点方案及其限制。CredSSP 增加凭据暴露；约束委派方法不能普遍解决 WinRM 到 WinRM 的第二跃点。对于 JEA，一起检查会话执行身份、允许用户、命令、参数和审核记录。DC 上的默认虚拟账户可能具有 Domain Admin 权限，与有限服务任务并不相称。优先选择合适的管理位置和明确受限的执行权限。证据应是权限与跃点图，以及允许和拒绝的操作，而不是使用可重复利用的管理员凭据执行成功的命令。Arc 管理控制器上的扩展权限，也需要单独审查。

</details>

## 5. 实验 VM 使用 Production 检查点，但来宾一致性处理失败，主机创建了 Standard 检查点。学生称其为独立的应用一致性备份。检查点与 VM 磁盘位于同一存储。需要纠正什么？

<details>
<summary>答案</summary>

应同时纠正一致性判断和保护边界。Production 模式可以允许回退到 Standard 检查点，所以请求的设置不如实际检查点类型和来宾处理结果有说服力。如果练习必须使用生产检查点且拒绝回退，应评估 ProductionOnly，并修复来宾集成、VSS 或相关文件系统冻结的前提条件。无法创建所需检查点，是有用的失败证据；默默接受另一种类型并不等价。

即使生产检查点成功，也不能证明存在独立且保留的备份。其磁盘链可能随 VM 存储一起丢失，应用恢复仍需要受支持的一致性与还原方法。要求需要时，应保留具有适当保留期和还原验证计划的受保护备份。使用受支持工具检查检查点元数据和存储余量，不要手动删除 AVHDX 文件。分别说明目标是撤销可丢弃实验中的更改、抵御主机或存储丢失，还是恢复到较早的有效应用状态。每个目标需要不同证据，也可能需要不同机制。

</details>

## 6. 现有教室 PC 继续工作，但新客户端无法获得地址。获授权 DHCP 服务器可通过正常中继到达，受影响作用域没有空闲租约。第二台服务器已经安装，但未建立故障转移关系。调查应该得出什么结论？

<details>
<summary>答案</summary>

所给证据表明，作用域耗尽是新分配失败的直接原因。现有客户端能按其租约状态继续使用，因此它们成功并不能证明服务器还能分配新地址。提出获批的容量修正前，应检查作用域范围、排除项、保留、活动租约和实际客户端子网。检查过期或异常分配模式，但不要不加区分地删除租约，也不要扩展到重叠地址范围。

安装第二台服务器不会自动协调租约。如果需要可用性，应为目标作用域设计受支持的 DHCP 故障转移关系，理解模式、伙伴状态、租约行为和恢复责任。不要启用同一范围内相互竞争、未经协调的副本。证据包括作用域清单、可用地址数、中继路径，以及同时涉及真正新客户端和现有客户端的测试。容量和故障转移解决不同故障条件：伙伴关系健康，并不意味着可以忽略过小的地址池。记录更改前的作用域；如果拟议范围与路由或另一分配管理方冲突，就停止。

</details>

## 7. 学生具有预期 SMB 共享权限，但 NTFS 拒绝访问项目文件夹。Azure File Sync 健康，其服务器终结点存在分层文件。授予 Azure Contributor，并把同步副本称为备份，能同时解决两个问题吗？

<details>
<summary>答案</summary>

不能。沿实际 Windows 文件路径和身份检查。即使已有共享级访问权，已确认的 NTFS 拒绝仍然有效。在保持适当组成员关系和隔离的前提下，修正预期文件夹授权，再测试受影响学生和必须继续被拒绝的学生。Azure 资源管理角色不会自动修复文件系统 ACL，也不会确立 SMB 数据访问。应检查有效访问，不能从单个配置条目推断结果。

恢复问题应单独处理。健康同步也可能传播删除，分层服务器文件可能不包含完整、独立的本地副本。确定云终结点、可用的保留备份、还原依赖和受支持恢复工作流。从操作系统映像或 VM 检查点回退、克隆已注册 File Sync 服务器，并不是通用的受支持恢复方法。证据应包括共享与 NTFS 决策、终结点和分层状态，以及历史恢复点计划。今天恢复访问和以后出错后能够恢复数据，是两种不同结果；没有各自对应的测试或明确标为设计证据的材料，就不能声称已经实现。

</details>

## 8. 服务器群混有 Windows Server 2022 和 2025。加固方案将 Windows Server 2025 的 OSConfig 基线应用到所有机器，并承诺移除管理就能恢复每一项旧设置，还把获取到的 LAPS 密码存进共享报告。必须改变什么？

<details>
<summary>答案</summary>

区分支持范围、更改恢复和机密处理。本次核对的 OSConfig 基线指南针对 Windows Server 2025，因此不能把相同配置描述为在 2022 机器上也受支持。记录操作系统与模块版本、按角色选择的设置和试点组。识别可能冲突的现有 GPO 或其他管理，检查有效设置，并规划必要的重启和访问验证。移除基线不能保证重建管理前存在的每一个值；应保留经过审查的原状态和恢复流程。

LAPS 支持受控密码轮换、备份和授权获取。把获取的密码复制到广泛可读的报告，会破坏这一访问边界。通过适当的事件或更改流程将其移除，按策略处理暴露，并在要求时轮换；公开的应只有去除敏感内容的策略和授权证据。恢复凭据需要受保护的访问路径，而且在预期故障期间仍可使用。证据应展示受支持部署、允许与拒绝获取的角色、经过审核的访问和恢复计划，而不是明文凭据，或被误认为能证明全部保护的合规截图。

</details>

## 9. Arc 服务器显示已连接，工作区也有最近的代理 Heartbeat 行，但缺少所需 Windows System 事件。这些事件在本地存在。空查询能证明 Windows 没有产生故障吗？

<details>
<summary>答案</summary>

不能。场景已经说明相关事件在本地存在。Arc 连通和代理 Heartbeat，与选定事件源成功送达是不同观察。确认目标机器、时间窗口、工作区和目标表，然后检查 AMA 扩展与服务状态、关联的 DCR、其事件选择和目标，以及代理实际收到的配置。只创建 DCR 并不会启动该机器的数据收集，还必须建立相应关联。

使用已遮盖敏感信息的本地事件标识符和时间戳，沿拟议管道追踪一个事件。区分源中不存在、收集失败、传输或配置问题，以及查询指向错误目标。将事件时间与采集到达时间分开，考虑文档说明的引入延迟，但不要把所有延迟都视为可接受。证据包括本地记录、机器身份、关联和查询上下文，以及随后进行的预期到达测试。不要一开始就重新安装所有代理：这会改变状态，可能抹去有用的排错上下文，却没有解决缺失的选择或关联。

</details>

## 10. 学生删除了重要 AD 对象，随后发现删除前未启用回收站。他们建议把生产域控制器回退到普通 VM 检查点，并强占全部 FSMO 角色。组织有受支持的目录备份和指定恢复负责人。更安全的决策过程是什么？

<details>
<summary>答案</summary>

升级到文档规定的目录恢复流程，并保留删除、复制和备份证据。事后启用回收站，不会凭空创建缺失的先前可恢复状态。选择恢复方法前，确定受影响对象和依赖、可用且受支持的备份，以及还原范围。单个对象误操作本身，不足以支持全林恢复或强占无关 FSMO 角色。

恢复负责人应选择适合实际故障、受支持的权威或非权威还原步骤，包括必要时的 DSRM 环境、受保护恢复凭据和 SYSVOL 考虑。普通 VM 检查点回退不能替代该计划。记录权威状态、复制影响、验证，以及确实需要强占时原角色持有者能够返回的条件。验证目录对象、身份验证、复制和受影响服务，不要停留在“VM 能启动”。在本仓库中，交付物是具有明确决策关口的桌面推演；没有执行目录还原、角色强占或实际恢复测量。

</details>
