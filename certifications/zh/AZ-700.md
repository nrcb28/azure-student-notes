## 1. 创建网络前先规划地址

先清点校园、Azure、合作方和未来网络的地址范围。私有地址重叠会给对等互连与混合路由带来困难；使用 RFC 1918 地址，不代表它在整个组织内天然唯一。

例如项目预留 10.70.0.0/16，Web 使用 10.70.1.0/24，数据层使用 10.70.2.0/24。一个 /24 有 256 个 IPv4 地址；普通 Azure 子网保留其中五个，所以可分配 251 个。仍要遵守服务专属要求。委派子网、网关或防火墙可能要求特定名称、大小、独占使用或委派配置。分配剩余空间前先核对。

为每个边界写出理由：生命周期、路由、信任、服务要求或增长。多画一个子网，不会自动形成有效执行的安全边界。

## 2. 有目的地连接网络

VNet 对等互连连接兼容且不重叠的网络，不会合并它们的所有权或安全控制。A 与 B 对等互连、B 与 C 对等互连，并不让 A 自动到达 C。每条必要路径都要画清楚。

中心网络可以承载共享连接与检查，但中心辐射图本身不是中转配置。要核对对等设置、转发流量、路由表，以及实际承载流量的设备或网关。网关传输允许在兼容设置下共享网关，不代表自动转发所有辐射网络之间的流量。[对等互连参考](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)。

## 3. 双向读取有效路由

路由选择下一跳，不授予应用访问权。确定源子网、目标地址、匹配前缀、路由来源和实际有效下一跳。不要假设宽泛的 0.0.0.0/0 用户定义路由会覆盖所有更具体的路由。

引入网络虚拟设备时，核对转发配置、支持的拓扑、容量和返回路径。请求可能经过一个有状态防火墙，响应却走另一条路；即使各子网单独看都能到达，这种不对称也可能使连接失败。增加例外前，先记录两个方向的路线。[Azure 路由](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-udr-overview)。

## 4. 把 DNS 当作连接的一部分

向真正的客户端确认服务主机名解析成哪个地址。如果客户端仍选择不可达的公共目标，已有专用终结点也无济于事。

记录专用区域、VNet 链接、DNS 服务器设置和校园与 Azure 间的转发。Azure DNS Private Resolver 可参与所支持的混合解析设计，但入站和出站行为要分别画出。继续使用服务主机名，保证证书验证和服务路由正确。不要用永久公共 IP 条目掩盖 DNS 错误。解析成功也不能证明服务接受调用者身份。[专用终结点 DNS](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns)。

## 5. 比较混合路径与故障域

站点到站点 VPN 通常通过互联网提供 IPsec 隧道。ExpressRoute 通过支持的连接安排提供专用连接。专用连接**不等于**流量自动加密。

按所需保护边界选择加密。MACsec 适用于受支持的 ExpressRoute Direct 物理链路；IPsec 设计可以保护端到端连接。要核对吞吐量和运维影响，而不是把两者看作没有成本的标签。

为韧性列出可能一起失效的线路、地点、提供商、网关、客户设备和路由。备用 VPN 需要正确的路由通告、返回路线、足够容量，以及应用恢复验证。图上两条连接仍可能共享一个故障域。[ExpressRoute 加密](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-about-encryption)。

## 6. 按协议与范围选择应用交付

| 需求 | 值得评估的候选服务 |
|---|---|
| 分配 TCP/UDP 流 | Azure Load Balancer |
| 区域 HTTP 路由、TLS 处理或 WAF | Application Gateway |
| 全球 HTTP 应用交付与加速 | Azure Front Door |
| 基于 DNS 选择终结点 | Traffic Manager |

这只是起点，不是互斥功能矩阵。Application Gateway 也有受支持的 TCP/TLS 能力；应核对当前功能与配置，不能断言它只处理 HTTP。Traffic Manager 回答 DNS 查询，不代理每一次用户请求；DNS 缓存会影响目标切换速度。

对任意候选，都要说明前端、后端、协议、探测、证书处理和故障行为。探测健康时，文档下载仍可能返回错误内容。[交付服务比较](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/load-balancing-overview)。

## 7. 区分两种服务访问方式

专用终结点为受支持服务在 VNet 中提供专用网络接口地址。服务终结点按服务自身的终结点模型识别并保护受支持子网到服务的访问；它不会把服务的公共终结点变成子网中的专用地址。

对存储要分别检查终结点批准状态、服务子资源、DNS、网络限制与数据授权。增加专用终结点，不会自动关闭所有公共访问。私有路径也不赋予读取容器的权限。应同时写明预期网络路径和获准身份。

## 8. 控制措施要对应具体问题

NSG 按优先级和有状态行为过滤适用网络流量。要一起查看子网与接口规则；修改规则未必立即终止所有已有连接。Azure Firewall 可集中处理受支持的网络或应用过滤与地址转换。WAF 检查受支持的 Web 流量，不能替代整体路由设计。DDoS 防护处理可用性威胁，不负责用户授权。

使用精确假设：“这条规则拒绝新的 TCP 443 流量”比“安全坏了”更有用。不要习惯性地用宽泛放行规则诊断。

## 9. 按有用的顺序收集证据

依次检查主机名解析、选定目标、有效下一跳、适用过滤、监听进程、TLS 和应用权限。按资源选择合适的 Network Watcher 能力：下一跳分析、IP 流验证、有效规则、连接故障排除或数据包捕获。它们的前提和范围不同。

一次数据包允许预测，不证明带身份验证的请求会成功。保留源、目标、协议、端口、时间戳、观察和下一个假设。Network Watcher 不能普遍替代 PaaS 或应用遥测。[诊断工具](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview)。

## 10. 不部署也能练习追踪数据包

画出校园、中心网络、Web 辐射网络和专用存储。为正常运行、DNS 失败和主链路失败建立表格，分别记录去程、回程、执行控制的位置、预期观察和一项确认测试。排除一个看似合理但不合适的修复方案。

再检查已有的[网络实验](network-lab.md)。其中的 VNet 与 NSG 配置不包含你设计里的网关或运行负载。将设计预测与实际观察分开。这些新练习没有在 Azure 部署；真实部署需要合适的测试订阅、权限、服务检查和清理。
