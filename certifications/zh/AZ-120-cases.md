# AZ-120 · 10 个案例与推理答案

[指南](AZ-120.md) · [练习册](AZ-120-workbook.md) · [目录](README.md)

原创大学企业场景，并非官方试题。展开答案前，解释决策与证据。所有检查建议都是离线设计，不宣称执行过 Azure 或 SAP。

## 1. 大学增加两台应用服务器，却保留一台 ASCS VM 和一台 HANA VM，是否消除了重要单点故障？

<details>
<summary>答案</summary>

没有。应用服务器冗余不保护中央服务或数据库。清点每个 SID，区分 ASCS、ERS、应用实例、HANA、共享文件及依赖。为中央服务和数据库提出受支持高可用设计，明确归属与客户端重连路径。证据应包含依赖图和各组件失效的预期影响，也要确认故障后应用容量。数 VM 不能证明采购事务能够承受协调或数据服务丢失。

</details>

## 2. 更便宜的 VM 与拟议 HANA VM 核数相同，这足以支持替换吗？

<details>
<summary>答案</summary>

不够。针对准确 VM 类型、工作负载、操作系统版本、数据库版本和部署模型检查 SAP HANA 认证。比较实测内存需求、增长、应用层适用 SAPS、存储吞吐量、日志延迟和网络限制，也要检查区域容量与配额。证据是受支持组合记录和带故障余量的规模表，不是 CPU 对比。较低基础设施估算不能决定可支持性，这些笔记也不能证明大学拥有 SAP 许可或生产容量足够。

</details>

## 3. 校园网络团队说 ExpressRoute 会加密每条 SAP 连接，架构记录应接受这个说法吗？

<details>
<summary>答案</summary>

不应。专用连接和加密是不同属性。画出校园到 Azure 路径、提供商交接、Azure 路由、应用终结点及选定加密边界。策略有要求时，规定受支持应用加密或其他适当安排，并核对服务具体能力。同时记录 DNS、认证依赖、路由韧性和允许流量。证据应说明哪些流量加密、保护从哪里开始和结束，以及如何核验。专用线路本身不能证明所有协议端到端保密。

</details>

## 4. 学生把两个高可用节点放进同一 PPG，并声称还能抵御可用区故障，推理应怎样改？

<details>
<summary>答案</summary>

区分为延迟共址与为韧性隔离。PPG 限制物理邻近，不提供跨可用区故障隔离。按恢复要求选择受支持可用性放置，再评估实际节点延迟和复制行为。确有依据使用 PPG 时，要遵循适当放置约束并记录分配限制。证据包括故障域图、实测或明确假设延迟、剩余容量和接管顺序。PPG 或可用区本身都不会配置安全 SAP 集群或数据库故障转移。

</details>

## 5. HANA 磁盘空闲很多，但保存点期间采购变慢，是否只需增加磁盘容量？

<details>
<summary>答案</summary>

调查数据与日志的吞吐量、延迟、排队和 VM 汇总 I/O 上限。即使空间充足，保存点流量仍可能与日志写入竞争。选择变更前，审查受支持布局、文件系统、磁盘配置、共享卷需求和负载时序。缓存与 Write Accelerator 必须遵循具体卷及存储指导，不能套用通用性能配方。证据是关联负载与 I/O 时间线及拟议受支持配置。授权测试真正提供测量前，应将它们标为待收集证据。

</details>

## 6. 通信故障后集群无法隔离对端节点，禁用 fencing 能恢复安全服务吗？

<details>
<summary>答案</summary>

不能。取消 fencing 可能允许冲突主节点，损坏数据完整性。保留证据并按事故流程处理，同时调查仲裁、节点通信、隔离代理权限与连接，或选定受支持 SBD 配置。接管前确认所谓失败节点不能继续独立写入。证据包括集群状态、时间戳、隔离结果、复制状态和明确权威主节点。修复设计应恢复受支持隔离与决策。资源显示已启动，不足以证明 SAP 服务能够安全接受写入。

</details>

## 7. 一次错误财务更新已经到达两个 HANA 副本，昨天受保护的备份为何仍有价值？

<details>
<summary>答案</summary>

复制维护可用性，也会复制逻辑错误。受保护备份与可用日志链可按受支持恢复流程回到错误前的可接受时间点。确定业务批准 RPO、恢复依赖、保留，以及需对账的后续合法事务。确认应用一致性，普通 VM 快照不会自动足够。证据应包含恢复点选择、备份与日志可用性、隔离恢复计划、数据库检查和业务验证。两个副本都收到错误后，仅有复制成功无法恢复历史正确性。

</details>

## 8. 切换通过基础检查后，用户创建新采购订单，回退能否直接把 DNS 指回未变更的源？

<details>
<summary>答案</summary>

这样会丢弃或分叉新事务。目标开始写入后，运行手册需要独立决策：再次冻结写入、确定权威数据集、保存新事务，并评估受支持对账或反向迁移。包括业务批准、接口队列、最终同步、源隔离，以及重新开放任一端之前的验证。证据是写入归属时间线和明确数据处理决定，而非仅有 DNS 步骤。演练应区分重新开放写入前的回退与之后的恢复，并明确期限和各关口操作人。

</details>

## 9. 研究门户无法连接 SAP RISE，操作员应该用大学 Azure 角色修改 SAP 订阅中的 NSG 吗？

<details>
<summary>答案</summary>

先尊重合同责任矩阵。SAP 在自己的 Azure 环境管理 RISE，大学订阅角色不授予这些资源的控制权。跟踪门户 DNS、路由、对等互连或连接、防火墙、身份和约定 SAP 接口，为各检查分配正确负责人。通过 SAP 协调 SAP 侧变更与升级处理。证据应包含失败交接点和双方责任。RISE 不会免除客户对自身集成服务、安全配置和通往可用接口网络路径的责任。

</details>

## 10. 灾备区域有当前数据库副本和运行中的 VM，采购却不可用，桌面演练还应验证什么？

<details>
<summary>答案</summary>

验证中央服务、应用启动顺序、身份、DNS、虚拟名称、路由、秘密、共享文件、集成终结点和足够受支持容量。将可用恢复点和预计恢复时间与业务 RPO、RTO 比较。防止原主节点独立接受写入。用成功采购流程与接口交换定义验收，再安排受控返回主区域。证据包括负责人、依赖顺序、复制状态、预计时间和验证标准。运行基础设施只是恢复完整大学 SAP 服务的一部分。

</details>
