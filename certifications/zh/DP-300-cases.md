# DP-300 · 十个案例与推理答案

[指南](DP-300.md) · [练习册](DP-300-workbook.md) · [目录](README.md)

原创练习，不是官方题。展开答案前先找出约束、提出决定并描述需收集的证据。这些案例不声称已经执行 Azure，也不覆盖全部考试范围。

## 1. 应用需要受支持的操作系统级扩展，能因为 SQL Database 支持 T-SQL 就选它吗？

<details>
<summary>推理过程</summary>

不能。操作系统要求改变了托管边界。先确认扩展是否必要，以及是否有受支持的托管服务替代方案。如果仍必须直接控制操作系统，应评估 VM 上的 SQL Server，并纳入补丁、备份、监控与可用性责任。兼容评估既要看 T-SQL，也要看数据库对象外的依赖。先验证真实应用要求；熟悉 SQL 语法不能证明部署兼容。

</details>

## 2. 数据迁移成功完成，可以马上恢复写入吗？

<details>
<summary>推理过程</summary>

传输完成只是一个检查点。应核验最终数据状态、重要业务总数、权限、应用路径和计划任务。确认源端何时停止写入，以及剩余变化是否已应用。恢复流量前明确目标为权威数据源。回滚方案必须处理切换后目标产生的写入，否则重新连接源端可能丢弃它们。使用明确的允许或禁止上线清单，区分观察过的检查和假设。

</details>

## 3. 应用能解析专用 SQL 地址并建立连接，但 SELECT 被拒，应继续开放网络吗？

<details>
<summary>推理过程</summary>

连接成功而语句被拒，更指向数据库授权，而不是普遍网络中断。确认身份验证主体、数据库、对象和操作。检查适用数据库权限，通过选定访问模型授予最小必要能力。Azure Contributor 分配不会自动提供表级读取。开放公共终结点只会扩大暴露，不会补足缺失权限。用相同身份重复同一个应用操作来验证诊断。

</details>

## 4. 要求数据库管理员不能看到某些明文值，仅使用 TDE 够吗？

<details>
<summary>推理过程</summary>

TDE 保护静态数据库文件，本身不会阻止获授权查询返回明文。应考察 Always Encrypted 这类方案，使用支持的客户端，并把密钥放在数据库管理员访问边界之外。核对所需查询操作、应用兼容性、密钥恢复和运维归属。动态掩码不是等价的保密边界。应以获允许的合成数据测试验证威胁模型，不能把名称中带“加密”的功能当作可互换。

</details>

## 5. 发布后某查询变慢，整体 CPU 却正常，先收集什么证据？

<details>
<summary>推理过程</summary>

识别查询，利用可用 Query Store 历史，在可比较时段对照计划和运行行为。检查应用参数、读取量、等待、阻塞以及近期架构或统计变化。整体 CPU 正常，不证明单个事务健康。修改服务规格前先提出具体假设。如果试用旧计划，定义成功标准和撤销路径，再监控代表性流量；单次快速执行不足以证明持续改善。

</details>

## 6. 新索引加快读取，却让导入慢很多，这个索引一定成功了吗？

<details>
<summary>推理过程</summary>

没有。数据改变时也要维护索引，因此必须评估整个负载的收益。比较修改前后的代表性读写延迟、吞吐量、存储和计划。检查是否与现有索引重叠，以及更窄或不同列顺序是否能满足要求。为导入和查找都规定验收阈值，不能只因演示查询更快就保留修改。

</details>

## 7. 长事务阻塞短查询，应该终止每个被阻塞的会话吗？

<details>
<summary>推理过程</summary>

决定中断前先找阻塞链和持有相关锁的事务。被阻塞会话通常是症状，不是来源。识别工作内容、事务持续时间、负责人和回滚后果。终止事务可能需要很长回滚时间，也会影响应用正确性。理解一致性要求后，可在受控调查中考虑缩短事务或合适的隔离策略。记录证据与事件决定，不要运行无差别终止脚本。

</details>

## 8. SQL Agent 作业要迁到 Azure SQL Database，只复制调度时间就可以吗？

<details>
<summary>推理过程</summary>

Azure SQL Database 没有 SQL Agent。先分类任务：跨数据库且受支持的 T-SQL 工作可能适合 Elastic Jobs；涉及外部服务的流程可能需要编排。应评估依赖、身份、目标发现、重试与通知，而不是只复制时间表达式。响应不确定时，重复执行不应产生重复业务输出。用隔离合成数据测试替代方案，同时比较执行记录和最终业务状态。

</details>

## 9. 意外 DELETE 同步到了辅助数据库，是复制失败了吗？

<details>
<summary>推理过程</summary>

复制可能正按配置工作，把合法提交的修改传到另一副本。可用性与历史恢复解决不同问题。确定事件时间和保留的恢复点，再计划还原到破坏性修改前的隔离数据库。选择恢复服务的方法前，要核对缺失记录和后续合法记录。不能假设用旧状态整体替换就可接受；恢复决定必须考虑之后产生的有效写入。

</details>

## 10. 数据库已经故障转移，笔记应用仍失败，RTO 目标达到了吗？

<details>
<summary>推理过程</summary>

如果目标是恢复面向用户的服务，就没有达到。应检查受支持的应用终结点、客户端 DNS、重连行为、身份、依赖和当前主库上的计划操作。用合成记录做功能检查，并从已定义起始事件测量恢复耗时。数据损失应单独与 RPO 比较。故障回复前明确权威副本和同步计划。数据库状态健康，不能独自证明应用和恢复目标已恢复。

</details>
