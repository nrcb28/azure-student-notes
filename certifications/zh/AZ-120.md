# AZ-120 · 规划和管理 Azure 上的 SAP 工作负载

我会以加入大学企业 SAP 团队的基础设施学生视角学习这项专项认证。虚构大学使用 SAP 处理采购和财务，并连接研究门户。我们设计 Azure 平台和恢复流程，不配置 SAP 业务流程。

## 1. 画虚拟机前先清点系统环境

记录每个 SAP 系统标识符（SID）、环境、版本、操作系统、数据库、接口、依赖和负责人。区分应用服务器、ABAP SAP Central Services（ASCS）、Enqueue Replication Server（ERS）、Java Central Services（SCS）和 HANA。ASCS 协调消息与排队锁服务，ERS 支持锁复制。增加应用服务器不会自动保护中央服务或数据库。

映射校园身份、DNS、时间同步、传输目录、批作业、打印机和研究门户连接。分配 Azure 基础设施、操作系统、SAP Basis、数据库、安全和业务验证责任。缺少这些边界，基础设施图就无法说明谁批准迁移、谁验证采购。参见[受支持配置](https://learn.microsoft.com/en-us/azure/sap/workloads/planning-supported-configurations)。

## 2. 为受支持的组合确定规模

仅凭 CPU 数量不能选择 SAP VM。核对具体工作负载、VM 系列、操作系统版本、数据库版本、存储和部署拓扑的认证与支持。SAP HANA 硬件认证存在特定工作负载条件；适用于应用层的 VM 不一定是经过认证的 HANA 目标。

使用 SAP 规模评估结果、适用的 SAP Application Performance Standard（SAPS）要求、实测峰值、HANA 内存需求、增长和故障余量。评估磁盘能力时，同时检查 VM 级存储吞吐量与网络限制。检查区域容量、配额和支持安排。与负责人记录许可要求；这些笔记不提供 SAP 许可证或使用权。交付物应是有理由的容量假设，不能声称某个固定 SKU 普遍足够。

## 3. 建立登陆区域与直接网络路径

通过适当订阅和资源组层级、最小权限角色、策略与特权管理，分离生产和非生产访问。跟踪用户、管理、集成、复制和备份流量。应用与数据库层须使用受支持网络安排；不能为了复用通用架构图，就在 SAP 内核的应用到数据库路径中插入网络设备。

规定 DNS 转发、名称归属、防火墙规则、路由和依赖可达性。ExpressRoute 提供专用连接，不自动提供端到端加密；有要求时应明确选择加密控制。验证 Accelerated Networking 支持与配置。ping 成功不能证明采购事务的延迟或身份验证路径。参见[部署规划](https://learn.microsoft.com/en-us/azure/sap/workloads/planning-guide)。

## 4. 平衡放置、延迟与故障隔离

可用性区域隔离基础设施故障域，可用性集解决另一类放置问题。二者都不会自行创建应用故障转移。针对真实区域、可用区、VM 类型和负载测量延迟，包括同步复制。拓扑必须同时满足响应时间与恢复要求。

邻近放置组（PPG）通过限制共址，在有依据时改善延迟。单个 PPG 不会把共址保证延伸到多个可用区，也不能代替可用区隔离。额外约束可能增加容量分配和调整大小难度。以受支持放置指导为起点，只有证据表明需要时才加入 PPG，并记录降级运行。对大学案例，解释一个可用区失效后，剩余应用容量和数据库接管会怎样。

## 5. 将 HANA 存储视为延迟设计

分别规划 `/hana/data`、`/hana/log` 和 `/hana/shared`，采用受支持文件系统与存储布局。数据加载和保存点需要吞吐量；事务日志写入需要低延迟；共享文件也影响启动与集群健康。仅有多少 TB 容量无法证明这些特性。

核对所选存储类型的 VM 兼容性、限制、条带化或数据卷分区指导，以及副本一致配置要求。主机缓存与 Write Accelerator 设置取决于具体磁盘、VM 和卷角色，不能把同一缓存策略复制到所有卷。明确备份位置和临时存储责任。记录各磁盘与 VM 汇总限制，并与代表需求对照。参见 [HANA 存储配置](https://learn.microsoft.com/en-us/azure/sap/workloads/hana-vm-operations-storage)。

## 6. 解释故障转移如何保持安全

HANA System Replication 复制数据库变化；受支持集群自动执行决策与资源迁移。ASCS/SCS 需要自己的受支持高可用设计，适用时包括 ERS 和共享文件。虚拟名称、负载均衡器探测、资源代理和启动依赖必须配置一致。

仲裁帮助决定哪个分区可以行动。隔离机制 fencing 将无法安全继续的节点隔离，降低脑裂风险。按发行版和架构选择受支持的 Azure fencing 代理或 SBD 安排。不能通过禁用 fencing 让不健康集群看起来可用。在纸面演练通信中断、探测失败和接管顺序，明确唯一允许写入者。参见 [SLES HANA 高可用指南](https://learn.microsoft.com/en-us/azure/sap/workloads/sap-hana-high-availability)。

## 7. 区分恢复副本与复制

复制可以迅速传播误删。备份、保留日志和受支持恢复流程才能提供回到较早可接受时间点的能力。恢复点目标（RPO）是可容忍数据损失，恢复时间目标（RTO）是可容忍中断；应与业务负责人共同确定。

选择了解数据库工作负载的备份和日志、保留、保护边界与恢复依赖。VM 或存储快照不自动等于应用一致的 SAP/HANA 备份。采用快照前明确受支持协调与一致性。备份作业成功的证据弱于实际恢复后通过数据库和业务验证。包括身份、加密密钥访问、所需文件，以及区域故障期间备份是否可用。

## 8. 让迁移切换能够真正回退

选择同构复制、数据库迁移、升级或 HANA 转换前，先评估兼容性与依赖。按源和目标匹配受支持工具及 SAP 流程；移动 VM 磁盘不能验证所有 SAP 迁移。估算传输耗时、变化速率、停机与最终同步，并用代表数据演练。

编写写入冻结、最终传输、源隔离、DNS/接口变化、技术检查、业务验收与重新开放写入的检查关口。指定决策负责人和回退期限。目标产生新写入后，切回 DNS 可能丢失或分叉事务：回退需要对账或受支持反向数据迁移。应记录这是一项数据决策及其授权人，不能把旧 VM 称为完整回退计划。

## 9. 用经过审查的自动化和明确归属运维

审查 Bicep/ARM 或 SAP Deployment Automation Framework 变更，检查受支持映像、放置、存储、身份、依赖与破坏性差异。凭据不要进入源代码管理；使用已批准秘密引用和访问控制。分阶段更新操作系统、内核、代理和数据库，包含兼容性检查、备份证据、了解集群的顺序和回退标准。

把 Azure VM、磁盘、网络和可用性证据与 SAP、数据库健康关联。[Azure Monitor for SAP solutions](https://learn.microsoft.com/en-us/azure/sap/monitor/about-azure-monitor-sap-solutions) 需要配置提供程序和采集；空工作簿不证明健康。对于 RISE，合同与责任矩阵决定 SAP 管理资源的责任。依据 [RISE 集成指南](https://learn.microsoft.com/en-us/azure/sap/workloads/rise-integration)，记录客户网络、身份、接口和升级处理边界。

## 10. 演练完整服务恢复

离线桌面演练在大学采购期间移除主要区域。按要求顺序恢复应用服务、中央服务、数据库、身份、DNS、路由、集成终结点、秘密和可用容量。决定复制延迟如何影响验收，并防止旧主节点独立恢复写入。

用成功采购和研究门户交换检验计划，指定验证人并预测时间。包括返回主区域的同步、受控切换和关闭证据。调整大小或承诺容量前，审查性能及持续成本类别；变更后再次测算故障余量。完成[案例](AZ-120-cases.md)和[练习册](AZ-120-workbook.md)。这些是架构与运行手册练习，不宣称已部署 Azure、执行 SAP 或测量故障转移。
