# AZ-802 · 管理 Windows Server

[认证](README.md) · [10 个推理案例](AZ-802-cases.md) · [五单元练习册](AZ-802-workbook.md) · [西班牙语](../es/AZ-802.md)

我会以负责一间小型大学 Windows 实验室的学生身份来学习这条路线。真正有用的问题通常不是“哪个控制台有这个设置”，而是“哪一层出了故障，什么证据支持这个判断，以及怎样在不丢失访问权或数据的情况下进行更改”。以下示例采用虚构环境，并非我们已经检查过的大学网络。

使用隔离的 VM，建立可随时丢弃的 AD 林 `lab.example.test`，准备两台域控制器、一台成员文件服务器和一个客户端。只有嵌套虚拟化、内存、存储和许可条件允许时，才添加 Hyper-V 主机。扩展到 Azure 是可选项，需要获授权的订阅、费用负责人以及受支持的网络。不要为了让练习成功，就把实验域接入生产信任关系。

## 2. 创建账户之前，先说明身份关系

AD DS 是一种目录，包含域控制器、复制、DNS 依赖和身份验证职责。Microsoft Entra ID 则是另一个身份系统。将 Windows 计算机加入 AD 域、注册到 Entra，以及连接到 Azure Arc，解决的是不同问题。图中应展示哪个系统验证用户、哪个身份管理 Azure，以及哪个账户访问文件共享。

身份清单应先记录林与域名称、DNS 命名空间、域控制器、功能兼容性、站点、子网、时间源和应用依赖。将普通学生账户与特权管理分开。区分用于授权的安全组，以及用于组织和策略定位的组织单位（OU）。把用户移入 OU，本身并不会授予文件访问权。

对于大学研究服务，可以考虑受支持的组托管服务账户，而不是使用学生持有、毕业后会到期的密码。gMSA 有前提条件，还需要明确哪些主机获准获取其托管密码；它不是通用登录账户。记录服务所需的权限和网络目标，并验证具体应用是否支持。参阅 [gMSA 概述](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-managed-service-accounts/group-managed-service-accounts/group-managed-service-accounts-overview)。

在具备 ActiveDirectory 模块和目录读取权限的 Windows 管理计算机上检查：

```powershell
Get-ADDomainController -Filter * |
    Select-Object HostName, Site, IsReadOnly, OperationMasterRoles
Get-ADDomain | Select-Object DNSRoot, PDCEmulator, RIDMaster, InfrastructureMaster
```

输出是一份清单，不能证明每台控制器都健康。应与预期拓扑对照。缺少站点分配、无法访问的控制器，或以特权人员账户运行的服务，都应成为调查问题，而不是重建域的理由。

## 3. 将 DNS、时间、站点和复制联系起来

域客户端需要合适的 DNS 才能发现 AD 服务。“互联网能用”是很弱的证据：公用名称解析可能成功，而域的 SRV 查询仍然失败。在实验中，使用客户端实际采用的解析器解析域和服务记录。然后测试返回的控制器及所需协议，不要一开始就重置密码。

```powershell
Get-DnsClientServerAddress -AddressFamily IPv4
Resolve-DnsName -Name '_ldap._tcp.dc._msdcs.lab.example.test' -Type SRV
w32tm /query /status
```

这些查询需要适当的网络访问；`w32tm` 是 Windows 工具。SRV 回答成功，并不能证明公布的服务器可达，也不能证明身份验证成功。应记录解析器、返回的目标、时间戳和错误。Kerberos 还依赖可接受的时间差。应诊断时间层级和同步状态，而不是独立修改每台机器的时钟。

AD 站点和子网映射描述网络位置，并影响服务定位和复制。仅创建站点而不分配相关 IP 子网，不会让客户端开始使用它。当校园账户更改迟迟未出现在远端楼宇时，应比较控制器选择、复制健康、拓扑、计划和连接情况。不要在不了解故障的情况下立即缩短所有间隔或强制复制。

使用 AD 工具及相关权限，查询选定的实验控制器：

```powershell
Get-ADReplicationFailure -Target 'LAB-DC1.lab.example.test' -Scope Server
repadmin /replsummary
```

把错误当作一条时间线来分析。复制症状可能源于 DNS、身份验证、时间、网络筛选或目录问题。修复传输并不能自动证明所有必要更改均已收敛；之后仍要验证具体对象或策略。利用 [AD 复制概念](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/replication/active-directory-replication-concepts)，解释为什么本地成功和林范围内收敛是不同的判断。

## 4. 有意识地选择控制器和策略操作

RODC 适用于物理或管理信任较弱的位置，但“只读”不等于“不存储凭据”。其密码复制策略决定哪些凭据可以缓存。应规划允许和拒绝的账户、委派管理、对可写控制器的访问，以及设备丢失后的响应。如果在不可信分支缓存特权账户，就破坏了大部分预期边界。参阅 [RODC 密码复制策略](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups)。

FSMO 角色是不同的职责，而不是一个负载均衡组。角色转移是在现有持有者可用时进行的受控迁移；角色强占则是持有者不可用时的恢复操作，并要求在原持有者返回之前，为其制定受支持的处理计划。一次用户登录失败不足以成为强占全部角色的理由。首先确定失败的操作、角色依赖、控制器健康情况和恢复负责人。

对于组策略，应区分策略存在、作用范围、处理过程和最终设置。检查相关用户或计算机的 OU、链接、继承、安全筛选、使用时的 WMI 筛选，以及客户端证据。用户策略不会自动应用到同一教室的每台计算机。环回处理会改变特定计算机上用户策略的选择方式，因此需要明确用途。

在受影响的 Windows 实验客户端上，`gpresult /r` 可以概述应用上下文。应解释“GPO 已链接”“此客户端处理了它”和“有效设置符合要求”之间的区别。组策略首选项不是发布可重复使用的特权密码的地方。明确设置的回退方法；取消链接并不能普遍保证每个旧值都会恢复。参阅[组策略概述](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-policy/group-policy-overview)。

## 5. 把远程和混合管理当作权限设计

画出操作人员、管理工作站、网关或终结点、目标服务器，以及需要访问的第二项资源。Windows Admin Center、Server Manager、PowerShell 远程处理、SSH 和 RDP 的前提条件与会话行为各不相同。打开端口不会赋予用户管理权限；大范围加入管理员组，也不能替代对实际所需操作的明确识别。

当服务器 B 上的会话需要以适当身份访问资源 C 时，会出现第二跃点问题。不要把管理员密码复制到脚本里来解决。[PowerShell 第二跃点指南](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/ps-remoting-second-hop)比较了各种方法及其限制。CredSSP 会委派凭据，增加暴露；约束委派方法也存在协议限制，包括 WinRM 第二跃点限制。应选择实际受支持的路径和身份验证机制，而不是把“启用委派”当作一个设置。

[JEA 会话配置](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/jea/session-configurations)可以提供受限制的管理终结点。要一起审查角色功能、可见命令与参数、执行身份、获授权用户和会话记录。默认情况下，JEA 虚拟账户在成员服务器上属于本地 Administrators 组，在域控制器上属于 Domain Admins 组。在受支持时配置受限制的执行组，并检查命令能否逃逸限制。如果允许的命令可以启动任意代码，即使命令清单很短，也不能证明符合最小权限。

Azure Arc 使非 Azure 服务器能够通过 Azure 服务管理；它不会使服务器加入 AD、创建林信任，也不会消除本地安全责任。[Arc 安全概述](https://learn.microsoft.com/en-us/azure/azure-arc/servers/security-overview)描述了敏感的代理和扩展边界。应决定谁能安装扩展和执行脚本，特别是在域控制器上。对于更新，要区分评估与安装、维护范围与重启处理，以及运行手册的计划时间与实际成功完成。扩大更改范围前，先在有代表性的成员服务器上试行。

## 6. 分别考虑 Hyper-V 容量、网络与恢复

为每台 VM 记录角色、来宾兼容性、内存、CPU、存储路径、虚拟网络、启动依赖和可接受的中断。动态内存是一项需要工作负载兼容性及主机余量的策略，并不是免费的额外容量。嵌套虚拟化和 GPU 分区要求具体硬件、操作系统、来宾和配置均受支持。不要因为另一个版本的截图里出现某项功能，就承诺当前环境也能使用。

使用 Hyper-V 模块和适当主机权限检查实验主机：

```powershell
Get-VM -Name 'LAB-APP' | Select-Object Name, State, Generation, MemoryAssigned, CheckpointType
Get-VMMemory -VMName 'LAB-APP'
Get-VMSwitch | Select-Object Name, SwitchType
Get-VMSnapshot -VMName 'LAB-APP' | Select-Object Name, SnapshotType, CreationTime
```

上面的清单不能证明生产检查点的一致性。`SnapshotType` 是 [Get-VMSnapshot](https://learn.microsoft.com/en-us/powershell/module/hyper-v/get-vmsnapshot) 提供的检查点分类，`CheckpointType` 则是 VM 配置的策略。应检查创建结果，以及适用的来宾一致性处理或 VSS 证据；不能仅凭 Standard 一词或请求的策略就认定 Production 处理已成功。

将外部、内部或专用虚拟交换机映射到预期通信边界。隔离交换机可以解释为什么两台实验来宾能够互通，却无法访问校园网络；仅改变来宾防火墙不会创建上行连接。应区分主机适配器问题、VM 适配器连接、来宾 IP 配置、DNS 和应用访问。

[检查点](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/checkpoints)尤其容易被误解。标准检查点捕获包含内存在内的 VM 状态；生产检查点则在受支持时使用与来宾协同的、一致性相关机制。生产配置可以允许回退到标准检查点，而 ProductionOnly 会拒绝这种回退。无论哪种设置，都不会把 VM 检查点链变成独立的受保护备份。不要为腾出空间手动删除 AVHDX 文件；应使用受支持的管理和合并流程。

Hyper-V 副本支持异步复制，以及计划、测试和非计划故障转移工作流。它不同于群集 VM 的高可用性，也不同于历史备份。副本可能包含错误的应用更改。设计审查时，应明确所针对的故障、可能的延迟、权威写入节点、网络映射、测试隔离和故障回复流程。参阅 [Hyper-V 副本概述](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/replication-overview)。

| 机制 | 适用场景 | 单独不能证明的内容 |
|---|---|---|
| 检查点 | 在受支持的实验更改中受控返回 VM 状态 | 存储链丢失后仍能保留的独立副本 |
| Hyper-V 副本 | 主节点故障后恢复已复制的 VM | 未受损的历史恢复点或零数据损失 |
| 群集 VM | 主机故障后重启或移动受支持的 VM | 应用级正确性或防止删除 |
| 经过还原测试的受保护备份 | 按所选保留和一致性策略进行历史恢复 | 自动故障转移或从未测量过的恢复时间 |

## 7. 将 Azure VM 作为完整的 Windows 工作负载诊断

Azure VM 可能显示运行中，但来宾服务仍不可用。应区分平台状态、启动、来宾网络、Windows 身份验证、服务健康和应用依赖。调整大小会改变可用资源，可能要求重启，也可能引入放置或容量限制；在把它称为性能修复之前，先检查 VM 和磁盘两方面的限制。

可用性集和可用区关注的是放置。增加第二台 VM，不会自动实现应用故障转移、复制可写目录或提供一致的文件服务。对于 Azure 中的 AD 域控制器，应遵循受支持的目录虚拟化和备份指南，安排合适的 DNS 和网络路径，不要将复制出的操作系统磁盘当作新的独立控制器。

Azure Bastion 提供托管访问路径；JIT 控制在受支持的条件下限制暴露。两者都不能替代 Windows 凭据、来宾授权或必要的应用权限。在开放永久公用 RDP 前，先调查获批路径为何失败。练习交付物应是路径图和最小权限访问说明，而不是为了方便创建的公用终结点。

## 8. 沿实际客户端路径排查 DNS 和 DHCP

建立一条名称解析链：客户端解析器、本地区域、条件转发器、上游目标和权威回答。条件转发器把特定命名空间的查询发送到选定 DNS 服务器，但不会创建到这些服务器的网络路由。DNSSEC 增加的是 DNS 数据验证，不是传输加密，也不会自动赋予私有应用访问权。说明查询必须返回什么，以及应从混合边界的哪一侧查询。

在具有 DnsServer 模块和适当读取权限的 DNS 管理主机上检查：

```powershell
Get-DnsServerZone -ComputerName 'LAB-DC1'
Get-DnsServerForwarder -ComputerName 'LAB-DC1'
```

对于 DHCP，检查作用域范围、排除项、租约、保留、选项、中继路径和已授权服务器。保留与客户端标识符绑定，并不会把来宾内部的地址设为静态。作用域满时，新客户端可能失败，而现有租约仍继续生效，所以两种情况都要测试。若服务器根本未收到请求，中继或 VLAN 问题看起来也可能像 DHCP 服务故障。

使用 DHCP Server 模块和相关权限检查：

```powershell
Get-DhcpServerv4Scope -ComputerName 'LAB-DHCP1'
Get-DhcpServerv4Failover -ComputerName 'LAB-DHCP1'
```

DHCP 故障转移在其受支持的行为范围内保护已配置关系和作用域；仅部署第二台服务器不会协调地址分配。记录模式、伙伴状态、受支持的租约行为和恢复流程。参阅 [DHCP 故障转移](https://learn.microsoft.com/en-us/windows-server/networking/technologies/dhcp/dhcp-failover)。

## 9. 追踪文件访问的每一个边界

学生能登录，并不一定有权访问共享。对于 Windows SMB 服务器，应检查实际身份的共享权限和 NTFS 权限，包括组成员身份及继承。显式拒绝和过期的组令牌都可能改变结果。记录预期协作组与隔离边界，而不是给 Everyone 完全控制直到症状消失。

在具备 SMBShare 模块并能访问选定文件夹的实验文件服务器上检查：

```powershell
Get-SmbShareAccess -Name 'LabNotes'
Get-Acl -LiteralPath 'D:\LabShares\Notes' | Format-List Owner, AccessToString
```

这些输出描述的是已配置条目，并非完整的有效访问证明。应让一名获准用户和一名应被拒绝的用户测试预期路径。Azure Files 有自身受支持的身份设置和共享级授权，还在适用时使用目录与文件权限。[Azure Files 授权](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-authorization-overview)明确解释了这种分层。资源管理的 Contributor 角色不自动等于 SMB 数据权限。

Azure File Sync 连接云终结点与服务器终结点，并能对文件分层。同步和可用性本身不能提供独立的历史恢复边界。应规划保留、受保护备份、还原依赖、终结点健康、缓存容量，以及删除或损坏文件的恢复方式。占位文件并不能证明所需内容已经立即位于本地。参阅 [Azure File Sync 规划](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-planning)。

已注册的 File Sync 服务器还有额外恢复限制：还原其操作系统映像、克隆服务器或回退 VM 检查点，并不是通用的受支持恢复路径。遵循 [File Sync 灾难恢复指南](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-disaster-recovery-best-practices)，根据实际情况确定完整的云副本、保留的保护，以及受支持的服务器重新注册和恢复流程。不要把普通 Hyper-V 回退当作练习册中的 File Sync 还原流程。

[SMB over QUIC](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-over-quic)需要受支持的操作系统版本与版本类型、客户端、连接和适当证书。本次审查时，指南列出 Windows Server 2022 Datacenter: Azure Edition 或 Windows Server 2025 各版本，以及 Windows 11 客户端。检查默认 UDP 443 路径，以及受信任的服务器身份验证证书；证书必须包含所需的 DNS 使用者可选名称，并具有可用私钥。当前 Windows Server 2025 的设置流程使用 PowerShell；不要在未核对版本特定流程的情况下，用旧的 Windows Admin Center 方法替代。QUIC 不会绕过文件授权，启用它也不等于允许暴露无关服务。

## 10. 区分存储容量、复原能力和可恢复性

磁盘大小只是一个维度。应绘出物理设备、池、虚拟磁盘、卷、文件系统、工作负载和保护之间的关系。Storage Spaces、Storage Spaces Direct、Storage Replica、DFS 命名空间和 DFS 复制用途不同。命名空间提供逻辑路径，但不保证引用的内容已同步，也不保证应用能安全接受并发写入。

在兼容的 Windows 存储主机上执行只读清单查询：

```powershell
Get-PhysicalDisk | Select-Object FriendlyName, HealthStatus, OperationalStatus
Get-VirtualDisk | Select-Object FriendlyName, ResiliencySettingName, HealthStatus
Get-Volume | Select-Object DriveLetter, FileSystem, HealthStatus, SizeRemaining, Size
```

将延迟、吞吐量、队列、容量和工作负载时间联系起来。健康的池仍可能性能不足。抵御设备故障并不能防止管理员删除文件夹。[Storage Replica](https://learn.microsoft.com/en-us/windows-server/storage/storage-replica/storage-replica-overview)也需要受支持的拓扑、适当的日志与数据布局，以及明确的恢复设计；复制不能普遍替代备份。

应根据受支持的工作负载要求选择 NTFS 或 ReFS，而不是宣称某一个永远更快。重复数据删除、SMB Direct/RDMA、存储 QoS、iSCSI 和 BitLocker 都有各自的兼容性与运维要求。对于加密，要单独保护恢复材料，并确认存在获授权的恢复路径。不要把恢复密钥作为练习册截图公开。重要恢复说明应保留独立副本，放在不会因中断而无法访问的位置。

## 11. 按角色加固，并保留恢复访问

文件服务器、Hyper-V 主机和域控制器不应被无理由地应用同一套设置。从资产角色、特权身份、暴露服务、允许的管理路径和恢复访问开始。分阶段更改防火墙和身份验证，并先测试回退通道。某项安全设置如果悄悄禁用唯一管理渠道，就可能把小问题变成恢复演练。

[OSConfig 安全基线](https://learn.microsoft.com/en-us/windows-server/security/osconfig/osconfig-how-to-configure-security-baselines)目前针对 Windows Server 2025。应用前核实已安装模块和受支持场景；不要将这些命令直接复制到旧服务器。检查计划设置，在合适的服务器角色上试行，审查符合性和漂移，并记录原状态。应用或移除基线均需要重启。移除配置管理不能保证每一个旧值都被恢复。

[Windows LAPS](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-overview)通过托管轮换和受控获取，减少本地管理员密码的重复使用。决定受支持的备份目标、账户策略、获取角色、审核和恢复流程。这并不授予为学生报告获取密码的权限。在控制器上，DSRM 恢复有自身受支持的 LAPS 条件；不要混淆域账户与机器的本地恢复凭据。

Credential Guard、应用控制、漏洞防护、Defender for Servers 和账户保护针对不同威胁。应验证硬件及操作系统前提条件，并观察实际强制执行，而不是把已安装功能当作保护证明。对于 AD 委派，在适当范围内授予所需的有限目录操作。帮助台重置密码不需要加入 Domain Admins。尽可能避免在日常浏览网页和处理邮件的计算机上使用特权会话。

## 12. 先建立有用的监视，再借助仪表板排错

先选一个问题：登录失败、磁盘延迟、复制失败、更新健康，或缺失的代理扩展。明确源、收集方式、目标、时间窗口、负责人和警报动作。性能监视器计数器和数据收集器集有助于建立基线；一个偏高样本不能说明原因。将应用症状与同一时间段关联，并与正常工作负载行为比较。

Azure Arc 连接状态、Azure Monitor Agent 健康、数据收集规则（DCR）、DCR 关联和目标权限，都是单独的检查项。[Windows Arc 服务器 AMA 故障排除](https://learn.microsoft.com/en-us/azure/azure-monitor/agents/azure-monitor-agent-troubleshoot-windows-arc)区分代理与配置路径以及引入路径。检测信号数据可以显示代理正在报告，但所需事件日志可能仍未收集。查询为空可能意味着时间范围、表、源选择、关联或工作区不对，并不一定代表“没有事件”。

在相关 Windows 实验服务器上，本地事件查询可以帮助确定源事件是否存在：

```powershell
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddHours(-2)} -MaxEvents 20 |
    Select-Object TimeCreated, Id, ProviderName, LevelDisplayName
```

读取某些日志需要提升权限或委派权限。记录查询时间和时区，保留有用的事件标识符，并遮盖敏感值。分别解释事件是否在本地发生，以及配置的收集流程是否将它送达。警报需要有用的阈值、接收者、响应负责人和验证案例；如果没有人收到规则通知，运维流程就不完整。

## 13. 使用诊断顺序和受支持的恢复方法

对于登录事件，我的第一张工作表会问：改了什么，哪些身份和设备失败，准确错误是什么，什么时候开始？随后依次检查 IP 配置、解析器与 SRV 结果、控制器可达性、时间、身份验证与安全通道证据、复制以及授权。这是检验假设的顺序，并非要求禁用防火墙或重置所有账户。在成员服务器上，`Test-ComputerSecureChannel` 可以检查信任；不要在没有单独论证更改的情况下添加 `-Repair`，也不要把这个成员服务器测试当作 DC 健康检查。

对于丢失文件，确定命名空间和权威位置、预期身份、共享与 NTFS 或 Azure 授权、同步状态、删除时间线，以及可用的历史副本。对于缓慢的 VM，把来宾工作负载与主机争用、内存压力、磁盘限制、队列和网络依赖进行比较。在重启使症状消失之前保留证据。

AD 恢复需要格外谨慎。通过回收站恢复对象有前提条件，并不等于恢复整个域。DSRM 是使用受保护凭据的恢复启动环境，不是普通管理会话。SYSVOL 恢复以及目录的权威或非权威还原，取决于实际故障和受支持流程。利用 [AD 林恢复指南](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/forest-recovery-guide/ad-forest-recovery-guide)规划负责人、干净恢复、备份、依赖和验证。不要根据这些笔记在真实目录中练习控制器回退或 FSMO 强占。

## 14. 将实验工作变成证据，而不只是截图

[练习册](AZ-802-workbook.md)把这些主题组合成五项调查。在每项调查之前，写出预期结果、一个竞争性解释、能够区分两者的命令、可能更改的状态和退出条件。Server Manager 截图的证据力度，弱于针对具体身份的测试记录；后者应包含时间戳、目标、命令、去除敏感内容的结果和解释。

使用更改台账，记录基线、拟议动作、真实环境中的审批负责人、观察、解释和回退关口。如果没有 Windows 实验环境，就制作拓扑和预期观察，并明确标为预测。不要编造输出，也不要把计划还原描述为已经完成。优先在可丢弃实验环境中进行小幅、可逆更改，每次只改变一个变量，并保有已知恢复路径。

| 示例类别 | 查询前应记录的前提条件 |
|---|---|
| AD 清单与复制 | ActiveDirectory/RSAT 工具、可达的实验控制器、相关目录读取权限 |
| DNS 客户端、时间、策略 | Windows 客户端、正确的用户与计算机上下文、对查询服务的访问 |
| DNS/DHCP 服务器 | DnsServer/DhcpServer 模块，以及选定服务器上的委派或管理员读取权限 |
| Hyper-V | 受支持的 Windows 主机、Hyper-V PowerShell 模块、获授权的主机访问 |
| 共享与文件系统 | SMBShare 支持、真实共享与路径、检查其 ACL 的权限 |
| 存储清单 | 受支持的 Storage 模块或提供程序，以及获授权的主机上下文 |
| 本地事件日志 | 存在的日志和时间范围、读取该日志的权限、敏感信息遮盖计划 |
