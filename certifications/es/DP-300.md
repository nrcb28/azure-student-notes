# DP-300 · Administración de soluciones Microsoft Azure SQL

[Rutas de certificación](README.md) · [Diez casos](DP-300-cases.md) · [Cuaderno](DP-300-workbook.md) · [English](../en/DP-300.md)

Que una base de datos acepte conexiones es solo el principio. Para DP-300, estudiaría cómo mantener los datos disponibles, protegidos, recuperables y con un rendimiento razonable cuando algo cambia. Seguimos con nuestra aplicación universitaria de apuntes: los estudiantes suben documentos y una base SQL guarda propietarios, asignaturas y permisos de descarga.

Referencia consultada el **30 de octubre de 2026**: [guía oficial DP-300](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/dp-300), objetivos desde el **27 de octubre de 2026**. La credencial asociada es [Azure Database Administrator Associate](https://learn.microsoft.com/en-us/credentials/certifications/azure-database-administrator-associate/).

Son apuntes propios: no cubren todos los objetivos ni contienen preguntas reales del examen. Revisa la guía oficial para el idioma y la fecha en que vayas a presentarte.

## 1. Elegir plataforma según los requisitos

Azure SQL Database encaja con aplicaciones centradas en bases de datos y una infraestructura administrada. Managed Instance admite más comportamientos de SQL Server a nivel de instancia, aunque hay que comprobar la compatibilidad. SQL Server en una VM de Azure ofrece control del sistema operativo y mayor compatibilidad, a cambio de más tareas de administración. No son nombres intercambiables del mismo despliegue.

Para la app de apuntes, anotaría funciones necesarias, dependencias, mantenimiento y objetivos de recuperación antes de elegir un tamaño. Un agente que necesite acceso al sistema operativo puede cambiar la decisión; conocer un producto no es un requisito técnico. Compara las capacidades actuales de Azure Arc y SQL database en Microsoft Fabric cuando proceda, sin tratar ninguno como sustituto automático de cualquier carga de Azure SQL.

[Comparación de plataformas](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview?view=azuresql).

## 2. Planificar una migración como una secuencia

Inventaría tamaño, versiones, inicios de sesión, tareas, dependencias entre bases y supuestos de la aplicación. La compatibilidad se evalúa antes de copiar. Separa conversión del esquema, transferencia inicial, cambios posteriores y transición final: terminar la transferencia no demuestra que la aplicación funcione.

Una migración sin conexión incluye una parada planificada de escrituras. Una modalidad en línea puede reducirla donde esté admitida, pero también necesita una transición final controlada. Define cuál es la fuente válida, cómo se detienen las escrituras, cómo se comprueban los últimos cambios y quién autoriza reabrir el acceso. Compara filas y totales de negocio importantes; prueba permisos, tareas y comportamiento de la app. El plan de vuelta debe contemplar las escrituras posteriores al cambio, no limitarse a reconectar con una copia antigua.

## 3. Seguir la ruta completa de acceso

Diagnostica en orden: resolución de nombres del cliente, ruta de red, configuración del servicio, autenticación y autorización en la base. Un private endpoint no crea un usuario de base de datos. Un rol de administración de Azure no concede automáticamente permiso para leer una tabla SQL.

Usa una identidad de Entra adecuada cuando esté admitida y configura el principal y los permisos necesarios en la base. A la aplicación le concedería las operaciones de su función, sin compartir una cuenta administradora. Separa identidades de despliegue, aplicación y respuesta a incidentes. Confirma la identidad real y la base de destino antes de cambiar accesos. La configuración de red depende de la modalidad elegida: las reglas de firewall de SQL Database no se trasladan sin más a Managed Instance.

[Seguridad por capas](https://learn.microsoft.com/en-us/azure/azure-sql/database/security-overview?view=azuresql).

## 4. Proteger los datos en la capa adecuada

El cifrado de transporte protege la conexión. TDE aborda el cifrado de archivos de la base en reposo. Always Encrypted establece otro límite e implica controladores compatibles y gestión de claves en el cliente. Si se exige ocultar determinados valores a los administradores de la base, hay que estudiar ese límite; activar TDE por sí solo no lo demuestra.

El enmascaramiento dinámico cambia cómo se presentan resultados a usuarios sin el permiso de desenmascarar correspondiente. No sustituye la autorización ni vuelve inocuo un acceso amplio a consultas. Decide quién consulta filas, quién administra claves y qué aparece en registros y exportaciones. La auditoría ayuda a registrar actividad, pero su destino, retención, acceso y revisión también necesitan responsables.

## 5. Establecer una referencia útil

«Va lento» necesita una medida: una consulta de permisos de descarga que antes tardaba 30 milisegundos ahora tarda 800. Registra consulta, franja horaria, duración, CPU, lecturas y concurrencia. Compara la misma operación con cargas similares; probar a medianoche sin usuarios dice poco sobre el tráfico de la tarde.

Query Store conserva información de consultas, planes y ejecución útil para investigar regresiones. Confirma su configuración y el historial disponible antes de esperar encontrar datos de ayer. Las métricas de plataforma indican presión sobre recursos; las esperas, cadenas de bloqueo y planes ayudan a explicar por qué se retrasa el trabajo. Si faltan evidencias, anótalo como limitación, sin convertirlo en una causa segura.

[Query Store](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store?view=sql-server-ver17).

## 6. Ajustar una hipótesis cada vez

Un plan nuevo, estadísticas desactualizadas, índices poco adecuados, cambios en los parámetros o una transacción larga pueden explicar una ralentización. Revisa evidencias y elige un experimento reversible. Un índice adicional puede acelerar búsquedas y aumentar el coste de escrituras y almacenamiento. Un recorrido completo no es siempre un error: importa cuántas filas se necesitan y qué accesos existen.

Prueba una carga representativa antes y después, incluidas escrituras concurrentes. Forzar un plan puede ayudar en una regresión demostrada, pero necesita seguimiento y una forma de retirarlo. Escalar recursos es razonable si se identifica falta de capacidad. Reducir archivos por costumbre, reconstruirlo todo o finalizar sesiones sin entender su trabajo puede provocar interrupciones y ocultar la causa inicial.

## 7. Automatizar para la plataforma real

SQL Server y Managed Instance admiten SQL Agent; Azure SQL Database no ofrece ese servicio. Elastic Jobs es una opción para tareas T-SQL compatibles sobre destinos de SQL Database. Un orquestador puede encajar mejor cuando el flujo cruza bases, almacenamiento y sistemas externos.

En cada tarea especifica identidad, destinos, calendario, tiempo máximo, política de reintentos y aviso de fallo. Una tarea que inserta un resultado mensual debería evitar duplicarlo si pierde la respuesta y vuelve a ejecutarse. Registra finalización por unidad de trabajo prevista y distingue una ejecución de un resultado de negocio comprobado. Prueba primero con datos sintéticos y un destino aislado.

[Opciones de automatización](https://learn.microsoft.com/en-us/azure/azure-sql/database/job-automation-overview?view=azuresql).

## 8. Separar copia, disponibilidad y recuperación ante desastres

Las copias permiten recuperar estados conservados. La restauración a un momento dado y la retención a largo plazo resuelven horizontes distintos: elige la retención según el requisito antes del incidente. En SQL Database, restaurar crea una base en lugar de sobrescribir otra existente. El plan incluye, por tanto, validación y reconexión adecuada de la aplicación.

La replicación y los mecanismos de disponibilidad atienden ciertos fallos, pero también pueden propagar un cambio destructivo válido. Otra réplica no sustituye recuperar un estado anterior. Define RPO como pérdida reciente de datos aceptable y RTO como tiempo de recuperación admisible. Comprueba ambos con dependencias realistas. Región, nivel, configuración y modalidad de replicación condicionan el diseño: no inventes una duración universal de recuperación.

[Restaurar copias](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups?view=azuresql) · [Continuidad del negocio](https://learn.microsoft.com/en-us/azure/azure-sql/database/business-continuity-high-availability-disaster-recover-hadr-overview?view=azuresql).

## 9. Recuperar la aplicación y planificar el retorno

La conmutación de la base no termina el trabajo. Comprueba endpoints admitidos, DNS, autenticación, reconexión y coherencia entre almacenes dependientes. El listener de un failover group puede conservar el endpoint de la app, pero los clientes tienen que reconectar correctamente. Incluye monitorización y tareas programadas en el nuevo primario.

Antes de volver, establece qué base es la válida y cómo se sincronizarán los cambios. Registra responsables y condiciones para detener el proceso. Una vuelta improvisada puede perder escrituras correctas aunque la recuperación inicial haya funcionado.

## 10. Ejercicio operativo sin despliegue

Sin crear recursos, prepara un procedimiento para la app de apuntes. Elige plataforma, dibuja límites de acceso y escribe una tabla de referencia de rendimiento. Inventa un incidente de regresión del plan y otro de borrado accidental; indica qué evidencias los distinguen. Describe una restauración a una base aislada y una comprobación funcional con registros sintéticos.

Marca cada entrada como **ESPERADO**, **OBSERVADO** o **NO EJECUTADO**. Un diagrama o ejercicio SQL local no demuestra cuánto tarda Azure en restaurar. Entrega supuestos, criterios de verificación, permisos, pasos de vuelta y decisión sobre limpieza de datos retenidos. Continúa con las [cinco unidades del cuaderno](DP-300-workbook.md) y los [diez casos propios](DP-300-cases.md). No se afirma ejecución en Azure.
