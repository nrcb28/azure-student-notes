## 1. Planificar direcciones antes de crear redes

Primero haría inventario de los rangos del campus, Azure, colaboradores y futuras redes. Los rangos privados solapados complican el emparejamiento y las rutas híbridas. Usar una dirección de RFC 1918 no la convierte en única dentro de nuestra organización.

Por ejemplo, reservamos 10.70.0.0/16 para el proyecto, 10.70.1.0/24 para web y 10.70.2.0/24 para datos. Un /24 contiene 256 direcciones IPv4; Azure reserva cinco en una subred ordinaria y quedan 251 asignables. Siguen existiendo requisitos por servicio. Una subred delegada, una puerta de enlace o un firewall pueden exigir un nombre, tamaño, uso exclusivo o delegación concretos. Conviene comprobarlo antes de repartir el espacio restante.

Cada separación necesita un motivo: ciclo de vida, rutas, confianza, requisitos del servicio o crecimiento. Crear otra subred no establece por sí solo una frontera de seguridad con controles útiles.

## 2. Conectar redes con una intención clara

El peering de VNet conecta redes compatibles sin solapamiento, pero no mezcla su administración ni sus controles de seguridad. Si A está emparejada con B y B con C, A no obtiene automáticamente conectividad con C. Hay que dibujar todos los caminos necesarios.

Un hub puede alojar conectividad e inspección compartidas, pero el dibujo hub-and-spoke no configura el tránsito. Revisaría las opciones de peering, el tráfico reenviado, las tablas de rutas y el dispositivo o gateway que transporta el tráfico. Gateway transit permite compartir una puerta de enlace con opciones compatibles; no promete reenvío automático entre todas las spokes. [Referencia de peering](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview).

## 3. Leer las rutas efectivas en ambos sentidos

Una ruta elige el siguiente salto; no concede acceso a la aplicación. Anota subred de origen, dirección de destino, prefijos coincidentes, origen de cada ruta y siguiente salto efectivo. No asumiría que una ruta definida por el usuario con 0.0.0.0/0 sustituye cualquier ruta más específica.

Al introducir un dispositivo virtual de red, comprobaría su reenvío, topología admitida, capacidad y camino de vuelta. Una petición puede atravesar un firewall con estado mientras la respuesta vuelve por otro sitio. Esa asimetría puede romper la conexión aunque cada subred parezca accesible por separado. Antes de añadir excepciones, registra la ruta en cada sentido. [Enrutamiento de Azure](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-udr-overview).

## 4. Tratar DNS como parte de la conexión

Pregunta al cliente real qué dirección obtiene para el nombre del servicio. Un private endpoint sirve de poco si ese cliente sigue eligiendo un destino público inaccesible.

Documenta las zonas privadas, enlaces a VNet, servidores DNS y reenvío entre campus y Azure. Azure DNS Private Resolver puede participar en diseños compatibles de resolución híbrida; dibuja por separado su comportamiento de entrada y salida. Conserva el nombre del servicio para que la validación del certificado y el enrutamiento funcionen como se espera. No tapes un error DNS con una entrada permanente de IP pública. Resolver el nombre tampoco demuestra que el servicio acepte la identidad del cliente. [DNS de private endpoints](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns).

## 5. Comparar caminos híbridos y fallos compartidos

Una VPN site-to-site suele proporcionar un túnel IPsec a través de Internet. ExpressRoute ofrece conectividad privada mediante modalidades de conexión compatibles. Que la conectividad sea privada **no** significa que el tráfico se cifre automáticamente.

Elige el cifrado según el tramo que deba protegerse. MACsec se aplica a enlaces físicos compatibles de ExpressRoute Direct; un diseño IPsec puede proteger una conexión de extremo a extremo. Revisa rendimiento y consecuencias operativas, en lugar de tratar esas opciones como una etiqueta sin condiciones.

Para la resiliencia, enumera circuitos, ubicaciones, proveedores, gateways, equipos del cliente y rutas que podrían fallar juntos. Una VPN de respaldo necesita anuncios de rutas, camino de vuelta, capacidad suficiente y recuperación de la aplicación comprobados. Dos conexiones dibujadas pueden compartir un único punto de fallo. [Cifrado en ExpressRoute](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-about-encryption).

## 6. Elegir entrega según protocolo y alcance

| Necesidad | Candidato que investigaría |
|---|---|
| Repartir flujos TCP/UDP | Azure Load Balancer |
| Rutas HTTP regionales, gestión TLS o WAF | Application Gateway |
| Entrega y aceleración global de aplicaciones HTTP | Azure Front Door |
| Selección de endpoints mediante DNS | Traffic Manager |

Son puntos de partida, no una tabla de capacidades exclusivas. Application Gateway también tiene funciones TCP/TLS compatibles: verifica la función y configuración actuales antes de afirmar que solo admite HTTP. Traffic Manager responde a consultas DNS; no actúa como proxy de cada petición. Las cachés DNS afectan a los cambios de destino.

Para cualquier candidato, concreta frontend, backend, protocolo, sondeo, certificados y comportamiento ante fallos. Un probe sano puede coexistir con descargas de documentos incorrectas. [Comparación de entrega](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/load-balancing-overview).

## 7. Diferenciar dos formas de acceso a servicios

Un private endpoint asigna a un servicio compatible una interfaz con dirección privada en la VNet. Un service endpoint identifica y protege el acceso compatible desde una subred al servicio según el modelo de endpoints del servicio; no coloca su endpoint público en una dirección privada de la subred.

Para Storage, comprueba aprobación del endpoint, subrecurso, DNS, restricciones de red y autorización de datos por separado. Añadir un private endpoint no desactiva automáticamente todo el acceso público. Tener un camino privado tampoco concede permiso para leer un contenedor. Indica tanto el camino de red previsto como la identidad autorizada.

## 8. Relacionar cada control con su problema

Los NSG filtran el tráfico aplicable mediante prioridades y comportamiento con estado. Revisa conjuntamente las reglas de subred e interfaz; cambiar una regla no tiene por qué cerrar de inmediato todas las conexiones establecidas. Azure Firewall permite centralizar funciones compatibles de filtrado de red, aplicación y traducción. Un WAF inspecciona tráfico web compatible y no sustituye el diseño general de rutas. La protección DDoS aborda amenazas a la disponibilidad, pero no autoriza usuarios.

Una hipótesis precisa, como «esta regla deniega tráfico TCP 443 nuevo», ayuda más que «la seguridad no funciona». Evita usar permisos generales de red como costumbre de diagnóstico.

## 9. Recoger evidencia en un orden útil

Comprueba resolución, destino seleccionado, siguiente salto efectivo, filtros, proceso a la escucha, TLS y permiso de aplicación. Usa funciones de Network Watcher apropiadas al recurso: siguiente salto, verificación de flujo IP, reglas efectivas, diagnóstico de conexión o captura de paquetes. Sus requisitos y ámbitos son distintos.

Predecir que se permite un paquete no demuestra una petición autenticada correcta. Guarda origen, destino, protocolo, puerto, momento, observación y siguiente hipótesis. Network Watcher no sustituye de forma universal la telemetría de PaaS o de la aplicación. [Herramientas de diagnóstico](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview).

## 10. Practicar el recorrido de un paquete sin desplegar

Dibuja campus, hub, spoke web y almacenamiento privado. Prepara una tabla para funcionamiento normal, fallo DNS y caída del enlace principal. En cada caso, anota ida y vuelta, controles aplicables, observación esperada y una prueba de confirmación. Descarta un arreglo que parezca razonable pero no resuelva el problema.

Después inspecciona el [laboratorio de red existente](network-lab.md). Su VNet y NSG no contienen los gateways ni las cargas en ejecución de tu diseño. Separa predicciones de resultados observados. Estos ejercicios nuevos no se han desplegado en Azure; una ejecución real requiere suscripción de pruebas adecuada, permisos, comprobación de los servicios y limpieza.
