## 1. Entender el consumo y la responsabilidad

Comprar servidores suele implicar inversión inicial, capacidad prevista y mantenimiento. Consumir nube permite solicitar capacidad sin comprar ese equipo, pero introduce dependencia de servicios, configuración y costes recurrentes.

**CapEx** se refiere a inversión de capital y **OpEx** a gasto operativo. No significa que cualquier organización transforme todos sus costes con solo migrar: contratos, licencias y personal siguen importando.

Ejemplo: durante exámenes, la web de apuntes recibe cinco veces más peticiones. Con escalado horizontal podemos añadir instancias. Para que ayude, la base de datos debe soportarlo y las sesiones no deberían depender de la memoria de una sola instancia.

**Predictibilidad** tiene dos caras. Para el rendimiento, medimos y dimensionamos. Para el coste, estimamos consumo y revisamos facturas. Una factura variable no es impredecible por definición, pero exige observarla.

En IaaS mantenemos el sistema operativo invitado. En PaaS se delega más plataforma. En SaaS usamos una aplicación, pero seguimos controlando accesos, tratamiento de datos y configuración disponible. La responsabilidad cambia de reparto, no desaparece.

### Escenario razonado

El profesor pide instalar módulos específicos del kernel de Linux. Una VM encaja mejor que una plataforma web que no permite ese nivel de control. Si pide publicar una API estándar, App Service puede ahorrar trabajo. El requisito decisivo es el control del sistema, no que una opción parezca más moderna.

## 2. Entender el mapa de Azure

Una suscripción agrupa administración y facturación. Un grupo de recursos organiza recursos con ciclos de vida relacionados. Los grupos de administración facilitan aplicar reglas a varias suscripciones.

Una región determina dónde se despliega un recurso regional. Una zona aporta separación física dentro de una región. Distribuir componentes entre zonas puede mejorar tolerancia a fallos, pero hay que confirmar el soporte del servicio.

Un availability set organiza VM entre dominios de fallo y actualización; no equivale a distribuirlas entre regiones. Azure Virtual Desktop proporciona capacidades para escritorios y aplicaciones virtualizados. No es simplemente otra VM con un nombre diferente.

Las nubes soberanas responden a necesidades específicas y pueden tener diferencias de servicios, endpoints y disponibilidad. No asumiría que un tutorial de Azure global funciona sin cambios en cualquier nube.

**Pregunta útil:** ¿qué protege mi diseño? Una instancia redundante puede ayudar ante un fallo de proceso. Varias zonas ayudan frente a otro ámbito de fallo. Varias regiones añaden opciones frente a fallos regionales y también más complejidad.

## 3. Elegir el tipo de cómputo

| Pista del enunciado | Opción que estudiaría | Por qué |
|---|---|---|
| Control del sistema operativo | VM | Permite administrar ese entorno |
| Web o API con runtime compatible | App Service | Reduce administración de servidores |
| Código activado por un evento | Functions | Encaja con ejecución por desencadenadores |
| Aplicación empaquetada como imagen | Plataforma de contenedores | Ejecuta el paquete de forma consistente |
| Escritorios remotos administrados | Azure Virtual Desktop | Responde a uso de escritorios y aplicaciones |

Un contenedor empaqueta dependencias y facilita consistencia, pero no garantiza seguridad ni escalabilidad. Serverless abstrae servidores; sigue teniendo planes, cuotas y facturación.

No mezclar **scale up**, cambiar capacidad de una instancia, con **scale out**, añadir instancias. Tampoco confundir autoscaling con alta disponibilidad: una única instancia grande sigue siendo una única instancia.

## 4. Redes: seguir el camino de la conexión

Una VNet define una red virtual. Las subredes dividen su espacio de direcciones. Un NSG filtra tráfico. DNS resuelve nombres: tener una ruta no sirve si el nombre lleva a un destino equivocado.

Una VPN usa un túnel cifrado. ExpressRoute ofrece conectividad privada mediante un proveedor; el cifrado es un requisito aparte. El peering conecta VNets, con limitaciones que hay que estudiar.

Un endpoint público es accesible mediante direccionamiento público según controles del servicio. Eso no significa acceso anónimo. Un endpoint privado permite llegar a un servicio compatible mediante una dirección privada de una VNet.

**Ejemplo:** la cuenta de almacenamiento puede mantener un endpoint público y exigir autenticación. Que un recurso tenga URL pública no demuestra que cualquiera pueda leerlo.

## 5. Almacenamiento, traslado y migración

Blob Storage encaja con objetos como PDFs. Azure Files ofrece recursos compartidos. Managed Disks sirve a máquinas virtuales. La opción correcta depende del patrón de uso, no solo de cuánto ocupa el archivo.

Los niveles de acceso cambian el equilibrio entre almacenar y recuperar. Un documento usado continuamente no suele encajar en Archive. Tampoco elegiría redundancia geográfica esperando recuperar cualquier versión anterior: replicación y backup resuelven riesgos distintos.

Para mover datos, distinguiría:

- **AzCopy:** transferencias automatizables mediante comandos.
- **Storage Explorer:** interacción gráfica con recursos de almacenamiento.
- **Azure File Sync:** sincronización y caché de archivos en escenarios compatibles con Windows Server.
- **Azure Migrate:** descubrimiento, evaluación y migración según la carga.
- **Data Box:** transferencia mediante dispositivos en escenarios compatibles cuando la red no resulta adecuada.

Migrar no consiste solo en copiar. También hay que validar permisos, integridad, dependencias y cómo se cambia al sistema nuevo.

## 6. Identidad y defensa en profundidad

Entra ID gestiona identidades. Entra Domain Services ofrece servicios de dominio administrados para escenarios compatibles. No hay que tratarlos como nombres intercambiables.

SSO reduce la necesidad de autenticarse repetidamente. MFA añade factores. Passwordless evita la contraseña en métodos compatibles. Ninguno elimina por sí solo la necesidad de autorización.

**Zero Trust** implica verificar explícitamente, aplicar mínimo privilegio y asumir que pueden producirse brechas. Defensa en profundidad combina capas: identidad, red, aplicación, datos y operación.

En nuestra app, un estudiante autenticado no debería poder modificar apuntes de otro solo cambiando un identificador en la URL. Esa comprobación corresponde a la autorización de la aplicación.

Defender for Cloud ayuda a evaluar postura y proteger cargas según configuración y planes. No reemplaza al equipo que analiza y corrige las recomendaciones.

## 7. Gobierno, herramientas y observación

| Necesidad | Herramienta o concepto |
|---|---|
| Restringir regiones permitidas | Azure Policy |
| Dar lectura a un equipo | Azure RBAC |
| Reducir borrados accidentales | Bloqueos de administración |
| Clasificar recursos por proyecto | Etiquetas |
| Gobierno y protección de datos | Capacidades de Microsoft Purview |
| Administrar servidores de otros entornos desde Azure | Azure Arc, según recurso y funciones |
| Recomendaciones de mejora | Azure Advisor |
| Incidencias que afectan a servicios usados | Service Health |

Portal, CLI y PowerShell son interfaces distintas para administrar. Cloud Shell ofrece una experiencia de shell administrada; no hace falta instalar todo en el portátil, pero sus características y persistencia dependen de la configuración.

ARM es la capa de administración. Las plantillas ARM y Bicep permiten describir infraestructura. Describirla en código mejora revisión y repetibilidad; no garantiza que el diseño sea correcto.

Monitor reúne métricas, registros y alertas. Application Insights aporta observación de aplicaciones. Log Analytics permite consultar los registros disponibles. No todos los logs aparecen automáticamente: hay que configurar su recogida.

## 8. Costes y decisiones con números

Una app tiene 100 GB de documentos, pocas lecturas y picos de tráfico. La factura no será solo 100 GB multiplicados por una tarifa: pueden contar operaciones, recuperación, transferencia, cómputo y monitorización.

Un presupuesto alerta; no constituye un interruptor universal de gasto. Una calculadora estima; no es una factura garantizada. Las etiquetas ayudan a analizar costes, pero no organizan permisos por sí solas.

Para comparar dos opciones, escribiría supuestos: horas encendidas, tráfico, región, redundancia y retención. Si cambian esos supuestos, recalcularía. No elegiría un compromiso de consumo a largo plazo para una práctica de una tarde.

## 9. Práctica sin necesidad de desplegar

Diseña en papel la aplicación de apuntes:

1. Elige dónde ejecutar la API y justifica el nivel de control.
2. Separa documentos y metadatos.
3. Identifica quién debe autenticarse.
4. Propón una regla de gobierno y un rol de acceso.
5. Explica qué fallo tolera el diseño.
6. Enumera cinco componentes de coste.
7. Escribe una señal que usarías para comprobar que funciona.

**Resultado esperado:** una tabla de decisiones y un dibujo donde cada componente tenga una razón. Si solo hay una lista de nombres, falta la parte importante.

Después puedes realizar el [laboratorio general](../../es/13-laboratorios.md), revisando costes y limpieza.

## 10. Preguntas originales con explicación

**Una empresa quiere conservar servidores propios e integrar servicios de Azure. ¿Qué modelo describe?** Híbrido. El dato importante es la integración de entornos, no que el proveedor sea Microsoft.

**¿MFA concede permiso de lectura a una base de datos?** No. Refuerza autenticación; la autorización se configura por separado.

**¿Qué elegir para impedir despliegues fuera de regiones aprobadas?** Una política con el efecto y ámbito apropiados. Una etiqueta documenta, pero no bloquea por sí sola.

**¿Qué investigar si una web tiene CPU baja y mucha latencia?** Dependencias, red, bloqueos y consultas. La CPU es solo una señal.

**¿Dos regiones eliminan las copias de seguridad?** No. Un error lógico puede afectar a datos replicados.

**¿Qué falta si solo hemos comprobado que el despliegue terminó?** Validar el comportamiento de la aplicación y sus dependencias.

## 11. Cómo repasaría

Primero explicaría cada comparación sin mirar. Después resolvería escenarios cambiando un requisito: control del sistema, acceso privado, pérdida de datos tolerable o presupuesto. Por último revisaría los objetivos oficiales y marcaría lo que todavía no sé explicar.

No usaría un porcentaje de aciertos memorizados como única prueba de preparación. Poder justificar por qué descartas una alternativa dice más que reconocer una respuesta.

**Criterio de salida:** explicar diez decisiones distintas, corregir tus errores y completar una práctica entendiendo qué has creado.
