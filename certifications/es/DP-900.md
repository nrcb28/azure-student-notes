## 1. Empezar por la pregunta que deben responder los datos

En nuestra app universitaria de apuntes, descargar un archivo, registrar una matrícula y consultar la actividad mensual son cargas distintas. Antes de elegir un producto, escribiría la operación que necesitamos resolver. ¿Qué registros deben cambiar juntos? ¿Cuánto retraso admite un resultado? ¿Quién puede leer los datos? Guardar un PDF no obliga a utilizar una base de datos, y trabajar con JSON tampoco obliga a descartarla.

## 2. Representación y carga de trabajo son decisiones diferentes

Los datos estructurados siguen una organización explícita, como una tabla de matrículas con columnas tipadas. Los semiestructurados contienen organización sin exigir que todos los registros tengan campos idénticos: un documento JSON puede incorporar metadatos opcionales. Una hoja escaneada se considera no estructurada al buscar en su contenido, aunque su nombre de archivo siga una convención.

CSV resulta cómodo para intercambios tabulares pequeños, pero exige acordar codificación, separador y tratamiento de valores ausentes. JSON permite estructuras anidadas. Parquet organiza los datos por columnas y suele encajar en lecturas analíticas. El formato, por sí solo, no aporta permisos, reglas de negocio ni calidad.

Una carga transaccional suele realizar operaciones concretas: reservar una plaza y actualizar la capacidad restante de forma coherente. Una carga analítica resume el historial: comparar matrículas por asignatura y trimestre. Una base puede participar en ambas, pero un informe pesado puede competir con la aplicación en uso. Conviene definir la frescura aceptable en vez de pedir «tiempo real» sin explicar para qué.

## 3. El diseño relacional hace explícitas las relaciones

Imagina Estudiantes, Asignaturas y Matrículas. Una clave primaria identifica una fila; una clave externa expresa una relación cuando la base impone esa restricción. Matrículas conecta estudiantes y asignaturas sin copiar el título de la asignatura en cada registro del estudiante. La normalización reduce determinadas duplicaciones y anomalías de actualización; no exige dividir cualquier esquema hasta que resulte incómodo para todas las consultas.

Una tabla guarda filas. Una vista presenta una consulta almacenada; no es necesariamente una copia independiente de sus resultados. Un índice facilita ciertos accesos y añade almacenamiento y trabajo de escritura. Un procedimiento almacenado agrupa operaciones en la base. Las transacciones ayudan a mantener cambios relacionados coherentes según la concurrencia y el aislamiento del motor. No corrigen una regla de negocio que nunca se definió.

Hay que entender para qué sirven SELECT, INSERT, UPDATE, DELETE, CREATE y GRANT. Antes de un UPDATE o DELETE, predice las filas afectadas y comprueba la condición con datos de ejemplo. Una instrucción correcta puede modificar los registros equivocados.

## 4. Elegir el modelo operativo de Azure SQL

Azure SQL Database es un servicio de base de datos administrado. Azure SQL Managed Instance ofrece compatibilidad orientada a instancia para muchas aplicaciones existentes de SQL Server. SQL Server en una VM de Azure proporciona acceso al sistema operativo y deja más administración al equipo. Compartir sintaxis de consultas no significa compartir despliegue, compatibilidad y responsabilidades de mantenimiento.

Para una app nueva de apuntes compararía funciones necesarias, conexiones, recuperación, esfuerzo operativo y forma de la carga. En una migración, primero inventariaría las dependencias: las funciones de instancia y los componentes externos pueden cambiar la elección. «Administrado» no elimina nuestra responsabilidad sobre acceso, esquema, consultas o requisitos de recuperación. PostgreSQL y MySQL también tienen servicios administrados en Azure; respetar el motor existente puede importar más que adoptar terminología de SQL Server. Comprueba el producto y la versión compatibles, sin tratar todos los motores como intercambiables.

[Fuente: alternativas de Azure SQL](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview).

## 5. Objetos, recursos compartidos y entidades cubren necesidades distintas

Blob Storage guarda objetos como PDF e imágenes. Azure Files ofrece recursos compartidos administrados para requisitos de acceso a archivos compatibles. Table Storage guarda entidades con un modelo no relacional; no es un servicio de tablas SQL relacionales. Un disco administrado pertenece, además, a otra abstracción de almacenamiento.

Un diseño posible para la app mantiene los archivos en Blob y sus metadatos de propiedad en una base. Hay que documentar cómo conservamos la coherencia si una subida falla a mitad. Separar archivo y metadatos es una decisión de diseño, no una coordinación transaccional automática. El permiso para crear una cuenta de almacenamiento también es distinto del permiso para leer sus blobs. Trata un token de descarga como una credencial y no lo pegues en apuntes compartidos.

[Fuente: servicios de Storage](https://learn.microsoft.com/en-us/azure/storage/common/storage-introduction).

## 6. Entender cuándo encaja una base documental

Azure Cosmos DB cubre escenarios de aplicaciones no relacionales mediante sus API y modelos admitidos. Un documento puede representar metadatos variables de una asignatura sin convertir cada atributo opcional en una columna relacional. Eso no demuestra que cualquier carga deba ir allí.

Parte de las lecturas, actualizaciones, relaciones, necesidades de coherencia y restricciones operativas de la aplicación. Un lenguaje de consulta parecido a SQL no implica comportamiento relacional ni joins relacionales sin restricciones. Para fundamentos, debes poder comparar un documento, una entidad clave-valor, un objeto y una fila relacional. La implementación detallada de aplicaciones y el ajuste de rendimiento quedan fuera de esta unidad.

[Fuente: introducción a Cosmos DB](https://learn.microsoft.com/en-us/azure/cosmos-db/overview).

## 7. Seguir el recorrido de los datos

El procesamiento por lotes trabaja con un conjunto acotado, como las descargas de ayer. El procesamiento en streaming atiende eventos que llegan con un retraso limitado, pero sigue necesitando gestionar duplicados, eventos tardíos y fallos. Que un panel cambie cada segundo no demuestra que todos los eventos de origen hayan llegado.

ETL transforma los datos antes de cargarlos en el destino previsto. ELT los carga y los transforma utilizando las capacidades del destino. Ninguna sigla garantiza datos limpios. Define identificadores, tipos, tratamiento de registros rechazados y comprobaciones de conciliación. Cuenta los eventos de origen, aceptados y rechazados; explica las diferencias. La orquestación coordina pasos, dependencias y recuperación tras un fallo; es distinta de la transformación en sí.

[Fuente: ETL y ELT](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/etl).

## 8. Convertir lo almacenado en análisis útil

Un lago de datos puede conservar información variada para procesarla después. Un almacén de datos organiza información analítica para consultas e informes coherentes; un lakehouse combina enfoques. Una carpeta llena de archivos necesita propietarios, formatos, calidad y mecanismos de descubrimiento para resultar útil. En un modelo en estrella, una tabla de hechos registra eventos medibles y las dimensiones añaden contexto descriptivo; define primero el nivel de detalle, antes de sumar.

Azure Synapse Analytics aporta capacidades analíticas y opciones de integración. Microsoft Fabric reúne varias cargas de datos y análisis en una plataforma SaaS. Power BI permite trabajar con modelos semánticos, informes y paneles. Son funciones relacionadas, no nombres intercambiables. Antes de dibujar una gráfica, define una medida como descargas completadas, su zona horaria y el límite de actualización. Dos informes con buen aspecto pueden estar contando cosas diferentes.

[Fuente: introducción a Fabric](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview).

## 9. Ejercicio de diseño y evidencias

Sin crear recursos en la nube, dibuja un diseño para PDF, matrículas e informes mensuales de descargas. Prepara seis registros sintéticos, incluido un evento duplicado y otro sin identificador de asignatura. Elige un almacén para cada conjunto, fija el retraso admisible del informe y describe el tratamiento del duplicado y del registro inválido. Escribe una consulta SQL de ejemplo o explica su resultado esperado en papel. Separa una predicción de diseño de un resultado observado al ejecutar.

Un DBA se ocupa de la operación de la base; un ingeniero de datos, de mover y transformar datos; un analista, de responder preguntas mediante modelos e informes. Las funciones se solapan: asigna un responsable a cada comprobación de calidad. Compara el diseño con el [capítulo general de datos](../../es/04-storage.md) y resuelve los [diez casos](DP-900-cases.md) antes de abrir sus respuestas.

Son apuntes independientes, sin cobertura exhaustiva del examen ni garantía de aprobar. No se afirma haber desplegado Azure. Los servicios y objetivos cambian: vuelve a la guía oficial antes de reservar el examen.
