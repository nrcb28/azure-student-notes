# AZ-140 · Configuración y operación de Microsoft Azure Virtual Desktop

[Certificaciones](README.md) · [10 casos](AZ-140-cases.md) · [Cuaderno](AZ-140-workbook.md) · [English](../en/AZ-140.md)

Yo estudiaría Azure Virtual Desktop (AVD) como un aula de informática cuyas máquinas pueden sustituirse mientras cada estudiante conserva su entorno. El ejemplo entrega la aplicación de apuntes y las herramientas de programación a una clase de mañana. Lo importante es que el estudiante pueda iniciar sesión, recuperar su perfil y trabajar con una experiencia aceptable.

Referencia consultada el **2026-11-01**: [guía oficial AZ-140](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/az-140), objetivos desde el **2026-07-20**. La credencial asociada es [Azure Virtual Desktop Specialty](https://learn.microsoft.com/en-us/credentials/certifications/azure-virtual-desktop-specialty/). Son apuntes propios; no cubren exhaustivamente los objetivos, no contienen preguntas oficiales y no garantizan aprobar.

## 1. Dibujar las responsabilidades del servicio y del equipo

Microsoft opera el broker, la puerta de enlace y otros componentes del servicio AVD. Nosotros seguimos siendo responsables de las VM de sesión, imágenes, aplicaciones, red, integración de identidad, almacenamiento de perfiles y políticas de operación. Un plano de control disponible no arregla un recurso compartido de perfiles sin capacidad.

Un host pool agrupa los hosts de sesión con configuración común. Un grupo de aplicaciones define escritorios o RemoteApps publicados y sus asignaciones; un workspace reúne los grupos registrados en la fuente de recursos del usuario. El host de sesión es la VM que ejecuta la sesión. Dibuja estas relaciones antes de diagnosticar una lista de recursos vacía. Aquí usamos recursos de Azure Resource Manager: AVD classic y Remote Desktop Services administrado por el equipo tienen modelos de gestión distintos.

## 2. Elegir capacidad compartida o personal con un motivo

Un pool compartido reparte los hosts entre usuarios; las imágenes compatibles de Windows Enterprise multisesión permiten varias sesiones concurrentes. Un pool personal asigna escritorios individuales, de forma automática o directa según el requisito. Esa asignación personal y el permiso sobre un grupo de aplicaciones resuelven problemas distintos.

Para el aula de puestos intercambiables, empezaría evaluando escritorios compartidos. Un investigador que necesita una máquina dedicada puede justificar asignación personal. Antes de elegir tamaño y sesiones máximas, mide CPU, memoria, disco, gráficos y comportamiento de las aplicaciones con una carga representativa. Ni la palabra multisesión ni el número de núcleos demuestran una densidad segura. Registra el sistema operativo y la elegibilidad de licencia: los requisitos de Windows cliente y Windows Server son diferentes. [Requisitos previos](https://learn.microsoft.com/en-us/azure/virtual-desktop/prerequisites).

## 3. Separar identidad, derecho al recurso e inicio de sesión

Microsoft Entra ID autentica el acceso a AVD. Existen configuraciones compatibles de hosts unidos a Entra, a un dominio AD DS y a Microsoft Entra Domain Services. AD DS es el servicio de dominio tradicional; Entra Domain Services ofrece capacidades de dominio administradas; Entra ID no es un controlador de dominio. La elección depende de aplicaciones, políticas, almacenamiento de perfiles y autenticación.

Sigue por separado la autenticación de la fuente de recursos, la asignación del grupo de aplicaciones, el inicio de sesión en el host y el acceso a archivos. Contributor sobre las VM no concede automáticamente un escritorio al estudiante. Planifica SSO y acceso condicional para el cliente, tipo de unión, método de autenticación y aplicaciones de servicio concretos. Una segunda petición de contraseña es una pista para investigar, no una prueba de fallo del acceso condicional. Separa la administración privilegiada del acceso del alumnado.

## 4. Explicar el recorrido real de la conexión

La conexión inversa básica establece conectividad saliente HTTPS/TCP desde el cliente y el host hacia los servicios AVD. No requiere publicar TCP 3389 en los hosts. Comprueba destinos exigidos, DNS, proxy y rutas.

RDP Shortpath añade transporte UDP cuando es compatible. La opción de listener administrado necesita alcance privado directo y un listener configurado, normalmente UDP 3390. Las opciones ICE/STUN para redes administradas o públicas descubren una ruta utilizable; TURN puede retransmitir sesiones compatibles de red pública. Sus requisitos son diferentes: una regla para el listener privado no es una configuración universal de Shortpath. La conexión inversa TCP queda como alternativa si no se establece UDP. Revisa compatibilidad del cliente, plataforma y nube. Compara transporte negociado, latencia, pérdidas y latencia del host al almacenamiento de perfiles. [Requisitos de Shortpath](https://learn.microsoft.com/en-us/azure/virtual-desktop/configure-rdp-shortpath) · [Fundamentos de red](../../es/05-networking.md).

## 5. Conservar perfiles fuera de hosts reemplazables

Los contenedores de perfil FSLogix conservan el perfil en almacenamiento compatible, sin depender del disco local de una VM compartida. Separa los datos oficiales de la app de apuntes de las preferencias y cachés del escritorio. La persistencia del perfil no equivale automáticamente a una copia de seguridad de los datos de la aplicación.

Para almacenamiento SMB, valida permisos del recurso compartido y permisos NTFS. Elige una combinación de identidad y Kerberos compatible con la unión del host y el servicio de almacenamiento; revisa DNS, tickets, hora y cifrado. Entrar en el portal de Azure no demuestra ninguna de esas condiciones. Dimensiona capacidad y latencia para los picos de inicio de sesión. La conexión predeterminada a un contenedor no autoriza escrituras simultáneas arbitrarias. Planifica desconexiones, bloqueos, copia, restauración y objetivos de recuperación. Varias rutas configuradas no demuestran por sí solas resiliencia. [Ejemplos de configuración FSLogix](https://learn.microsoft.com/en-us/fslogix/concepts-configuration-examples).

## 6. Elegir y validar cómo se entregan las aplicaciones

Instalar aplicaciones compatibles en la imagen base resulta directo, pero vincula sus actualizaciones al ciclo de la imagen. Un proceso administrado de instalación puede actualizar otras aplicaciones por separado. App Attach permite entregar paquetes compatibles desde almacenamiento accesible. Publicar una RemoteApp controla presentación y permisos; empaquetar controla la entrega. Son decisiones relacionadas, pero distintas.

Para el editor de apuntes, documenta dependencias, licencia, compatibilidad del paquete, acceso al almacenamiento y asignaciones al pool y al usuario. Prueba primer arranque, actualizaciones y un segundo usuario en un host multisesión. No supongas que cualquier instalador se convierte en un paquete funcional ni uses instrucciones antiguas de MSIX app attach como modelo actual de gestión. Conserva una versión alternativa probada. [App Attach actual](https://learn.microsoft.com/en-us/azure/virtual-desktop/app-attach-overview).

## 7. Tratar las imágenes como versiones de software

Construye una imagen de referencia documentada: sistema compatible, agentes, aplicaciones, seguridad y estado de actualizaciones. Conserva entradas de construcción y versiones para reconstruir el aula. Azure Compute Gallery distribuye versiones; repasa los [fundamentos de cómputo](../../es/03-compute.md) antes de planificar el ciclo de las VM.

Introduce la nueva versión en un grupo pequeño de validación. Comprueba autenticación, perfil, edición de apuntes, impresión o redirección cuando se requieran, y rendimiento. Pon los hosts antiguos en drenaje para impedir nuevas sesiones, gestionando las existentes según la política de mantenimiento: drenar no cierra instantáneamente todas las sesiones. Sustituye hosts gradualmente. Conserva la imagen anterior y una vuelta atrás que respete la capacidad necesaria. Parchear todos los hosts activos a la vez debilita una dependencia compartida del aula.

## 8. Ajustar el escalado al horario de clase

Un plan de escalado gobierna comportamientos compatibles mediante horarios y capacidad. Distingue el encendido de hosts existentes de la creación y eliminación dinámica de hosts, cuyas condiciones y disponibilidad deben comprobarse. Start VM on Connect inicia hosts detenidos aptos cuando los usuarios conectan; no es una estrategia completa de horario o reserva de capacidad.

Si llegan 48 estudiantes y el límite medido es de 12 sesiones por host, cuatro hosts disponibles cubren la demanda sin margen para fallos. Cinco dejan margen para perder uno bajo esas condiciones. Modela arranque, hosts enfermos, drenaje y límites de almacenamiento. Especifica permisos del servicio, exclusiones y política para sesiones activas antes de reducir capacidad. El cálculo de ahorro también debe considerar discos, almacenamiento, red, monitorización y licencias. [Requisitos del plan de escalado](https://learn.microsoft.com/en-us/azure/virtual-desktop/autoscale-create-assign-scaling-plan).

## 9. Seguir una conexión fallida mediante evidencias

Registra hora UTC, usuario seudonimizado, versión de cliente, recurso, host e identificador de correlación. Relaciona conexiones, checkpoints, errores, salud del agente y registros de red con rendimiento del host y logs de FSLogix. Configura diagnósticos y recolección del host antes de esperar evidencias históricas. AVD Insights ayuda a investigar la experiencia, pero también necesita configurar su recopilación de datos.

Distingue una fuente de recursos vacía, un inicio de sesión fallido, un perfil lento y una aplicación lenta tras entrar. La ausencia de registro de conexión puede significar que el intento nunca llegó a AVD. Compara una sesión correcta a la misma hora y evita recoger apuntes o credenciales. [Categorías y correlación de diagnósticos](https://learn.microsoft.com/en-us/azure/virtual-desktop/diagnostics-log-analytics).

## 10. Ensayar la recuperación sin desplegar

Realiza una simulación sobre papel para un pico de inicios de sesión, un host no disponible y un recurso compartido de perfiles inaccesible. Escribe predicciones, evidencia necesaria, responsable, condiciones de vuelta atrás y criterio claro de recuperación. Restaurar VM no restaura por sí solo identidad, DNS, paquetes, perfiles ni la API de apuntes.

Acuerda objetivos de tiempo y punto de recuperación para perfiles y datos de la app por separado. Incluye dependencias de otra región, coherencia de perfiles, capacidad disponible y retorno a la región principal. Asigna responsables a costes continuos y alertas. Completa los [diez casos](AZ-140-cases.md) y las [cinco unidades](AZ-140-workbook.md). Estos ejercicios no cambian un tenant ni acreditan despliegues o conmutaciones probados en Azure.
