## 1. Identidades: directorio y recursos no son lo mismo

Entra ID contiene usuarios, grupos y otras identidades. Los roles del directorio administran aspectos de ese directorio. Azure RBAC autoriza acciones sobre recursos. Tener un rol de administración de usuarios no equivale a ser Owner de una suscripción.

Para gestionar acceso de un equipo, preferiría un grupo frente a asignaciones individuales repetidas. Hay que considerar el tipo de grupo, sus miembros y quién puede modificarlos. Si el grupo tiene privilegios, la capacidad de cambiar sus miembros también importa.

Los usuarios invitados colaboran mediante identidades externas. Invitar a alguien no debería concederle acceso amplio: hay que asignar el recurso y permiso concreto. Revisa también las políticas del directorio.

SSPR permite restablecimiento de contraseña bajo métodos, licencias y configuración compatibles. No asumiría que habilitarlo para algunos usuarios lo habilita para todos o que todos han registrado métodos válidos.

### Interpretar una asignación

Una identidad tiene Reader en la suscripción y Contributor en un grupo. Dentro de ese grupo reúne los permisos concedidos por ambas asignaciones; fuera no obtiene Contributor.

Quitar una asignación directa de un recurso puede no eliminar un acceso heredado. Para diagnosticar, revisaría identidad efectiva, pertenencia a grupos, ámbito, rol, condiciones aplicables y propagación.

Las exclusiones NotActions de una definición de rol no constituyen una denegación global. Otra asignación puede conceder esa acción. Las deny assignments tienen otro funcionamiento.

**Fuente técnica:** [modelo de Azure RBAC](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview).

## 2. Gobierno y administración de suscripciones

Un grupo de administración es útil para reglas compartidas entre suscripciones. Un grupo de recursos es útil para ciclo de vida. No organizaría producción y pruebas únicamente con nombres si requieren permisos o políticas distintas.

Para introducir Policy en un entorno existente:

1. Elegir un ámbito acotado.
2. Revisar parámetros y exclusiones.
3. Auditar el impacto.
4. Configurar identidad y permisos si el efecto lo requiere.
5. Ejecutar remediación cuando corresponda.
6. Comprobar nuevos despliegues y recursos previos.

Los bloqueos ReadOnly y CanNotDelete operan sobre administración y pueden tener efectos sobre operaciones que parecen lectura pero usan POST. No cubren de forma general todas las acciones de datos.

Mover recursos exige comprobar soporte, dependencias y restricciones de origen y destino. Cambiar de región puede requerir un procedimiento diferente a mover de grupo. No lo trataría como una operación universal de cortar y pegar.

**Ejemplo:** antes de eliminar un grupo antiguo, listar sus recursos y comprobar bloqueos, dependencias y recuperación. El nombre old no demuestra que esté sin uso.

## 3. Almacenamiento: separar autorización, red y protección

Si falla una operación sobre un blob, comprobaría tres preguntas: ¿llego al servicio?, ¿quién soy?, ¿puedo ejecutar esta acción? Cambiar permisos no arregla DNS y abrir la red no arregla un rol de datos ausente.

### Formas de acceso

- Entra ID con roles de datos permite permisos asociados a identidades.
- Una clave de cuenta tiene alcance amplio; no conviene repartirla a cada aplicación.
- Una SAS delega permisos con restricciones y caducidad.
- Las stored access policies se aplican a tipos de SAS compatibles, no a todas.
- Una user delegation SAS para Blob utiliza una delegación basada en Entra ID.

Una SAS es una credencial. No la pegaría en issues, capturas ni logs. Revocarla depende de cómo se emitió; no asumir que todos los tokens se revocan del mismo modo.

### Protección de datos

Versionado conserva versiones cuando está soportado y configurado. Soft delete facilita recuperar objetos o contenedores dentro de su retención. Las snapshots de Azure Files aportan puntos de recuperación según configuración.

Las reglas de ciclo de vida automatizan transiciones y eliminación según condiciones. Antes de aplicarlas, revisaría si afectan a versiones antiguas y si existen requisitos de retención o inmutabilidad.

La replicación de objetos tiene requisitos de cuenta, versiones, políticas y blobs compatibles. No es una solución genérica para cualquier protocolo o dato.

Para Azure Files, distinguiría permisos de acceso al recurso compartido y permisos de directorio/archivo cuando se utilice autorización basada en identidad. Revisaría protocolo, conectividad y compatibilidad del entorno de identidad.

**Práctica:** completar el [laboratorio de almacenamiento](../../es/13-laboratorios.md) y explicar por qué un Contributor puede crear la cuenta y aun así no listar blobs.

## 4. VM: inventario, cambios y disponibilidad

Una VM necesita más que una imagen: tamaño, discos, interfaz, subred y configuración de acceso. Una IP pública no es obligatoria para toda VM.

Para una incidencia de arranque:

1. Verificar estado y diagnósticos.
2. Revisar cambios recientes y espacio de disco.
3. Diferenciar fallo del sistema de fallo de red.
4. Utilizar herramientas de recuperación compatibles.
5. Evitar borrar discos sin copia y sin entender su función.

El disco temporal de una VM no debe tratarse como almacenamiento persistente. Un disco de datos tampoco se convierte en backup por estar separado del disco del sistema.

Redimensionar puede necesitar reinicio o desasignación, y la disponibilidad del tamaño depende de restricciones y capacidad. Comprobaría compatibilidad antes de prometer un cambio sin interrupción.

Las zonas y availability sets resuelven distribución de fallos de forma diferente. VM Scale Sets coordina grupos de instancias; aun así necesita imagen, escalado, actualización y health checks adecuados.

El cifrado de discos y encryption at host actúan en capas distintas. Hay que comprobar compatibilidad de tamaño y configuración en lugar de asumir que activar una opción cubre cualquier ubicación de datos.

## 5. PaaS, contenedores y despliegue declarativo

El App Service Plan proporciona capacidad a las apps alojadas. Escalar el plan y cambiar el número de instancias no es lo mismo que cambiar código.

Un dominio personalizado necesita validación y DNS. HTTPS necesita certificado válido y enlace apropiado. Resolver el nombre correctamente no demuestra que TLS esté configurado.

Los slots permiten preparar otra versión si el plan lo admite. Revisaría qué ajustes son específicos del slot y qué dependencias comparten: una aplicación de pruebas no debería escribir sin querer en la base de producción.

**Red de App Service:** la integración con VNet ayuda a conexiones salientes hacia recursos de la red. No convierte automáticamente la entrada de la web en privada. Para la entrada, revisar private endpoints y controles compatibles. [Referencia de integración](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration).

En contenedores, el registro almacena imágenes; el servicio de ejecución las inicia. Un error de pull puede deberse a credenciales, red, nombre o etiqueta inexistente.

Para Bicep o ARM, leería parámetros, recursos, dependencias y outputs antes de ejecutar. Un recurso exportado no siempre produce una plantilla reutilizable y limpia: puede requerir revisión.

## 6. Redes: razonar con reglas y rutas efectivas

Ejemplo: VNet 10.30.0.0/16, subred web 10.30.1.0/24 y datos 10.30.2.0/24. Una regla permite HTTPS desde un origen concreto a web. Eso no concede acceso a la base de datos ni acceso de aplicación.

Los NSG evalúan prioridades: un número menor se evalúa antes. Si hay NSG en subred e interfaz, la conexión debe superar los filtros aplicables. Son filtros con estado; cambiar una regla no equivale necesariamente a cortar cada conexión ya establecida.

Las application security groups ayudan a referenciar grupos lógicos de interfaces en reglas. Los service tags representan conjuntos de direcciones mantenidos por Azure; no son usuarios ni identidades de aplicación.

Las rutas se seleccionan considerando prefijos y origen según las reglas de Azure. Para diagnosticar, consultaría rutas efectivas antes de agregar rutas a ciegas.

**Fuente técnica:** [NSG](https://learn.microsoft.com/en-us/azure/virtual-network/network-security-groups-overview).

### DNS y balanceo

Una zona privada necesita enlaces y resolución adecuados para sus consumidores. Crear un private endpoint sin revisar DNS puede dejar al cliente usando el endpoint público.

En un balanceador comprobaría frontend, backend, regla y health probe. Un backend sano necesita responder al sondeo y atender tráfico real. Permitir el sondeo pero bloquear el puerto de la app no basta.

Bastion permite acceso administrativo mediante mecanismos compatibles sin exponer directamente RDP o SSH de cada VM a Internet. Su despliegue también tiene requisitos y coste.

## 7. Monitorización con un objetivo

Definiría primero qué significa estar bien: proporción de peticiones correctas, latencia y capacidad de procesar documentos. Después elegiría métricas, logs y alertas.

Los diagnostic settings envían categorías compatibles a destinos configurados. No significa que toda señal de cualquier recurso aparezca en un workspace sin más.

Una alerta tiene ámbito, señal, condición y acciones. Un action group configura destinatarios y acciones. Las alert processing rules permiten modificar el procesamiento de notificaciones según reglas; no arreglan la causa del incidente.

Network Watcher y Connection Monitor ayudan a investigar conectividad. Antes de atribuirlo todo al firewall, comprobaría resolución, ruta, regla efectiva y escucha del proceso.

**Ejercicio:** un backend aparece unhealthy. Documenta qué puerto usa el sondeo, qué respuesta espera, qué reglas lo permiten y si el proceso realmente está escuchando.

## 8. Backup y recuperación

Recovery Services vault y Backup vault soportan diferentes cargas y capacidades. Elegir el almacén depende del recurso protegido, no de cuál nombre nos resulte familiar.

Una política define calendario y retención. La evidencia importante es que se generan puntos de recuperación y que una restauración sirve para el objetivo.

Site Recovery replica cargas compatibles para recuperación. Un test failover permite comprobar una recuperación sin confundirlo con el cambio real de producción; hay que preparar aislamiento y limpieza de la prueba.

Antes de un failover, revisaría RPO, salud de replicación, red de destino, DNS y dependencias. Después comprobaría servicio y plan de retorno.

## 9. Laboratorio operativo propuesto

En una suscripción de pruebas:

1. Reutiliza el laboratorio general y conserva sus variables.
2. Consulta las asignaciones de acceso desde el portal, sin modificarlas de forma amplia.
3. Comprueba etiquetas, configuración de almacenamiento y autenticación.
4. Revisa métricas disponibles y escribe qué alerta configurarías.
5. Dibuja una VNet con dos subredes sin desplegar recursos de red adicionales.
6. Predice qué reglas permitirían API a datos.
7. Explica una restauración de un archivo y qué configuración habría hecho falta.
8. Ejecuta la limpieza del laboratorio general.

No se ha desplegado este ejercicio en Azure desde estos apuntes. Entrega resultados esperados y observados por separado.

## 10. Casos para pensar

**Puede crear cuentas, pero no descargar blobs.** Revisar rol de datos y método de autenticación antes de aumentar a Owner.

**Puede entrar por IP, pero no por nombre.** Revisar DNS, certificado y host esperado; no concluir automáticamente que es NSG.

**El slot nuevo funciona con la base real.** Revisar ajustes y conexiones específicas del slot antes del intercambio.

**Una regla nueva no corta una sesión existente.** Considerar el comportamiento con estado, el origen real y reglas efectivas.

**El backup figura como correcto, pero no hay servicio recuperado.** El trabajo de copia y la recuperación de una aplicación completa son evidencias distintas.

**Preparación:** ser capaz de describir los pasos, predecir un resultado y justificar cómo comprobarlo sin recurrir siempre a permisos amplios.
