# AZ-305 · Designing Microsoft Azure Infrastructure Solutions

[Certificaciones](README.md) · [English](../en/AZ-305.md)

## Diseñar es defender decisiones

En arquitectura rara vez existe una opción mejor para todo. Hay una opción que cumple unos requisitos con un coste y una complejidad aceptables. La práctica consiste en explicar esa relación sin esconder los límites.

## 1. Convertir frases vagas en requisitos

Nuestra aplicación universitaria debe admitir documentos de varias facultades. Antes de elegir servicios preguntaría:

- ¿Cuántos usuarios simultáneos y qué crecimiento se espera?
- ¿Qué datos son públicos y cuáles privados?
- ¿En qué países pueden almacenarse?
- ¿Cuánto tiempo puede estar caída?
- ¿Cuántos datos recientes pueden perderse?
- ¿Qué presupuesto y capacidad operativa tiene el equipo?
- ¿Qué integraciones y licencias ya existen?

Separaría requisitos funcionales, como subir un PDF, de atributos de calidad, como latencia y recuperación.

**Ejemplo:** disponible siempre no es verificable. Un objetivo de disponibilidad mensual definido sobre operaciones concretas sí puede medirse. No basta con elegir un recurso que anuncie un SLA parecido: el recorrido completo tiene varias dependencias.

Para un servicio compuesto, multiplicar disponibilidades puede ilustrar el efecto de dependencias en serie bajo supuestos simplificados. No lo usaría como cálculo exacto si los fallos están correlacionados o hay redundancia y degradación parcial.

## 2. Identidad y gobierno a escala

Diseñaría la separación según administración, riesgo, facturación y políticas. Una suscripción para cada pequeño componente puede dificultar la gestión; una única suscripción para todo puede impedir el aislamiento que se necesita.

Los grupos de administración permiten políticas comunes. Las suscripciones delimitan administración y cuotas. Los grupos de recursos agrupan ciclos de vida. Las etiquetas aportan clasificación, pero no son una frontera de seguridad.

Para usuarios, considerar federación y experiencia de inicio de sesión. Para cargas, preferir identidades administradas cuando encajen. Para administradores, limitar privilegios permanentes y revisar elevación temporal y auditoría cuando las capacidades y licencias lo permitan.

Un servicio local que necesita protocolos de dominio no se migra sustituyendo cualquier dominio por Entra ID sin análisis. Hay que revisar dependencia real de Kerberos, LDAP, unión a dominio u otros mecanismos.

**Decisión de ejemplo:** dar a la API acceso de datos solo a sus documentos. Permitir a los desarrolladores desplegar en pruebas no debería convertirlos automáticamente en administradores de producción.

Guardar secretos en Key Vault no basta si cualquier desarrollador puede leerlos o si nunca rotamos los que lo requieren. Diseñar también quién accede, cómo se recuperan y qué ocurre ante una indisponibilidad.

## 3. Observabilidad como parte del diseño

Para una universidad con varios equipos, decidiría dónde se envían los logs, quién los consulta, su retención y su coste. Centralizar facilita correlación; separar puede responder a límites de acceso y residencia. No impondría un único workspace sin estudiar esos requisitos.

La señal de negocio importa: documentos subidos y disponibles para lectura. El estado de una VM es útil, pero no demuestra que un estudiante pueda descargar.

Definiría un SLI, por ejemplo proporción de lecturas correctas, y un SLO con ventana y exclusiones justificadas. Un error budget representa el margen de fallo permitido por ese objetivo. Ayuda a decidir cuándo priorizar fiabilidad.

Los logs deben permitir investigación sin almacenar innecesariamente contenido académico, tokens o datos personales. La retención necesita justificación operativa y legal.

## 4. Elegir almacenamiento y bases de datos

Empezaría por forma de los datos, consultas, consistencia, tamaño, latencia, recuperación y coste.

| Requisito dominante | Alternativa a evaluar | Pregunta pendiente |
|---|---|---|
| Relaciones y transacciones | Base relacional administrada | ¿Qué compatibilidad y capacidad necesita? |
| Compatibilidad avanzada con una instancia SQL existente | SQL Managed Instance u otra ruta compatible | ¿Qué funciones concretas exige la aplicación? |
| Control total del motor y del SO | Base en VM | ¿Podemos asumir mantenimiento y recuperación? |
| Documentos binarios | Blob Storage | ¿Qué acceso, retención y redundancia? |
| Archivos compartidos | Azure Files u opción compatible | ¿Qué protocolo e identidad? |

No escogería Cosmos DB solo porque la aplicación tenga JSON. Hace falta analizar el modelo de consultas y requisitos distribuidos; un formato de serialización no define por sí solo una base de datos.

Escalar lectura no implica escalar escritura. Las réplicas de lectura pueden ayudar con ciertas consultas, pero hay que considerar consistencia y soporte. Un caché introduce invalidación, expiración y riesgo de datos antiguos.

Para compartir capacidad entre bases, estudiar soluciones como elastic pools cuando encajen. Para cargas variables, evaluar opciones serverless compatibles sin asumir que eliminan costes en cualquier circunstancia.

### Integración y análisis

Un proceso ETL o ELT mueve y transforma datos con un propósito analítico. No debería cargar el servidor transaccional con consultas históricas ilimitadas si perjudican al usuario.

Separaría datos operativos de analíticos cuando los patrones lo justifiquen. Elegir herramientas de integración, lago o almacén según volumen, frecuencia, transformación, gobierno y experiencia del equipo.

## 5. Continuidad: diseñar la recuperación completa

Nuestro ejemplo requiere RTO de dos horas y RPO de quince minutos. Son requisitos del ejercicio, no prestaciones atribuidas automáticamente a un producto.

Para satisfacerlos, documentaría:

1. Qué datos tienen cada objetivo.
2. Cómo se crean puntos de recuperación.
3. Qué replica de forma síncrona o asíncrona.
4. Cuánto tarda aprovisionar capacidad de destino.
5. Cómo se restauran identidad, red y configuración.
6. Cómo cambian clientes y DNS.
7. Cómo se valida integridad.
8. Cómo se vuelve al entorno principal.

**Activo-activo** puede repartir tráfico, pero complica datos y coordinación. **Activo-pasivo** reduce ciertas complejidades, aunque puede necesitar más tiempo de recuperación. Un destino vacío no recupera al instante.

Las dependencias también fallan: registro de imágenes, secretos, DNS, automatizaciones y proveedores externos. Una aplicación replicada que no puede obtener credenciales puede seguir caída.

Las pruebas de recuperación deben estar aisladas para no enviar correos reales, cobrar o sobrescribir producción. Medir el tiempo observado y compararlo con el objetivo.

**Fuente de criterios:** [Well-Architected Framework](https://learn.microsoft.com/en-us/azure/well-architected/).

## 6. Cómputo y arquitectura de aplicación

Elegiría VM para requisitos de SO específicos; PaaS para reducir operación cuando encaje; contenedores para empaquetado y despliegue de cargas compatibles; procesamiento batch para trabajos que requieren planificación y ejecución de lotes.

Microservicios no es una obligación. Para un equipo pequeño, un monolito modular puede facilitar transacciones y despliegues. Separaría un componente cuando su escalado, disponibilidad o ciclo de cambios lo justifique.

Para análisis de documentos, una cola permite responder pronto a la subida. Pero la interfaz debe mostrar estados y fallos; la asincronía no hace desaparecer el trabajo.

API Management puede aportar políticas, publicación y control de APIs según nivel y configuración. No sustituye toda la autorización interna. App Configuration puede centralizar configuración y feature flags; no lo usaría como almacén indiscriminado de secretos.

## 7. Redes y entrada de tráfico

Distinguiría tráfico global y regional, web y no web, entrada y salida, público y privado. Esto evita elegir un producto por la palabra balanceador.

- Front Door: entrada global para aplicaciones web en escenarios compatibles.
- Application Gateway: enrutamiento web regional y opciones de WAF.
- Load Balancer: conexiones TCP/UDP en capa 4.
- Traffic Manager: selección mediante DNS, con efectos de caché.

Hub-spoke puede centralizar conectividad y servicios compartidos. No implica que todas las rutas sean correctas automáticamente. Hay que diseñar resolución de nombres, inspección, retorno y evitar caminos asimétricos no deseados.

Para conexión local, comparar VPN y ExpressRoute según ancho de banda, latencia, resiliencia, costes y requisitos. Un circuito privado no sustituye el diseño de cifrado.

Un private endpoint necesita clientes que resuelvan y alcancen la IP privada. Si hay redes locales, la resolución híbrida forma parte de la solución.

## 8. Migrar sin perder dependencias

Antes de mover una aplicación:

1. Inventariar servidores, bases, archivos y dependencias.
2. Medir uso y capacidad reales.
3. Identificar compatibilidad y licencias.
4. Elegir estrategia por carga.
5. Preparar identidad y red.
6. Migrar un piloto.
7. Validar datos y comportamiento.
8. Preparar cutover y rollback.
9. Retirar origen cuando exista evidencia suficiente.

Rehost mueve con pocos cambios; replatform adapta a una plataforma; refactor cambia más la aplicación. Retirar o conservar una carga también pueden ser decisiones válidas.

Azure Migrate ayuda según escenario, pero no reemplaza conversaciones con quienes conocen tareas programadas e integraciones ocultas. Migrar la VM sin su directorio de archivos compartidos puede dejar una aplicación incompleta.

Para datos, elegir una transferencia inicial y una estrategia para cambios durante la migración. El volumen y la ventana de corte deciden tanto como el producto.

## 9. Caso completo con alternativas

**Situación:** cinco facultades, datos privados, subida y descarga de PDFs, picos estacionales y equipo de tres personas.

**Propuesta inicial:** API en PaaS, base relacional administrada para metadatos, Blob para documentos, identidad de carga y cola para análisis. Acceso privado entre componentes si lo justifican requisitos y costes.

**Por qué:** reduce administración de SO y separa binarios de consultas. Permite escalar el procesamiento de documentos de forma distinta al acceso web.

**Qué descartaría inicialmente:** AKS sin necesidad demostrada, varias regiones sin RTO/RPO definidos y una gran plataforma analítica para informes sencillos.

**Qué falta validar:** soporte regional, planes necesarios, autenticación de estudiantes, permisos por documento, backup, recuperación, observabilidad, costes y carga.

**Nueva condición:** los datos no pueden salir de una jurisdicción. Hay que revisar localización de recursos, réplicas, copias, logs y dependencias. No basta con cambiar una sola región.

## 10. Ejercicios de diseño y respuestas

**RPO cero significa RTO cero. ¿Correcto?** No. Pérdida de datos y tiempo de recuperación son objetivos distintos.

**Una solución activa en dos regiones siempre es mejor.** No. Puede incumplir residencia, añadir conflictos o exceder la capacidad operativa.

**Una app exige transacciones relacionales, pero usa JSON en la API. ¿Elegimos NoSQL?** No por ese dato. El requisito transaccional y las consultas pesan más que el formato de intercambio.

**¿Qué documento dejarías para una decisión difícil?** Un ADR con contexto, requisitos, alternativas, decisión, consecuencias y condición de revisión.

### Entrega práctica

Escribe dos ADR: cómputo y recuperación. Incluye una alternativa razonable descartada, una medida de validación y un supuesto que, si cambia, obligaría a revisar la decisión.

**Preparación:** poder defender la solución y explicar qué requisito haría preferible otra opción. Memorizar una arquitectura de referencia no resuelve todos los casos.
