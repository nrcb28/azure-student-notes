## Qué quiero aprender aquí

El objetivo es entregar cambios pequeños, comprobables y recuperables. Un pipeline rápido que publica fallos con rapidez no resuelve el problema.

Referencia consultada el **27 de octubre de 2026**: [guía oficial AZ-400](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/az-400), objetivos desde el **27 de julio de 2026**.

| Área | Peso publicado | Desarrollo |

| Procesos y comunicación | 10–15 % | 1 |
| Control de versiones | 10–15 % | 2 |
| Pipelines de compilación y entrega | 50–55 % | 3 a 7 |

## 1. Flujo de trabajo y comunicación

Para nuestra app, cada cambio debería poder seguirse desde una necesidad hasta una versión desplegada. Issue, pull request, ejecución del pipeline y release necesitan una relación comprensible.

Un tablero útil muestra trabajo pendiente, en curso, bloqueado y terminado. Limitar trabajo en curso puede reducir tareas a medias y facilitar detectar el cuello de botella.

No confundir:

- **Lead time:** tiempo desde el punto de inicio definido hasta la entrega.
- **Cycle time:** tiempo desde que el trabajo entra en ejecución hasta terminar.
- **Frecuencia de despliegue:** cuántas entregas realizamos.
- **Tasa de fallos de cambios:** qué proporción provoca incidentes o requiere intervención.
- **Tiempo de recuperación:** cuánto tardamos en restaurar el servicio.

Hay que definir exactamente inicio y fin para comparar métricas. Medir personas por commits o líneas de código incentiva comportamientos poco útiles.

Las notificaciones deben llegar a quien puede actuar. Un canal lleno de todos los eventos del repositorio acaba ignorado. Las release notes explican cambios y riesgos; un listado de hashes puede no servir al usuario.

Webhooks integran sistemas, pero requieren autenticación o validación apropiada, reintentos y tratamiento de duplicados. No asumir que una notificación llegará una sola vez.

## 2. Git y estrategia de ramas

**Trunk-based** favorece integrar cambios pequeños y frecuentes. **Feature branches** aíslan trabajo durante un tiempo. **Release branches** pueden ayudar cuando hay varias versiones mantenidas. La estrategia debe corresponder al modo de entregar, no a una plantilla popular.

Para una app pequeña usaría ramas cortas, PR y una rama principal protegida. Los cambios grandes pueden dividirse con feature flags para evitar semanas de divergencia.

### Operaciones que hay que entender

- Merge combina historias.
- Rebase reaplica commits y cambia sus identificadores.
- Revert crea un cambio que deshace otro.
- Reset mueve referencias y puede modificar índice y archivos según modo.
- Cherry-pick aplica un cambio seleccionado en otra rama.
- Reflog puede ayudar a encontrar referencias locales anteriores, mientras estén disponibles.

En una rama compartida, revert suele preservar mejor el historial que reescribirlo para deshacer un cambio publicado. No convertir una técnica local en una política universal.

Git LFS almacena archivos grandes mediante punteros y almacenamiento aparte. Añadir LFS hoy no elimina automáticamente los binarios históricos.

Si se publica una credencial, primero revocarla o rotarla. Borrarla del último commit no elimina copias ni historial. La limpieza de historia puede requerir coordinación y herramientas, pero nunca reemplaza la revocación.

## 3. Construir una vez y promover el mismo artefacto

Una ejecución debería producir un paquete o imagen identificable. Ese artefacto pasa de pruebas a producción con configuración del entorno, sin recompilar código diferente por el camino.

Un tag de imagen puede cambiar. Para despliegues reproducibles interesa registrar el digest o un identificador inmutable, además de la relación con el commit.

### Versionado y paquetes

SemVer expresa major, minor y patch según el contrato del proyecto. CalVer usa fechas. Ninguno funciona si publicamos versiones distintas con el mismo identificador.

Feeds como Azure Artifacts o GitHub Packages permiten distribuir dependencias bajo permisos y formatos compatibles. Hay que pensar en paquetes internos, orígenes externos, retención y promoción.

Un lockfile reduce cambios inesperados de dependencias. No garantiza por sí solo que una dependencia sea segura ni que todo el proceso sea reproducible.

**Caso:** el pipeline funcionó ayer y falla hoy sin cambios de código. Revisaría imágenes base, dependencias no fijadas, herramientas del agente y servicios externos.

## 4. Pruebas y puertas de calidad

Las pruebas unitarias validan unidades pequeñas. Las de integración comprueban colaboración real de componentes. Las end-to-end recorren un flujo completo. Las de carga estudian comportamiento con demanda.

No pondría toda la confianza en end-to-end lentas ni solo en unidades aisladas. Elegiría una combinación según los fallos que queremos detectar.

Cobertura indica código recorrido, no calidad automática de aserciones. Un 100 % con pruebas que no comprueban resultados aporta poca confianza.

Una puerta útil debe tener criterio, responsable y procedimiento de excepción. Si todo se puede saltar sin dejar rastro, el control es débil. Si el control bloquea por ruido constante, el equipo buscará rodearlo.

Las pruebas intermitentes necesitan investigación. Repetir hasta verde oculta problemas y altera las métricas. Puede existir una cuarentena temporal con responsable y fecha de revisión, no un olvido permanente.

## 5. Agentes, runners y ejecución

Un runner hospedado reduce mantenimiento. Uno propio puede acceder a redes o herramientas específicas, pero exige parches, aislamiento, capacidad y limpieza.

No ejecutaría código no confiable de forks en un runner persistente que tiene acceso a producción. Un PR puede modificar scripts, no solo archivos de aplicación.

En YAML, distinguir etapas, trabajos y pasos. Las dependencias establecen orden; las condiciones pueden modificar si algo corre. Paralelizar tareas independientes reduce tiempo, pero puede aumentar consumo y conflictos sobre recursos compartidos.

Las plantillas reutilizables reducen repetición. Hay que versionarlas y revisar quién puede cambiarlas, porque un cambio en una plantilla puede afectar a muchos repositorios.

Los cachés aceleran restauraciones; los artefactos transportan resultados. No son intercambiables. Una clave de caché incompleta puede reutilizar datos incompatibles.

## 6. Estrategias de despliegue

| Estrategia | Idea | Riesgo que vigilar |
|---|---|---|
| Rolling | Sustituir instancias progresivamente | Compatibilidad entre versiones |
| Blue-green | Preparar un entorno alternativo y cambiar tráfico | Coste y datos compartidos |
| Canary | Exponer una parte del tráfico | Señales insuficientes o muestra sesgada |
| Rings | Ampliar por grupos sucesivos | Diferencias entre grupos |
| Feature flags | Activar comportamiento sin nuevo despliegue | Deuda de flags y combinaciones |
| A/B | Comparar variantes con un objetivo experimental | No confundir experimento con despliegue seguro |

Un canary no sirve si solo miramos CPU y la funcionalidad nueva devuelve resultados incorrectos. Definir señales, umbral, duración, responsable y cómo revertir.

Los slots no crean una copia aislada de toda la aplicación: pueden compartir dependencias. Revisar configuración, conexiones y comportamiento del intercambio.

### Cambios de base de datos

Aplicaría expand-and-contract cuando encaje: añadir una estructura compatible, desplegar código capaz de convivir, migrar datos y retirar lo antiguo después.

Si el código anterior no entiende el esquema nuevo, hacer rollback puede no recuperar el servicio. Ensayar la secuencia de versiones y no ejecutar una migración destructiva antes de necesitarla.

## 7. IaC y configuración

La infraestructura debe seguir un flujo de revisión parecido al código de aplicación: cambio, validación, plan, aprobación donde corresponda, aplicación y comprobación.

Terraform mantiene estado; requiere protegerlo, coordinar accesos y utilizar bloqueo cuando el backend lo soporte. Ese estado puede contener información sensible.

Bicep expresa recursos de Azure y utiliza ARM. What-if ayuda a revisar cambios previstos; no garantiza disponibilidad, permisos ni ausencia de todos los efectos secundarios.

Configuración de aplicación no es lo mismo que infraestructura ni que secretos. Separar valores por entorno sin duplicar toda la lógica del pipeline.

Las aprobaciones y checks de recursos en Azure Pipelines no se definen simplemente como una condición YAML que el mismo autor pueda modificar: los administran responsables del recurso mediante las capacidades correspondientes. [Referencia oficial](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals?view=azure-devops).

## 8. Seguridad de la cadena de entrega

Pensaría en código, dependencias, identidad, runner, artefacto y destino:

- Revisar cambios y proteger ramas.
- Analizar código con herramientas adecuadas.
- Revisar vulnerabilidades de dependencias.
- Detectar secretos.
- Analizar imágenes y sus bases.
- Registrar procedencia y composición cuando corresponda.
- Limitar permisos de automatizaciones.
- Controlar quién aprueba y despliega.

Una SBOM enumera componentes; no certifica que sean seguros. Un escáner produce hallazgos que requieren contexto y tratamiento.

OIDC permite intercambiar tokens de corta duración mediante confianza federada. Esa confianza debe restringir el repositorio, rama o entorno apropiado y relacionarse con permisos mínimos en Azure. [Modelo de GitHub](https://docs.github.com/en/actions/concepts/security/openid-connect).

Los identificadores de cliente, tenant y suscripción no sustituyen a una credencial. Guardarlos como variables no concede acceso sin identidad y confianza válidas.

No habilitaría credenciales de producción para cualquier evento de PR. Revisaría especialmente datos controlados por el autor, scripts y eventos que combinan privilegios con contenido no confiable.

## 9. Instrumentación y feedback

Desplegar es el comienzo de observar el cambio. Necesitamos relacionar la versión con errores, latencia y comportamiento de usuario.

OpenTelemetry aporta un modelo y herramientas para instrumentación y transmisión de señales. Elegir integración compatible con runtime y destino, sin copiar ejemplos antiguos de SDK sin revisar su soporte.

En nuestra app mediría:

- Porcentaje de descargas correctas.
- Latencia de subida y lectura.
- Tiempo hasta completar el análisis.
- Antigüedad de mensajes pendientes.
- Errores por versión desplegada.
- Coste y capacidad en picos.

Las trazas necesitan propagación de contexto para relacionar operaciones. No basta con generar logs separados en cada servicio.

Un postmortem útil explica impacto, cronología, factores y acciones con responsables. Buscar culpables suele reducir la información que el equipo comparte. Una acción como tener más cuidado no es verificable.

## 10. Laboratorio sin acceso a producción

Usa una rama de prueba de un proyecto de aprendizaje:

1. Crea un issue que describa una mejora pequeña.
2. Implementa el cambio con una prueba que pueda fallar de forma significativa.
3. Abre un PR y ejecuta las comprobaciones locales.
4. Define una versión de artefacto y su relación con el commit.
5. Diseña en papel una etapa de publicación en pruebas.
6. Identifica qué identidad usaría y con qué ámbito.
7. Escribe una condición de promoción y otra de rollback.
8. Define cómo comprobar la versión tras publicar.

Este repositorio incorpora una [comprobación de documentación ejecutable localmente](../../tools/check_docs.py). No despliega Azure y sirve para practicar una validación determinista antes de publicarla.

## 11. Preguntas razonadas

**¿Recompilar para producción conserva exactamente lo probado?** No necesariamente. Dependencias o herramientas pueden haber cambiado. Promover el artefacto reduce esa diferencia.

**¿Añadir OIDC elimina los permisos de Azure?** No. Evita una credencial duradera, pero sigue haciendo falta autorización.

**¿Una cobertura alta demuestra calidad?** No por sí sola. Hay que comprobar qué verifican las pruebas.

**¿A/B y canary son lo mismo?** No. Pueden compartir reparto de tráfico, pero responden a objetivos distintos.

**¿Cambiar YAML elimina cualquier aprobación?** No si los checks están controlados en el recurso mediante el sistema apropiado.

**¿Borrar un secreto del archivo lo vuelve seguro?** No. Revocarlo y analizar exposición es prioritario.

**Preparación:** seguir un cambio desde la necesidad hasta producción, demostrar qué se probó y explicar cómo detectarlo y recuperarlo si falla.
