# DP-300 · Администрирование решений Microsoft Azure SQL

[Маршруты сертификации](README.md) · [Десять случаев](DP-300-cases.md) · [Тетрадь](DP-300-workbook.md) · [English](../en/DP-300.md)

База, принимающая соединения, — только начало. Для DP-300 я изучал бы сохранение полезности, безопасности, восстанавливаемости и разумной скорости данных после изменений. Наш пример — университетское приложение: студенты загружают документы, а SQL-база хранит владельцев, учебные модули и разрешения скачивания.

Источники проверены **2026-10-30**: [официальное руководство DP-300](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/dp-300), цели действуют с **2026-10-27**. Соответствующая сертификация — [Azure Database Administrator Associate](https://learn.microsoft.com/en-us/credentials/certifications/azure-database-administrator-associate/).

Это независимые конспекты, не полное покрытие целей и не реальные вопросы. Перед записью проверь официальное руководство для выбранных языка и даты.

## 1. Выбирать платформу по требованиям

Azure SQL Database подходит приложениям, ориентированным на базу с управляемой инфраструктурой. Managed Instance поддерживает больше функций экземпляра SQL Server, но совместимость всё равно проверяется. SQL Server на Azure VM даёт контроль ОС и больше совместимости вместе с дополнительным администрированием. Это не разные названия одного развёртывания.

Для приложения сначала перечисли функции, зависимости, обслуживание и цели восстановления, затем выбирай размер. Агент ОС может изменить выбор; знакомство с продуктом требованием не является. Если уместно, сравни актуальные возможности Azure Arc и SQL database в Microsoft Fabric, не считая их автоматической заменой любой Azure SQL-нагрузки.

[Сравнение платформ](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview?view=azuresql).

## 2. Планировать миграцию как последовательность

Перечисли объём базы, версии, логины, задачи, зависимости между базами и предположения приложения. До копирования оцени совместимость. Отдели преобразование схемы, исходный перенос, продолжающиеся изменения и переключение: успешный перенос не доказывает работу приложения.

Миграция offline включает плановый перерыв записи. Поддерживаемый online-подход уменьшает его, но всё равно требует контролируемого финального перехода. Определи источник истины, остановку записи, проверку остаточных изменений и ответственного за открытие доступа. Сверь строки и важные бизнес-итоги, затем разрешения, задания и поведение приложения. Откат должен учитывать записи после переключения, а не просто возвращать старое подключение.

## 3. Проследить весь путь доступа

Разбирай отказы по порядку: DNS клиента, сеть, настройки службы, аутентификация и авторизация базы. Private endpoint не создаёт пользователя базы. Роль управления Azure не даёт автоматически чтение SQL-таблицы.

Где поддерживается, используй подходящую Entra-идентичность и создай нужного субъекта базы с разрешениями. Приложению выдавай необходимые его функции операции вместо общего администратора. Разделяй идентичности развёртывания, приложения и реакции на инциденты. Перед изменением проверь реальную идентичность и целевую базу. Учитывай вариант SQL: правила firewall SQL Database нельзя просто перенести в Managed Instance.

[Многоуровневая безопасность](https://learn.microsoft.com/en-us/azure/azure-sql/database/security-overview?view=azuresql).

## 4. Защищать данные на нужном уровне

Транспортное шифрование защищает соединение. TDE шифрует файлы базы при хранении. Always Encrypted задаёт другую границу, требует совместимых клиентских драйверов и управления ключами. Если отдельные значения нужно скрыть от DBA, изучи именно эту границу; одного TDE недостаточно.

Dynamic data masking меняет представление результатов пользователям без соответствующего разрешения снятия маски. Она не заменяет авторизацию и не делает широкий доступ запросами безопасным. Реши, кто читает строки, управляет ключами и что попадает в журналы и экспорт. Audit фиксирует действия, но назначение, хранение, доступ и разбор журнала тоже требуют владельца.

## 5. Создать полезную исходную линию

«Медленно» нужно измерить: проверка разрешения скачивания обычно занимает 30 мс, теперь 800. Запиши ID запроса, период, длительность, CPU, чтения и параллельность приложения. Сравнивай одинаковую операцию при похожей нагрузке; тихая полночь плохо сравнивается с рабочим днём.

Query Store хранит сведения о запросах, планах и выполнении для анализа регрессий. Проверь настройки и доступную историю до ожидания вчерашних доказательств. Метрики платформы показывают давление ресурсов, ожидания, блокирующие цепочки и планы объясняют задержку. Отсутствие данных — ограничение вывода, а не повод уверенно назвать причину.

[Query Store](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store?view=sql-server-ver17).

## 6. Проверять по одной гипотезе

Замедление могут объяснить новый план, старые статистики, неподходящие индексы, другие параметры или долгая транзакция. Проверь основания и выбери обратимый эксперимент. Новый индекс ускоряет поиск, но добавляет запись и место. Scan не обязательно ошибка: важны нужные строки и доступные пути.

Проверь представительную нагрузку до и после изменения, включая конкурентную запись. Принудительный план помогает доказанной регрессии, но требует наблюдения и способа отмены. Масштабирование уместно при подтверждённой нехватке ресурсов. Регулярное shrinking, перестройка всего и завершение неизвестных сессий могут нарушить работу и скрыть причину.

## 7. Автоматизировать с учётом реальной платформы

SQL Server и Managed Instance поддерживают SQL Agent; Azure SQL Database этой службы не предоставляет. Elastic Jobs подходит для поддерживаемых T-SQL-задач на SQL Database. Оркестратор уместен, когда процесс охватывает базы, Storage и внешние системы.

Для задания определи идентичность, цели, расписание, timeout, повторы и уведомление об ошибке. Вставка месячного результата не должна создавать дубль после потери ответа и повторного запуска. Учитывай завершение каждой единицы работы, различай запуск задания и проверенный бизнес-результат. Начинай с синтетических данных и изолированной цели.

[Варианты автоматизации](https://learn.microsoft.com/en-us/azure/azure-sql/database/job-automation-overview?view=azuresql).

## 8. Разделять копии, доступность и аварийное восстановление

Backup возвращает сохранённые состояния. Point-in-time restore и long-term retention решают разные горизонты времени; срок выбирается до происшествия. В SQL Database восстановление создаёт базу, а не перезаписывает существующую. План должен включать проверку и правильное переподключение приложения.

Репликация и доступность покрывают отказы, но могут передать допустимое разрушительное изменение. Вторая реплика не заменяет возврат к прошлому состоянию. RPO — допустимая потеря недавних данных, RTO — допустимое время восстановления. Проверяй оба с реальными зависимостями. Регион, уровень, конфигурация и режим репликации меняют возможности; универсальную длительность восстановления выдумывать нельзя.

[Восстановление копий](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups?view=azuresql) · [Непрерывность работы](https://learn.microsoft.com/en-us/azure/azure-sql/database/business-continuity-high-availability-disaster-recover-hadr-overview?view=azuresql).

## 9. Восстановить приложение и подготовить возврат

Переключение базы — не финиш. Проверь поддерживаемые точки подключения, DNS, аутентификацию, переподключение и согласованность зависимых хранилищ. Listener группы переключения может сохранить адрес приложения, но клиенты всё равно должны успешно переподключиться. Учти мониторинг и задания на новом primary.

До возврата определи авторитетную базу и синхронизацию изменений. Назначь ответственных и условия остановки. Необдуманный failback способен потерять корректные записи даже после успешного начального восстановления.

## 10. Операционное упражнение без облака

Без создания ресурсов подготовь инструкцию для приложения. Выбери платформу, нарисуй границы доступа и исходную таблицу метрик. Придумай отдельные инциденты регрессии плана и случайного удаления; укажи различающие доказательства. Опиши восстановление в изолированную базу и функциональную проверку синтетическими записями.

Каждый пункт пометь **ОЖИДАЕТСЯ**, **НАБЛЮДАЛОСЬ** или **НЕ ВЫПОЛНЯЛОСЬ**. Схема и локальный SQL не доказывают длительность Azure restore. Сдай предположения, критерии, нужные разрешения, откат и решение об очистке сохранённых данных. Продолжи [пятью модулями](DP-300-workbook.md) и [десятью случаями](DP-300-cases.md). Выполнение в Azure здесь не заявляется.
