## 1. Сначала вопрос, на который должны ответить данные

В нашем университетском приложении с конспектами скачивание файла, запись на курс и отчёт за месяц — разные нагрузки. Я сначала записал бы операцию и только потом выбирал продукт. Какие записи должны меняться вместе? Насколько свежим должен быть результат? Кто имеет право читать данные? Для хранения PDF не обязательно нужна база данных, а наличие JSON само по себе не исключает её.

Источники проверены **30 октября 2026 года**: [официальное руководство DP-900](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/dp-900), цели действуют с **21 июля 2026 года**. Соответствующая сертификация — [Azure Data Fundamentals](https://learn.microsoft.com/en-us/credentials/certifications/azure-data-fundamentals/). Это полезная подготовка, но не обязательное условие маршрута администратора баз данных.

| Область | Опубликованный вес | На чём сосредоточиться |
|---|---|---|
| Основные понятия данных | 25–30% | Представление, операции, обязанности |
| Реляционные данные в Azure | 20–25% | Связи, SQL, выбор службы |
| Нереляционные данные в Azure | 15–20% | Объекты, файлы, сущности, документы |
| Аналитические нагрузки | 25–30% | Конвейеры, модели, отчётность |

## 2. Представление и нагрузка — разные решения

Структурированные данные следуют явной схеме, например таблице записей на курс с типизированными столбцами. Полуструктурированные данные сохраняют организацию, хотя поля записей могут различаться: JSON-документ допускает необязательные метаданные. Скан задания считается неструктурированным при поиске по содержимому, даже если его имя составлено по шаблону.

CSV удобен для небольшого обмена таблицами, но требует договориться о кодировке, разделителе и пропусках. JSON поддерживает вложенность. Parquet хранит данные по столбцам и часто подходит для аналитического чтения. Формат сам по себе не обеспечивает разрешения, бизнес-правила или качество данных.

Транзакционная работа обычно состоит из небольших операций: занять место и согласованно уменьшить остаток. Аналитика обобщает историю: сравнить записи по курсам и семестрам. База может участвовать в обоих процессах, но тяжёлая отчётность конкурирует с работающим приложением. Нужно определить допустимую задержку, а не требовать «реального времени» без причины.

## 3. Реляционная модель явно задаёт связи

Представим Students, Courses и Enrolments. Первичный ключ идентифицирует строку; внешний ключ задаёт связь, если СУБД обеспечивает это ограничение. Enrolments связывает студентов и курсы без копирования названия курса в каждую запись студента. Нормализация уменьшает определённое дублирование и аномалии обновления; она не требует максимально раздробленной схемы для любого отчёта.

Таблица хранит строки. Представление задаёт сохранённый запрос и не обязательно является отдельной копией данных. Индекс создаёт путь доступа, требуя места и работы при записи. Хранимая процедура объединяет операции на стороне базы. Транзакции помогают согласованно менять данные с учётом параллельности и изоляции СУБД. Они не исправят бизнес-правило, которое никто не реализовал.

Разберись в назначении SELECT, INSERT, UPDATE, DELETE, CREATE и GRANT. Перед UPDATE или DELETE предскажи затронутые строки и проверь условие на учебных данных. Успешный запрос вполне может изменить не те записи.

## 4. Выбрать модель эксплуатации Azure SQL

Azure SQL Database — управляемая служба баз данных. Azure SQL Managed Instance даёт совместимость на уровне экземпляра для многих существующих приложений SQL Server. SQL Server на Azure VM предоставляет доступ к ОС, но оставляет команде больше администрирования. Похожий синтаксис запросов не делает одинаковыми развёртывание, совместимость и обслуживание.

Для нового приложения я сравнил бы функции, подключения, восстановление, трудозатраты и характер нагрузки. Перед миграцией нужен список зависимостей: функции экземпляра и внешние компоненты могут изменить выбор. «Управляемая» не снимает ответственность за доступ, схему, запросы приложения и требования восстановления. Для PostgreSQL и MySQL в Azure тоже есть управляемые варианты; сохранить нужный приложению движок бывает важнее терминологии SQL Server. Проверяй конкретный продукт и версию, не считай движки взаимозаменяемыми.

[Источник: варианты Azure SQL](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview).

## 5. Объекты, общие папки и сущности решают разные задачи

Blob Storage хранит объекты, например PDF и изображения. Azure Files предоставляет управляемые файловые ресурсы для подходящих способов доступа. Table Storage хранит нереляционные сущности, а не реляционные SQL-таблицы. Управляемый диск относится к ещё одному уровню абстракции хранения.

Один разумный вариант для приложения — содержимое файлов в Blob, а владельцы и связи с курсами в базе. Опиши согласование этих частей, если загрузка оборвалась посередине. Раздельное хранение файла и метаданных само по себе не координирует транзакцию. Право создать аккаунт хранения также отличается от права читать его blobs. Токен скачивания — учётные данные, ему не место в общих конспектах.

[Источник: службы хранения](https://learn.microsoft.com/en-us/azure/storage/common/storage-introduction).

## 6. Когда подходит документная база

Azure Cosmos DB поддерживает нереляционные приложения через доступные API и модели данных. Документ может удобно представить гибкие метаданные курса без отдельного реляционного столбца на каждый необязательный атрибут. Из этого не следует, что туда относится любая нагрузка.

Начни с чтений, обновлений, связей, требований согласованности и эксплуатации приложения. SQL-подобный язык сам по себе не обещает реляционное поведение или произвольные реляционные соединения. На уровне основ важно сравнить документ, сущность «ключ–значение», объект и строку таблицы. Подробная реализация приложения и настройка производительности выходят за рамки этой темы.

[Источник: обзор Cosmos DB](https://learn.microsoft.com/en-us/azure/cosmos-db/overview).

## 7. Проследить путь данных в конвейере

Пакетная обработка работает с ограниченным набором, например вчерашними скачиваниями. Потоковая обрабатывает поступающие события с ограниченной задержкой, но тоже должна учитывать дубликаты, опоздавшие события и сбои. Обновление панели каждую секунду не доказывает, что все исходные события уже пришли.

ETL преобразует данные до загрузки в целевую систему. ELT сначала загружает их, затем использует вычисления цели для преобразования. Ни одна аббревиатура не гарантирует чистоту. Определи идентификаторы, типы, обработку отклонённых записей и сверку. Посчитай исходные, принятые и отклонённые события; объясни разницу вместо сокрытия. Оркестрация координирует шаги, зависимости и восстановление после сбоя и отличается от самого преобразования.

[Источник: ETL и ELT](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/etl).

## 8. Превратить сохранённое в полезную аналитику

Озеро данных может хранить разные данные для последующей обработки. Хранилище данных организует аналитические данные для согласованных запросов и отчётности; lakehouse объединяет подходы. Набор файлов полезен только при определённых владельцах, форматах, качестве и поиске. В модели «звезда» таблица фактов хранит измеряемые события, а измерения дают описательный контекст. До итогов выбери детализацию записи.

Azure Synapse Analytics даёт аналитические возможности и средства интеграции. Microsoft Fabric объединяет несколько направлений данных и аналитики в SaaS-платформе. Power BI поддерживает семантические модели, отчёты и панели. Это связанные, но не взаимозаменяемые роли. До диаграммы определи показатель, например завершённые скачивания, его часовой пояс и границу обновления. Иначе два правдоподобных отчёта будут считать разное.

[Источник: обзор Fabric](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview).

## 9. Проектное упражнение и доказательства

Без облачных ресурсов нарисуй решение для PDF, записей на курсы и месячной отчётности. Сделай шесть синтетических записей, включая повторное событие и отсутствие ID курса. Выбери хранилище для каждого набора, допустимую задержку отчёта и обработку дубликата и ошибки. Напиши пример SQL-запроса или предскажи его результат на бумаге. Отделяй проектное предположение от наблюдаемого выполнения.

DBA отвечает прежде всего за работу базы, инженер данных — за перемещение и преобразование, аналитик — за ответы через модели и отчёты. Обязанности пересекаются; каждой проверке качества нужен владелец. Сравни решение с [общей главой о данных](../../ru/04-storage.md), затем реши [десять случаев](DP-900-cases.md) до открытия ответов.

Это независимые конспекты, не полное покрытие экзамена и не гарантия сдачи. Развёртывание в Azure не заявляется. Службы и цели меняются; перед записью перечитай официальное руководство.
