## 1. Partir de la question à laquelle les données doivent répondre

Dans notre application universitaire de partage de notes, télécharger un fichier, enregistrer une inscription et produire un bilan mensuel d’activité correspondent à des charges différentes. Je commencerais par écrire l’opération avant de choisir un produit. Quels enregistrements doivent changer ensemble ? Quel retard du résultat est acceptable ? Qui peut lire les données ? Conserver un PDF n’exige pas automatiquement une base de données, et utiliser JSON n’exclut pas une base.

## 2. Distinguer représentation et charge de travail

Les données structurées suivent une organisation explicite, par exemple une table d’inscriptions avec des colonnes typées. Les données semi-structurées possèdent une organisation sans imposer des champs identiques à chaque enregistrement : un document JSON peut contenir des métadonnées facultatives. Une feuille scannée reste non structurée pour la recherche dans son contenu, même si son nom de fichier suit une convention.

CSV convient aux petits échanges tabulaires, mais il faut convenir de l’encodage, du séparateur et du traitement des valeurs manquantes. JSON permet des structures imbriquées. Parquet organise les données par colonnes et convient souvent aux lectures analytiques. Un format ne fournit à lui seul ni autorisations, ni règles métier, ni qualité des données.

Une charge transactionnelle comporte généralement de nombreuses opérations ciblées : réserver une place et mettre à jour la capacité restante de manière cohérente. Une charge analytique agrège l’historique : comparer les inscriptions par cours et semestre. Une base peut participer aux deux, mais des rapports lourds peuvent concurrencer l’application active. Il faut définir la fraîcheur acceptable plutôt qu’exiger du « temps réel » sans raison.

## 3. Rendre les relations explicites dans le modèle relationnel

Imaginons les tables Students, Courses et Enrolments. Une clé primaire identifie une ligne ; une clé étrangère exprime une relation lorsque la base fait respecter cette contrainte. Enrolments relie les étudiants aux cours sans recopier le titre du cours dans chaque dossier étudiant. La normalisation réduit certaines duplications et anomalies de mise à jour ; elle n’impose pas de fragmenter au maximum le schéma de chaque rapport utile.

Une table stocke des lignes. Une vue présente une requête enregistrée ; ce n’est pas nécessairement une copie stockée séparément. Un index fournit des chemins d’accès et ajoute du stockage ainsi que du travail à chaque écriture. Une procédure stockée regroupe des opérations côté base. Les transactions aident à maintenir la cohérence des changements liés, selon les mécanismes de concurrence et d’isolation de la base. Elles ne corrigent pas une règle métier qui n’a jamais été exprimée.

Il faut connaître le rôle de SELECT, INSERT, UPDATE, DELETE, CREATE et GRANT. Avant un UPDATE ou un DELETE, prévoir les lignes touchées et tester la condition sur des données d’exemple. Une instruction réussie peut tout de même modifier les mauvais enregistrements.

## 4. Choisir le modèle d’exploitation d’Azure SQL

Azure SQL Database est un service de base de données managé. Azure SQL Managed Instance propose une compatibilité à l’échelle de l’instance pour de nombreuses applications SQL Server existantes. SQL Server sur une VM Azure donne accès au système d’exploitation et laisse davantage d’administration à l’équipe. Une syntaxe de requête similaire ne rend pas identiques les déploiements, la compatibilité ou les responsabilités de maintenance.

Pour une nouvelle application de notes, je comparerais les fonctions requises, les connexions, la récupération, l’effort d’exploitation et le profil de charge. Pour une migration, il faut d’abord inventorier les dépendances : les fonctions au niveau de l’instance et les composants externes peuvent modifier le choix. « Managé » ne supprime pas la responsabilité des accès, du schéma, des requêtes de l’application ou des exigences de récupération. PostgreSQL et MySQL disposent aussi d’offres Azure managées ; conserver le moteur existant peut compter davantage qu’adopter le vocabulaire de SQL Server. Vérifier le produit et la version pris en charge au lieu de supposer tous les moteurs interchangeables.

[Source : choix Azure SQL](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview).

## 5. Objets, partages et entités répondent à des besoins différents

Blob Storage stocke des objets tels que des PDF et des images. Azure Files fournit des partages de fichiers managés lorsque le besoin d’accès aux fichiers est compatible. Table Storage conserve des entités dans un modèle non relationnel ; ce n’est pas un service de tables SQL relationnelles. Un disque managé correspond encore à une autre abstraction de stockage.

Pour l’application, une conception possible conserve les fichiers dans Blob et les métadonnées de propriété dans une base. Il faut expliquer comment ces deux parties restent cohérentes si un téléversement échoue à mi-chemin. Séparer fichier et métadonnées est une décision de conception, pas une coordination transactionnelle automatique. Le droit de créer un compte de stockage diffère aussi du droit de lire ses blobs. Un jeton de téléchargement est un justificatif d’accès : il ne doit pas figurer dans des notes partagées.

[Source : services de stockage](https://learn.microsoft.com/en-us/azure/storage/common/storage-introduction).

## 6. Comprendre où une base documentaire est adaptée

Azure Cosmos DB prend en charge des scénarios applicatifs non relationnels au moyen de ses API et modèles de données compatibles. Un document peut convenir aux métadonnées variables d’un cours sans transformer chaque attribut facultatif en colonne relationnelle distincte. Cela ne prouve pas que toutes les charges doivent y être placées.

Partir des lectures, mises à jour, relations, exigences de cohérence et contraintes d’exploitation de l’application. Un langage ressemblant à SQL n’implique pas à lui seul un comportement relationnel ou des jointures relationnelles sans restriction. Au niveau fondamental, savoir comparer un document, une entité clé-valeur, un objet et une ligne relationnelle. L’implémentation détaillée d’une application et le réglage des performances dépassent cette unité.

[Source : présentation de Cosmos DB](https://learn.microsoft.com/en-us/azure/cosmos-db/overview).

## 7. Suivre les données dans le pipeline

Un traitement par lots traite une collection délimitée, par exemple les téléchargements d’hier. Un traitement en flux traite les événements entrants avec un délai borné, mais doit encore gérer doublons, événements tardifs et pannes. Un tableau de bord actualisé chaque seconde ne prouve pas que tous les événements sources sont déjà arrivés.

ETL transforme les données avant de les charger dans la cible prévue. ELT les charge puis les transforme avec les capacités de traitement de la cible. Aucun de ces sigles ne garantit des données propres. Définir les identifiants, les types, la gestion des rejets et les contrôles de rapprochement. Compter les événements sources, acceptés et rejetés ; expliquer les écarts au lieu de les cacher. L’orchestration coordonne les étapes, leurs dépendances et la reprise après un échec ; elle se distingue de la transformation elle-même.

[Source : ETL et ELT](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/etl).

## 8. Transformer les données stockées en analyse utile

Un lac de données peut conserver des données variées pour un traitement ultérieur. Un entrepôt organise des données analytiques pour des requêtes et rapports cohérents ; un lakehouse combine des approches. Un ensemble de fichiers n’est utile que si la propriété, les formats, la qualité et la découverte sont définis. Dans un modèle en étoile, une table de faits enregistre les événements mesurables et les dimensions apportent le contexte descriptif ; choisir la granularité avant d’ajouter les totaux.

Azure Synapse Analytics fournit des fonctions analytiques et des possibilités d’intégration. Microsoft Fabric réunit plusieurs charges de données et d’analyse dans une plateforme SaaS. Power BI permet de créer modèles sémantiques, rapports et tableaux de bord. Ces rôles sont liés, mais leurs noms ne sont pas interchangeables. Définir une mesure comme les téléchargements terminés, son fuseau horaire et sa limite d’actualisation avant de dessiner un graphique. Sinon, deux rapports apparemment corrects peuvent compter des choses différentes.

[Source : présentation de Fabric](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview).

## 9. Exercice de conception et éléments de preuve

Sans créer de ressources cloud, dessiner une solution pour les PDF, les inscriptions et les rapports mensuels de téléchargement. Produire six enregistrements synthétiques, dont un événement en double et un identifiant de cours absent. Choisir un stockage pour chaque ensemble, préciser le retard acceptable du rapport et expliquer le traitement du doublon et de l’enregistrement invalide. Écrire une requête SQL d’exemple ou expliquer son résultat attendu sur papier. Distinguer une prévision de conception d’un résultat réellement observé.

Un DBA se concentre sur l’exploitation des bases, un ingénieur de données sur leur déplacement et leur préparation, un analyste sur les réponses obtenues avec des modèles et rapports. Les responsabilités se recoupent ; désigner un responsable pour chaque contrôle qualité. Comparer la conception au [chapitre général sur les données](../../fr/04-storage.md), puis résoudre les [dix cas](DP-900-cases.md) avant d’ouvrir les réponses.
