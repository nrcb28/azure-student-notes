# AZ-140 · Configuring and Operating Microsoft Azure Virtual Desktop

[認定資格](README.md) · [10ケース](AZ-140-cases.md) · [ワークブック](AZ-140-workbook.md) · [Español](../es/AZ-140.md)

Azure Virtual Desktop（AVD）は、マシンを交換しても学生の作業環境が残る大学の計算機室として学ぶと分かりやすいでしょう。例では、午前の授業にノートアプリとプログラミングツール一式を提供します。重要なのは、学生がサインインし、プロファイルを取り戻し、快適に作業できるかです。

参照確認日：**2026-11-01**。[AZ-140公式ガイド](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/az-140)の試験目標は**2026-07-20**から有効です。対応資格は[Azure Virtual Desktop Specialty](https://learn.microsoft.com/en-us/credentials/certifications/azure-virtual-desktop-specialty/)です。この独自の学習ノートは、全範囲の網羅、公式試験問題、合格保証ではありません。

## 1. サービスと顧客の責任を図示する

MicrosoftはAVDのブローカー、ゲートウェイ、その他のサービスコンポーネントを運用します。セッションホストVM、イメージ、アプリ、ネットワーク、ID連携、プロファイルストレージ、運用ポリシーは顧客の責任です。制御プレーンが正常でも、枯渇したプロファイル共有を修復できません。

ホストプールは共通構成のセッションホストをまとめます。アプリケーショングループは公開デスクトップやRemoteAppと利用者割り当てを定義し、ワークスペースは登録したアプリケーショングループを利用者のフィードにまとめます。セッションホストはセッションを実行するVMです。空のフィードを診断する前に、この関係を描きます。このノートはAzure Resource Managerのリソースを使います。旧AVD classicや従来の自己管理型Remote Desktop Servicesは、異なる管理モデルです。

## 2. プール型か個人用かを意図的に選ぶ

プール型ホストプールは複数利用者でセッションホストを共有します。対応するWindows Enterpriseマルチセッションイメージでは、複数セッションを同時に実行できます。個人用プールは、要件に応じた自動または直接割り当てで、利用者ごとにデスクトップを割り当てます。個人割り当てとアプリケーショングループの利用資格は、別の問題を解決します。

交換可能な学生実習環境では、まずプール型を検討します。専用マシンが必要な研究者なら個人割り当てが妥当かもしれません。VMサイズや最大セッション数の決定前に、代表的なCPU、メモリ、ディスク、グラフィックス、アプリ動作を測定します。「マルチセッション」という名称やコア数だけでは、安全な学生収容数は分かりません。OSとライセンス対象資格を記録します。WindowsクライアントとWindows Serverの要件は異なります。[前提条件](https://learn.microsoft.com/en-us/azure/virtual-desktop/prerequisites)。

## 3. ID、利用資格、セッションのサインインを分ける

Microsoft Entra IDはAVDへのアクセスを認証します。対応するホスト構成には、Entra参加、AD DSドメイン参加、Microsoft Entra Domain Services参加があります。AD DSは従来のドメインサービス、Entra Domain Servicesはマネージドドメイン機能です。Entra IDはドメインコントローラーではありません。アプリ、ポリシー、プロファイルストレージ、認証の依存関係に応じて選びます。

フィード認証、アプリケーショングループ割り当て、ホストのサインイン権限、ファイルアクセスを別々に追います。Azure管理のContributorは、学生に自動的にデスクトップを与えません。正確なクライアント、参加種類、認証方式、必要なサービスアプリに合わせ、対応するSSOと条件付きアクセスを計画します。二度目のパスワード要求は調査の手掛かりであり、条件付きアクセス失敗の証拠ではありません。特権管理と学生アクセスは分離します。

## 4. 実際のネットワーク経路を説明する

基本のreverse connectは、クライアントとホストからAVDサービスへ送信するHTTPS/TCP接続を確立します。セッションホストで公開TCP 3389を開ける必要はありません。最新の必須エンドポイント、DNS、プロキシ動作、ルートを確認します。

対応環境ではRDP ShortpathがUDPトランスポートを追加します。マネージドリスナー方式には直接のプライベート到達性と、通常UDP 3390のリスナー設定が必要です。マネージドまたはパブリックのICE/STUN方式は利用可能経路を探索し、対応するパブリックネットワークのセッションではTURNが中継できます。前提が異なるため、プライベートリスナーの規則を全Shortpath共通設定と考えてはいけません。UDPを確立できなければTCP reverse connectへフォールバックします。クライアント・プラットフォーム対応とクラウドの提供状況を確認します。実際の転送方式、往復遅延、パケット損失、ホストとプロファイル間の遅延を比較します。[Shortpath要件](https://learn.microsoft.com/en-us/azure/virtual-desktop/configure-rdp-shortpath)・[ネットワークの基礎](../../ja/05-networking.md)。

## 5. 永続プロファイルを交換可能なホストの外に置く

FSLogixプロファイルコンテナーは、特定のプール型VMのローカルディスクに頼らず、対応ストレージ上に利用者プロファイルを保持します。ノートアプリの正本データは、デスクトップ設定やキャッシュと分けます。プロファイルの永続化が、そのままアプリデータのバックアップになるわけではありません。

SMBストレージでは共有レベルのアクセスとNTFS権限の両方を検証します。ホスト参加とストレージサービスに対応するID・Kerberos構成を選び、DNS、チケット、時刻、暗号化の互換性を確認します。Azureポータルへのログイン成功は、これらを一つも証明しません。サインイン集中、容量、遅延に合わせてストレージを設計します。既定の単一コンテナー接続は、任意の同時書き込みを許すものではありません。障害前に切断、ロック、バックアップ、復元、復旧目標を計画します。パスを複数書くだけでは回復性は確立しません。[FSLogix構成例](https://learn.microsoft.com/en-us/fslogix/concepts-configuration-examples)。

## 6. アプリ配信方法を選び、検証する

対応アプリをベースイメージへ入れる方法は分かりやすい一方、更新がイメージのライフサイクルに結び付きます。適切なアプリなら、管理されたインストール手順で別に更新できます。現在のApp Attachは、到達できるストレージから対応パッケージを配信できます。RemoteAppの公開は表示と利用資格、パッケージ化は配信を制御します。関連しつつ異なる判断です。

ノート編集アプリでは、依存関係、ライセンス、パッケージ互換性、ストレージアクセス、ホストプールと利用者への割り当てを記録します。初回起動、更新、同じマルチセッションホストの二人目の利用者を試します。全インストーラーが動くパッケージになるとは考えず、旧MSIX app attachの手順を現在の管理モデルとして使いません。テスト済みの代替バージョンを保持します。[現在のApp Attach概要](https://learn.microsoft.com/en-us/azure/virtual-desktop/app-attach-overview)。

## 7. イメージを版管理したリリースとして扱う

対応OS、エージェント、アプリ、セキュリティ設定、更新状態を持つゴールデンイメージを文書化して作ります。実習環境を再構築できるよう、ビルド入力とイメージの版を保存します。Azure Compute Galleryで版を配布できます。VMのライフサイクルを計画する前に、[コンピューティングの基礎](../../ja/03-compute.md)を確認します。

新版は小さな検証グループへ導入します。認証、プロファイル接続、ノート編集、必要な印刷やリダイレクト、セッション性能を試します。旧ホストをドレインして新規セッションを止め、既存セッションは保守ポリシーに従って扱います。ドレインモードは即座に全員をログアウトさせません。ホストは段階的に交換します。前版と、容量を考慮した切り戻し経路を残します。稼働ホストを一斉更新すると、共有教室の依存先が脆弱になります。

## 8. 授業時間割にスケーリングを合わせる

スケーリングプランは、スケジュールと容量設定によって対応する自動スケーリングを制御します。既存ホストの電源管理と、ホストの動的な作成・削除を区別します。後者はホストプールの前提条件と提供状況の確認が必要です。Start VM on Connectは、接続時に対象の停止ホストを起動しますが、時間割や予備容量の戦略全体を代替しません。

同時利用48人、実測上限がホスト当たり12セッションなら、使用可能な四台で需要を満たしても障害余力はありません。この仮定では五台で一台分の余力ができます。起動時間、異常ホスト、ドレイン状態、ストレージ制限をモデル化します。縮小前に、サービス権限、除外の扱い、アクティブセッション方針を定めます。削減予測にはVM稼働だけでなく、ディスク、ストレージ、ネットワーク、監視、ライセンスも含めます。[スケーリングプランの要件](https://learn.microsoft.com/en-us/azure/virtual-desktop/autoscale-create-assign-scaling-plan)。

## 9. 一つの接続失敗を証拠で追う

UTC時刻、仮名化した利用者ID、クライアント版、リソース、セッションホスト、接続相関IDを記録します。接続、チェックポイント、エラー、エージェント状態、関係するネットワーク記録を、ホスト性能とFSLogixログと相関させます。過去の証拠を期待する前に、診断設定とホスト側収集を有効にします。AVD Insightsは利用体験の調査を助けますが、データ収集の設定は必要です。

フィードなし、ホストのサインイン失敗、プロファイル接続遅延、サインイン後のアプリ遅延を区別します。AVD接続記録がないのは、要求がサービスまで届かなかったためかもしれません。同時刻の成功した学生セッションと比べ、ノート本文や資格情報の収集は避けます。[診断分類と相関](https://learn.microsoft.com/en-us/azure/virtual-desktop/diagnostics-log-analytics)。

## 10. デプロイせずに復旧を演習する

朝のサインイン集中、一台の利用不能ホスト、到達不能のプロファイル共有を題材に、オフラインの机上演習をします。予測、仮説を確認する証拠、責任者、切り戻し条件、明確な復旧基準を書きます。VMだけを復元しても、ID、DNS、アプリパッケージ、プロファイルアクセス、ノートAPIは復元されません。

プロファイルとアプリデータのRTO、RPOを別々に合意します。代替リージョンの依存関係、プロファイル整合性、利用可能なVM容量、プライマリへ戻す手順を含めます。継続費用の所有者と、アラート対応者を記録します。[10ケース](AZ-140-cases.md)と[五つのワークブック単元](AZ-140-workbook.md)を終えます。演習ではテナントを変更せず、Azureへのデプロイやフェールオーバーテストを行ったとは主張しません。
