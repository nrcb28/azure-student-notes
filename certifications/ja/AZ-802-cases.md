# AZ-802 · 理由付き解答のある 10 ケース

[ガイド](AZ-802.md) · [5 単元のワークブック](AZ-802-workbook.md) · [目次](README.md)

大学の実習環境を題材にした独自シナリオであり、公式試験問題ではない。解答を開く前に、仮説、別の説明、必要な証拠を述べる。ここで挙げるコマンドは、許可された Windows 実習環境での確認案であり、実行や本番復旧を行ったとは主張しない。トレーナーと Anki のエクスポートにも文脈が残るよう、各問いにシナリオ全体を含めている。

## 1. 教室のネットワーク変更後、ドメインクライアントは公開 Web サイトを名前解決できるが、ドメインコントローラーを見つけられない。リゾルバーは公開 DNS サービスで、設定上の AD DNS サーバーには到達でき、SRV レコードも正常と確認済み。クライアントの時刻も正しい。最初の修復として全学生のパスワードをリセットするべき？

<details>
<summary>解答</summary>

いいえ。示された証拠から、まずクライアントの名前解決経路に注目する。公開 DNS の成功は、非公開の AD サービスレコードを検出できる証明にはならない。クライアントのリゾルバー、関係する SRV の照会と結果を記録し、その経路を承認済みの実習 DNS 構成と比較する。適切な修正は、意図した AD 対応のリゾルバー経路を戻し、検出、コントローラーへの到達、影響を受けたログオンを検証してから変更を広げるものになる。

サーバーが正常で時刻も正しいという前提は、この調査の範囲を絞るもので、実際のログオン障害がすべて DNS の問題という意味ではない。検出が成功しても認証が失敗するなら、正確なエラー、アカウント状態、プロトコル、セキュアチャネルの証拠へ進む。タイムスタンプと実際に選択されたコントローラーを含む変更前後の記録を残す。全パスワードのリセットは、判明したリゾルバーの不一致を直さず、無関係な状態を変えて有用な証拠を隠しかねない。ロールバックは、承認済みの変更が他の必要な名前解決を壊したら、記録したクライアント構成を戻すこと。動作を理解していない公開と非公開のリゾルバーの組み合わせを残すことではない。

</details>

## 2. 研究グループの所属変更が LAB-DC1 には見えるが、離れた建物のコントローラーには見えない。その建物のクライアントは後者を使い、レプリケーションは DNS 関連の失敗を報告しており、新しい共有にもアクセスできない。利用者を別の特権グループへ加えるのは適切な修正？

<details>
<summary>解答</summary>

いいえ。観察されたディレクトリのバージョン差とレプリケーション失敗は、権限を広げる前に調べるべき具体的な説明を与える。変更時刻、変更を受け付けたコントローラー、クライアントが選んだコントローラー、レプリケーションエラーを記録する。レプリケーションのパートナーの DNS レコード、設定したリゾルバー、接続、認証の前提条件を確認する。遠隔拠点のサブネットが意図したサイトに対応するかも確認するが、サイトのスケジュール変更で DNS 障害が直るとは考えない。

サポートされる修復後、対象の所属変更が関係するコントローラーへ届いたと確認する。その後、利用者の適切な新しいログオンまたはセッションのトークンを取得し、その利用者として想定した共有をテストする。ディレクトリの収束と、認可の文脈の更新は別の確認。まだ失敗するなら、共有とファイルシステムの権限も調べる。グループの権限を狭く保ち、許可と拒否の両方を記録する。無関係な特権グループを加えると、レプリケーションを壊れたまま残し、学生のアクセスを広げながら症状だけを隠すかもしれない。成果物は変更の収束とアクセスの時系列であり、実習テストで実測できるまでは予測だと明記する。

</details>

## 3. 隔離した分校の教室で RODC を使う予定。WAN 停止中にも大学の特権管理者がサインインできるよう、そのパスワードをキャッシュする案が出た。教室の物理的な保護は主データセンターより弱い。設計レビューで何を求めるべき？

<details>
<summary>解答</summary>

RODC ならどんな資格情報でも安全にキャッシュできる、という前提を退ける。パスワードレプリケーションポリシー、実効的な許可と拒否の所属、管理の委任、物理的に機器を失った場合の手順を確認する。特権アカウントは、その拠点の資格情報キャッシュから除外する。実効ポリシーで許可と拒否の両方に該当する場合、拒否が優先される。本当に切断中のアクセスが必要な一般アカウントを限定して特定し、グループ名だけを頼らず、結果としての実効ポリシーを確認する。

計画では、キャッシュ済み利用者の認証と、新規や変更後のディレクトリ状態など、書き込み可能なコントローラーが必要な操作を分ける。WAN 停止中も使えるサービスと、ドメインの境界を弱めずに操作者が承認された管理経路を得る方法を定義する。証拠には、拠点の脅威に関する前提、選んだアカウント、実効キャッシュの判断、コントローラーへの接続、機器紛失時の対応を含める。パスワードやキャッシュの内容は証拠として公開しない。復旧計画では、影響を受けるキャッシュ済み資格情報と侵害されたサーバーを考慮する。ハードウェアを取り替えればディレクトリの秘密はすべて守られた、と考えてはいけない。

</details>

## 4. Azure Arc へ接続したサーバーでも、サーバー B からファイルサーバー C へのリモート処理が失敗している。広い資格情報の委任と、ドメインコントローラー上の既定の JEA 仮想アカウントが提案されたが、作業に必要なのは限定的なサービス操作だけ。Arc 接続はこの設計の根拠になる？

<details>
<summary>解答</summary>

いいえ。Arc 接続は Azure での管理関係を作るもので、サーバーの AD 参加、フォレストの信頼作成、対話操作する人の資格情報の C への自動委任は行わない。第 1 と第 2 のホップ、それぞれのプロトコル、実効 ID、正確に必要な操作を図示する。どの認可と認証の境界で失敗するかを診断する。最初のセッションが成功しても、次のリソースが意図した ID を受け付ける証明にはならない。

方式を選ぶ前に、対応するセカンドホップの選択肢と制約を調べる。CredSSP は資格情報の露出を増やし、制約付き委任の方式は WinRM から WinRM へのセカンドホップを一般的に解決するものではない。JEA ではセッションの実行 ID、許可された利用者、コマンド、パラメーター、監査記録をまとめて確認する。DC の既定の仮想アカウントは Domain Admins の権限を持ち得るため、限定的なサービス作業には過剰。適切な管理場所と、明示的に制限した実行権限を選ぶ。証拠は権限とホップの図、および許可と拒否の操作であり、再利用可能な管理者資格情報で成功させたコマンドではない。Arc 管理下のコントローラーの拡張機能権限も、別途確認が必要。

</details>

## 5. 実習 VM は運用チェックポイントを使うが、ゲストの整合性処理が失敗してホストが標準チェックポイントを作った。学生はこれを、独立したアプリ整合性バックアップと呼んでいる。チェックポイントと VM のディスクは同じストレージにある。何を訂正する必要がある？

<details>
<summary>解答</summary>

整合性の主張と保護の境界を、両方訂正する。Production モードは標準チェックポイントへのフォールバックを許可できるため、指定した設定より、実際のチェックポイントの種類とゲスト処理の結果のほうが強い証拠になる。演習で運用チェックポイントを必須とし、フォールバックを認めないなら、ProductionOnly を検討し、ゲスト統合と VSS、または関係するファイルシステムの凍結の前提条件を直す。必要なチェックポイントを作れないことは有用な失敗の証拠であり、黙って別の種類を受け入れることと同等ではない。

運用チェックポイントが成功しても、独立した保持済みバックアップの証明にはならない。VM ストレージと一緒にディスクチェーンを失う可能性があり、アプリ復旧には対応する整合性と復元方法も必要。要件が求める場合は、適切な保持と復元検証の計画を持つ保護済みバックアップを用意する。対応するツールでチェックポイントのメタデータとストレージの余力を確認し、AVHDX ファイルを手動削除しない。目的が、使い捨て実習の変更を戻すこと、ホストやストレージの喪失に耐えること、以前の正しいアプリ状態を復元することのどれかを、それぞれ説明する。目的ごとに別の証拠が必要で、仕組みも変わり得る。

</details>

## 6. 既存の教室 PC は使い続けられるが、新しいクライアントはアドレスを取得できない。承認済み DHCP サーバーは正常なリレー経由で到達可能だが、対象スコープに空きリースがない。サーバーをもう 1 台インストールしたものの、フェールオーバー関係はない。調査でどう結論付けるべき？

<details>
<summary>解答</summary>

示された証拠は、新しい割り当ての直接原因としてスコープの枯渇を示す。既存クライアントはリース状態に従って続けられるので、その成功だけでは新しいアドレスを割り当てられると証明できない。承認を受ける容量修正を提案する前に、スコープの範囲、除外、予約、使用中リース、実際のクライアントのサブネットを調べる。古い割り当てや想定外の傾向を確認するが、無差別にリースを削除したり、重複するアドレス範囲へ拡張したりしない。

サーバーをもう 1 台入れただけでは、リースを自動調整しない。可用性が必要なら、対象スコープに対応する DHCP フェールオーバー関係を設計し、モード、パートナーの状態、リースの動作、復旧責任を理解する。同じ範囲の管理されていない競合コピーを有効化してはいけない。証拠には、スコープ一覧、空きアドレス数、リレーの経路、既存クライアントだけでなく本当に新しいクライアントを使ったテストを含める。容量とフェールオーバーは異なる障害に対応する。パートナー関係が正常でも、小さすぎるプールを無視してよいわけではない。変更前のスコープを記録し、提案範囲がルーティングや他の割り当て主体と競合したら中止する。

</details>

## 7. 学生には想定した SMB 共有権限があるが、NTFS がプロジェクトフォルダーへのアクセスを拒否している。Azure File Sync は正常で、サーバーエンドポイントには階層化したファイルがある。Azure の共同作成者を付与し、同期コピーをバックアップと呼べば、両方の懸念を解消できる？

<details>
<summary>解答</summary>

いいえ。実際の Windows ファイルの経路と ID をたどる。共有レベルのアクセス権があっても、判明した NTFS の拒否は依然として有効。適切なグループ所属と分離を保って意図したフォルダーの認可を直し、影響を受けた学生と、拒否のままにするべき学生を試す。Azure のリソース管理ロールでは、ファイルシステムの ACL の修正や SMB データアクセスの確立は自動で行われない。設定済みの一つのエントリから推測せず、実効アクセスを調べる。

復旧の問いは別に扱う。正常な同期でも削除は伝播し得て、階層化したサーバーファイルは完全で独立したローカルコピーを含まない可能性がある。クラウドエンドポイント、使える保持済みバックアップ、復元の依存関係、対応する復旧ワークフローを特定する。登録済み File Sync サーバーを OS イメージや VM チェックポイントから巻き戻したり複製したりすることは、一般的に使えるサポート済みの復旧方法ではない。証拠には、共有と NTFS の判断、エンドポイントと階層化の状態、過去の復旧ポイントの計画を含める。今日アクセスを戻せることと、後日の間違いの後にデータを復旧できることは別の結果。それぞれのテストや、設計上の証拠だと明示した資料なしに、どちらも実現したと主張してはいけない。

</details>

## 8. Windows Server 2022 と 2025 が混在している。強化案は Windows Server 2025 向け OSConfig ベースラインを全台に適用し、管理を外せば以前の設定がすべて戻ると約束している。取得した LAPS パスワードも共有レポートに保存している。何を変える必要がある？

<details>
<summary>解答</summary>

サポート、変更からの復旧、秘密の扱いを分ける。確認した OSConfig ベースラインのガイダンスは Windows Server 2025 向けなので、同じ構成を 2022 マシンでも対応済みと示してはいけない。OS とモジュールのバージョン、役割別の設定、試行対象グループを記録する。競合し得る既存 GPO や他の管理を特定し、実効設定を調べ、必要な再起動とアクセス検証を計画する。ベースラインを外しても、管理前の値がすべて再構築される保証はない。確認済みの以前の状態と復旧手順を保持する。

LAPS は、制御されたパスワードのローテーション、バックアップ、許可された取得を支える。取得したパスワードを多くの人が読めるレポートへコピーすれば、このアクセス境界を壊す。適切なインシデントや変更の手順で除去し、ポリシーに従って露出に対応し、必要ならローテーションする。公開するのは、機密値を除いたポリシーと認可の証拠だけにする。復旧用資格情報には、想定した障害中にも使える保護されたアクセスが必要。証拠では、対応する展開、取得を許可するロールと拒否するロール、監査付きアクセス、復旧計画を示す。平文の資格情報や、すべての保護を証明すると決め付けた準拠のスクリーンショットを示すものではない。

</details>

## 9. Arc サーバーは接続済みで、ワークスペースには最近のエージェントの Heartbeat 行もあるが、必要な Windows System イベントがない。そのイベントはローカルには存在する。空のクエリは、Windows で障害が起きなかった証明になる？

<details>
<summary>解答</summary>

いいえ。このシナリオでは、関係するイベントがローカルにあると明示している。Arc の接続とエージェントの Heartbeat は、選んだイベントソースが正常に届いたこととは異なる観察。対象マシン、時間範囲、ワークスペース、送信先テーブルを確かめ、AMA の拡張機能とサービスの状態、関連付けた DCR、イベントの選択と送信先、エージェントが実際に受け取った構成を調べる。DCR を作成しても、対象マシンへの関連付けがなければデータ収集は始まらない。

機密値を除いたローカルイベントの識別子とタイムスタンプで、一つのイベントを提案パイプラインに沿って追跡する。元に存在しない場合、収集の失敗、通信や構成の問題、誤った送信先への照会を区別する。イベント発生時刻と収集後の到着時刻を分け、文書化された取り込み遅延は考慮しつつ、すべての遅延を許容してよいとは考えない。証拠にはローカル記録、マシンの ID、関連付け、クエリの文脈と、その後に行う到着予測のテストを含める。最初に全エージェントを再インストールするのは避ける。状態を変え、欠けた選択や関連付けを直さないまま、有用な調査の文脈を消す可能性がある。

</details>

## 10. 学生が重要な AD オブジェクトを削除し、削除前にはごみ箱が有効でなかったと分かった。本番ドメインコントローラーを通常の VM チェックポイントへ戻し、すべての FSMO ロールを強制取得しようと提案している。組織には対応するディレクトリバックアップと担当の復旧責任者がある。より安全な判断の流れは？

<details>
<summary>解答</summary>

文書化されたディレクトリ復旧手順へエスカレーションし、削除、レプリケーション、バックアップの証拠を保全する。事後にごみ箱を有効にしても、失われた以前の復旧可能な状態が現れるわけではない。復旧方法を選ぶ前に、影響するオブジェクトと依存関係、利用可能な対応バックアップ、復元範囲を定める。一つのオブジェクトの誤操作だけでは、フォレスト全体の復旧や、関係のない FSMO ロールの強制取得の理由にはならない。

復旧責任者は、実際の障害に合った、サポートされる権限のある復元（authoritative）または権限のない復元（non-authoritative）の手順を選ぶ。必要なら DSRM の文脈、保護した復旧資格情報、SYSVOL の検討も含める。一般的な VM チェックポイントへの巻き戻しは、この計画の代わりにならない。正とする状態、レプリケーションへの影響、検証、本当に強制取得が必要な場合に旧ロール保持者が復帰できる条件を文書化する。「VM が起動する」で止めず、ディレクトリオブジェクト、認証、レプリケーション、影響を受けるサービスを検証する。このリポジトリの成果物は、明確な判断条件を伴う机上演習である。ディレクトリ復元、ロールの強制取得、復旧時間の測定は実行していない。

</details>
