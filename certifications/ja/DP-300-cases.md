# DP-300 · 理由を考える 10 ケース

[ガイド](DP-300.md) · [ワークブック](DP-300-workbook.md) · [目次](README.md)

独自の演習で、公式問題ではない。答えを見る前に制約、判断案、集める確認材料を書く。Azure での実行や試験範囲の完全な網羅を主張するケースではない。

## 1. アプリが対応する OS 拡張を必要とする。T-SQL が動くという理由だけで SQL Database を選べる？

<details>
<summary>考え方</summary>

OS 要件はホスティングの境界を変える。拡張が本当に必須か、管理サービス側に対応する代替があるかを調べる。直接の OS 制御が残るなら VM 上の SQL Server を評価し、更新、バックアップ、監視、可用性の責任も含める。互換性の評価対象は T-SQL やデータベースオブジェクトだけでなく、外側の依存も含む。構文を使い慣れていても展開の互換性の証明にはならないので、実際のアプリ要件を確かめる。

</details>

## 2. データ移行の転送が成功した。すぐ書き込みを再開して安全？

<details>
<summary>考え方</summary>

転送の完了は一つの通過点だ。最終データ、重要な業務の合計、権限、アプリ経路、定期処理を検証する。移行元の書き込み停止時点と残りの変更の反映を確認し、再開前に移行先を正本と決める。切り替え後の書き込みをどう扱うかも切り戻し案に含める。元へつなぐだけではそれを失い得る。実行可否の確認表を使い、観測した確認と仮定を分けて残す。

</details>

## 3. アプリは SQL のプライベート IP を解決して接続できるが SELECT が拒否される。ネットワークをもっと開く？

<details>
<summary>考え方</summary>

接続できて文が拒否されるなら、一般的な通信障害よりデータベース認可が有力だ。認証されたプリンシパル、データベース、対象、操作を確かめる。適用権限を調べ、選んだアクセスモデルで必要最小限を与える。Azure の Contributor だけではテーブルの読み取り権限は得られない。公開接続を開いても不足する権限は得られず、露出だけ変わる。同じ ID と同じアプリ操作で診断を確認する。

</details>

## 4. 管理者から特定の平文値を隠したい。TDE だけで十分？

<details>
<summary>考え方</summary>

TDE は保存されたデータベースファイルを守るが、認可済みクエリが平文を返すのを単独では防がない。対応するクライアントと、DB 管理者のアクセス境界外に鍵を置く Always Encrypted などを検討する。必要なクエリ、アプリ互換性、鍵の回復、運用担当者を調べる。動的マスクは同じ機密性の境界ではない。「暗号化」という名前の機能を同一視せず、認可された架空データの試験で脅威モデルを検証する。

</details>

## 5. リリース後に一つのクエリだけ遅くなり、全体 CPU は正常だ。最初に役立つ確認材料は？

<details>
<summary>考え方</summary>

クエリを特定し、利用可能な Query Store の履歴で、同等の期間のプランと実行状況を比較する。パラメーター、読み取り、待機、ブロック、最近のスキーマや統計変更を見る。全体 CPU が正常でも、一つの処理が健全とは限らない。サイズを変える前に仮説を立てる。古いプランを試すなら成功条件と戻し方を定め、代表的な通信で監視する。一度速かっただけでは継続的な改善の証拠として弱い。

</details>

## 6. 新しいインデックスで検索は速くなったが、取り込みが大幅に遅くなった。成功と呼べる？

<details>
<summary>考え方</summary>

インデックスはデータ変更時にも維持されるので、負荷全体で判断する。代表的な読み取りと書き込みの遅延、処理量、容量、プランを変更前後で比べる。既存インデックスとの重複や、より狭い定義・異なる列順で要件を満たせるかも調べる。検索だけでなく取り込みにも許容基準を置く。デモのクエリ一つが速くなっただけで、その変更を残すべきではない。

</details>

## 7. 長いトランザクションが短い参照をブロックしている。待っているセッションを全部終了する？

<details>
<summary>考え方</summary>

何を中断するか決める前に、ブロックの連鎖とロックを持つトランザクションを探す。待たされる側は原因ではなく症状であることが多い。作業内容、経過時間、担当者、ロールバックの影響を調べる。終了しても巻き戻しに時間がかかり、アプリの正しさにも影響し得る。管理された調査で整合性要件を理解した後、短いトランザクションや適切な分離方式を検討する。無差別な終了スクリプトではなく、根拠と判断を残す。

</details>

## 8. SQL Agent のジョブを Azure SQL Database へ移す。時刻だけコピーすればよい？

<details>
<summary>考え方</summary>

Azure SQL Database に SQL Agent はない。処理を分類し、対応する T-SQL の横断処理なら Elastic Jobs、外部サービスを含む流れならオーケストレーションを検討する。時刻だけでなく、依存、ID、対象の発見、再試行、通知を評価する。応答が不明な後の再実行で業務結果を重複させない。隔離した架空データで代替を試し、実行記録と業務データの状態を両方比較する。

</details>

## 9. 誤った DELETE がセカンダリへ伝わった。レプリケーションの失敗？

<details>
<summary>考え方</summary>

正規に確定した変更を別のコピーへ伝えるという、設定通りの動作かもしれない。可用性と過去への復旧は別の問題だ。事故時刻と保持中の復旧点を調べ、不要な変更前の状態を隔離したデータベースへ復元する計画を立てる。欠けた記録と、その後の正当な記録を確かめてから復旧方法を選ぶ。古い状態に全部置き換えてよいとは限らず、その後の有効な書き込みも考慮する。

</details>

## 10. データベースはフェールオーバーしたが、ノートアプリはまだ動かない。RTO を達成した？

<details>
<summary>考え方</summary>

利用者のサービス復旧が目標なら未達だ。接続先、クライアント DNS、再接続、ID、依存、現在のプライマリの定期処理を確認する。架空記録で機能を試し、定義した開始イベントからの時間を測る。データ損失は RPO として別に記録する。フェールバック前には正本と同期計画を確立する。データベースが正常という表示だけでは、アプリや復旧目標が回復した証拠にならない。

</details>
