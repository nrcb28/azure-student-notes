# SC-900 · Security, Compliance, and Identity Fundamentals

## 1. 責任分担と境界だけに頼れない理由

大学のノートアプリを管理された基盤で動かしていても、未公開の解答を誰が見られるかはチームが決める。責任の分担はサービスモデルで変わる。インフラを任せても、ID、データ、設定、利用方法に関する判断をすべて任せたわけではない。

多層防御では、権限、端末制御、ネットワーク境界、アプリ側の確認、暗号化、監視、対応を組み合わせる。一つの制御の成功は全層の成功を意味しない。Zero Trust では、要求を検証し、権限を絞り、侵害される前提で備える。学内 Wi-Fi にいるだけで無制限に許可すべきではない。[Zero Trust の出典](https://learn.microsoft.com/en-us/security/zero-trust/zero-trust-overview)。

## 2. 誰が接続し、何を許されるのか

認証は ID を確かめ、認可はその ID が操作を実行してよいかを決める。サインインできてもアクセスを拒否されることはある。権限を変える前に、ID、リソース、操作、スコープを記録しよう。

Entra ID は人とワークロードの ID を扱う。職員、ゲスト、アプリケーション、サービスプリンシパル、マネージド ID にはそれぞれ用途とライフサイクルがある。対応するワークロードでは、マネージド ID によってアプリにクライアントシークレットを保存せずトークンを取得できるが、権限は別に必要だ。Entra のディレクトリロールと Azure のリソースロールも対象が違う。ユーザー管理者になっても、全学生の文書を読めるわけではない。[ID のノート](../../ja/06-identity.md)で境界を確認しよう。

## 3. 資格情報、MFA、ハッシュ、暗号化

二つのパスワードも同じ種類の要素だ。MFA は異なるカテゴリの要素を組み合わせるが、どの方法も同じようにフィッシングに強いわけではない。特権アクセスなら、単に二回目の確認があるかではなく、対応するフィッシング耐性のある方法と回復手順を評価する。利用者の登録、端末の対応、実際のポリシー適用も重要だ。

暗号化は鍵を使ってデータを保護し、認可された側が元の内容を復元できる。暗号学的ハッシュは比較に使うダイジェストであり、元に戻せる暗号化ではない。ファイルのハッシュ一致は、前提の範囲で内容が一致する確認材料にはなるが、作成者の証明ではない。パスワード保存にはソルトや計算コストを含む適切な方式が必要であり、このノートを認証システムの実装手順にはしない。

## 4. 条件付きアクセスは判断のポリシー

条件付きアクセスはシグナルとアクセス制御を組み合わせる。たとえば財務アプリに、適切な認証強度と準拠した端末を要求できる。対象の ID、アプリ、条件、許可の制御、除外を説明する。一つのアプリを対象にしたルールは、すべてのアプリが守られている証拠にはならない。

アプリの権限やサービス拒否攻撃への対策を置き換えるものでもない。導入案では、仮想的な試験グループとレポート専用の分析を使い、許可・拒否の想定、管理者の回復手段、依存関係を検討する。このガイドではテナント全体のルールを有効にしない。[条件付きアクセスの出典](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview)。

## 5. 特権、アクセスレビュー、ID のリスク

PIM は、特権を常時有効にせず、有資格または期間限定で利用したい場面を扱う。有効化に承認、理由、認証の条件を付けられる。有資格であることはロールが有効な証拠ではないし、短時間でも広すぎるロールが適切になるわけではない。

アクセスレビューは、既存の権限がまだ必要かを確認する。ID Protection は ID に関するリスクのシグナルを検出する。リスク検出は調査材料であり、すべてのインシデントの完全な説明ではない。組み合わせて使えても、誰が特権を有効にできるか、誰に権限を残すか、どの行動が疑わしいかという別々の問いに答える。[PIM の出典](https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/pim-configure)。

## 6. Azure のセキュリティにも複数の層がある

NSG は対象となるネットワーク通信をフィルターする。Azure Firewall、WAF、DDoS Protection は目的が違い、どれもアプリの正しい認可を自動で与えない。プライベートエンドポイントは通信経路を変えるが、DNS と ID の制御は個別の設定が必要だ。

Defender for Cloud はクラウドのセキュリティ態勢の評価を助け、該当するプランでワークロード保護機能を提供する。推奨事項があるのは評価すべき状態があるという意味で、有効にしただけで是正が完了した証拠にはならない。ノートアプリなら、公開された管理ポート、過剰な権限、別の学生のファイルを返す不具合を分ける。それぞれ必要な材料と担当者が異なる。

## 7. 製品をまたぐ検知と対応

Defender XDR は、対応しオンボードされた Microsoft セキュリティ製品のシグナルを関連付け、活動の調査を助ける。メール、ID のイベント、端末のアラートが一つの攻撃かもしれない場面に役立つ。ただし、必要なデータを送っていないセンサーの情報まで関連付けられるわけではない。[Defender XDR の出典](https://learn.microsoft.com/en-us/defender-xdr/microsoft-365-defender)。

Sentinel は複数のソースからセキュリティデータを集めて分析する SIEM 機能と、対応の自動化・オーケストレーションを提供する。SIEM は情報とイベント管理、SOAR は連携した対応手順に関わる。コネクタ、ルール、保持期間、権限、対応担当者を定めよう。自動でアカウントを無効化する処理は、通知より慎重な設計が必要だ。[Sentinel の出典](https://learn.microsoft.com/en-us/azure/sentinel/overview)。

## 8. Purview：保護と証拠を区別する

秘密度ラベルは内容を分類し、対応する環境では設定された保護を適用できる。「機密」というラベル名だけで、あらゆる外部共有が止まるわけではない。DLP は機密データの扱いを評価し、条件に一致する操作へ警告や制限を行う。

保持は適用される規則に従って内容を残す・削除する仕組みだ。監査は活動を記録し、eDiscovery は調査のために情報を検索・保全・確認する。どちらもバックアップ戦略そのものではない。Compliance Manager は改善策や評価を整理できるが、その点数は法的な適合性の判断ではない。具体的なデータ上の義務、担当者、範囲、証拠から始める。[Purview の概要](https://learn.microsoft.com/en-us/purview/purview)。

## 9. テナントを変更しない実践演習

ゲストがノートを取得し、編集者が解答をアップロードし、管理者がアクセスを管理する架空の流れを描く。文書名は架空にし、個人情報は使わない。信頼境界を記入し、各段階で脅威を一つ挙げる。

各脅威について、予防策、検知シグナル、担当者、回復操作を書く。ゲストは未公開の解答を取得できない、という失敗すべき要求も加える。要求の拒否、監査イベント、アラートのどれで結論を確かめられるか説明する。これは期待結果であり、Azure での観測結果ではない。構成図と六行の確認表を提出し、ポリシーの有効化やサービス展開は行わない。

## 10. 実習前に対象範囲と前提を確認する

ライセンス、サービスプラン、対応ワークロード、ロール、オンボード状況によって使える機能は変わる。見慣れたポータル画面でも、利用権がある証明にはならない。展開や運用負担の見積もりを提案する前に、対象の機能を確認する。このノートでは料金を仮定していない。
