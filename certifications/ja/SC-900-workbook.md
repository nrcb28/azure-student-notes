# SC-900 · 判断と確認材料のワークブック

[ガイド](SC-900.md) · [十のケース](SC-900-cases.md) · [目次](README.md)

どの言語でも同じ学習目標を適用する五つの独自単元。架空の大学とデータを使う。オフライン設計演習であり、ポリシー展開、テナント変更、Azure での実行を完了したとは主張していない。

<a id="sc-900-unit-1"></a>

## 1. 責任と信頼境界を描く

ブラウザー、ID プロバイダー、アプリ、文書ストアを描く。各境界で何を検証し、誰が制御を運用するかを説明する。提供者の基盤運用と、組織が決める利用者・共有・設定・データの責任を分ける。学内ネットワークにいるだけでは、要求を信頼する根拠にならない理由を書く。

**シナリオ：**ゲストは公開ノートを読めるが、未公開の解答は読めない。**確認材料：**構成図と、許可二つ・拒否二つの操作、その担当者、検証に必要な観測を表にする。**提出物：**期待結果と実際に観測した結果を区別した一ページ。この演習では本物のテナントを試験しない。

<a id="sc-900-unit-2"></a>

## 2. アクセス判断を設計する

ID の種類、対象アプリ、要求操作、最低限の権限を指定する。認証の条件を提案し、要素のカテゴリとフィッシング耐性を説明する。条件付きアクセスで考えるシグナルと、アプリ側に残る確認を分ける。「全員に MFA」とだけ書かず、範囲、除外、回復、ライセンスの依存を記録する。

**シナリオ：**客員講師が個人端末から教材を開く。**確認材料：**許可される要求、不十分な認証方法、担当外の資料への要求について期待判断を書く。**提出物：**理由つきのアクセス表。実際のテナントは変更しない。レポート専用の観測を強制済みの判断と扱わない。

<a id="sc-900-unit-3"></a>

## 3. 特権、付与、リスクを分ける

「誰が特権ロールを有効にできるか」「誰にプロジェクト権限を残すか」「どの ID の行動を調べるか」の三問を書く。それぞれ PIM、アクセスレビュー、ID リスクの考え方に結び付ける。短時間の広いロールが自動で最小権限になると思わず、スコープと期間を定義する。

**シナリオ：**離脱したメンバーがグループに残り、管理者は一時保守の権限を必要としている。**確認材料：**付与経路、所有者の判断、有効化の案、不審な行動があれば別の記録。**提出物：**承認者と完了確認を記した短い手順書。特権の割り当ては作らない。

<a id="sc-900-unit-4"></a>

## 4. 検知と範囲を絞った対応を計画する

メール、ID、ワークロードを含む架空の攻撃経路を一つ選ぶ。仮説を支持・否定するイベントを挙げる。Defender XDR の関連付けと、Sentinel のコネクタ・分析・対応連携が役立つ箇所を説明する。不足するデータを明示する。結果が空でも、イベントが存在しなかった証明にはならない。

**シナリオ：**フィッシングメールの後に疑わしいサインインが発生した。**確認材料：**時系列、収集対象、分析担当者、影響のある操作前の通知案。**提出物：**誤検知と回復手順を含む検知・対応表。この演習ではデータ取り込み、有料機能の有効化、アカウントの自動ブロックを行わない。

<a id="sc-900-unit-5"></a>

## 5. 機密データのライフサイクルを追う

架空文書を、作成、内部利用、共有、調査、廃棄まで追う。分類、設定された保護、DLP、保持、監査証拠、eDiscovery を分ける。提案した機能ごとに、ワークロードとライセンスの前提を書く。適合性の点数は、組織が負う実際の義務の判断を代替しない。

**シナリオ：**架空の解答を公開日まで非公開にし、調査用メッセージは保全する。**確認材料：**期待する処理判断、必要な操作記録、保持の前提、担当者。**提出物：**一つのラベル、ログ、バックアップだけでは全要件を満たせない理由を示す表。法的要件は、権限のある担当者から受け取る入力として扱う。
