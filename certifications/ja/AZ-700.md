## 1. ネットワークを作る前にアドレスを計画する

学内、Azure、パートナー、将来のネットワーク範囲を棚卸しする。プライベートアドレスが重複すると、ピアリングやハイブリッドの経路設計が難しくなる。RFC 1918 の範囲だからといって、組織内で一意とは限らない。

たとえばプロジェクト用に 10.70.0.0/16 を確保し、Web に 10.70.1.0/24、データに 10.70.2.0/24 を割り当てる。/24 は IPv4 アドレス 256 個を含むが、通常の Azure サブネットでは五つが予約され、割り当て可能なのは 251 個になる。サービス固有の条件もある。委任サブネット、ゲートウェイ、ファイアウォールには、特定の名前、サイズ、専用利用、委任が必要な場合がある。残りを埋める前に確認しよう。

境界ごとに、ライフサイクル、経路、信頼、サービス要件、拡張のどれが理由かを書く。サブネットを一つ増やすだけでは、実際に強制できるセキュリティ境界にはならない。

## 2. 接続は意図して設計する

VNet ピアリングは、互換性があり範囲の重複しないネットワークを接続するが、所有者やセキュリティ制御まで統合するわけではない。A と B、B と C をピアリングしても、A から C へ自動で接続できるようにはならない。必要な経路をすべて描こう。

ハブに共有接続や検査を置くことはできるが、ハブ・スポークの図だけでは中継設定にならない。ピア設定、転送トラフィック、ルートテーブル、通信を運ぶ装置やゲートウェイを確認する。ゲートウェイ転送は対応する設定で共有を可能にする機能で、あらゆるスポーク間通信を自動中継する保証ではない。[ピアリングの出典](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-peering-overview)。

## 3. 往復の有効なルートを読む

ルートは次のホップを選ぶもので、アプリへのアクセス許可ではない。送信元サブネット、宛先アドレス、一致するプレフィックス、ルートの由来、実際の有効な次ホップを確認する。0.0.0.0/0 の広い UDR が、すべてのより具体的なルートを上書きするとは考えない。

ネットワーク仮想アプライアンスを入れるなら、転送設定、対応する構成、容量、戻りの経路も見る。要求が一つのステートフルなファイアウォールを通り、応答が別経路を戻ると、各サブネットが個別には到達可能でも接続が失敗し得る。例外を増やす前に両方向の経路を記録する。[Azure の経路選択](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-networks-udr-overview)。

## 4. DNS も接続の一部として扱う

実際のクライアントから、サービス名がどのアドレスに解決されるかを確認する。プライベートエンドポイントがあっても、到達できないパブリック宛先を選んでいれば役に立たない。

プライベートゾーン、VNet リンク、DNS サーバー設定、学内と Azure 間の転送を記録する。Azure DNS Private Resolver は対応するハイブリッド名前解決に使えるが、受信側と送信側の動作を分けて描く。証明書検証やサービスの経路選択のため、サービスのホスト名は使い続ける。恒久的なパブリック IP の書き換えで DNS の誤りを隠さない。名前解決の成功も、ID がサービスに受け入れられる証明ではない。[プライベートエンドポイント DNS](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-dns)。

## 5. ハイブリッド経路と障害領域を比較する

サイト間 VPN は通常、インターネット上に IPsec トンネルを作る。ExpressRoute は対応する接続構成を通じてプライベート接続を提供する。プライベートであることは、通信が自動で暗号化されるという意味ではない。

守りたい区間に応じて暗号化を選ぶ。MACsec は対応する ExpressRoute Direct の物理リンクに使え、IPsec の設計では端から端までの保護を検討できる。単なる無料の追加項目のように扱わず、処理能力や運用上の影響を確かめる。

回復性では、回線、拠点、事業者、ゲートウェイ、利用者側の装置、ルートのうち、一緒に故障するものを挙げる。予備 VPN にも、正しい経路広告と戻り、十分な容量、アプリの復旧試験が要る。図に二本線があっても、同じ障害領域に依存しているかもしれない。[ExpressRoute の暗号化](https://learn.microsoft.com/en-us/azure/expressroute/expressroute-about-encryption)。

## 6. プロトコルと範囲で配信サービスを選ぶ

| 必要なこと | 調べる候補 |
|---|---|
| TCP/UDP フローの分散 | Azure Load Balancer |
| リージョン内の HTTP ルーティング、TLS、WAF | Application Gateway |
| グローバルな HTTP 配信と高速化 | Azure Front Door |
| DNS による接続先の選択 | Traffic Manager |

これは候補を探す出発点で、排他的な機能一覧ではない。Application Gateway にも対応する TCP/TLS 機能があるので、HTTP 専用と断言せず、現在の機能と設定を確認する。Traffic Manager が返すのは DNS の応答であり、全リクエストを代理送信するものではない。宛先変更には DNS キャッシュも影響する。

どの候補でも、フロントエンド、バックエンド、プロトコル、プローブ、証明書、故障時の動作を指定する。プローブが正常でも、文書ダウンロードの内容が誤っている場合はある。[配信の比較](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/load-balancing-overview)。

## 7. 二つのサービス接続方式を区別する

プライベートエンドポイントは、対応するサービスに VNet 内のプライベートなネットワークインターフェースのアドレスを与える。サービスエンドポイントは、サービスのエンドポイント方式に従い、対応するサブネットからサービスへのアクセスを識別・保護する。サービスのパブリックな接続先を、サブネット内のプライベートアドレスに置き換える機能ではない。

ストレージでは、エンドポイントの承認、対象サブリソース、DNS、ネットワーク制限、データへの認可を別々に確かめる。プライベートエンドポイントを追加しても、すべてのパブリックアクセスが自動で無効にはならない。プライベート経路があるだけでコンテナーを読む権限も得られない。意図した経路と許可する ID の両方を書く。

## 8. 問題に合う制御を選ぶ

NSG は優先順位と状態を持つ通信フィルターだ。サブネットとインターフェースのルールを合わせて確認する。変更しても、既存の接続がすべて即時終了するとは限らない。Azure Firewall は対応するネットワーク・アプリケーションのフィルターやアドレス変換を集約できる。WAF は対応する Web 通信の検査で、一般的な経路設計を置き換えない。DDoS 対策は可用性への脅威を扱い、ユーザーを認可しない。

「セキュリティがおかしい」より「新しい TCP 443 の通信がこのルールで拒否される」の方が検証しやすい。調査のたびに広く許可する習慣は避けよう。

## 9. 順序立てて確認材料を集める

名前解決、選ばれた宛先、有効な次ホップ、適用されるフィルター、待ち受けプロセス、TLS、アプリ権限を追う。対象に合う Network Watcher の機能を選ぶ。次ホップの分析、IP フロー検証、有効なルール、接続のトラブルシューティング、パケットキャプチャでは、前提と範囲が違う。

一つのパケットが許可されるという予測だけでは、認証された要求の成功は分からない。送信元、宛先、プロトコル、ポート、時刻、観測、次の仮説を残す。Network Watcher は PaaS やアプリのテレメトリを何でも代替する道具ではない。[診断ツール](https://learn.microsoft.com/en-us/azure/network-watcher/network-watcher-overview)。
