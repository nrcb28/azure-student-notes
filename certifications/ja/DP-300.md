# DP-300 · Administering Microsoft Azure SQL Solutions

[認定資格のルート](README.md) · [十のケース](DP-300-cases.md) · [ワークブック](DP-300-workbook.md) · [English](../en/DP-300.md)

データベースにつながるのは始まりにすぎない。DP-300 では、何かが変わったときもデータを使える状態に保ち、守り、復旧でき、必要な速さで処理する方法を学びたい。例は大学のノートアプリだ。学生が文書をアップロードし、SQL データベースが所有者、科目、ダウンロード権限を保存する。

## 1. 要件から基盤を選ぶ

Azure SQL Database は管理された基盤でデータベース中心のアプリを動かす選択肢だ。Managed Instance はインスタンス単位の SQL Server の動作に多く対応するが、互換性の確認は必要だ。Azure VM 上の SQL Server は OS の制御と広い互換性を得る代わりに、管理作業が増える。同じ展開方式の別名ではない。

ノートアプリなら、サイズを選ぶ前に、機能、依存、保守責任、復旧目標を挙げる。OS 上のエージェントが選択を変える場合もある。ある製品を使い慣れていること自体は要件ではない。必要に応じて Azure Arc や Microsoft Fabric の SQL データベースの現行機能も比較する。ただし、どんな Azure SQL ワークロードでも自動で置き換えられるとは扱わない。

[基盤の比較](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview?view=azuresql)。

## 2. 移行を順序のある作業として計画する

サイズ、バージョン、ログイン、ジョブ、データベース間の依存、アプリの前提を棚卸しする。コピー前に互換性を評価し、スキーマ変換、初回転送、変更の継続反映、切り替えを分ける。転送に成功してもアプリが動くとは限らない。

オフライン移行では書き込み停止を計画する。対応するオンライン方式なら停止を短縮できるが、最後の移行は管理された手順が必要だ。どちらを正本とするか、書き込みをどう止めるか、残った変更をどう確かめるか、誰が再開を承認するかを決める。行数と重要な業務の合計を比較し、権限、定期処理、アプリ動作を試す。切り戻しでは古いコピーへの再接続だけでなく、切り替え後の書き込みも扱う。

## 3. アクセスの全経路を追う

接続失敗は、クライアントの名前解決、ネットワーク経路、サービス設定、認証、データベース認可の順に診断する。プライベートエンドポイントはデータベースユーザーを作らない。Azure の管理ロールも、SQL テーブルを読む権限を自動で与えない。

対応する場合は適切な Entra ID を使い、必要なデータベースプリンシパルと権限を用意する。共有管理者を使わず、アプリの機能に必要な操作だけを与える。展開、アプリ、インシデント対応の ID を分け、権限変更前に実際の ID と対象データベースを確かめる。ネットワーク設定も製品ごとに確認する。SQL Database のファイアウォール規則を Managed Instance にそのまま移すことはできない。

[多層のセキュリティ](https://learn.microsoft.com/en-us/azure/azure-sql/database/security-overview?view=azuresql)。

## 4. 正しい層でデータを保護する

通信の暗号化は接続を守る。TDE は保存されたデータベースファイルの暗号化を扱う。Always Encrypted は違う保護境界を持ち、対応クライアントドライバーと鍵の管理も関係する。データベース管理者から特定の平文を隠す要件なら、その境界を調べる必要がある。TDE の有効化だけでは満たした証明にならない。

動的データマスクは、該当するマスク解除権限のない利用者への結果表示を変える。認可を置き換えたり、広いクエリ権限を無害にしたりはしない。行を読める人、鍵を管理する人、ログやエクスポートに出る内容を決める。監査も、出力先、保持期間、アクセス、確認手順を誰が担当するかが重要だ。

## 5. 役立つ基準値を作る

「遅い」を測定できる形にする。たとえば通常 30 ミリ秒の権限確認が 800 ミリ秒になった、と記録する。クエリ、時間帯、実行時間、CPU、読み取り、アプリの並行数を残す。同じ操作と似た負荷で比較する。静かな深夜の結果は、昼の混雑時との比較には弱い。

Query Store は、回帰の調査に使えるクエリ、プラン、実行情報を保持する。昨日の証拠があると期待する前に設定と履歴を確認する。基盤メトリックは資源の逼迫を示し、待機、ブロックの連鎖、実行プランは作業が遅れる理由を調べる助けになる。証拠の不足は制約として記録し、確信を持った原因に置き換えない。

[Query Store](https://learn.microsoft.com/en-us/sql/relational-databases/performance/monitoring-performance-by-using-the-query-store?view=sql-server-ver17)。

## 6. 仮説を一つずつ調整する

新しいプラン、古い統計、不適切なインデックス、パラメーターの変化、長いトランザクションなどが遅延を説明するかもしれない。材料を確認し、戻せる実験を選ぶ。インデックス追加は検索を速くしても、書き込み処理や容量を増やす。スキャン自体が必ず誤りなのではなく、必要な行数と使えるアクセス方法を見る。

変更前後で、同時書き込みも含む代表的な負荷を試す。プラン強制は確認された回帰に役立つ場合があるが、監視と解除手順が必要だ。容量が制約と分かったなら、資源を増やす判断も妥当だ。定期的な縮小、全部の再構築、処理内容を知らないままのセッション終了は、混乱を増やして元の原因を隠す場合がある。

## 7. 実際に使う基盤に合わせて自動化する

SQL Server と Managed Instance には SQL Agent があるが、Azure SQL Database にはない。SQL Database の対象に T-SQL 処理を行う場合、対応する Elastic Jobs が候補になる。データベース、ストレージ、外部システムをまたぐ流れなら、オーケストレーションのサービスが適する場合もある。

ジョブごとに ID、対象、時刻、タイムアウト、再試行方針、失敗通知を決める。月次結果を挿入する処理では、成功応答を失って再実行しても重複を作らないようにする。作業単位ごとに完了を記録し、ジョブが動いたことと業務結果を確認したことを分ける。最初は架空データと隔離した対象で試す。

[自動化の選択肢](https://learn.microsoft.com/en-us/azure/azure-sql/database/job-automation-overview?view=azuresql)。

## 8. バックアップ、可用性、災害復旧を分ける

バックアップは保持された状態への復元を支える。ポイントインタイムリストアと長期保持では時間軸が違うので、事故前に要件から保持を決める。SQL Database の復元は既存のものを上書きせず、データベースを作る。そのため、検証とアプリの適切な再接続まで復旧計画に含める。

レプリケーションや可用性の仕組みは障害に対応する一方、正規に確定した破壊的変更も伝える場合がある。レプリカが一つ増えても、以前の状態へ戻る必要はなくならない。RPO は許容する直近データの損失、RTO は許容する復旧時間として定義し、現実的な依存関係で両方を試す。リージョン、層、設定、複製方式で設計は変わる。万能な復旧時間を作り上げない。

[バックアップからの復元](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups?view=azuresql) · [事業継続](https://learn.microsoft.com/en-us/azure/azure-sql/database/business-continuity-high-availability-disaster-recover-hadr-overview?view=azuresql)。

## 9. アプリを復旧し、その後の復帰を計画する

データベースのフェールオーバーは終了地点ではない。対応する接続先、DNS、認証、再接続、依存する保存先との整合性を確認する。フェールオーバーグループのリスナーで接続先を維持できても、クライアントが正常に再接続する必要はある。新しいプライマリの監視と定期処理も含める。

戻す前に、どのデータベースが正本で、変更をどう同期するかを確立する。判断の担当者と中止条件を記録する。最初の復旧が成功しても、根拠のないフェールバックで有効な書き込みを失う可能性がある。

## 10. オフラインの運用演習

クラウドリソースを作らず、ノートアプリの手順書を準備する。基盤を選び、アクセス境界と基準値の表を描く。プラン回帰と誤削除という別々の事故を想定し、区別に必要な材料を挙げる。隔離したデータベースへの復元と、架空の記録による機能確認を説明する。

各記録に **期待（EXPECTED）**、**観測（OBSERVED）**、**未実行（NOT EXECUTED）** を付ける。構成図やローカル SQL の演習で Azure の復元時間は証明できない。前提、検証基準、必要権限、切り戻し、残るデータの後片付けを提出する。[五単元](DP-300-workbook.md)と[十の独自ケース](DP-300-cases.md)へ進もう。ここでは Azure で実行したとは主張していない。
