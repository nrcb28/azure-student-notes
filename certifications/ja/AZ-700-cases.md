# AZ-700 · 理由を考える 10 ケース

[ガイド](AZ-700.md) · [ワークブック](AZ-700-workbook.md) · [目次](README.md)

独自の学習シナリオで、公式問題や流出した試験問題ではない。要件、別案を除く理由、必要な確認材料を考えてから解答を見る。Azure で実行したとは主張していない。

## 1. 学内と新しい VNet が両方 10.70.0.0/16 を使っている。通常のピアリングや VPN で宛先を一意にできる？

<details>
<summary>考え方</summary>

重複はアドレス設計の問題であり、許可ルールの不足ではない。標準的なピアリングやハイブリッド接続の前に、現状を調べて非重複の範囲を選ぶ。条件によって対応する変換構成もあるが、制約を含めて明示的に設計する必要がある。同じアドレス範囲を宛先にしたパケットからは、意図した拠点を判断できない。範囲の一覧、修正後のアドレス計画、宛先ごとの予想ルートが確認材料になる。

</details>

## 2. A と B、B と C をピアリングしたが A から C に届かない。送信元 VM に Owner を与えるべき？

<details>
<summary>考え方</summary>

VNet ピアリングは自動で推移的にはならず、管理ロールは足りないネットワーク経路を作らない。直接接続か、対応する中継構成かを決める。両方向のルート、転送、セキュリティを確認する。共有ゲートウェイがあるなら、スポーク間を何でも転送すると思わず、固有の転送設定を見る。必要な材料は完全なパケット経路と有効な次ホップであり、より広い管理権限ではない。

</details>

## 3. 既定ルートをファイアウォールへ向けたのに、より具体的な宛先への通信は別に行く。UDR が全部壊れた？

<details>
<summary>考え方</summary>

そうとは限らない。適用されるルートと実際の宛先を調べる。広い既定ルートが、すべての具体的なルートに優先するとは想定しない。Azure の選択規則に沿って、プレフィックス、ルートの由来、有効な次ホップを比較する。ルートテーブルが送信元サブネットに関連付いているかも確認する。競合するプレフィックスと観測した次ホップを示す。セキュリティルールを変えても、どのルートが選ばれたかは分からない。

</details>

## 4. 要求はステートフルな装置を通るが、応答は別の経路を戻る。許可されていても失敗する理由は？

<details>
<summary>考え方</summary>

状態を管理する装置は、往復の両方を見る必要がある場合がある。非対称経路では、最初のフローを記録した装置を戻りが通らなかったり、状態を持たない別の装置へ届いたりする。往復ルート、装置の転送設定、アドレス変換を確認する。仮説を試す前に、無関係な受信許可を加えない。両経路の図と、端点または対応する診断ツールの観測が有用な提出物になる。

</details>

## 5. ストレージの公開アクセスを無効にし、API からプライベート接続できるはずなのに名前はパブリック IP に解決される。最初に見るのは？

<details>
<summary>考え方</summary>

API クライアントの実際の DNS 経路、サーバー設定、プライベートゾーン、VNet リンク、ハイブリッド転送を調べる。サービスのホスト名を使い、意図したプライベート接続に合うよう解決させる。Storage Blob Data Reader を付けても DNS 応答は直らない。名前解決と経路が動いてから、データ認可を別に確かめる。名前、IP、リゾルバー、サブリソース、その後の認証済み操作を別々の証拠として残す。

</details>

## 6. 学内から Azure まで暗号化する要件がある。ExpressRoute を契約しただけで満たせる？

<details>
<summary>考え方</summary>

ExpressRoute のプライベート接続と暗号化は別であり、既定で暗号化されない。何をどこからどこまで守るかを指定する。MACsec は ExpressRoute Direct の対応リンクで選べるが、すべての事業者回線で自動的に使えるものではない。端から端までなら適切な IPsec 構成を検討できる。互換性、性能、鍵の運用を比較・記録する。プライベート経路の図だけでは暗号化の証拠にならない。

</details>

## 7. DNS によるリージョン選択が必要で、全要求が Traffic Manager を通る設計になっている。何を直す？

<details>
<summary>考え方</summary>

Traffic Manager は DNS に基づいて接続先を選ぶのであって、要求を代理送信するものではない。クライアントは選ばれた宛先へ接続し、DNS の変更が効くまでキャッシュの影響を受ける。グローバルな HTTP プロキシ配信が必要なら Azure Front Door を、リージョン内の HTTP ルーティングなら Application Gateway を要件に照らして検討する。DNS の交換とアプリ接続を分けて描き、正常性情報が選択にどう使われるかを説明する。

</details>

## 8. サブネットでサービスエンドポイントを有効にした。ストレージにプライベートエンドポイントのアドレスができた証明にならないのはなぜ？

<details>
<summary>考え方</summary>

サービスエンドポイントとプライベートエンドポイントは別の設計だ。有効にしても、そのストレージのプライベートなネットワークインターフェースがサブネット内に作られるわけではない。実際の設定、サービス側のネットワークルール、認証方法を見る。プライベートな宛先 IP が要件なら、対応するプライベートエンドポイントと DNS・アクセス設定を検討する。同じ「エンドポイント」という語で同一視せず、解決先と関連リソースの設定を記録する。

</details>

## 9. 新しい拒否ルールで新規接続は止まるが、既存セッションが続く。NSG はルールを無視している？

<details>
<summary>考え方</summary>

NSG は状態を持つため、変更が既存フローを即時に切断するとは限らない。新しい接続と再利用したセッションを区別し、サブネットとインターフェースの有効なルールを調べる。ルール名だけでなく、送信元、宛先、ポート、プロトコル、優先順位を確認する。試験が新しいフローを作ったかも観測に含める。管理ロールを広げたり、VM を削除したりしても、この動作の説明にはならない。

</details>

## 10. 図に ExpressRoute と予備 VPN がある。回復性のあるアプリ接続と言う前に、何が足りない？

<details>
<summary>考え方</summary>

共通の障害領域を特定し、予備経路全体を検証する。利用者側装置、事業者、接続拠点、ゲートウェイ、経路広告、戻り、トンネル容量、DNS、アプリの再接続を見る。二本目の線だけでは、障害時に正しく選択されると分からない。期待と観測、復旧、通常運用へ戻す条件を含め、隔離された認可済みの試験を計画する。このノートはその設計演習であり、フェールオーバーを実行したとは主張していない。

</details>
