## 1. データで何に答えたいのかから始める

大学のノート共有アプリでも、ファイルのダウンロード、履修登録、月ごとの利用状況レポートは別の処理だ。製品を選ぶ前に、どの操作をしたいかを書き出したい。どの記録を一緒に変更する必要があるか。結果はどの程度古くてもよいか。誰が読めるのか。PDF を保存するだけなら必ずしもデータベースは必要ないし、JSON だからデータベースを使えないわけでもない。

参照確認日：**2026 年 10 月 30 日**。[DP-900 公式学習ガイド](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/dp-900)の目標は **2026 年 7 月 21 日**からの版。対応する資格は [Azure Data Fundamentals](https://learn.microsoft.com/en-us/credentials/certifications/azure-data-fundamentals/)。データベース管理の学習準備には役立つが、その資格を受けるための必須条件ではない。

## 2. 表現形式と処理の種類は分けて考える

構造化データには、型を定めた列を持つ履修登録表のような明確な構造がある。半構造化データにも構造はあるが、全レコードが同じ項目を持つとは限らない。JSON には任意のメタデータを入れられる。スキャンしたワークシートは、ファイル名に規則があっても、内容の検索という観点では非構造化データになる。

CSV は小さな表形式の交換に便利だが、文字コード、区切り文字、欠損値の扱いを決める必要がある。JSON は入れ子を表せる。Parquet は列指向で、分析時に必要な列を読み取る処理などに向く。形式を選んだだけでは、権限、業務ルール、データ品質は整わない。

トランザクション処理では、席の予約と残席数の更新など、関連する小さな操作を整合的に行うことが多い。分析処理では、科目や学期ごとの履修人数など、過去の記録を集計する。同じデータベースが両方に関わる場合もあるが、重いレポート処理が本番アプリと資源を取り合う可能性がある。理由なく「リアルタイム」を要求する前に、許容できる鮮度を決めよう。

## 3. リレーショナル設計では関係を明示する

Students、Courses、Enrolments を考える。主キーは行を識別し、外部キーは、その制約をデータベースが強制する場合に関係を保証する。Enrolments で学生と科目を結べば、全学生の記録に科目名を複製せずに済む。正規化は特定の重複や更新時の不整合を減らすための考え方であり、あらゆるレポートを最大限に細分化した表から作るという規則ではない。

テーブルは行を保存する。ビューは保存したクエリによる見え方で、必ずしも別のデータのコピーではない。インデックスはアクセスを助けるが、保存容量と書き込み時の処理も増やす。ストアドプロシージャはデータベース側の処理をまとめる。トランザクションは並行実行や分離レベルの動作に従って関連変更の整合性を保つ助けになるが、実装していない業務ルールまで直してはくれない。

SELECT、INSERT、UPDATE、DELETE、CREATE、GRANT の目的を説明できるようにする。UPDATE や DELETE の前には対象行を予測し、サンプルデータで条件を確かめる。文が正常終了しても、間違った行を変更している可能性は残る。

## 4. Azure SQL では運用形態も選ぶ

Azure SQL Database は管理されたデータベースサービスだ。Azure SQL Managed Instance は、既存の SQL Server アプリケーションで必要になる多くのインスタンス単位の互換性に対応する。Azure VM 上の SQL Server では OS にアクセスできる分、チームの管理作業も増える。同じような SQL が使えるからといって、展開方法、互換性、保守の責任まで同じとは限らない。

新しいノートアプリなら、必要な機能、接続、復旧要件、運用負担、負荷の形を比較する。移行なら、最初に依存関係を棚卸しする。インスタンス固有の機能や外部コンポーネントで選択が変わる場合がある。「管理されたサービス」でも、アクセス、スキーマ、アプリのクエリ、復旧要件の責任は残る。PostgreSQL や MySQL にも Azure の管理サービスがある。SQL Server に寄せるより、既存のエンジンと合わせる方が大事な場合もある。製品とサポート対象バージョンを個別に確認しよう。

[出典：Azure SQL の選択肢](https://learn.microsoft.com/en-us/azure/azure-sql/azure-sql-iaas-vs-paas-what-is-overview)。

## 5. オブジェクト、共有、エンティティは用途が違う

Blob Storage は PDF や画像などのオブジェクトを保存する。Azure Files は、対応するファイルアクセスが必要な場面で管理されたファイル共有を提供する。Table Storage は非リレーショナルなエンティティの保存先であり、SQL のリレーショナルテーブルを提供するサービスではない。マネージドディスクも別の抽象化だ。

ノートアプリなら、ファイル本体を Blob、所有者情報をデータベースに置く設計が考えられる。ただしアップロードが途中で失敗したとき、両者をどう整合させるかを記録する。保存先を分けただけでは、トランザクションが自動で調整されるわけではない。ストレージアカウントを作る権限と、その中の Blob を読む権限も別だ。ダウンロード用トークンは資格情報として扱い、共有ノートに貼らない。

[出典：ストレージサービス](https://learn.microsoft.com/en-us/azure/storage/common/storage-introduction)。

## 6. ドキュメントデータベースが合う場面を理解する

Azure Cosmos DB は、対応する API とデータモデルを通じて非リレーショナルなアプリケーション用途を支える。科目ごとに異なる任意のメタデータなら、すべてを個別の列にするよりドキュメント形式が合うかもしれない。ただし、それで全ワークロードの保存先が決まるわけではない。

読み取り、更新、関係、整合性の要件、運用上の制約から考える。SQL に似たクエリ言語があるだけで、リレーショナルな動作や制限のない結合ができるとは判断しない。基礎としては、ドキュメント、キーと値のエンティティ、オブジェクト、リレーショナルな行を比較できればよい。具体的なアプリ実装や性能調整は、この単元の範囲外とする。

[出典：Cosmos DB の概要](https://learn.microsoft.com/en-us/azure/cosmos-db/overview)。

## 7. パイプラインを通るデータを追う

バッチ処理は昨日のダウンロード記録のように区切られた集合を処理する。ストリーミングは到着するイベントを一定の遅延内で処理するが、重複、遅延イベント、障害への対応は必要だ。ダッシュボードが毎秒更新されても、すべての元イベントが届いた証拠にはならない。

ETL は目的の保存先にロードする前に変換する。ELT は先にロードし、保存先の処理能力を使って変換する。どちらの略語もデータの正しさを保証しない。識別子、型、不正なレコードの行き先、突合方法を決める。入力数、受理数、拒否数を数え、差を隠さず説明する。オーケストレーションは手順、依存関係、障害後の再開を調整する役割であり、変換処理そのものとは違う。

[出典：ETL と ELT](https://learn.microsoft.com/en-us/azure/architecture/data-guide/relational-data/etl)。

## 8. 保存したデータを使える分析にする

データレイクは、多様なデータを後で処理できる形で保存する。ウェアハウスは、一貫したクエリやレポートに使う分析用データを整理する。レイクハウスは両方の考え方を組み合わせる。ファイルが大量にあっても、所有者、形式、品質、発見方法が決まっていなければ活用しにくい。スタースキーマでは、ファクト表が測定対象の出来事を、ディメンション表が説明のための文脈を表す。集計前に一行の粒度を決めよう。

Azure Synapse Analytics は分析機能やデータ統合の選択肢を提供する。Microsoft Fabric は複数のデータ・分析ワークロードを SaaS 基盤にまとめる。Power BI はセマンティックモデル、レポート、ダッシュボードを支える。関係はあっても同じ役割ではない。グラフを作る前に「完了したダウンロード」の定義、タイムゾーン、更新の境界を決める。そうしないと、どちらも正しそうなレポートが違う件数を数えてしまう。

[出典：Fabric の概要](https://learn.microsoft.com/en-us/fabric/fundamentals/microsoft-fabric-overview)。

## 9. 設計演習と確認材料

クラウドリソースを作らず、PDF、履修登録、月次ダウンロードレポートの構成図を描く。重複イベントと科目 ID の欠損を含む六件の架空データを用意する。各データの保存先、許容するレポート遅延、重複と不正レコードの扱いを決める。サンプルの SQL を一つ書くか、その結果を紙上で説明する。設計上の予測と実行して観測した結果は分けて記録する。

DBA はデータベース運用、データエンジニアは移動と加工、アナリストはモデルとレポートで問いに答える部分を主に担当する。仕事は重なるので、品質確認ごとに担当者を決める。[データの一般ノート](../../ja/04-storage.md)と比較し、[十のケース](DP-900-cases.md)を解答を見る前に解いてみよう。

独立した学習ノートであり、試験範囲の完全な網羅や合格を保証しない。Azure への展開を実施したとは主張していない。サービスや目標は変わるため、受験予約前に公式ガイドを確認する。
