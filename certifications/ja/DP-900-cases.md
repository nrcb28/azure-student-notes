# DP-900 · 理由を考える 10 ケース

[ガイド](DP-900.md) · [ワークブック](DP-900-workbook.md) · [目次](README.md)

独自の練習シナリオで、実際の試験問題ではない。まず要件を述べ、別の案を退ける理由と集めたい確認材料を説明しよう。クラウドへの展開を行ったとは主張していない。

## 1. ノートアプリが PDF と検索用の所有者情報を保存する。両方を一つの SQL テーブルに入れる必要がある？

<details>
<summary>考え方</summary>

必須ではない。PDF を Blob Storage、所有者や科目との関係をデータベースに置く設計が考えられる。大事なのはアクセスと整合性の境界だ。アップロードが成功しても、メタデータの更新は失敗するかもしれない。再開できる処理と、取り残されたファイルの検出方法を決める。一つのデータベース内で表す設計にも根拠があればよいが、「すべてのデータは SQL の行にする」と決めつける必要はない。

</details>

## 2. JSON に任意の入れ子項目があり、一部のフィールドがない。非構造化データになる？

<details>
<summary>考え方</summary>

JSON は、キーや入れ子で構造を持つ半構造化データを表せる。レコード間で項目が違っても、その構造は失われない。表現形式、品質、保存先の選択を分けて考える。項目がないのは正常なのか、不明なのか、取り込み時のエラーなのかを定め、利用側の動作を記録する。アクセス方法にドキュメントデータベースが合う可能性はあるが、JSON であることだけでは設計は決まらない。

</details>

## 3. 履修登録の各行に科目名と担当教員を繰り返している。正規化で防げる問題は？

<details>
<summary>考え方</summary>

科目名の変更時に一部だけ更新され、古い名称が残る可能性がある。安定したキーを持つ Courses を Enrolments から参照すれば、この更新時の不整合を減らせる。必要な制約と、結合によって結果を組み立てる方法も説明する。ただし重複をあらゆる場所で禁止するという意味ではない。分析用スナップショットでは当時の名称を意図して保存する場合もある。現在の登録情報か、履歴レポートかを明確にしよう。

</details>

## 4. レポート用クエリで履修登録が遅くなった。グラフを Power BI に移せば負荷は自動でなくなる？

<details>
<summary>考え方</summary>

データの取得方法と更新方法によるので、自動ではなくならない。本番データを直接クエリしたり、重い更新処理を発生させたりする可能性がある。鮮度、クエリの形、元システムの容量を確認する。分析用コピーで処理を分離できる場合もあるが、更新遅延とパイプライン運用の責任が加わる。表示ツールが変わればアクセスも変わると思い込まず、元データへの負荷と「最新」の意味を測定・定義する。

</details>

## 5. 既存の SQL Server アプリが OS 上の部品を必要とする。Azure SQL Database に必ずそのまま移せる？

<details>
<summary>考え方</summary>

その保証はない。対象を選ぶ前に、OS の部品やほかの依存関係を調べる。Azure SQL Database、Managed Instance、Azure VM 上の SQL Server は、管理範囲と互換性が違う。VM なら OS に触れられるが、保守責任が増える。Managed Instance が一部のインスタンス単位の要件を満たしても、外部依存をすべて満たすとは限らない。互換性一覧と移行試験を用意し、同じエンジン名だけでアプリ全体の動作を判断しない。

</details>

## 6. 名前に Table とあるので Azure Table Storage でも外部キーを使える、と言われた。どう設計を見直す？

<details>
<summary>考え方</summary>

Table Storage は非リレーショナルなエンティティストアであり、管理された SQL サービスではない。名前から結合や外部キーの強制を想定しない。必要な読み取り、更新、関係、整合性を整理し、エンティティモデルとリレーショナル設計を比較する。履修登録から科目を取得する方法や、不正な参照を防ぐ・検出する方法を具体例で示す。製品名は調査の手掛かりで、機能の確認そのものではない。

</details>

## 7. 夜間処理で翌朝の報告に間に合う。新しそうだからストリーミングに変えるべき？

<details>
<summary>考え方</summary>

まず業務が許容する遅延を見る。夜間バッチで必要な結果を確実に出せるなら、ストリーミングは利用者の判断を変えずに運用作業だけ増やすかもしれない。数分で過負荷に対応したいなら、その要件に低遅延経路を検討する。どちらでも、重複、不完全な入力、再試行への対応は必要だ。一つの部品の実行頻度だけでなく、端から端までの鮮度と障害復旧を比較する。

</details>

## 8. 生データをウェアハウスに読み込み、そこで整形している。ETL なのか。検証はもう不要？

<details>
<summary>考え方</summary>

この順序は、先にロードし、保存先の処理能力で変換する ELT だ。ETL は目的の保存先へロードする前に変換する。どちらでも、データの取り決めと検証は必要だ。不正レコードの行き先、再実行可能な変換、入力と受理件数の突合を決める。アナリストが整形済みのモデルだけを見る場合も、制限のある生データへのアクセスは管理する。クエリが容易でも、元の記録が安全で正しいとは証明できない。

</details>

## 9. ダウンロードイベントを COUNT(*) で数えている。再試行で同じ ID が重複する場合も完了件数になる？

<details>
<summary>考え方</summary>

数える一行が完了した一回のダウンロードだと定義できる場合に限る。重複配信があれば COUNT(*) は増える。業務上のイベント、安定した識別子、完了条件、集計期間を定義し、その定義に沿って重複排除や集計を行う。重複・拒否件数も残し、修正理由を説明できるようにする。同じ ID と未完了記録を含む小さなデータで試す。もっともらしいグラフだけでは、利用者の知りたい数を数えている証拠にならない。

</details>

## 10. 六件の科目データをドキュメントで表せた。保存先は Cosmos DB 以外あり得ない？

<details>
<summary>考え方</summary>

六件を保存できるサービスは多く、この例が示すのは表現できることだけだ。想定クエリ、関係、更新、整合性、運用要件、チームの知識を比較する。制約や関連エンティティが中心ならリレーショナルな方が簡単な場合があるし、別のアクセス方法ならドキュメントが合う場合もある。推奨する根拠と、その選択を変える条件を一つずつ書く。JSON の例に製品名を機械的に対応させるのではなく、理由を考えるのが基礎学習の目的だ。

</details>
