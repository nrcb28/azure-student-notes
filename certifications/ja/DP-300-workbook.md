# DP-300 · 共通の運用ワークブック

[ガイド](DP-300.md) · [十のケース](DP-300-cases.md) · [目次](README.md)

八言語で目標と確認材料が対応する五単元。必要なら Azure なしで設計演習を行う。期待する動作と実際の観測を分ける。Azure での実行や試験範囲全体の網羅を主張していない。

<a id="dp-300-unit-1"></a>

## 1. 基盤と移行の選択を説明する

必要な機能、OS アクセス、インスタンス依存、許容する書き込み停止、保守担当、復旧目標をノートアプリの要件表にする。慣れた名前に点を付けるのでなく、SQL Database、Managed Instance、VM 上の SQL Server を要件と比較する。

**ケース：**既存の定期処理が OS のツールに依存する。**確認材料：**依存が必要か、対応する移行先または再設計、互換性確認を示す。**提出物：**初回転送、書き込み停止、検証、切り替え、切り戻し担当、切り替え後の書き込みの扱いを含む手順。コピー完了だけを受け入れ試験にしない。

<a id="dp-300-unit-2"></a>

## 2. アクセスと機密性の境界を分ける

アプリ ID からテーブル上の許可操作までを描く。名前解決、ネットワーク、認証、データベースプリンシパル、オブジェクト権限を記入する。アプリ、展開、緊急管理の責任を分ける。クエリ、ログ、エクスポート、バックアップに何が出てよいかを書く。

**ケース：**プライベート接続は成功するがテーブルを読めない。**確認材料：**実際の ID、DB、対象、拒否操作。診断の代わりに公開ネットワークを広げない。**提出物：**最小権限の設計と、具体的な機密要件に対する通信暗号化、TDE、Always Encrypted、マスクの比較。鍵の回復と担当も含める。

<a id="dp-300-unit-3"></a>

## 3. 測定した性能回帰を診断する

文書権限のクエリについて、時間、読み取り、CPU、並行数、プランを含む比較可能な二つの負荷時間帯を作る。変化と材料を結ぶ仮説、その仮説を否定する観測を書く。Query Store の履歴だけでなく、ブロックとトランザクション時間も含める。基盤メトリックが正常でも、プランの一演算が高そうでも、それだけで原因とは言えない。

**ケース：**インデックスで検索は速くなり、取り込みが遅くなった。**確認材料：**代表的な負荷での両操作の変更前後。**提出物：**戻せる実験一つ、許容基準、切り戻し、材料の限界。日常保守として縮小や全セッション終了を提案しない。

<a id="dp-300-unit-4"></a>

## 4. 自動化を観測・再実行できる形にする

夜間タスクを処理内容と対象基盤で分類する。対応する SQL Server・Managed Instance の SQL Agent と、SQL Database の T-SQL 用 Elastic Jobs を比較する。ID、対象、時刻、タイムアウト、再試行上限、失敗通知を指定する。外部依存があれば、より広いオーケストレーターが要る場合もある。

**ケース：**結果はコミットしたが成功応答を失った。**確認材料：**再実行で業務結果を重複させない方法と、運用者の完了確認。**提出物：**待機中、実行中、完了、不明の状態表と架空データの試験計画。スケジューラー起動の成功を、業務結果の検証と混同しない。

<a id="dp-300-unit-5"></a>

## 5. データとサービス全体を復旧する

誤削除とリージョン障害を別の事故として定義する。それぞれの問題に合う保持された状態と可用性の仕組みを選ぶ。ノートアプリを基準に RPO・RTO を定め、必要な権限、復旧先容量、接続先、DNS、認証、依存を挙げる。レプリケーションは不要な確定済み変更も伝え得る。

**ケース：**新しいプライマリは正常でも、利用者がノートを取得できない。**確認材料：**再接続まで含む機能確認と時系列。**提出物：**隔離した復元・検証計画、フェールバック前の正本の判断、保持データの後片付け担当。適切な環境で観測するまで時間は期待値と表示する。机上演習で Azure の復旧を測定したことにはならない。
