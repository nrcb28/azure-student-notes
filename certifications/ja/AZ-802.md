# AZ-802 · Windows Server の管理

[認定資格](README.md) · [理由付き解答のある 10 ケース](AZ-802-cases.md) · [5 単元のワークブック](AZ-802-workbook.md) · [スペイン語](../es/AZ-802.md)

私は、小さな大学の Windows 実習環境を任された学生として、この分野を学ぶと思う。役立つ問いは、たいてい「この設定はどのコンソールにあるか」ではない。「どの層で障害が起き、その判断を何が裏付け、アクセスやデータを失わずにどう変更できるか」だ。以下の例は架空の環境を使っており、実際に調査した大学のネットワークではない。

## 1. 現行の試験範囲と明確な実習の境界から始める

公式参照先の確認日：**2026-11-03**。[AZ-802 学習ガイド](https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/az-802)、[試験ページ](https://learn.microsoft.com/en-us/credentials/certifications/exams/az-802/)、[Windows Server Administrator Associate](https://learn.microsoft.com/en-us/credentials/certifications/windows-server-hybrid-administrator/)。学習ガイドの「評価されるスキル」の見出しには日付がなく、ページ更新メタデータは **2026-10-19** となっている。このメタデータは、試験目標の発効日として告知されたものではない。確認時点で試験ページに記載されている言語は英語。このノートは翻訳した学習教材であり、試験に他の言語が用意されていることを示すものではない。従来の AZ-800/AZ-801 のノートや資格の古い概要は背景の理解に役立つが、AZ-802 の 7 分野のガイドに代わるものではない。

隔離した VM で、使い捨てにできる AD フォレスト `lab.example.test`、ドメインコントローラー 2 台、メンバーファイルサーバー、クライアントを用意する。Hyper-V ホストを追加するのは、入れ子の仮想化、メモリ、ストレージ、ライセンスの条件が許す場合だけにする。Azure への拡張は任意で、許可されたサブスクリプション、費用責任者、対応するネットワークが必要。演習を動かすためだけに、実習ドメインを本番の信頼関係へ接続してはいけない。

以下の PowerShell 例は状態の確認用であり、インストールスクリプトではない。Windows と指定の役割やモジュール、適切な権限が必要で、名前は実習環境に置き換える。この Linux の文書作成環境では実行していない。資格情報、回復キー、個人識別情報、生の本番ログは公開する証拠に含めない。変更する前に、バージョン、所有者、期待する動作、復旧経路、中止条件を記録する。

## 2. アカウントを作る前に ID を説明する

AD DS は、ドメインコントローラー、レプリケーション、DNS への依存、認証の責任を備えたディレクトリ。Microsoft Entra ID は別の ID システムである。Windows マシンを AD ドメインへ参加させること、Entra に登録すること、Azure Arc へ接続することは、それぞれ異なる問題を解決する。図には、どのシステムが利用者を認証し、どの ID が Azure を管理し、どのアカウントがファイル共有にアクセスするかを示す。

ID の一覧は、フォレストとドメインの名前、DNS 名前空間、ドメインコントローラー、機能の互換性、サイト、サブネット、時刻源、アプリの依存関係から始める。一般の学生アカウントと特権管理を分ける。認可に使うセキュリティグループと、整理やポリシーの対象指定に使う組織単位（OU）を区別する。利用者を OU に移動しただけでは、ファイルへのアクセス権は付かない。

大学の研究サービスでは、卒業後に期限が切れる学生所有のパスワードより、対応するグループ管理サービスアカウントを検討する。gMSA には前提条件があり、その管理対象パスワードを取得できるホストも定める。あらゆるログインに使えるアカウントではない。サービスに必要な権限と接続先を記録し、そのアプリで対応しているか検証する。[gMSA の概要](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-managed-service-accounts/group-managed-service-accounts/group-managed-service-accounts-overview)を参照。

ActiveDirectory モジュールとディレクトリの読み取り権限がある Windows 管理マシンで確認する：

```powershell
Get-ADDomainController -Filter * |
    Select-Object HostName, Site, IsReadOnly, OperationMasterRoles
Get-ADDomain | Select-Object DNSRoot, PDCEmulator, RIDMaster, InfrastructureMaster
```

出力は一覧であり、すべてのコントローラーが正常だという証明ではない。想定したトポロジーと比較する。サイトの割り当て漏れ、到達できないコントローラー、特権を持つ人間のアカウントで動くサービスが見つかったら、調査する問いにする。ドメインを作り直す理由にはしない。

## 3. DNS、時刻、サイト、レプリケーションを結び付ける

ドメインのクライアントが AD サービスを検出するには、適切な DNS が必要。「インターネットが使える」は弱い証拠であり、公開名の解決が成功しても、ドメインの SRV 検索は失敗し得る。実習では、クライアントが実際に使うリゾルバーでドメインとサービスのレコードを解決する。その後、パスワードのリセットから始めるのではなく、返されたコントローラーと必要なプロトコルをテストする。

```powershell
Get-DnsClientServerAddress -AddressFamily IPv4
Resolve-DnsName -Name '_ldap._tcp.dc._msdcs.lab.example.test' -Type SRV
w32tm /query /status
```

これらの照会には適切なネットワークアクセスが必要で、`w32tm` は Windows のツール。SRV の応答が成功しても、通知されたサーバーへ到達できることや、認証の成功までは証明しない。リゾルバー、返された接続先、タイムスタンプ、エラーを記録する。Kerberos は許容範囲内の時刻関係にも依存する。各時計を個別に変更せず、時刻の階層と同期状態を診断する。

AD のサイトとサブネットの対応付けは、ネットワーク上の場所を表し、サービスの選択やレプリケーションに影響する。サイトを作っても、関係する IP サブネットを割り当てなければ、クライアントがそのサイトを使うようにはならない。学内のアカウント変更が離れた建物へ遅れて反映される場合は、コントローラーの選択、レプリケーションの正常性、トポロジー、スケジュール、接続を比較する。障害を理解せずに、すべての間隔を短くしたり、レプリケーションを強制したりしない。

AD ツールと関係する権限を使い、選んだ実習コントローラーへ照会する：

```powershell
Get-ADReplicationFailure -Target 'LAB-DC1.lab.example.test' -Scope Server
repadmin /replsummary
```

エラーは時系列として扱う。レプリケーションの症状の原因は、DNS、認証、時刻、ネットワークフィルター、ディレクトリの問題かもしれない。通信を直しても、必要な変更すべての収束が自動的に証明されるわけではない。対象のオブジェクトやポリシーを後から検証する。[AD レプリケーションの概念](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/replication/active-directory-replication-concepts)を使い、ローカルでの成功とフォレスト全体の収束が別の主張である理由を説明する。

## 4. コントローラーとポリシーの操作を意図的に選ぶ

RODC は物理面や管理面の信頼が弱い場所で役立つが、「読み取り専用」は「資格情報を保存しない」という意味ではない。どの資格情報をキャッシュできるかは、パスワードレプリケーションポリシーで決まる。許可と拒否の対象アカウント、管理の委任、書き込み可能なコントローラーへのアクセス、機器を失った場合の対応を計画する。信頼できない拠点に特権アカウントをキャッシュすると、意図した保護の多くが失われる。[RODC のパスワードレプリケーションポリシー](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-groups)を参照。

FSMO ロールは異なる責任であり、負荷分散のグループではない。ロールの転送は、現在の保持者が利用可能な間に行う管理された移動。強制取得は、保持者が使えない場合の復旧操作であり、その旧保持者を復帰させる前に、サポートされる扱いの計画が必要。利用者のログオンが一度失敗しただけで、すべてのロールを強制取得する理由にはならない。まず、失敗した操作、ロールへの依存、コントローラーの正常性、復旧責任者を特定する。

グループポリシーでは、ポリシーの存在、対象範囲、処理、結果の設定を分ける。関係する利用者やコンピューターの OU、リンク、継承、セキュリティフィルター、使っていれば WMI フィルター、クライアントの証拠を確認する。利用者ポリシーは、同じ教室にあるすべてのコンピューターに自動適用されるものではない。ループバックは、特定のコンピューターで利用者ポリシーを選ぶ方法を変えるため、明確な用途が必要。

影響を受ける Windows 実習クライアントでは、`gpresult /r` が適用の文脈を要約する。「GPO がリンクされている」「このクライアントが処理した」「実効設定が要件に合う」の違いを説明する。グループポリシーの基本設定は、再利用できる特権パスワードを公開する場所ではない。設定のロールバックを明示する。ポリシーのリンクを外せば、すべての以前の値へ戻るとは限らない。[グループポリシーの概要](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-policy/group-policy-overview)を確認する。

## 5. リモート管理とハイブリッド管理を権限の設計として扱う

操作者、管理ワークステーション、ゲートウェイまたはエンドポイント、対象サーバー、さらにアクセスするリソースを図示する。Windows Admin Center、Server Manager、PowerShell リモート処理、SSH、RDP では、前提条件やセッションの動作が異なる。ポートを開けても管理権限は付かず、管理者グループへの広い追加は、必要な操作を特定する代わりにはならない。

セカンドホップ問題は、サーバー B 上のセッションから、適切な ID を使ってリソース C へアクセスする必要があるときに起きる。管理者パスワードをスクリプトにコピーして解決しない。[PowerShell のセカンドホップのガイダンス](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/ps-remoting-second-hop)は、方式と制限を比較している。CredSSP は資格情報を委任するため露出が増え、制約付き委任の方式にも WinRM のセカンドホップ制限などのプロトコル上の制約がある。「委任を有効にする」を一つの設定として扱わず、実際にサポートされる経路と認証方式を選ぶ。

[JEA セッション構成](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/jea/session-configurations)では、管理機能を制限したエンドポイントを提供できる。ロール機能、見えるコマンドとパラメーター、実行 ID、許可された利用者、トランスクリプトをまとめて確認する。JEA の仮想アカウントは既定で、メンバーサーバーではローカルの Administrators、ドメインコントローラーでは Domain Admins のメンバーになる。対応する場合は実行グループを制限する構成にし、コマンドから制限を抜けられる経路も調べる。許可したコマンドが任意コードを実行できるなら、コマンドの一覧が短くても最小権限とは言えない。

Azure Arc は Azure 外のサーバーを Azure サービスで管理できるようにするが、AD 参加、フォレストの信頼関係の作成、ローカルのセキュリティ責任の解消は行わない。[Arc のセキュリティ概要](https://learn.microsoft.com/en-us/azure/azure-arc/servers/security-overview)では、機密性の高いエージェントや拡張機能の境界を説明している。特にドメインコントローラーでは、誰が拡張機能をインストールし、スクリプトを実行できるか決める。更新では、評価とインストール、保守対象の範囲と再起動処理、手順書のスケジュールと完了の成功を分ける。変更を広げる前に、代表的なメンバーサーバーで試す。

## 6. Hyper-V の容量、ネットワーク、復旧を分けて考える

各 VM について、役割、ゲストの互換性、メモリ、CPU、ストレージのパス、仮想ネットワーク、起動の依存関係、許容中断時間を記録する。動的メモリは、ワークロードの互換性とホストの余力が必要なポリシーであり、無料で容量が増える機能ではない。入れ子の仮想化と GPU パーティション分割には、正確なハードウェア、OS、ゲスト、構成の対応が必要。他のエディションのスクリーンショットに表示されているからといって、その機能を使えると約束しない。

Hyper-V モジュールと適切なホスト権限で、実習ホストを確認する：

```powershell
Get-VM -Name 'LAB-APP' | Select-Object Name, State, Generation, MemoryAssigned, CheckpointType
Get-VMMemory -VMName 'LAB-APP'
Get-VMSwitch | Select-Object Name, SwitchType
Get-VMSnapshot -VMName 'LAB-APP' | Select-Object Name, SnapshotType, CreationTime
```

上の一覧だけでは、運用チェックポイントの整合性を証明できない。`SnapshotType` は [Get-VMSnapshot](https://learn.microsoft.com/en-us/powershell/module/hyper-v/get-vmsnapshot) が公開するチェックポイントの分類で、`CheckpointType` は VM に設定された方針を表す。作成結果と、該当するゲストの整合性処理や VSS の証拠を確認する。Standard という語や要求した設定だけから、Production の処理が成功したと判断してはいけない。

外部、内部、プライベートの仮想スイッチを、意図した通信範囲に対応付ける。隔離したスイッチなら、実習ゲスト同士は通信できても学内へ届かない理由を説明できる。ゲストのファイアウォールだけを変えても、上位ネットワークへの接続は生まれない。ホストのアダプターの問題、VM アダプターの接続、ゲストの IP 設定、DNS、アプリへのアクセスを区別する。

[チェックポイント](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/checkpoints)は特に誤解されやすい。標準チェックポイントはメモリを含む VM 状態を保存し、運用チェックポイントは、対応していればゲストを考慮した整合性の仕組みを使う。運用の設定では標準へのフォールバックを許可できるが、ProductionOnly はそのフォールバックを拒否する。どちらに設定しても、VM のチェックポイントチェーンが独立した保護済みバックアップになるわけではない。容量を空けるために AVHDX ファイルを手動削除せず、サポートされる管理とマージの手順を使う。

Hyper-V レプリカは、非同期レプリケーションと、計画済み、テスト、計画外のフェールオーバーのワークフローを支える。クラスター化 VM の高可用性や、過去に戻るバックアップとは異なる。レプリカにも、アプリの誤った変更が含まれ得る。設計レビューでは、対応する障害、想定される遅延、正とする書き込み主体、ネットワークの対応付け、テストの隔離、フェールバックの流れを特定する。[Hyper-V レプリカの概要](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/replication-overview)を参照。

| 仕組み | 役立つ用途 | それだけでは示せないこと |
|---|---|---|
| チェックポイント | 対応する実習変更で、管理された方法で VM 状態を戻す | ストレージチェーンを失っても残る独立コピー |
| Hyper-V レプリカ | プライマリ障害後に複製済み VM を復旧する | 破損していない過去の復旧ポイントやデータ損失ゼロ |
| クラスター化 VM | ホスト障害後に対応する VM を再起動または移動する | アプリレベルの正しさや削除への保護 |
| 復元をテストした保護済みバックアップ | 選んだ保持と整合性のポリシーによる過去の状態への復旧 | 自動フェールオーバーや、測定していない復旧時間 |

## 7. Azure VM を Windows ワークロード全体として診断する

Azure VM が稼働中でも、ゲストのサービスは使えないことがある。プラットフォームの状態、起動、ゲストのネットワーク、Windows 認証、サービスの正常性、アプリの依存関係を分ける。サイズ変更は利用可能なリソースを変えるが、再起動が必要になったり、配置や容量の制約が加わったりすることがある。性能の修復だと言う前に、VM とディスクの両方の上限を確認する。

可用性セットや可用性ゾーンは配置に関するもの。VM を 1 台追加しても、アプリのフェールオーバー、書き込み可能なディレクトリの複製、整合性のあるファイルサービスが自動で得られるわけではない。Azure 上の AD ドメインコントローラーでは、サポートされるディレクトリの仮想化とバックアップのガイダンスに従い、適切な DNS とネットワーク経路を用意する。OS ディスクをコピーしただけのものを、新しい独立したコントローラーとみなさない。

Azure Bastion はマネージドなアクセス経路を提供し、JIT 制御は対応する条件の下で露出を制限する。どちらも、Windows の資格情報、ゲストの認可、必要なアプリ権限を置き換えない。永続的な公開 RDP を開く前に、承認された経路が失敗する理由を調べる。演習の成果物は、経路図と最小権限でのアクセスの説明であり、便宜のために作った公開エンドポイントではない。

## 8. 実際のクライアント経路で DNS と DHCP を調べる

クライアントのリゾルバー、ローカルゾーン、条件付きフォワーダー、上流の接続先、権威ある回答をつないで、名前解決の経路を作る。条件付きフォワーダーは、特定の名前空間の問い合わせを選んだ DNS サーバーへ送るが、そこへのネットワークルートは作らない。DNSSEC が加えるのは DNS データの検証であり、通信の暗号化やプライベートアプリへの自動アクセスではない。検索で何が返るべきか、ハイブリッドの境界のどちら側から確認するかを指定する。

DnsServer モジュールと適切な読み取り権限がある DNS 管理ホストで確認する：

```powershell
Get-DnsServerZone -ComputerName 'LAB-DC1'
Get-DnsServerForwarder -ComputerName 'LAB-DC1'
```

DHCP では、スコープの範囲、除外、リース、予約、オプション、リレーの経路、承認されたサーバーを調べる。予約はクライアントの識別子に結び付くもので、ゲスト内のアドレスを固定設定にするものではない。スコープが満杯だと既存のリースは継続しても、新しいクライアントは失敗し得るので、両方を試す。サーバーに要求が届いていない場合、リレーや VLAN の問題が DHCP サービスの障害に見えることがある。

DHCP Server モジュールと関係する権限で確認する：

```powershell
Get-DhcpServerv4Scope -ComputerName 'LAB-DHCP1'
Get-DhcpServerv4Failover -ComputerName 'LAB-DHCP1'
```

DHCP フェールオーバーは、対応する動作の下で設定済みの関係とスコープを保護する。サーバーをもう 1 台置くだけでは、割り当ては調整されない。モード、パートナーの状態、対応するリースの動作、復旧手順を記録する。[DHCP フェールオーバー](https://learn.microsoft.com/en-us/windows-server/networking/technologies/dhcp/dhcp-failover)を参照。

## 9. ファイルアクセスのすべての境界をたどる

サインインできる学生でも、共有を使う権利があるとは限らない。Windows SMB サーバーでは、グループ所属や継承も含め、実際の ID に対する共有権限と NTFS 権限を調べる。明示的な拒否や古いグループトークンで結果が変わることがある。症状が消えるまで Everyone にフルコントロールを与えるのではなく、想定した共同作業グループと隔離の境界を記録する。

SMBShare モジュールがあり、対象フォルダーにアクセスできる実習ファイルサーバーで確認する：

```powershell
Get-SmbShareAccess -Name 'LabNotes'
Get-Acl -LiteralPath 'D:\LabShares\Notes' | Format-List Owner, AccessToString
```

これらの出力が示すのは設定済みのエントリであり、完全な実効アクセスの証明ではない。想定した経路で、許可する利用者と拒否する利用者を試す。Azure Files には独自の対応する ID 設定と共有レベルの認可があり、適用される場合はディレクトリやファイルの権限もある。[Azure Files の認可](https://learn.microsoft.com/en-us/azure/storage/files/storage-files-authorization-overview)は、この層の関係を明示している。リソース管理の共同作成者ロールは、SMB のデータ権限を自動で与えるものではない。

Azure File Sync はクラウドエンドポイントとサーバーエンドポイントを接続し、ファイルを階層化できる。同期と可用性だけでは、独立した過去の復旧境界は得られない。保持、保護済みバックアップ、復元の依存関係、エンドポイントの正常性、キャッシュ容量、削除や破損したファイルをどう復旧するかを計画する。プレースホルダーがあるだけでは、必要な内容がすぐローカルで使える証拠にならない。[Azure File Sync の計画](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-planning)を参照。

登録済みの File Sync サーバーの復旧には、追加の制約がある。OS イメージの復元、クローン作成、VM チェックポイントへの巻き戻しは、一般的に使えるサポート済みの復旧経路ではない。[File Sync のディザスターリカバリーのガイダンス](https://learn.microsoft.com/en-us/azure/storage/file-sync/file-sync-disaster-recovery-best-practices)に従い、必要に応じて完全なクラウドコピー、保持された保護、サポートされるサーバーの再登録と復旧手順を特定する。通常の Hyper-V ロールバックを、ワークブックの File Sync 復元手順にしてはいけない。

[SMB over QUIC](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-over-quic)には、対応する OS のエディションとバージョン、クライアント、接続、適切な証明書が必要。この確認時点で、ガイドは Windows Server 2022 Datacenter: Azure Edition または Windows Server 2025 の各エディションと、Windows 11 クライアントを挙げている。既定の UDP 443 の経路と、必要な DNS のサブジェクト代替名および使用可能な秘密キーを備えた、信頼されるサーバー認証用証明書を確認する。現行の Windows Server 2025 のセットアップは PowerShell を使う。バージョン別の手順を確認せず、古い Windows Admin Center の設定例で代用してはいけない。QUIC はファイルの認可を迂回せず、有効にしたからといって無関係なサービスを公開してよいわけではない。

## 10. ストレージの容量、回復力、復旧可能性を分ける

ディスク容量は一つの側面にすぎない。物理デバイス、プール、仮想ディスク、ボリューム、ファイルシステム、ワークロード、保護の対応を整理する。Storage Spaces、Storage Spaces Direct、Storage Replica、DFS 名前空間、DFS レプリケーションは目的が異なる。名前空間は論理的なパスを与えるが、参照先の内容の同期や、アプリが同時書き込みを安全に受け付けられることを保証しない。

互換性がある Windows ストレージホストで、読み取り専用の一覧を取得する：

```powershell
Get-PhysicalDisk | Select-Object FriendlyName, HealthStatus, OperationalStatus
Get-VirtualDisk | Select-Object FriendlyName, ResiliencySettingName, HealthStatus
Get-Volume | Select-Object DriveLetter, FileSystem, HealthStatus, SizeRemaining, Size
```

待ち時間、スループット、キュー、容量、ワークロードの時間帯を関連付ける。プールが正常でも、性能が足りないことはある。デバイス故障に耐えられても、管理者によるフォルダー削除からは守れない。[Storage Replica](https://learn.microsoft.com/en-us/windows-server/storage/storage-replica/storage-replica-overview)にも、対応するトポロジー、適切なログとデータの配置、明示的な復旧設計が必要。レプリケーションは、あらゆるバックアップの代わりになるわけではない。

NTFS と ReFS は、どちらかが常に速いという宣伝文句ではなく、対応するワークロードの要件に基づいて選ぶ。重複除去、SMB Direct/RDMA、ストレージ QoS、iSCSI、BitLocker には、それぞれ互換性と運用上の条件がある。暗号化では回復情報を別に保護し、権限のある人が使える復旧経路を確認する。回復キーをワークブックのスクリーンショットとして公開しない。停止中にも読める場所に、不可欠な復旧手順の独立コピーを保持する。

## 11. 役割に合わせて強化し、復旧用アクセスを残す

ファイルサーバー、Hyper-V ホスト、ドメインコントローラーに、理由を示さず同じ設定一式を適用してはいけない。資産の役割、特権 ID、公開サービス、許可する管理経路、復旧用アクセスから始める。ファイアウォールと認証の変更は、元に戻れる方法を試したうえで段階的に行う。唯一の管理経路を気付かぬうちに止めるセキュリティ設定は、小さな問題を復旧作業に変えてしまう。

[OSConfig のセキュリティベースライン](https://learn.microsoft.com/en-us/windows-server/security/osconfig/osconfig-how-to-configure-security-baselines)は、現時点では Windows Server 2025 が対象。適用前に、インストール済みモジュールと対応するシナリオを確認し、古いサーバーへそのままコマンドをコピーしない。予定する設定を調べ、適切なサーバーの役割で試し、準拠とドリフトを確認して以前の状態を記録する。ベースラインの適用にも削除にも再起動が必要。構成管理を外しても、以前の値がすべて戻るとは限らない。

[Windows LAPS](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-overview)は、管理されたローテーションと制御された取得によって、ローカル管理者パスワードの再利用を減らす。対応するバックアップ先、アカウントポリシー、取得できるロール、監査、復旧手順を決める。だからといって、学生レポートのためにパスワードを取得してよいわけではない。コントローラー上の DSRM 復旧には、別途対応する LAPS の条件がある。ドメインアカウントと、マシンのローカルな復旧用資格情報を混同しない。

Credential Guard、アプリケーション制御、Exploit Protection、Defender for Servers、アカウント保護は、それぞれ異なる脅威に対応する。機能が入っているだけで保護を証明したとせず、ハードウェアと OS の前提条件を確認し、実際の強制適用を観察する。AD の委任では、必要な限定的なディレクトリ操作を適切な範囲で付与する。ヘルプデスクのパスワードリセットに Domain Admins の所属は要らない。可能な限り、通常の Web 閲覧やメール用マシンで特権セッションを使わない。

## 12. ダッシュボードで調べる前に、役立つ監視を作る

まず、サインイン失敗、ディスク待ち時間、レプリケーション失敗、更新の状態、見つからないエージェント拡張機能など、問いを決める。ソース、収集方法、送信先、時間範囲、責任者、警告時の対応を指定する。パフォーマンスモニターのカウンターとデータコレクターセットは基準値の把握に役立つが、一つの高いサンプルだけでは原因は特定できない。同じ時間帯のアプリの症状と関連付け、通常のワークロードの動作と比較する。

Azure Arc の接続状態、Azure Monitor Agent の正常性、データ収集ルール（DCR）、DCR の関連付け、送信先の権限は別々に確認する。[Windows Arc サーバーの AMA トラブルシューティング](https://learn.microsoft.com/en-us/azure/azure-monitor/agents/azure-monitor-agent-troubleshoot-windows-arc)は、エージェントと構成の経路、取り込みの経路を分けている。ハートビートでエージェントの送信が分かっても、必要なイベントログは未収集かもしれない。クエリが空でも「インシデントがない」とは限らず、時間範囲、テーブル、ソースの選択、関連付け、ワークスペースが違う可能性がある。

関係する Windows 実習サーバーでローカルのイベントを照会し、元のイベントがあるか確認できる：

```powershell
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddHours(-2)} -MaxEvents 20 |
    Select-Object TimeCreated, Id, ProviderName, LevelDisplayName
```

ログによっては、昇格または委任された権限が必要。照会時刻とタイムゾーンを記録し、役立つイベント識別子を残し、機密値を伏せる。イベントがローカルで発生したかと、設定した収集によって届けられたかは、別々に説明する。警告には適切なしきい値、受信者、対応責任者、検証ケースが必要。誰にも届かないルールでは、運用手順は完成していない。

## 13. 診断の順序とサポートされる復旧方法を使う

ログオンのインシデントなら、私の最初のワークシートは「何が変わったか」「どの ID と機器が失敗するか」「正確なエラーは何か」「いつ始まったか」を問うものになる。その後、IP 設定、リゾルバーと SRV の結果、コントローラーへの到達、時刻、認証とセキュアチャネルの証拠、レプリケーション、認可をたどる。これは仮説を調べる順序であり、ファイアウォールを止めたり全アカウントをリセットしたりする指示ではない。メンバーサーバーでは `Test-ComputerSecureChannel` で信頼関係を調べられる。別途根拠のある変更として扱わずに `-Repair` を加えず、このメンバーサーバー用のテストを DC の正常性確認とみなさない。

ファイルが見つからない場合は、名前空間と正とする場所、想定した ID、共有と NTFS または Azure の認可、同期状態、削除の時系列、使える過去のコピーを特定する。VM が遅い場合は、ゲストのワークロードを、ホストの競合、メモリ不足、ディスク上限、キュー、ネットワークの依存関係と比較する。再起動で症状を消す前に、証拠を保全する。

AD の復旧には特に注意が必要。ごみ箱からのオブジェクト復元には前提条件があり、ドメイン全体の復旧とは同じではない。DSRM は保護された資格情報を使う復旧用起動の文脈であり、通常の管理セッションではない。SYSVOL の復旧、ディレクトリの権限のある復元（authoritative）と権限のない復元（non-authoritative）は、実際の障害とサポートされる手順に依存する。[AD フォレスト復旧のガイダンス](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/forest-recovery-guide/ad-forest-recovery-guide)で、責任者、クリーンな復旧、バックアップ、依存関係、検証を計画する。このノートを使い、実ディレクトリでコントローラーのロールバックや FSMO の強制取得を練習してはいけない。

## 14. 実習をスクリーンショットではなく証拠にする

[ワークブック](AZ-802-workbook.md)は、これらの題材を 5 つの調査にまとめている。各調査の前に、期待する結果、競合する説明、それらを区別するコマンド、変更される可能性がある状態、終了条件を書く。Server Manager の画像よりも、タイムスタンプ、対象、コマンド、機密値を除いた結果、説明を備えた ID ごとのテストのほうが強い証拠になる。

変更台帳を使い、基準状態、提案する操作、実環境での承認責任者、観察、解釈、ロールバックの判断条件を記録する。Windows 実習環境がない場合は、トポロジーと予測される観察結果を作り、予測だと明記する。出力を捏造せず、予定した復元を完了済みと書かない。使い捨ての実習環境で、既知の復旧経路を用意し、一度に一つの変数だけを小さく元に戻せる形で変更する。

| 例の種類 | 照会前に記録する前提条件 |
|---|---|
| AD の一覧とレプリケーション | ActiveDirectory/RSAT ツール、到達可能な実習コントローラー、関係するディレクトリ読み取り権限 |
| DNS クライアント、時刻、ポリシー | Windows クライアント、正しい利用者とコンピューターの文脈、照会先サービスへのアクセス |
| DNS/DHCP サーバー | DnsServer/DhcpServer モジュールと、対象サーバーに対する委任または管理上の読み取り権限 |
| Hyper-V | 対応する Windows ホスト、Hyper-V PowerShell モジュール、許可されたホストアクセス |
| 共有とファイルシステム | SMBShare の対応、実際の共有とパス、その ACL を確認する権限 |
| ストレージ一覧 | 対応する Storage モジュールまたはプロバイダーと、許可されたホストの文脈 |
| ローカルイベントログ | 存在するログと時間範囲、そのログの読み取り権限、機密値を伏せる計画 |
