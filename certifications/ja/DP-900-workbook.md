# DP-900 · 共通の応用ワークブック

[ガイド](DP-900.md) · [十のケース](DP-900-cases.md) · [目次](README.md)

八言語で対応する五単元。架空データを使い、予測と観測を分けて記録する。Azure に展開する演習ではなく、試験範囲全体を網羅した証明にもならない。

<a id="dp-900-unit-1"></a>

## 1. 保存先の前にデータを説明する

PDF、履修登録の行、任意のメタデータを持つ JSON、ダウンロードイベントを棚卸しする。それぞれの構造、識別子、生成元、利用側、保存期間、機密項目を説明する。次に、ファイル取得、登録の記録、イベント集計など、重要な操作を書く。形式の選択とワークロードの要件を分けよう。

**シナリオ：**同じアプリのデータなので全部を一つのデータベースに置く提案が出た。**確認材料：**四行の判断表、各行で退けた案、その選択を変える新しい条件を提出する。サービスの制限を作り上げたり、JSON なら必ず Cosmos DB が必要と決めつけたりしない。

<a id="dp-900-unit-2"></a>

## 2. リレーショナルな整合性を見える形にする

Students、Courses、Enrolments と安定した識別子を描く。六行の架空データを作り、主キー、参照、履修重複を防ぐルールを説明する。結合結果を予測し、科目名を変更した場合に必要な更新を、全登録行に名称を複製した設計と比較する。正規化の標語を暗記するのではなく、具体的な更新異常を見つけるのが目的だ。

**シナリオ：**存在しない科目へ学生が登録された。**確認材料：**拒否または検出するルール、不正なサンプル、期待する結果を示す。ローカルで SQL を実行したならエンジン名を記録する。SQLite の動作は Azure SQL の試験結果ではない。

<a id="dp-900-unit-3"></a>

## 3. データベースを誰が運用するか決める

新規アプリと移行の両方で、Azure SQL Database、Managed Instance、VM 上の SQL Server を比較する。互換性の依存、ネットワークと ID、保守責任、復旧の期待値を一覧にする。既存アプリの要件に合うなら、オープンソースのエンジンも加える。根拠ある推奨と「常にこの製品が最良」という主張は違う。

**シナリオ：**移行元にゲスト OS のアクセスを必要とする部品がある。**確認材料：**互換性の質問一覧、運用責任表、成功条件つきの概念実証計画を提出する。展開は不要だが、対象を採用する前にどの前提を試す必要があるかを書く。

<a id="dp-900-unit-4"></a>

## 4. 小さなデータパイプラインを突合する

同じ ID の重複と科目の欠損を含む六件の架空ダウンロードイベントを作る。正常な入力、一意のイベント、完了条件を定義する。ETL と ELT の経路を描き、検証と拒否レコードの保存先を置く。バッチで遅延要件を満たせる条件と、ストリーミングを検討する条件を説明する。

**シナリオ：**ダッシュボードの合計が入力行数と違う。**確認材料：**入力、重複、拒否、受理の各件数と、再現できる差の説明を提出する。失敗した実行の担当者と対応も決める。パイプラインの正常終了だけでは、業務の合計値が正しい証拠にならない。

<a id="dp-900-unit-5"></a>

## 5. 信頼できる分析指標を一つ定義する

完了した一回のダウンロードなど、レポートの粒度を選び、科目と日付の文脈を持つファクトを定義する。タイムゾーン、遅れて届くイベント、鮮度を指定する。保存、変換、セマンティックモデル、レポート表示をそれぞれどこが担当するか説明する。レイク、ウェアハウス、レイクハウスは製品名ではなく、必要な作業に照らして比較する。

**最終提出物：**保存先の判断表、関係の図、パイプラインの突合結果、指標定義つきの月次レポート案。Fabric、Synapse、Power BI の役割も説明する。公式ガイドで確認したい未解決の問いを一つ挙げる。よいレポート案だけで、クラウド運用能力や受験準備が整ったとは判断できない。
