# DP-700 · オフラインのデータエンジニアリングワークブック

[ガイド](DP-700.md) · [10ケース](DP-700-cases.md) · [目次](README.md) · [Español](../es/DP-700-workbook.md)

5単元で合成した大学データを使います。アカウント、有料容量、Fabric実行は不要です。言語版ごとに同じ成果物を作ります。推論した出力は**EXPECTED**、ローカルな観察は**OBSERVED**、未実施のプラットフォーム検査は**NOT EXECUTED**と記します。出典の範囲と参照確認の限界は[ガイド](DP-700.md)にあります。

<a id="dp-700-unit-1"></a>

## 1. プラットフォームと所有権の地図を描く

テナント、容量、ワークスペース、アイテム、OneLakeの場所、実行エンジンの違いを説明します。大学の履修登録元、未加工のダウンロードファイル、整備済みテーブル、図書館カタログのショートカット、分析利用者を描きます。レイクハウスとウェアハウスをどこに使えるか、それぞれ具体的理由を一つ付けて決めます。各テーブルの粒度も記します。

**シナリオ：** 図書館がショートカットの参照先を管理し、アクセス方針を変更します。**証拠：** 参照先の所有者、内部・外部認証の前提、必要権限、スキーマ契約、参照先削除の影響を記録します。**成果物：** 依存関係図とアクセス表。過去データ保持の要件を別途含めます。ショートカット自体はバックアップや復旧の要件を満たしません。

<a id="dp-700-unit-2"></a>

## 2. 増分変更ログを照合する

次の完全な合成ログを使います。`version`が正しいソース順序、`key`が履修登録IDです。空の出力先から始めます。削除には版付きトゥームストーンを保持します。キーごとに最大版へまとめ、同じ重複を一つにしてから、新しい版だけをマージします。同じ版で異なるペイロードは隔離が必要です。

| key | version | operation | module |
|---|---:|---|---|
| E1 | 1 | upsert | CS101 |
| E2 | 1 | upsert | DB201 |
| E1 | 2 | upsert | AI301 |
| E1 | 2 | upsert | AI301 |
| E2 | 2 | delete | DB201 |
| E2 | 1 | upsert | DB201 |

**シナリオ：** 成功応答を失った後、ログを再処理します。**期待する証拠：** E1は版2でAI301に有効、E2は版2で削除済みです。どちらの実行後も有効件数は1です。**成果物：** 途中状態と進捗コミット規則。遅いE2の版1が復活させられない理由を説明します。

<a id="dp-700-unit-3"></a>

## 3. 品質とイベント時刻の規則を指定する

イベントID、科目、イベント時刻、到着時刻、スキーマ版を持つダウンロードレコードを設計します。null、型、許容値、重複の規則を定義します。任意の新フィールドの承認と、不正レコードの受け入れの違いを説明します。隔離では、機密内容へのアクセスを制限しつつ、修復可能なIDと理由を残します。

**シナリオ：** UTCの23:59にイベントが起き、翌日UTCの00:07に届きます。指定された許容遅延は10分です。**期待する証拠：** イベント時刻上の日付は前日です。受け入れられるかを判断するには、到着時のエンジンのウォーターマークも必要です。実時間で8分遅れたという事実だけでは、受け入れは証明できません。**成果物：** 受け入れと訂正の規則、照合、ウィンドウ境界、チェックポイントの目的、許容時間を超えた場合の動作。

<a id="dp-700-unit-4"></a>

## 4. 管理されたデプロイを設計する

有限の履修登録区間をコピーし、検証と変換を呼び、受け入れた結果だけを公開するパイプラインを説明します。該当する変換ごとにSQL、PySpark、KQLを選び、理由を付けます。対応する定義のGit版管理、対応コンテンツのデプロイ、データ移動を区別します。

**シナリオ：** テストのノートブックが依然として本番レイクハウスを指します。**証拠：** 実行前にアイテム参照、接続の関連付け、実行ID、パラメーター、環境依存関係、スケジュールを調べます。**成果物：** 開発・テスト・本番の構成表、レポートとファイルの両経路で許可・拒否される閲覧テスト、巻き戻し手順。秘密度ラベルだけでは完全な権限設計を実装しない理由も説明します。

<a id="dp-700-unit-5"></a>

## 5. 架空の遅い実行を診断する

所要時間、入出力件数、拒否件数、鮮度、容量使用率の基準値を作ります。同じ入力量なのに2倍の時間がかかる事例を追加します。偏ったSpark結合、大量の小ファイル、同時の容量需要という3つの仮説を含めます。各仮説を支持・否定する証拠を述べ、必要に応じてパーティションの絞り込みとクエリ動作も調べます。

**シナリオ：** 部分書き込みの後で再試行します。**証拠：** 単元2の版規則で業務状態が変わるかを示します。**成果物：** 受け入れ閾値と正しさの照合を伴う、元に戻せる調整実験を一つ。Fabricの時間計測はすべてNOT EXECUTEDと記します。合成した推論では実際のスループット、復旧時間、クラウドデプロイ成功は確立できません。
