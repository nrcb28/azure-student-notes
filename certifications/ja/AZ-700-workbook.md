# AZ-700 · 共通の応用ワークブック

[ガイド](AZ-700.md) · [十のケース](AZ-700-cases.md) · [目次](README.md) · [ネットワーク演習](network-lab.md)

八言語で目標、シナリオ、提出物が対応する五単元。設計と診断の演習であり、予測は Azure の観測ではない。新しい展開を行ったとは主張していない。

<a id="az-700-unit-1"></a>

## 1. アドレスと依存関係を計画する

ノートアプリ向けの学内、ハブ、Web、データのネットワークを設計する。新しい CIDR を選ぶ前に既存範囲を調べ、成長とサービス専用のサブネット用に余地を残す。通常の /24 で、全アドレス数より Azure で割り当てられる IPv4 が少ない理由を説明する。委任サービスが任意の空きサブネットに入るとは想定しない。

**シナリオ：**パートナーの範囲がハブ案と重複している。**確認材料：**所有者、プレフィックス、用途、制約、成長余地の表。**提出物：**重複を取り除いた設計、解消した衝突、最新のサービス資料で確認すべき条件を一つ示す。

<a id="az-700-unit-2"></a>

## 2. 要求と応答を追う

Web スポークから検査装置を経由し、別ネットワークの宛先へ送る API 呼び出しを描く。各段階の宛先プレフィックス、次ホップ、転送設定を書く。応答は別に描く。状態を持つ検査やアドレス変換によって、一見妥当な非対称経路が失敗することがある。ピアリングだけでハブが中継ルーターになるわけではない。

**シナリオ：**UDR 変更後、要求は出るが応答がない。**確認材料：**競合するルートと両方向の有効な次ホップ。**提出物：**検証可能な仮説一つ、裏付ける観測、変更案を戻す条件を示す。

<a id="az-700-unit-3"></a>

## 3. プライベートアクセスを層ごとに診断する

学内クライアントが、選んだ DNS と転送構成を通してストレージ名を解決する流れを書く。プライベートエンドポイントのサブリソース、IP、承認状態、意図したネットワーク制限を特定する。名前解決、到達性、TLS、データ権限を分ける。一つの成功は残りの証明ではない。

**シナリオ：**公開アクセスは無効だが、呼び出し元は公開 IP を解決する。**確認材料：**名前、リゾルバーの経路、応答 IP、期待するプライベート宛先。**提出物：**DNS 修正案と、その後の経路・認証済みデータアクセスの確認。恒久的な公開 IP の上書きが不適切な理由も説明する。

<a id="az-700-unit-4"></a>

## 4. 配信と保護の制御を選ぶ

TCP サービス、リージョン内 Web アプリ、グローバル Web アプリを比較する。暗記した製品名一つで決めず、プロトコル、範囲、ルーティング、故障時の動作から候補を選ぶ。プローブと証明書の扱いも含める。DNS 選択とプロキシ配信、WAF とネットワークフィルターと DDoS の可用性保護を区別する。

**シナリオ：**プローブは正常なのに、文書のダウンロード内容が誤る。**確認材料：**プローブが試す内容と実際の操作が確かめる内容。**提出物：**退けた別案と、不具合のあるリリースの昇格を止める機能上のシグナルを含む短い判断記録。

<a id="az-700-unit-5"></a>

## 5. ハイブリッドの復旧を設計・検証する

主・予備の学内接続を計画する。同時に起きる障害、ルート変更、暗号化要件、容量、アプリ依存を挙げる。ExpressRoute のプライベート接続は既定の暗号化の証明ではない。守る区間と対応する暗号化構成を指定し、回線種別が違っても同じ機能を使えるとは想定しない。

**シナリオ：**学生が大量にノートを取得している間に主回線が落ちた。**確認材料：**往復の期待経路、予備容量の前提、測定可能なアプリ復旧条件。**提出物：**隔離した試験計画、通常運用へ戻す手順、期待と観測の欄。認可済み環境がなければ設計を提出し、観測欄には未試験と明記する。
