# AZ-802 · 証拠に基づく Windows Server ワークブック

[ガイド](AZ-802.md) · [理由付き解答のある 10 ケース](AZ-802-cases.md) · [目次](README.md)

対応する 5 単元で、AZ-802 の 7 つの学習分野を組み合わせる。架空の隔離した大学実習環境 `lab.example.test` を使う。動画から写した設定一覧ではなく、レビュー可能な判断と証拠一式を作る。これは Windows 演習の提案であり、AD、Hyper-V、Azure、復元、セキュリティ制御を実行したとは主張しない。互換性のある Windows 実習環境がなければ、結果を作り上げず、設計と予測した観察結果だと明記して提出する。

各単元で、基準状態、仮説、競合する説明、選んだ読み取り専用の確認、変更案、予想する観察、実行した場合の実際の観察、中止とロールバックの条件を台帳に残す。OS のエディションとバージョン、インストール済みモジュール、必要な権限、対象 ID を記録する。秘密と個人データは伏せる。ガイドの前提条件表はコマンド例にも適用される。コマンドがあることは、無関係なシステムを調べる権限を与えるものではない。

## 1. ディレクトリからアクセスまで ID の変更を追う

**シナリオ：** LAB-DC1 が研究グループの所属変更を受け付けたが、離れた建物のクライアントは依然として `\\LAB-FS1\LabNotes` にアクセスできない。クライアントは LAB-DC2 を選んでいる。別の拠点案では、教室の物理的な保護が限られるため、RODC を使う。

**調査：** フォレストとドメイン、書き込み可能なコントローラー 2 台、拠点の RODC、DNS リゾルバー、サイト、IP サブネットの対応を図示する。変更を受け付けたコントローラーと、クライアントが使ったものを印で示す。レプリケーションの経路、関係する SRV レコード、時刻の階層、利用者トークン、共有と NTFS の境界を特定する。古いディレクトリ状態と実効アクセスの問題を区別できる確認の順序を選ぶ。最初の仮説を否定する予想観察も一つ含める。

ガイドの AD 一覧、リゾルバーと時刻、レプリケーションの照会は、適切な Windows 管理の文脈からだけ使う。グループポリシーでは、範囲、クライアントの処理、実効設定を別々に説明する。RODC では、切断中のアクセス対象にする一般アカウント、拒否を維持するアカウント、拠点管理の委任、機器紛失時の対応を定義する。グループ名で証明できると考えず、実効パスワードレプリケーションポリシーを検証する。

**証拠：** ID の境界を示したトポロジー、機密値を除いた照会の文脈とタイムスタンプ、オブジェクト変更の時系列、意図したコントローラーと実際の選択、許可と拒否を組み合わせたファイルアクセステスト、パスワードを含まない RODC キャッシュの判断。

**成果物と判断条件：** 修正案を狭く限定した 1 ページの診断を書く。許可された実習変更の前に、元のリゾルバー、サイト、ポリシー設定を保存する。問題のコントローラーや名前空間が使い捨て実習の外なら中止する。症状を消すために権限を広げたり、FSMO ロールを強制取得したり、全アカウントをリセットしたりしない。成功とは、必要なディレクトリ変更が収束し、対象利用者に意図したアクセスだけが付与され、拒否する利用者は拒否されたままであること。

## 2. リモート管理と VM 復旧の境界を確認する

**シナリオ：** 操作者はメンバーサーバーへリモート接続できるが、次のリソースにアクセスできない。再利用可能な資格情報の委任を有効にし、DC 上で JEA エンドポイントを動かす案がある。一方、VM の運用整合性の処理が失敗したが、標準チェックポイントは作られた。実習環境には 64 GiB のホストが 2 台あり、ホスト用に仮定した 12 GiB の予約と、固定 4 GiB のゲスト 12 台を各ホストへ割り当てている。

**調査：** 認証の各ホップ、プロトコル、実効 ID、必要な操作を図示する。対応するセカンドホップの設計を、CredSSP のリスクや、プロトコルごとの委任の制約と比較する。JEA の許可コマンドとパラメーター、実行グループ、監査、配置を確認する。DC の既定の仮想アカウント権限が、限定的なメンバーサーバーのサービス作業には過剰な理由を説明する。Arc 管理マシンでは、Azure 拡張機能の権限とローカル権限を別々に特定する。

VM、スイッチ、メモリ、チェックポイントの一覧を使い、ゲストネットワークと復旧の状態を説明する。チェックポイント、レプリカ、クラスター、保護済みバックアップを、それぞれが対応する障害で比較する。Production と ProductionOnly、および実際のチェックポイントの種類が重要な理由を説明する。この仮定のサイジングでは、通常の割り当てメモリはホストごとに 48 + 12 = 60 GiB。全 24 ゲストを 1 台へ移すと 96 + 12 = 108 GiB が必要。前提を示し、通常時に収まるだけでは 1 台故障時の容量を証明できない理由を示す。

**証拠：** 権限とホップの図、制限したエンドポイントのレビュー、スイッチとゲストの経路、メモリ計算表、入手できる場合の実際のチェックポイントメタデータ、独立した復元用コピーの計画。

**成果物と判断条件：** サポートされ、範囲を狭く限定した管理設計と、それぞれ独立した復旧の仕組みを提案する。委任で実在の特権 ID を露出させる場合や、VM の対応する整合性要件が不明な場合は中止する。変更前のエンドポイント設定と復旧アクセスを記録する。AVHDX を削除せず、レプリカで論理破損が直ると主張せず、同じストレージのチェックポイントを独立バックアップと呼ばない。コマンドの成功と安全に復旧できるサービスには、別の検証が必要。

<a id="az-802-unit-3"></a>

## 3. ネットワークとストレージを通るクライアントからファイルへの経路を診断する

**シナリオ：** 教室の新しいクライアントはアドレスを取得できないが、以前のリースは続いている。承認されたネットワーク修正後、ある研究利用者は共有へ到達できるものの、フォルダーで拒否される。サーバーは Azure File Sync に登録済みで、一部のファイルは階層化されている。図には、ハイブリッド DNS の条件付きフォワーダーと、未構成の 2 台目の DHCP サーバーもある。

**調査：** クライアントの VLAN とリレー、承認済み DHCP スコープ、除外と予約、オプション、空き容量をたどる。実際の新規割り当てテストが、既存クライアントのテストに何を追加するか定義する。2 台目のサーバーがあることと、対応するフェールオーバー関係が設定済みであることを区別する。想定したリゾルバー、名前空間、条件付き転送先、戻りの経路、アプリのポートをたどる。正しい DNS 応答だけでは、使える SMB 接続は証明できない。

次に、実際の利用者、共有の認可、NTFS の継承、グループトークンの文脈を記録する。許可する ID と、拒否されたままにするべき ID を試す。Azure Files では、対応する ID 設定、共有レベルの認可、ディレクトリとファイルの権限を分ける。File Sync のエンドポイント、ローカルキャッシュの前提、独立して保持したバックアップ、対応する復旧手順を一覧化する。登録済みサーバーの OS や VM の復元、クローン作成、巻き戻しを、一般的な File Sync の復旧方法として明確に退ける。

**証拠：** アドレス割り当ての計算表、リゾルバーとルートの図、秘密を除いた共有と ACL の観察、許可と拒否のテスト基準、クラウドとサーバーのエンドポイント図、選んだ過去の復旧ポイントとその依存関係。

**成果物と判断条件：** ネットワーク障害と権限の障害を、別々の発見として説明する。許可された変更の前に、既存のスコープと ACL を記録する。割り当て範囲の重複、意図しない権限拡大、保護されていない復旧依存関係があれば中止する。成功には、対象の新規クライアントが有効な設定を取得し、対象利用者がフォルダーへアクセスし、拒否する利用者は遮断されたままであり、復旧計画が単なる別の同期エンドポイントではなく保護されたコピーを特定することが必要。

## 4. 復旧アクセスを失わずに役割別の強化を設計する

**シナリオ：** Windows Server 2022 と 2025、メンバーサーバー、DC、ファイルサーバーが混在する。一つの OSConfig ベースラインを全台へ展開し、証明書を確認せずに SMB over QUIC を公開し、LAPS パスワードをレポートで共有する案がある。ベースラインの削除を完全なロールバックと説明している。

**調査：** 制御を選ぶ前に、役割とバージョンの対応表を作る。確認した OSConfig セキュリティベースラインのガイダンスは Windows Server 2025 向け。モジュールのバージョン、シナリオ、予想する設定差、再起動の必要性、既存 GPO や他の管理との競合を記録する。正しい役割で試す。管理を外せば以前の状態が再構築されると考えられない理由を説明する。保護した以前の状態の記録と、代わりの許可された管理経路を保つ。

LAPS では、ローテーション、バックアップ先、許可された取得、監査、復旧アクセスを分ける。必要な場合は、パスワードを取得も公開もせず、DSRM 復旧の条件を文書化する。SMB over QUIC では、サーバーとクライアントの正確な対応を確認する。確認したガイダンスは、Windows Server 2022 Datacenter: Azure Edition または Windows Server 2025 の各エディションと、Windows 11 クライアントを挙げている。証明書の信頼、名前、秘密キーの利用、許可する UDP 経路を確認し、共有とファイルの認可を維持する。QUIC を認可の代わりと考えない。

**証拠：** 役割とバージョンの対応表、参照先付きの選んだ制御、設定差分とロールバックの判断条件、取得を許可するロールと拒否するロール、機密値を除いた証明書確認表、隔離した許可と拒否のアクセステスト計画。

**成果物と判断条件：** 復旧責任者を明示した段階的な変更案を書く。ベースラインが非対応、唯一の管理経路が失われる、証明書の要件が未解決、証拠に実際の秘密がある場合は中止する。すでに資格情報が漏れている場合は、組織の対応手順で扱う。準拠の結果、機能が入っていること、強制適用を実証したことは別の観察。

## 5. 届かないイベントを追跡し、ディレクトリ復旧を演習する

**シナリオ：** Arc 管理サーバーは接続済みと報告し、AMA は Heartbeat を送るが、必要な System イベントはローカルにしかない。別の机上演習では AD オブジェクトが削除され、ごみ箱は事前に有効化されていなかった。対応するディレクトリバックアップはある。チームは復元目標を 2 時間に定め、「VM が起動する」より強い証拠を求めている。

**調査：** 機密値を除いた一つのローカルイベントを、想定した AMA の拡張機能とサービス、DCR、関連付け、ソースの選択、送信先、クエリ時間範囲に沿って追跡する。マシンの ID、イベント発生時刻、到着時刻を別々に記録する。元のイベントがない場合、収集構成が欠けている場合、誤ったテーブルやワークスペースへ照会した場合を区別するテストを定義する。Arc の接続と Heartbeat がそれぞれ何を示し、何を不確かなまま残すか説明する。

ディレクトリ復旧では、影響するオブジェクトと依存関係、利用できる対応バックアップ、復旧責任者、保護した DSRM 資格情報、適切な復元範囲を特定する。ごみ箱によるオブジェクト復旧、権限のある復元（authoritative）と権限のないディレクトリ復元（non-authoritative）、SYSVOL の復旧、フォレスト全体の復旧を区別する。実際の障害に合う対応手順を選ぶ。一つのオブジェクトの間違いを、自動的なコントローラーの巻き戻しや FSMO の強制取得へ変えてはいけない。依存関係の順序、レプリケーションへの影響、検証、復旧したサービスの安全な復帰を演習する。

**証拠：** イベントソースから送信先への追跡、タイムスタンプ付きの仮説記録、復旧ポイントの一覧、見積もりだと明記した復旧時間の予測、必要なオブジェクト、認証、レプリケーション、ポリシー、影響するアプリを含む受け入れ確認。

**成果物と判断条件：** 監視と復旧の手順書を別々に作る。変更前に元の DCR と関連付けの証拠を保存する。復旧範囲や正とするコピーが不明なら中止する。RTO と RPO を混同しないよう、業務中断と使える復旧済みデータの時系列を残す。許可された実習環境で実行し、記載した観察が得られた後にだけ、その操作を完了と記録する。このリポジトリ自体は Windows や AD の復元、測定済みの 2 時間の結果を主張しない。
